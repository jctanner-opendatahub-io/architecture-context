## Purpose

**Short**: llm-d-kv-cache is a Go-based KV cache management toolkit for the llm-d distributed LLM inference platform, providing cache indexing, scoring, event processing, and a controller-runtime reconciler for pod lifecycle tracking. [source: Dockerfile:58, examples/kv_events/online/main.go:66, examples/kv_cache_index_service/server/main.go:98-101, pkg/kvcache/kvblock/redis.go:32-41]

**Detailed**: llm-d-kv-cache implements the KV cache awareness layer for the llm-d distributed inference stack. It provides multiple runtime components: a KV cache manager that subscribes to vLLM cache events via ZeroMQ and maintains a Redis/Valkey-backed index of KV cache blocks across inference engine pods; HTTP scoring endpoints that rank pods by cache affinity for prefix-aware routing; a gRPC IndexerService for programmatic cache lookups; and a controller-runtime pod reconciler that tracks pod lifecycle events. The Helm chart packages the kv-cache-manager as a Deployment with ZMQ (5557/TCP) and HTTP (8080/TCP) service ports, optionally co-locating an external tokenizer sidecar communicating over a Unix domain socket. The component connects to Redis or Valkey (API-compatible) for cache block storage and to an OpenTelemetry Collector for distributed tracing via OTLP/gRPC. [source: Dockerfile:58, vllm-setup-helm/templates/kv-cache-manager.yaml:1-24, vllm-setup-helm/values.yaml:97-135, examples/kv_events/online/main.go:236-322, pkg/kvcache/kvblock/redis.go:32-58]

## Architectural Analysis

llm-d-kv-cache follows a modular library-plus-examples architecture. The core packages under `pkg/` implement KV cache block indexing (`pkg/kvcache/kvblock/`) with pluggable storage backends (Redis, Valkey, in-memory via Ristretto), while the `examples/` directory contains standalone executables demonstrating different deployment patterns: an online event processor with HTTP scoring endpoints, an offline batch processor, a gRPC-fronted indexer service, and a controller-runtime pod reconciler for tracking inference engine pod lifecycle.

The component uses ZeroMQ pub/sub as its primary ingestion path — vLLM engines publish cache events that the kv-cache-manager subscribes to, processes, and indexes into Redis/Valkey. This decouples the cache awareness layer from the inference engine, allowing independent scaling. The Redis/Valkey client supports both plaintext (`redis://`) and TLS (`rediss://`) connection schemes via URL parsing, but defaults to unauthenticated plaintext TCP. No authentication middleware is applied to the HTTP or gRPC endpoints; these are expected to be network-isolated within the cluster or protected by platform-level network policies.

The Helm chart (`vllm-setup-helm/`) packages the kv-cache-manager as a Kubernetes Deployment with an optional external tokenizer sidecar that communicates over a Unix domain socket mounted from an emptyDir volume. The chart also optionally deploys a Redis instance as a lookup server. The kustomize manifests (`deploy/`) define an alternative StatefulSet-based deployment with RBAC, but the referenced resource files are incomplete in this checkout. The controller-runtime reconciler watches Pod resources to track inference engine lifecycle, using standard Kubernetes ServiceAccount authentication for API server access. ## Data Flows

- **KV cache event ingestion:** vLLM inference engines publish KV cache events over ZeroMQ (TCP, default port 5557). The kv-cache-manager subscribes to these events, processes them with configurable pool concurrency, and indexes cache block metadata into Redis or Valkey via the go-redis client (default `redis://127.0.0.1:6379`, supports TLS via `rediss://` scheme). [source: vllm-setup-helm/values.yaml:127-133, vllm-setup-helm/templates/kv-cache-manager.yaml:62-76, pkg/kvcache/kvblock/redis.go:43-90]
- **Scoring and lookup:** External routing components (e.g., llm-d-router) query the kv-cache-manager via HTTP POST to `/score_completions` or `/score_chat_completions` (port 8080/TCP) or via the gRPC IndexerService to retrieve pod-level cache affinity scores. The scoring handler reads the KV cache index from Redis/Valkey and returns ranked pod lists. [source: examples/kv_events/online/main.go:248-298, examples/kv_cache_index_service/server/main.go:97-106]
- **Pod lifecycle tracking:** The pod_reconciler uses controller-runtime to watch /v1/Pod resources via the Kubernetes API (port 6443, TLS, ServiceAccount auth), tracking inference engine pod creation and deletion to maintain an accurate view of available cache sources. [source: examples/kv_events/pod_reconciler/pod_reconciler.go:91, 180]
- **Observability:** Prometheus metrics are exposed at `/metrics` on the HTTP service port. Distributed traces are exported to an OpenTelemetry Collector via OTLP/gRPC, with the gRPC IndexerService instrumented using `otelgrpc.NewServerHandler()`.
