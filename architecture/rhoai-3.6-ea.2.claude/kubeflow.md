## Purpose

**Short**: Kubeflow Notebook Controller manages the lifecycle of Jupyter notebook workbenches on RHOAI, reconciling Notebook CRs into StatefulSets with sidecar injection for authentication, network isolation, and Gateway API routing. [source: components/notebook-controller/controllers/notebook_controller.go:159, components/odh-notebook-controller/controllers/notebook_controller.go:748]

**Detailed**: The kubeflow repository contains two cooperating controller-runtime operators. The upstream **notebook-controller** reconciles `kubeflow.org/Notebook` CRs into StatefulSets, Services, and Events, and runs a CullingReconciler that stops idle notebook pods based on activity metrics. The downstream **odh-notebook-controller** extends this with OpenShift-specific capabilities: it injects a kube-rbac-proxy sidecar for per-notebook authentication, creates NetworkPolicies for tenant isolation, manages Gateway API HTTPRoutes and ReferenceGrants for ingress, and provisions Elyra pipeline runtime secrets by reading DataSciencePipelinesApplication CRs. Both controllers expose health/readiness probes and admission webhooks (mutating, validating, and CRD conversion) served over TLS on port 8443. The TLS configuration is derived from the OpenShift APIServer TLS profile when available. [source: components/notebook-controller/main.go:125, components/odh-notebook-controller/main.go:142-208, components/odh-notebook-controller/controllers/notebook_mutating_webhook.go:54, components/odh-notebook-controller/controllers/notebook_dspa_secret.go:49]

## Architectural Analysis

The kubeflow component follows a two-tier controller pattern where the upstream notebook-controller provides core Notebook CR lifecycle management, and the odh-notebook-controller layers OpenShift platform integration on top. Both controllers run as separate binaries (`/manager`) in the same deployment, each with their own controller-runtime manager and webhook server.

The odh-notebook-controller's mutating webhook is the primary extension point. On every Notebook CREATE or UPDATE, it injects a kube-rbac-proxy sidecar container to enforce per-user authentication on notebook access, reads the cluster's OpenShift Proxy configuration to propagate corporate proxy environment variables, and optionally mounts Elyra pipeline runtime secrets when a DataSciencePipelinesApplication CR exists in the notebook's namespace. The kube-rbac-proxy image reference is a required startup flag (`--kube-rbac-proxy-image`), making the controller inoperable without it. [source: components/odh-notebook-controller/controllers/notebook_mutating_webhook.go:54-68, components/odh-notebook-controller/main.go:150-174]

Network isolation is enforced per-notebook through NetworkPolicies that the OpenshiftNotebookReconciler creates and owns. Ingress routing uses Gateway API resources: the controller creates HTTPRoutes targeting a `data-science-gateway` Gateway in the `openshift-ingress` namespace, with corresponding ReferenceGrants for cross-namespace access. The controller watches both HTTPRoute and ReferenceGrant resources and reconciles them on notebook changes. [source: components/odh-notebook-controller/controllers/notebook_route.go:166, components/odh-notebook-controller/controllers/notebook_network.go:73, components/odh-notebook-controller/controllers/notebook_dspa_secret.go:44-45]

TLS posture is actively managed: at startup, the controller fetches the OpenShift APIServer TLS profile to configure cipher suites and minimum TLS version for its webhook and metrics servers, with hardened defaults when the profile is unavailable. The FIPS-compliant build chain (`GOEXPERIMENT=strictfipsruntime`, `CGO_ENABLED=1`) ensures cryptographic operations use the platform OpenSSL provider at runtime. [source: components/odh-notebook-controller/main.go:179-208, components/odh-notebook-controller/Dockerfile.konflux:24]

## Data Flows

### Flow 1: Notebook CR Reconciliation

When a user creates or updates a `kubeflow.org/Notebook` CR, the Kubernetes API server invokes the mutating webhook (`/mutate-notebook-v1` on port 8443) followed by the validating webhook (`/validate-notebook-v1`). The mutating webhook injects a kube-rbac-proxy sidecar container, propagates cluster proxy environment variables, and optionally mounts an Elyra pipeline runtime secret if a DataSciencePipelinesApplication CR exists in the namespace. The NotebookReconciler then creates or updates a StatefulSet, Service, and related resources. The OpenshiftNotebookReconciler adds NetworkPolicies, HTTPRoutes via the `data-science-gateway` Gateway, and ReferenceGrants for cross-namespace routing. [source: components/odh-notebook-controller/controllers/notebook_mutating_webhook.go:54, components/notebook-controller/controllers/notebook_controller.go:159, components/odh-notebook-controller/controllers/notebook_route.go:166]

### Flow 2: Idle Notebook Culling

The CullingReconciler periodically checks notebook pod activity by reading Pod metadata and Notebook annotations. When a notebook exceeds its idle timeout, the controller scales the StatefulSet to zero by updating the Notebook CR status. [source: components/notebook-controller/controllers/culling_controller.go:92-580]

### Flow 3: Elyra Pipeline Secret Provisioning

The OpenshiftNotebookReconciler watches for DataSciencePipelinesApplication CRs. When a DSPA instance named `dspa` is found in a notebook's namespace and is in a ready state, the controller constructs a pipeline server URL using the `data-science-gateway` Gateway in `openshift-ingress` and creates a `ds-pipeline-config` secret with the Elyra runtime configuration, mounted at `/opt/app-root/runtimes` in the notebook pod. [source: components/odh-notebook-controller/controllers/notebook_dspa_secret.go:38-51]
