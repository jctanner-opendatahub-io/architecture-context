## Purpose

**Short**: Data container and CI/CD tooling that collects model metadata from HuggingFace, GitHub, and OCI container registries, generates structured YAML catalogs, and packages them into a volume-mountable container image for consumption by other RHOAI components. [source: Dockerfile:1-53, Dockerfile.konflux:1-29, cmd/model-extractor/main.go:102, cmd/metadata-report/main.go:13]

**Detailed**: model-metadata-collection provides two Go CLI tools (`model-extractor` and `metadata-report`) that run during CI/CD to collect and enrich AI model metadata from external sources—HuggingFace API, GitHub API, and OCI container registries—and produce structured YAML catalog and index files. The `model-extractor` tool fetches model information including HuggingFace collections, model cards, container image architectures, and agent metadata from GitHub repositories, then generates comprehensive model catalogs covering Red Hat AI models, validated models, MCP servers, and agents. The `metadata-report` tool generates completeness reports from already-extracted metadata. The final container image (built from `Dockerfile.konflux` using `ubi-minimal-pqc` base) contains only the pre-generated YAML data files exposed via volume mount points at `/app/data`; the Go binaries are not included in the shipped image. The container runs `sleep infinity` to serve as a data sidecar, allowing other platform components to mount and read the catalog data. [source: Dockerfile:1-53, Dockerfile.konflux:1-43, cmd/model-extractor/main.go:36-56, cmd/metadata-report/main.go:13-54, internal/huggingface/client.go:54-75, internal/github/client.go:30-46, internal/registry/registry.go:76-80]

## Architectural Analysis

model-metadata-collection follows a pipeline-then-package architecture where CI/CD build tools generate static data artifacts that are then packaged into a minimal container image for runtime consumption. The two Go CLI tools—`model-extractor` and `metadata-report`—are build-time utilities only; neither binary ships in the production container image.

The `model-extractor` tool aggregates metadata from three external sources: (1) HuggingFace API for model collections, model cards, and enrichment data, (2) GitHub API for agent metadata and README files, and (3) OCI container registries for image architecture inspection via the `containers/image` library. Authentication to these sources is optional, using environment variables `HF_TOKEN` (HuggingFace Bearer token) and `GITHUB_TOKEN` (GitHub Bearer token); container registry auth follows the standard `containers/image` credential chain. The tool supports concurrent model processing with configurable parallelism.

The production image is a data-only sidecar built on `ubi-minimal-pqc` that copies pre-generated YAML catalog and index files into `/app/data` and exposes them as a volume mount. It runs as a non-root user (UID 1001) with `sleep infinity` as its CMD, serving purely as a data volume for other platform components that need model and MCP server catalog information. There are no Kubernetes manifests, services, or ingress definitions in this repository; the container's deployment is managed externally by the platform operator.

The repository has no direct FIPS build instrumentation—the Go binaries use default `go build` with no GOEXPERIMENT or strictfipsruntime tags, and the linux cross-compilation target explicitly sets `CGO_ENABLED=0`. However, since no Go binary ships in the production image and the `ubi-minimal-pqc` base image provides the post-quantum cryptography runtime, FIPS compliance at the container level is inherited from the base image rather than enforced by the application.

## Data Flows

- **CI/CD metadata collection:** During build, the `model-extractor` CLI fetches model metadata from HuggingFace API (`https://huggingface.co/api/`), agent metadata from GitHub API (`https://api.github.com/`), and container image architectures from OCI registries. It writes structured YAML catalogs and index files to the `data/` directory. The `metadata-report` CLI then reads these outputs to generate completeness reports. [source: cmd/model-extractor/main.go:36-56, internal/huggingface/client.go:54-75, internal/github/client.go:78-79, internal/registry/registry.go:76-80]
- **Runtime data serving:** The production container image packages the pre-generated YAML files into `/app/data` as a volume mount. Other platform components mount this volume to read model catalog data at runtime. The container itself performs no computation—it runs `sleep infinity` as a data sidecar. [source: Dockerfile.konflux:9-10, Dockerfile.konflux:26-29]
