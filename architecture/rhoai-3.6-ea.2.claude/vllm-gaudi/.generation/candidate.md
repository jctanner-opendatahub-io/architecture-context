## Purpose

**Short**: Intel Gaudi (Habana) HPU plugin for vLLM, providing hardware-accelerated large language model inference via the vLLM OpenAI-compatible API server. [source: pyproject.toml:13, Dockerfile.konflux.gaudi:244]

**Detailed**: vllm-gaudi is an HPU (Habana Processing Unit) plugin package for the vLLM inference engine, enabling high-performance LLM serving on Intel Gaudi accelerators. The repository packages the `vllm_gaudi` Python plugin and builds container images that bundle both the upstream vllm OpenAI-compatible API server and the Gaudi-specific acceleration layer. The Konflux production image (`Dockerfile.konflux.gaudi`) builds a multi-stage container on UBI 9 with Habana SynapseAI drivers, PyTorch with HPU support, and the vLLM framework, exposing `vllm.entrypoints.openai.api_server` as its entrypoint. Additional Dockerfile variants exist for development (`Dockerfile.hpu.ubi`) and CI/testing (`.cd/Dockerfile.rhel.ubi.vllm`, `.cd/Dockerfile.ubuntu.pytorch.vllm`). The component runs as a non-root user (UID 2000) for OpenShift compatibility and does not define its own Kubernetes services or CRDs — it is deployed as a container image within RHOAI serving runtime pods managed by KServe. [source: pyproject.toml:13, 17, Dockerfile.konflux.gaudi:1-244, requirements.txt:1-6]

## Architectural Analysis

vllm-gaudi follows a plugin architecture pattern where the `vllm_gaudi` Python package provides Intel Gaudi HPU-specific implementations that plug into the upstream vLLM framework's device abstraction layer. The Konflux build pipeline constructs a multi-stage container image starting from UBI 9, layering Habana SynapseAI drivers and runtime libraries (version 1.23.0), PyTorch with HPU support (version 2.9.0), the upstream vllm framework (cloned at build time from `vllm-project/vllm`), and finally the vllm-gaudi plugin itself. The build explicitly targets `VLLM_TARGET_DEVICE=hpu` to select Gaudi-optimized code paths. [source: Dockerfile.konflux.gaudi:21-22, 213-216]

A notable architectural decision is the explicit removal of the OpenSSL FIPS provider (`openssl-fips-provider-so`) across all Dockerfile variants. This is done consistently in the Konflux, development, and CI images, indicating that FIPS-mode OpenSSL is incompatible with the Habana software stack or introduces performance penalties for inference workloads. This makes the component non-FIPS-compliant at the application crypto layer. [source: Dockerfile.konflux.gaudi:59-63, Dockerfile.hpu.ubi:59-63, .cd/Dockerfile.rhel.ubi.vllm:60-64]

The component does not implement its own authentication, authorization, service mesh integration, or Kubernetes service definitions. These concerns are delegated to the platform layer — the container image is consumed by KServe ServingRuntime definitions that manage pod lifecycle, networking, and ingress. The HTTP API surface (OpenAI-compatible `/v1/` endpoints) is defined entirely by the upstream vllm framework, not by this repository. [source: Dockerfile.konflux.gaudi:244]

### FIPS Compliance

The component explicitly removes the OpenSSL FIPS provider during container build. All three Dockerfile variants execute `rpm -e --nodeps openssl-fips-provider-so || true`, which removes FIPS-validated cryptographic modules from the image. The comment in `.cd/Dockerfile.rhel.ubi.vllm` notes this also handles RHEL 9.4 where the package may not be installed. This is a Python application that delegates TLS to system OpenSSL, but with the FIPS provider removed, the runtime OpenSSL operates in non-FIPS mode. No explicit FIPS build flags or crypto configuration is present. [source: Dockerfile.konflux.gaudi:59-63, Dockerfile.hpu.ubi:59-63, .cd/Dockerfile.rhel.ubi.vllm:60-64]

## Data Flows

- **Inference request flow:** Client requests arrive at the vLLM OpenAI-compatible API server (port configured at runtime, default 8000/TCP in upstream vLLM). The server processes inference requests through the vLLM engine, which delegates hardware-specific tensor operations to the `vllm_gaudi` HPU plugin layer. The plugin interfaces with Intel Habana SynapseAI runtime and Gaudi hardware for accelerated model execution. Model weights are loaded from a configured storage path at startup. [source: Dockerfile.konflux.gaudi:244, pyproject.toml:17]
- **Build-time dependency flow:** The Konflux build clones the upstream `vllm-project/vllm` repository at a pinned commit (`v0.16.0`), installs it with `VLLM_TARGET_DEVICE=empty`, then installs the `vllm_gaudi` plugin with `VLLM_TARGET_DEVICE=hpu` to register Gaudi-specific device backends. [source: Dockerfile.konflux.gaudi:193-217]
