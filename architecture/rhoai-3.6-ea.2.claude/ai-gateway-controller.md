## Purpose

**Short**: Timer-driven manifest installer that deploys and maintains the praxis-extproc external processing stack for Istio-based AI Gateway routing in the RHOAI platform. [source: cmd/manager/main.go:39, 110-125, pkg/render/installer.go:29-47]

**Detailed**: ai-gateway-controller is a Go controller-runtime application that periodically renders vendored kustomize manifests and applies them via Server-Side Apply (SSA) to deploy the praxis-extproc workload alongside an Istio Gateway. Unlike typical Kubernetes controllers that reconcile Custom Resources via watch-based loops, this controller operates on a fixed resync interval (default 5 minutes) without watching any CRs. It deploys into the `opendatahub` namespace but manages resources in the Gateway namespace (default `openshift-ingress`), creating Deployments, Services, Istio networking resources (EnvoyFilter, DestinationRule, ServiceEntry), NetworkPolicies, and RBAC objects for praxis-extproc. The controller coordinates with maas-controller by targeting the same Gateway (`maas-default-gateway`) and excluding maas-api routes from ext_proc processing. [source: cmd/manager/main.go:56-71, 110-125, pkg/render/installer.go:29-47, config/self/manager/manager.yaml:3-87]

## Architectural Analysis

ai-gateway-controller is a timer-driven manifest installer rather than a traditional CRD reconciler. Its core loop renders vendored praxis-extproc kustomize manifests with runtime parameters (namespace, gateway name, container image, maas-api route name), then applies them to the cluster via Server-Side Apply. This "render-and-apply" pattern runs once at startup and repeats every resync interval (default 5 minutes), which is the only re-apply trigger besides pod restart. The controller does not watch any Custom Resource in its current phase, meaning external changes to managed resources are only corrected on the next resync tick. [source: pkg/render/installer.go:57-98, cmd/manager/main.go:68-71]

The controller deploys in the `opendatahub` namespace with a single replica and leader election (`ai-gateway-controller-leader.opendatahub.io`), ensuring only one instance applies manifests at a time to prevent SSA conflicts. Its managed resources span the Gateway namespace (`openshift-ingress` by default), where it creates the praxis-extproc deployment stack: Deployments, Services (payload-processing on port 9004/HTTP2), Istio networking resources (EnvoyFilter, DestinationRule, ServiceEntry), NetworkPolicies, and RBAC objects. The praxis-extproc container image is configurable via a ConfigMap (`ai-gateway-controller-parameters`) using the `RELATED_IMAGE_ODH_PRAXIS_EXTPROC_IMAGE` pattern, consistent with ODH's related-image convention for disconnected deployment support. [source: config/self/manager/manager.yaml:28-49, cmd/manager/main.go:59-67, config/manifests/praxis-extproc/base/instance/service.yaml:1-12]

The controller coordinates with maas-controller as a sibling deployment, targeting the same Gateway resource (`maas-default-gateway`) and using the `--maas-api-route-name` flag to exclude maas-api's own HTTPRoute from ext_proc processing. The security posture is hardened with `runAsNonRoot`, a read-only root filesystem, dropped capabilities, and a `RuntimeDefault` seccomp profile. FIPS compliance is enforced at build time through `GOEXPERIMENT=strictfipsruntime` and `CGO_ENABLED=1` in the Konflux Dockerfile, producing a dynamically linked binary on a UBI9 base. No Kubernetes Service is defined for the controller itself; its container ports (8080 for metrics, 8081 for health probes) are pod-local and not exposed via a cluster Service object. [source: config/self/manager/manager.yaml:22-65, Dockerfile.konflux:5-6, cmd/manager/main.go:65-67]

## Data Flows

- **Manifest render-and-apply loop:** On startup and every resync interval (default 5 minutes), the controller renders vendored praxis-extproc kustomize manifests, applies parameter substitution (namespace, gateway name, container image, maas-api route name), and SSA-applies the resulting Kubernetes resources to the cluster. Render failures are logged and retried on the next tick without crashing the process. [source: pkg/render/installer.go:57-98, cmd/manager/main.go:110-125]
- **Gateway and Istio integration:** The controller targets a named Gateway resource (default `maas-default-gateway`) in the configured namespace (default `openshift-ingress`), creating EnvoyFilter, DestinationRule, and ServiceEntry resources that configure ext_proc filtering in the Istio service mesh. The managed praxis-extproc stack includes payload-processing and payload-pre-processing Deployments and Services (port 9004/HTTP2). [source: cmd/manager/main.go:59-67, config/manifests/praxis-extproc/overlays/odh/pre-processing/kustomization.yaml:24-35, config/manifests/praxis-extproc/base/instance/service.yaml:1-12]
- **Kubernetes API egress:** All resource operations flow through the Kubernetes API server (port 6443, HTTPS/WSS, TLS 1.2+) using the controller's ServiceAccount token (`ai-gateway-controller`) for authentication. RBAC is enforced via the `ai-gateway-controller-role` ClusterRole, which grants permissions across core resources, apps, networking.k8s.io, networking.istio.io, gateway.networking.k8s.io, rbac.authorization.k8s.io, and inference.opendatahub.io API groups. [source: cmd/manager/main.go:87, config/self/rbac/clusterrole.yaml:5, config/self/rbac/clusterrole_binding.yaml:1]
- **Health and metrics surface:** The controller exposes two unauthenticated HTTP endpoints on port 8081 (/healthz, /readyz) for Kubernetes probes, and a metrics endpoint on port 8080. No Kubernetes Service object backs these ports; they are pod-local. [source: cmd/manager/main.go:101-105, config/self/manager/manager.yaml:53-78]
