## Purpose

**Short**: Kubernetes operator that manages the lifecycle of Model Registry, AI Hub, and Catalog custom resources, provisioning per-instance deployments with PostgreSQL backends, kube-rbac-proxy sidecars, and Gateway API or OpenShift Route ingress. [source: Dockerfile.konflux:22, api/aihub/v1alpha1/aihub_types.go:79, api/catalog/v1alpha1/catalog_types.go:121, api/v1alpha1/modelregistry_types.go:440]

**Detailed**: The model-registry-operator is a Go-based Kubernetes operator built on controller-runtime that manages three custom resource types: ModelRegistry (v1alpha1/v1beta1), AIHub (v1alpha1), and Catalog (v1alpha1). For each ModelRegistry CR, the operator provisions a complete stack including a model-registry REST deployment with a kube-rbac-proxy sidecar for authenticated HTTPS access, a PostgreSQL database deployment for metadata storage, Kubernetes Services, RBAC Roles and RoleBindings for tenant-scoped access, NetworkPolicies, and ingress resources (OpenShift Routes or Gateway API HTTPRoutes depending on cluster capabilities). The AIHub controller acts as a higher-level orchestrator that manages Catalog sub-resources and their associated deployments. The operator integrates with the ODH platform through odh-platform-utilities for platform detection and manifest rendering, watches `services.platform.opendatahub.io/Auth` resources for platform authentication configuration, and uses `components.platform.opendatahub.io/ModelRegistries` for component lifecycle coordination with the ODH operator. Admission webhooks enforce validation and defaulting on ModelRegistry resources, and a CRD conversion webhook supports migration between API versions. [source: Dockerfile.konflux:22, go.mod:11, internal/controller/kubebuilder.go:22-23, internal/controller/modelregistry_gateway.go:29-51, internal/webhook/modelregistry_webhook.go:57]

## Architectural Analysis

The model-registry-operator follows a multi-controller pattern with three independent reconciliation loops sharing a single manager process. The ModelRegistryReconciler handles the primary workload: each ModelRegistry CR triggers creation of a REST API deployment (backed by the upstream model-registry server image), a PostgreSQL deployment, associated Services, Secrets, RBAC resources, and ingress routes. The Catalog controller manages model-catalog deployments with a similar stack, and the AIHub controller orchestrates Catalog sub-resources as a higher-level aggregation point.

A notable architectural pattern is the dual ingress strategy. The operator detects cluster capabilities at startup through the Kubernetes discovery API (`internal/setup/setup.go:80-91`) and conditionally provisions either OpenShift Routes or Gateway API HTTPRoutes. For Gateway API, each registry gets a per-instance HTTPRoute while a namespace-scoped ReferenceGrant is shared across all registries in the namespace and intentionally preserved during single-registry deletion (`internal/controller/modelregistry_gateway.go:61-70`). This design prevents cross-tenant interference in Gateway API permissions.

Authentication for managed registry endpoints is delegated to kube-rbac-proxy sidecars running alongside the REST containers on port 8443. The proxy performs TokenReview and SubjectAccessReview calls against the Kubernetes API, with per-registry RBAC Roles (`registry-user-{registry-name}`) scoping access to tenant-specific user groups. TLS certificates for the proxy are managed through Kubernetes Secrets provisioned by the operator templates. The operator itself authenticates to the Kubernetes API using its ServiceAccount token, with TLS configuration inherited from the cluster's TLS security profile when running on OpenShift (`internal/setup/setup.go:101-128`).

The operator integrates with the broader RHOAI platform through two platform API groups: it watches `services.platform.opendatahub.io/Auth` resources for centralized authentication configuration, and `components.platform.opendatahub.io/ModelRegistries` for lifecycle coordination with the ODH operator's component management. The `odh-platform-utilities` library (v0.3.0) provides platform detection, manifest rendering, and deployment helpers used across all three controllers. CRD version migration between v1alpha1 and v1beta1 is supported through a conversion webhook and StorageVersionMigration resources.

## Data Flows

### Flow 1: ModelRegistry Instance Provisioning

| Step | Source | Destination | Port | Protocol | Encryption | Auth |
|------|--------|-------------|------|----------|------------|------|
| 1 | User/Platform | Kubernetes API | 6443/TCP | HTTPS | TLS 1.2+ | Bearer Token |
| 2 | Kubernetes API | Webhook Server | 9443/TCP | HTTPS | TLS | Kubernetes admission |
| 3 | ModelRegistryReconciler | Kubernetes API | 6443/TCP | HTTPS | TLS 1.2+ | ServiceAccount |
| 4 | ModelRegistryReconciler | PostgreSQL Deployment | -- | -- | -- | Provisioned via Secret |
| 5 | ModelRegistryReconciler | Gateway API / Route | -- | Kubernetes API | TLS 1.2+ | ServiceAccount |

A user or the ODH operator creates a ModelRegistry CR. The admission webhooks validate and default the resource. The ModelRegistryReconciler then provisions the full stack: REST deployment with kube-rbac-proxy sidecar, PostgreSQL deployment, Services, Secrets (database credentials, TLS certificates), RBAC resources, NetworkPolicies, and ingress routes. [source: internal/webhook/modelregistry_webhook.go:57, internal/controller/modelregistry_gateway.go:29-51]

### Flow 2: Registry API Access

| Step | Source | Destination | Port | Protocol | Encryption | Auth |
|------|--------|-------------|------|----------|------------|------|
| 1 | Client | OpenShift Route / HTTPRoute | 443/TCP | HTTPS | TLS | kube-rbac-proxy |
| 2 | kube-rbac-proxy | Kubernetes API | 6443/TCP | HTTPS | TLS 1.2+ | TokenReview/SAR |
| 3 | kube-rbac-proxy | REST container | 8080/TCP | HTTP | None | Proxy-authenticated |

External clients access registry endpoints through OpenShift Routes or Gateway API HTTPRoutes on port 8443. The kube-rbac-proxy sidecar authenticates requests via TokenReview and SubjectAccessReview against the Kubernetes API, then proxies authenticated requests to the REST container on port 8080. Access is scoped through per-registry RBAC roles bound to user groups.
