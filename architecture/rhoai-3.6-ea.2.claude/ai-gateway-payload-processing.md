## Purpose

**Short**: Kubernetes controller and Envoy External Processing (ExtProc) gRPC server that bridges external LLM provider APIs with the RHOAI AI Gateway through declarative CRD-based routing and authentication configuration. [source: cmd/runner.go:88-96, cmd/main.go:33-53, api/inference/v1alpha1/common_types.go:20-32]

**Detailed**: ai-gateway-payload-processing defines two CRDs—ExternalModel and ExternalProvider—to declaratively configure routing and authentication for external AI model endpoints within the RHOAI AI Gateway. The ExternalProvider controller reconciles each provider into a set of Kubernetes networking resources: an ExternalName Service for DNS-level routing, an Istio ServiceEntry for mesh integration, and an Istio DestinationRule for TLS origination to the external endpoint. The ExternalModel controller reconciles Gateway API HTTPRoutes to direct traffic through the configured gateway. On the data plane, a gRPC ExtProc server receives per-request processing callouts from Envoy and executes a configurable plugin pipeline that handles model selection (random, weighted-random, max-score, session-affinity, cost-guard), request/response transformation (body-field-to-header, base-model-extractor, model-name-to-header), and metadata extraction. Authentication is configured per-provider through a CRD enum supporting apikey, sigv4, and oauth2 types, each referencing a Kubernetes Secret for credentials. [source: pkg/controller/externalprovider/reconciler.go:59-136, cmd/runner.go:88-96, 251-268, api/inference/v1alpha1/common_types.go:20-32]

## Architectural Analysis

ai-gateway-payload-processing has a dual-plane architecture: a **control plane** that reconciles CRD-specified intent into Kubernetes networking primitives, and a **data plane** that processes live Envoy request/response flows through a plugin pipeline.

The control plane runs two controllers under controller-runtime. The ExternalProvider controller watches ExternalProvider CRs and creates three child resources per provider: an ExternalName Service for cluster-internal DNS resolution of the external endpoint, an Istio ServiceEntry for service mesh registration, and an Istio DestinationRule for TLS origination. The ExternalModel controller watches ExternalModel CRs and reconciles Gateway API HTTPRoute resources against a configured gateway, optionally managed with `GATEWAY_NAME` and `GATEWAY_NAMESPACE` environment variables. Both controllers validate credential references by fetching the referenced Kubernetes Secrets. [source: pkg/controller/externalprovider/reconciler.go:59-136, cmd/main.go:35-46]

The data plane is a gRPC ExtProc server adapted from the upstream `llm-d-inference-payload-processor` library, wrapped with a `dynamicmetadata.WrapServer` interceptor that enables plugins to set Envoy `ProcessingResponse.DynamicMetadata` via pseudo-headers. The plugin system supports pre-processors, post-processors, response-header post-processors, and a profile-based model selection pipeline with multiple strategies. Optional TLS on the ExtProc gRPC listener uses self-signed certificates generated at startup with `crypto/tls` (minimum TLS 1.2). A separate plaintext gRPC Health service provides health checking. Metrics are served via controller-runtime's HTTP metrics server with optional `WithAuthenticationAndAuthorization` protection. [source: cmd/runner.go:88-96, 147-155, 216-293]

The component is built with `GOEXPERIMENT=strictfipsruntime` and `CGO_ENABLED=1`, targeting a `ubi9/ubi-minimal-pqc` base image. This establishes FIPS-compliant cryptographic provider selection at build time through OpenSSL delegation. The recent migration to the PQC base image variant indicates alignment with post-quantum cryptography readiness. [source: Dockerfile.konflux:10-34]

## Data Flows

- **Control plane flow:** An ExternalProvider CR triggers the ExternalProvider controller, which validates the referenced Secret (containing provider credentials), then creates or updates an ExternalName Service, Istio ServiceEntry, and Istio DestinationRule (TLS origination) to establish mesh-integrated connectivity to the external provider endpoint. An ExternalModel CR triggers the ExternalModel controller, which reconciles a Gateway API HTTPRoute to direct traffic for that model through the configured gateway. [source: pkg/controller/externalprovider/reconciler.go:67-136, pkg/controller/externalmodel/reconciler.go:91, 210, 258-260]
- **Data plane flow:** Envoy sends per-request gRPC ExtProc callouts to the payload processing server. The plugin pipeline processes each request through pre-processors (model selection, header injection, metadata extraction), routes to a selected model profile, and applies post-processors to the response. The dynamicmetadata wrapper intercepts pseudo-headers from plugins and translates them into Envoy ProcessingResponse DynamicMetadata. [source: cmd/runner.go:216-224, 251-268, 291-293]
- **Service surface:** The component exposes two gRPC services (ExternalProcessor with optional TLS, Health without TLS) and one HTTP metrics endpoint via controller-runtime. No static Kubernetes Service definitions are shipped; Services are created dynamically by the ExternalProvider controller for each reconciled provider. [source: cmd/runner.go:226-240, 147-155, pkg/controller/externalprovider/reconciler.go:108-115]
- **Security context:** Authentication to external providers is CRD-configured with three supported types (apikey, sigv4, oauth2), each requiring a Secret reference. The ExtProc gRPC server has no application-level authentication interceptor; transport security is provided by optional TLS. The metrics endpoint optionally enables authentication via controller-runtime's WithAuthenticationAndAuthorization filter. [source: api/inference/v1alpha1/common_types.go:20-32, cmd/runner.go:147-154, 276-293]
