## Purpose

**Short**: rhoai-mcp is an MCP (Model Context Protocol) server that enables AI agents to interact with Red Hat OpenShift AI environments, providing tool-based access to workbenches, model serving, pipelines, and training resources via the Kubernetes API. [source: pyproject.toml:2-4, src/rhoai_mcp/server.py:300-305]

**Detailed**: rhoai-mcp implements a Model Context Protocol server for Red Hat OpenShift AI, enabling AI agents (such as Claude Desktop) to manage RHOAI platform resources programmatically. The server uses a pluggy-based plugin system to expose MCP tools for managing Kubeflow Notebooks (workbenches), KServe InferenceServices (model serving), Data Science Pipelines, Kubeflow Training jobs, and Model Registry operations. It connects to the Kubernetes API using the Python kubernetes client and supports both in-cluster and kubeconfig-based authentication. [source: pyproject.toml:2-4, 27-33, src/rhoai_mcp/server.py:68-69, 281-328, deploy/kustomize/base/clusterrole.yaml:1]

The server supports three transport modes: stdio (for local agent integration), SSE, and streamable-http (for remote access). When deployed with OIDC enabled, it enforces per-user authentication via JWT or Kubernetes TokenReview validation and applies RBAC-based tool-level access control, allowing administrators to restrict which MCP tools each user can invoke based on their Kubernetes permissions. [source: src/rhoai_mcp/config.py:22-28, 54-65, src/rhoai_mcp/server.py:324-327, 419-504]

## Architectural Analysis

rhoai-mcp follows a plugin-based architecture where domain-specific capabilities (notebooks, model serving, pipelines, training) are implemented as pluggy plugins that register MCP tools, resources, and prompts with the FastMCP server. This design enables feature isolation and allows selective plugin loading via the `RHOAI_MCP_ENABLED_PLUGINS` configuration. External plugins can be discovered via Python entrypoints, extending the server without modifying its core. The server uses HMAC-signed workflow tokens to enforce ordered multi-step tool invocations, preventing agents from skipping prerequisite steps in complex operations. [source: src/rhoai_mcp/server.py:281-316, src/rhoai_mcp/utils/workflow_token.py:1-6, 33-49]

The authentication architecture has two layers: transport-level OIDC authentication (via OIDCAuthMiddleware wrapping the SSE/streamable-http ASGI apps) and tool-level RBAC filtering (via patched MCP request handlers that check Kubernetes SubjectAccessReview permissions before exposing or executing tools). When OIDC is enabled, the server supports two Kubernetes auth strategies: direct user-token forwarding (passing the caller's bearer token to the K8s API) and impersonation (using the service account credentials with Impersonate-User/Group headers). The `/health` and `/.well-known/oauth-protected-resource` endpoints are excluded from authentication to support Kubernetes probes and OIDC discovery. [source: src/rhoai_mcp/server.py:96-117, 330-504, src/rhoai_mcp/config.py:240-289]

The server's ClusterRole grants broad access across 13 RBAC rules spanning core resources (namespaces, pods, secrets, PVs), Kubeflow Notebooks, KServe InferenceServices and ServingRuntimes, Kubeflow Training (TrainJobs, TrainingRuntimes, ClusterTrainingRuntimes), and Data Science Pipelines CRDs. This reflects the server's role as a comprehensive platform management proxy that operates on behalf of authenticated users. The deployment uses an AIPCC CPU base image and runs as a single-container Deployment with a ClusterIP service on port 8000. No ingress resources are defined in the base manifests; external access is expected to be configured at the platform level via OpenShift Routes or Gateway API. ## Data Flows

- **Agent-to-server:** AI agents connect to rhoai-mcp via one of three transports: stdio (local pipe), SSE, or streamable-http. HTTP transports listen on the ClusterIP service at port 8000. When OIDC is enabled, the OIDCAuthMiddleware validates the bearer token (via JWT JWKS verification or Kubernetes TokenReview API) before the request reaches the MCP protocol handler. [source: src/rhoai_mcp/config.py:117-130, src/rhoai_mcp/server.py:300-308, 382-415, deploy/kustomize/base/service.yaml:1]
- **Server-to-Kubernetes:** MCP tool invocations translate to Kubernetes API calls via the Python `kubernetes` client. The server authenticates to the API server using either the pod's service account token, the caller's forwarded bearer token (user-token strategy), or impersonation headers. Operations span core resources (namespaces, pods, secrets, PVs, PVCs), Kubeflow CRDs (Notebooks, TrainJobs, TrainingRuntimes), KServe CRDs (InferenceServices, ServingRuntimes), and Data Science Pipelines CRDs. [source: src/rhoai_mcp/server.py:96-117, 205-224, deploy/kustomize/base/clusterrole.yaml:1]
- **Server-to-platform services:** The server integrates with Model Registry via HTTP at `model-registry.odh-model-registries.svc:8080` (configurable, supports none/OAuth/token auth) and with the Planner Backend at `backend.planner.svc.cluster.local:8000`. [source: src/rhoai_mcp/config.py:190-231]
