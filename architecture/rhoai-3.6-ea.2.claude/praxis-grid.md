## Purpose

**Short**: Kubernetes operator for multi-site AI inference orchestration that manages GridNetwork, GridSite, and InferenceProvider custom resources, uses a SWIM gossip protocol for peer-to-peer mesh formation, and delivers routing overlays to the Praxis data-plane proxy. [source: operator/src/main.rs:1-5, deploy/crds/gridnetwork.yaml:1, deploy/crds/gridsite.yaml:1, deploy/crds/inferenceprovider.yaml:1]

**Detailed**: praxis-grid is a Rust-based Kubernetes operator that orchestrates multi-site AI inference routing. It manages three primary custom resources — GridNetwork (cluster-wide mesh topology), GridSite (per-site membership), and InferenceProvider (backend endpoint registration with credential resolution) — plus AgentToolProvider for MCP-based tool discovery. The operator optionally starts a SWIM membership runtime for peer-to-peer state propagation across sites, using AES-256-GCM encrypted UDP gossip with pre-shared keys sourced from Kubernetes Secrets. A companion sidecar, grid-overlay-sync, watches a ConfigMap through the Kubernetes API and atomically writes validated routing overlays to a shared emptyDir volume consumed by the Praxis data-plane proxy. The operator discovers its provider gateway address either from an explicit environment variable or by polling a Kubernetes LoadBalancer Service. [source: operator/src/main.rs:1-5, 104, 118-134, operator/src/resources/credentials.rs:1-31, overlay-sync/src/main.rs:1-8, operator/src/gateway.rs:1-5]

## Architectural Analysis

praxis-grid follows a CRD-driven controller pattern where three cluster-scoped resources define the inference mesh topology. GridNetwork captures the cluster-wide routing configuration including TLS settings and SWIM encryption keys. GridSite represents per-site membership in the mesh, with the operator populating status fields such as `connectedSites` and `distributedProviderCount` from SWIM state. InferenceProvider registers backend inference endpoints along with their credential strategy and health/metrics probing configuration. A fourth resource, AgentToolProvider, extends the mesh to MCP-compatible tool endpoints using the `rmcp` crate's reqwest-backed Streamable HTTP transport. [source: operator/src/main.rs:1-5, 130-134, Cargo.toml:45-49]

The SWIM membership protocol (via the `foca` crate) provides eventually-consistent peer-to-peer state propagation. Each operator instance binds a UDP listener, advertises its gateway address, and joins seed peers. Gossip packets are encrypted with AES-256-GCM when a pre-shared key is configured through `GridNetwork.spec.tls.swimKeyRef` (production) or the `GRID_SWIM_ENCRYPT_KEY` environment variable (development). Revision leases are durably tracked in a ConfigMap to ensure disjoint transport-revision ranges across concurrent operator instances, preventing published-revision reuse. [source: operator/src/main.rs:8-32, 162-208, 210-222]

The data-plane integration follows a sidecar pattern: grid-overlay-sync watches a named ConfigMap, validates the content-addressed overlay envelope, and atomically writes the routing overlay to a shared emptyDir volume that the Praxis proxy reads. This decouples the control-plane reconciliation loop from the data-plane configuration path and provides crash-safe file delivery. [source: overlay-sync/src/main.rs:1-8]

Credential resolution for InferenceProvider backends follows a strategy pattern. The current v1 implementation (`KubernetesSecretResolver`) reads bearer tokens from Kubernetes Secrets referenced by `InferenceProvider.spec.auth.secretRef`. The credential path is pure-data planning followed by I/O resolution, with explicit failure reasons surfaced in `InferenceProvider.status.reason` for operational visibility. Future backends (Vault, External Secrets Operator, OAuth2, SigV4, workload identity) implement the same `CredentialResolver` trait. [source: operator/src/resources/credentials.rs:1-31]

All TLS in the operator uses rustls with `ring` as the explicitly installed process-wide CryptoProvider. The ring provider is selected intentionally over aws-lc-rs to avoid runtime conflicts between hyper-rustls and reqwest's crypto provider selection. This means the operator does not use a FIPS-validated cryptographic provider. [source: operator/src/main.rs:89-106, Cargo.toml:33, 39-43, 44, 50, 60]

### FIPS Compliance

The operator explicitly installs `ring::default_provider()` as the process-wide rustls `CryptoProvider` at startup. The workspace `Cargo.toml` configures all TLS dependencies — `hyper-rustls`, `tokio-rustls`, and `reqwest` (via `rustls-no-provider`) — to use the `ring` cryptographic backend. The `reqwest` and `rmcp` entries intentionally avoid `aws-lc-rs` to prevent provider conflicts. `ring` is not a FIPS-validated cryptographic provider; therefore the operator does not operate in a FIPS-compliant mode. SWIM gossip encryption uses the `aes-gcm` crate (v0.10) for AES-256-GCM, which is a standalone implementation not backed by a FIPS-validated module. ## Data Flows

- **Control-plane reconciliation:** The operator watches GridNetwork, GridSite, InferenceProvider, and AgentToolProvider CRDs cluster-wide. On reconciliation, it resolves credentials from Kubernetes Secrets, probes InferenceProvider health and metrics endpoints over TLS (rustls/ring), and publishes routing-overlay ConfigMaps that capture provider availability and scoring weights. [source: operator/src/main.rs:130-134, operator/src/resources/credentials.rs:1-10, operator/src/resources/endpoint_tls.rs:1-9]
- **SWIM gossip mesh:** When `GRID_SWIM_BIND_ADDR` is set, the operator binds a UDP listener and joins seed peers for eventually-consistent state propagation. Each site broadcasts its gateway address, connected provider count, and membership state. Gossip packets are optionally encrypted with AES-256-GCM using a pre-shared key from `GridNetwork.spec.tls.swimKeyRef`. Revision leases tracked in a ConfigMap prevent revision reuse across concurrent operators. [source: operator/src/main.rs:8-32, 162-208, 210-222]
- **Data-plane overlay delivery:** The grid-overlay-sync sidecar watches a named ConfigMap, validates the content-addressed overlay envelope, and atomically writes the routing overlay to a shared emptyDir volume consumed by the Praxis data-plane proxy. This path is the control-to-data-plane boundary. [source: overlay-sync/src/main.rs:1-8]
- **Gateway discovery:** The operator discovers its provider gateway address by polling a Kubernetes Service named `provider-gateway` in the `grid-system` namespace for its LoadBalancer IP, or uses an explicit `GRID_GATEWAY_ADDRESS` override. The discovered address is advertised to SWIM peers via `GridSite.spec.egress.address`. [source: operator/src/gateway.rs:1-5, 37-69]
