## Purpose

**Short**: OGX distribution packages the OGX framework (formerly llama-stack) as a containerized AI agent server for RHOAI, exposing OpenAI-compatible and Anthropic Messages APIs on port 8321. [source: distribution/config.yaml:257, Dockerfile.konflux:77]

**Detailed**: ogx-distribution is the Red Hat productization of the OGX (formerly llama-stack) AI agent framework, packaged as a single-container Python application server. The distribution configures the OGX server with a curated set of API surfaces — responses, messages, batches, inference, tool_runtime, vector_io, files, and file_processors — and connects them to pluggable inference backends (primarily vLLM), vector databases (Milvus, PGVector, Qdrant), and PostgreSQL for state persistence. The container image is built from an AIPCC base image using Hermeto/cachi2 for hermetic dependency installation, and includes pre-baked model artifacts from a modelcar OCI image for offline document processing (Docling, HuggingFace, Tiktoken). Authentication is handled via optional OAuth2 token validation with JWKS-based JWT verification when `AUTH_ISSUER` is configured. The entrypoint supports Kubernetes-native secret file mounts and optional OpenTelemetry instrumentation. ## Architectural Analysis

ogx-distribution follows a distribution-as-configuration pattern: the upstream OGX framework provides the server runtime and API implementations, while this repository contributes the RHOAI-specific packaging — a Konflux Dockerfile, a generated `config.yaml` with environment-variable-driven provider activation, and an entrypoint script that bridges Kubernetes secret mounting conventions to the OGX runtime. The `Dockerfile.konflux.in` is the template; `Dockerfile.konflux` is auto-generated from it by `scripts/sync_labels.py`, embedding the full configuration as a base64-encoded OCI label for operator introspection. Both share the same `ENTRYPOINT [ "/opt/app-root/entrypoint.sh" ]`.

The server architecture is provider-pluggable: each API surface (inference, vector_io, tool_runtime, files, etc.) is backed by one or more providers activated by environment variables using shell-style conditional expansion (`${env.VLLM_URL:+vllm-inference}`). This means the deployed server's integration footprint varies by deployment configuration. The core dependency is always PostgreSQL for KV and SQL storage backends. vLLM is the primary inference provider for RHOAI deployments.

A notable security design is the entrypoint's `_FILE` secret resolution pattern, which reads Kubernetes-mounted secret files into environment variables at startup, avoiding `/proc` exposure. Authentication is delegated to an optional OAuth2 token validator configured via `AUTH_ISSUER`, with JWKS-based JWT verification and a three-rule access policy (public read for system resources, create for authenticated users, owner-scoped CRUD). The `--insecure` flag passed to `ogx run` in the entrypoint disables TLS at the application layer, indicating that TLS termination is expected at the platform ingress level (e.g., OpenShift Route or Istio gateway).

The container image packages pre-baked model artifacts from a separate "modelcar" OCI image, providing offline Docling document processing, HuggingFace model caches, and Tiktoken tokenizer data. This hermetic model packaging avoids runtime downloads and supports air-gapped deployments. The ServiceMonitor configuration at `config/monitoring/servicemonitor.yaml` reveals integration with the ogx-operator for lifecycle management and Prometheus metrics scraping on a dedicated metrics port. ## Data Flows

- **Inference request flow:** Client sends an HTTP request (e.g., `/v1/chat/completions` or `/v1/messages`) to the OGX server on port 8321. The server authenticates the request via OAuth2 JWT (when configured), routes it to the appropriate API handler (inference, responses, messages), and proxies the inference call to the configured vLLM backend. Responses are persisted in the PostgreSQL SQL store and returned to the client. [source: distribution/config.yaml:14-80, distribution/config.yaml:257-281]
- **RAG flow:** When vector_io providers are configured, the server can perform retrieval-augmented generation by querying vector databases (Milvus, PGVector, or Qdrant) for relevant documents, then passing context to the inference provider. File uploads are stored via the localfs or S3 file provider, with metadata in PostgreSQL. [source: distribution/config.yaml:81-121, distribution/config.yaml:166-185]
- **Secret resolution at startup:** The entrypoint script iterates over a fixed list of secret environment variables and resolves `_FILE` variants by reading Kubernetes-mounted secret files, then exports the values and unsets the file paths. This occurs before the OGX server process starts. [source: distribution/entrypoint.sh:11-57]
