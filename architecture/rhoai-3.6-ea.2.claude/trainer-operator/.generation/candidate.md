## Purpose

**Short**: Kubernetes operator that manages the lifecycle of Kubeflow Trainer v2 components on RHOAI, deploying and reconciling TrainJob, ClusterTrainingRuntime, and TrainingRuntime resources along with their supporting infrastructure. [source: cmd/main.go:71, internal/controller/trainer_controller.go:64-82, config/crd/bases/components.platform.opendatahub.io_trainers.yaml:2]

**Detailed**: trainer-operator is a controller-runtime based Kubernetes operator that reconciles a cluster-scoped `Trainer` custom resource (components.platform.opendatahub.io/v1alpha1). When a Trainer CR is created, the operator renders and deploys the upstream Kubeflow Trainer v2 controller, its CRDs (TrainJob, ClusterTrainingRuntime, TrainingRuntime), RBAC, webhooks, and supporting services into a target namespace. The operator uses the odh-platform-utilities framework for manifest rendering, server-side-apply deployment, garbage collection of stale resources, and deployment status tracking. It reads platform version information from the `odh-trainer-config` ConfigMap and manages ImageStream resources for OpenShift integration. The operator serves metrics over HTTPS on port 8443 with Kubernetes authn/authz enforcement and resolves TLS configuration from the cluster's OpenShift APIServer TLS profile. [source: cmd/main.go:71-218, internal/controller/trainer_controller.go:178-219, internal/tls/metrics.go:35-49, internal/tls/profile.go:52-80]

## Architectural Analysis

trainer-operator follows the ODH platform component-operator pattern: a single controller watches a cluster-scoped platform CR (`Trainer`) and renders the upstream Kubeflow Trainer v2 stack into a target namespace using the odh-platform-utilities framework's action pipeline. The reconciliation pipeline chains dependency checks, namespace creation, release metadata updates, manifest rendering via kustomize overlays, server-side-apply deployment, deployment readiness tracking, and garbage collection of orphaned resources from prior releases. [source: internal/controller/trainer_controller.go:192-219]

The operator manages a substantial set of downstream resources — the Kubeflow Trainer controller deployment, ClusterTrainingRuntime and TrainingRuntime CRDs, webhook configurations, RBAC roles, NetworkPolicies, and ImageStreams — all tracked via platform labels for cache filtering and garbage collection. Cache hardening scopes informers to labeled resources and a configurable `APPLICATIONS_NAMESPACE`, while Namespace objects are excluded from the cache entirely to avoid cluster-wide informer overhead. [source: cmd/main.go:103-145, internal/controller/trainer_controller.go:192-218]

The TLS architecture is notably mature for an early-access component: the operator resolves the cluster's OpenShift APIServer TLS profile at startup, applies it to the metrics server, and installs a watcher that triggers a graceful restart when the profile changes. Metrics are served over HTTPS with controller-runtime's `WithAuthenticationAndAuthorization` filter, requiring Kubernetes TokenReview and SubjectAccessReview for access. Service-CA provisioned certificates are loaded dynamically via `GetCertificate` to support rotation without restart. [source: internal/tls/profile.go:52-155, internal/tls/metrics.go:35-63, cmd/main.go:97-112]

A key external dependency is the JobSet operator: the controller dynamically watches the `JobSetOperator` CRD and checks its availability before proceeding with deployment, gating the training stack on this prerequisite. [source: internal/controller/trainer_controller.go:198-201]

## Data Flows

- **Reconciliation flow:** The platform operator creates a `Trainer` CR, which triggers the trainer-operator controller. The controller checks JobSetOperator availability, ensures the target namespace exists, reads platform version from the `odh-trainer-config` ConfigMap, renders Kubeflow Trainer manifests via kustomize overlays, and applies them using server-side apply. It then monitors deployment readiness and garbage-collects stale resources. [source: internal/controller/trainer_controller.go:192-219, cmd/main.go:188-196]
- **Metrics and observability:** The operator exposes a metrics endpoint on port 8443 over HTTPS with TLS certificates provisioned by OpenShift service-CA. Access requires Kubernetes TokenReview and SubjectAccessReview authentication/authorization. A ServiceMonitor enables Prometheus scraping via the prometheus-operator. [source: internal/tls/metrics.go:35-49, cmd/main.go:76-79, 112, config/default/metrics_service.yaml:5]
- **TLS lifecycle:** At startup, the operator resolves the cluster TLS profile from the OpenShift APIServer resource. A SecurityProfileWatcher monitors for profile changes and triggers a graceful shutdown-and-restart cycle to reload updated TLS configuration. [source: internal/tls/profile.go:52-155, cmd/main.go:97-101, 208-211]
- **Health probes:** Liveness (/healthz) and readiness (/readyz) probes are served on port 8081 over HTTP without authentication, following Kubernetes probe conventions. [source: cmd/main.go:199-206]
