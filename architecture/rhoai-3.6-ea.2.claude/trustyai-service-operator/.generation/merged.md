## Purpose

**Short**: Multi-controller Kubernetes operator that manages AI model trustworthiness, evaluation, and guardrails services within Red Hat OpenShift AI, reconciling TrustyAIService, EvalHub, LMEvalJob, GuardrailsOrchestrator, and NemoGuardrails custom resources. [source: cmd/main.go:95, api/tas/v1/trustyaiservice_types.go:12, api/evalhub/v1/evalhub_types.go:28]

**Detailed**: trustyai-service-operator provides the control plane for AI trustworthiness and evaluation capabilities within the RHOAI platform. The operator manages six custom resource definitions across two API groups: TrustyAIService and EvalHub (with v1 and v1alpha1 versions), GuardrailsOrchestrator, LMEvalJob, and NemoGuardrails (all v1alpha1), plus the platform-level TrustyAI resource (components.platform.opendatahub.io/v1alpha1). The repository produces multiple deployable artifacts: the primary operator binary (`/manager`), an LM evaluation driver (`/bin/driver`), an LM evaluation job runner (Python-based), and a guardrails orchestrator binary. A separate trustyai-operator-module provides platform-level TrustyAI lifecycle management using odh-platform-utilities for manifest rendering and deployment. The operator creates TLS-secured services with kube-rbac-proxy sidecars for managed TrustyAI instances and integrates with KServe InferenceService for model serving state, prometheus-operator for monitoring, Kueue for batch scheduling, and the OpenTelemetry Collector for distributed tracing. Runtime configuration is read from the OpenDataHub operator's `trustyai-dsc-config` ConfigMap, which governs evaluation security policies. ## Architectural Analysis

The trustyai-service-operator employs a multi-controller architecture built on controller-runtime v0.23.3, running seven reconcilers within a single manager process. The TrustyAIServiceReconciler manages per-namespace TrustyAI deployments with TLS-secured services (port 443→8443) and kube-rbac-proxy sidecars, creating both OpenShift Route and Istio VirtualService ingress resources for external access. The EvalHubReconciler orchestrates model evaluation across tenant namespaces, managing ServiceMonitor resources for Prometheus integration and creating per-evaluation RBAC bindings via dedicated service accounts and ClusterRoleBindings. The GuardrailsOrchestratorReconciler watches KServe InferenceService resources to coordinate guardrails enforcement with model serving, while the LMEvalJobReconciler manages evaluation job pods with PersistentVolumeClaim storage and Kueue workload integration for batch scheduling. The NemoGuardrailsReconciler adds NVIDIA NeMo guardrails support with Gateway API resource reads for network routing. [source: controllers/tas/trustyaiservice_controller.go:299, controllers/evalhub/evalhub_controller.go:370-378, controllers/gorch/guardrailsorchestrator_controller.go:410-449, controllers/lmes/lmevaljob_controller.go:341-347]

A key design pattern is TLS configuration inheritance from the OpenShift APIServer resource (`config.openshift.io/v1/APIServer`), which the ProfileWatcher reads with a bounded 10-second timeout, falling back to hardened intermediate cipher suites with ALPN on non-OpenShift clusters or transient errors. This enables the operator to respect cluster-wide TLS policies without requiring per-component TLS configuration. The metrics server conditionally enables Kubernetes-delegated authentication and authorization via controller-runtime's `WithAuthenticationAndAuthorization` filter when the `secureMetrics` flag is set, ensuring the Prometheus scrape surface is access-controlled in production deployments. [source: pkg/tls/tls.go:96-119, cmd/main.go:159-161]

The operator reads runtime policy from the OpenDataHub operator's `trustyai-dsc-config` ConfigMap, which controls evaluation security policies (`eval.lmeval.permitOnline` and `eval.lmeval.permitCodeExecution`). The manager disables informer caching for ConfigMaps, Secrets, Pods, and Services to prevent OOM from cluster-wide cache flooding in large environments, using direct API server reads instead. The FIPS-compliant build pipeline uses `CGO_ENABLED=1` with `GOEXPERIMENT=strictfipsruntime` on a UBI9 PQC (Post-Quantum Cryptography) base image, and the recent migration to PQC base images (commit a10f5162) aligns with post-quantum cryptography readiness. OTLP trace and metric export supports both gRPC (default) and HTTP protocols for flexible OpenTelemetry integration. ## Data Flows

- **Operator startup and configuration:** On startup, the manager reads the OpenShift APIServer TLS profile with a 10-second bounded timeout, configures the controller-runtime metrics server with optional Kubernetes token-delegated authentication, and registers all reconciler controllers. The operator reads the `trustyai-dsc-config` ConfigMap from the OpenDataHub operator to configure evaluation security policies. [source: cmd/main.go:146-161, pkg/tls/tls.go:96-119, controllers/dsc/config.go:37-67]
- **TrustyAI service lifecycle:** When a TrustyAIService CR is created, the TrustyAIServiceReconciler creates a Deployment with a TrustyAI container and kube-rbac-proxy sidecar, a TLS-secured ClusterIP Service (443→8443), an OpenShift Route or Istio VirtualService for external access, and per-namespace RBAC bindings (proxy-role, auth-reviewer-role). TLS certificates are provisioned as Kubernetes secrets. [source: controllers/tas/trustyaiservice_controller.go:299-300, controllers/tas/templates/service/service-tls.tmpl.yaml:1, controllers/tas/templates/service/route.tmpl.yaml:1]
- **Evaluation and guardrails flow:** EvalHub reconciliation manages evaluation jobs across tenant namespaces, creating Deployments, Services, Routes, and ServiceMonitors per evaluation instance. LMEvalJob resources spawn evaluation pods with PVC storage, integrated with Kueue for workload scheduling. The GuardrailsOrchestrator watches KServe InferenceService resources to coordinate guardrails with model serving endpoints. [source: controllers/evalhub/evalhub_controller.go:370-378, controllers/lmes/lmevaljob_controller.go:341-347, controllers/gorch/guardrailsorchestrator_controller.go:449]
- **Observability:** The operator exports traces and metrics to an OpenTelemetry Collector via OTLP, supporting both gRPC (default) and HTTP protocols based on runtime configuration. Prometheus metrics are exposed via a conditionally authenticated metrics server, and per-evaluation ServiceMonitor resources enable Prometheus scraping of managed workloads. [source: pkg/tracing/tracing.go:365-389, cmd/main.go:154-161, controllers/evalhub/evalhub_controller.go:378]
