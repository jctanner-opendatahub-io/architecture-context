## Purpose

**Short**: kube-rbac-proxy is a TLS-terminating reverse proxy sidecar that enforces Kubernetes RBAC authentication and authorization in front of upstream HTTP services within the RHOAI platform. [source: cmd/kube-rbac-proxy/app/kube-rbac-proxy.go:229-337, Dockerfile.konflux:25]

**Detailed**: kube-rbac-proxy runs as a sidecar container alongside application workloads, intercepting inbound HTTPS requests on port 8443 and enforcing authentication and authorization before forwarding to the upstream service on localhost. Authentication is pluggable: the proxy supports either OIDC token validation or delegated Kubernetes TokenReview via the kube-apiserver, selected at startup based on configuration. Authorization uses a union chain of a hardcoded metrics authorizer, a static policy authorizer, and a SubjectAccessReview (SAR) authorizer that delegates to the Kubernetes API. Requests matching configured ignore-paths bypass authentication and authorization entirely, while allow-paths restrict which URL paths the proxy will serve. The proxy supports configurable TLS with certificate hot-reloading, configurable minimum TLS version and cipher suites, and optional HTTP/2 or H2C upstream connections. It is built with `GOEXPERIMENT=strictfipsruntime` and `CGO_ENABLED=1` for FIPS-compliant cryptography on RHOAI. [source: cmd/kube-rbac-proxy/app/kube-rbac-proxy.go:229-298, 300-337, 344-401, 507-521, Dockerfile.konflux:8-10, pkg/filters/auth.go:37-117]

## Architectural Analysis

kube-rbac-proxy implements a sidecar proxy pattern where it sits in a pod alongside an application container, terminating TLS and enforcing Kubernetes-native authentication and authorization before forwarding requests to the upstream service. This design externalizes authn/authz from application code, allowing services like Prometheus exporters to expose metrics without implementing their own authentication.

The authentication layer is dual-mode: when an OIDC issuer URL is configured, the proxy validates OIDC tokens directly; otherwise, it delegates token validation to the Kubernetes API via TokenReview. The authorization layer chains three authorizers in a union: a hardcoded metrics authorizer that permits well-known OpenShift monitoring identities, a static policy authorizer for file-based rules, and a SubjectAccessReview authorizer that queries the Kubernetes API to evaluate resource-based access decisions. This chain means a request is authorized if any single authorizer permits it. [source: cmd/kube-rbac-proxy/app/kube-rbac-proxy.go:234-275]

The proxy's TLS configuration supports certificate hot-reloading via a file watcher, configurable minimum TLS version and cipher suite selection through Kubernetes apiserver flag utilities, and client certificate request (though not requirement). When no certificate files are provided, it generates a self-signed certificate. The proxy also supports HTTP/2 on both the listener and upstream sides, with an option to force H2C (HTTP/2 cleartext) for upstream connections. [source: cmd/kube-rbac-proxy/app/kube-rbac-proxy.go:344-401, 285-298]

A separate health check endpoint (`/healthz`) runs on a configurable proxy-endpoints port using the same TLS configuration but without the authentication/authorization handler chain, ensuring liveness probes are not blocked by auth failures. Path-based request routing supports ignore-paths (bypass auth entirely) and allow-paths (restrict servable URLs), providing operational flexibility for mixed-auth environments. [source: cmd/kube-rbac-proxy/app/kube-rbac-proxy.go:420-456, 300-338]

## Data Flows

- **Inbound request flow:** External clients connect to kube-rbac-proxy on port 8443 over TLS. The proxy terminates TLS using either provided certificate files (with hot-reload support) or a self-signed certificate. Requests are routed through the main handler chain: first allow-paths filtering restricts which URLs are served, then non-ignored paths pass through WithAuthentication (OIDC or Kubernetes TokenReview), WithAuthorization (hardcoded metrics + static + SAR union), and WithAuthHeaders before reaching the reverse proxy. Ignored paths bypass auth and go directly to the upstream. [source: cmd/kube-rbac-proxy/app/kube-rbac-proxy.go:282-337, 344-418, pkg/filters/auth.go:37-117]
- **Upstream forwarding:** Authenticated and authorized requests are forwarded by `httputil.ReverseProxy` to the upstream service URL, typically on localhost port 8080 over plain HTTP. The upstream transport supports configurable CA bundles, client certificates, timeouts, and forced H2C mode for HTTP/2 cleartext connections. [source: cmd/kube-rbac-proxy/app/kube-rbac-proxy.go:277-298]
- **Kubernetes API interactions:** The proxy makes outbound calls to the Kubernetes API server for TokenReview (authentication delegation) and SubjectAccessReview (authorization delegation), using either in-cluster ServiceAccount credentials or a provided kubeconfig. These calls happen on every authenticated request unless OIDC mode is active for authentication. [source: cmd/kube-rbac-proxy/app/kube-rbac-proxy.go:201-275]
- **Health check path:** A separate `/healthz` endpoint runs on a dedicated proxy-endpoints port with the same TLS configuration but no authentication middleware, providing an unauthenticated liveness signal for Kubernetes probes. [source: cmd/kube-rbac-proxy/app/kube-rbac-proxy.go:420-456]
