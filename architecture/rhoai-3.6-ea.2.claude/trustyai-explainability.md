## Purpose

**Short**: TrustyAI Explainability is a Quarkus-based Java service that provides AI model fairness monitoring, data drift detection, and explainability capabilities for models served via KServe/ModelMesh on OpenShift AI. [source: explainability-service/src/main/resources/application.properties:103-118, explainability-service/manifests/base/trustyai-deployment.yaml:27-145]

**Detailed**: trustyai-explainability deploys a Quarkus 3.8 native application as a Kubernetes Deployment that consumes inference payloads from KServe/ModelMesh-served models via a `/consumer/kserve/v2` HTTP endpoint, stores them on a PVC or optional MariaDB database, and computes fairness metrics (Statistical Parity Difference, Disparate Impact Ratio) and drift metrics (KS Test, Meanshift, Fourier MMD) on the collected data. The service exposes computed metrics to Prometheus via `/q/metrics` annotations and a scheduled metric computation system. An init container creates a `model-serving-config` ConfigMap that registers the TrustyAI consumer endpoint as a KServe payload processor, establishing the integration loop. The RHOAI distribution profile disables local explainer endpoints (SHAP, LIME, Counterfactual, TSSaliency) and global explainers, retaining only fairness and drift monitoring. TLS is configured at the application level on port 4443 using certificates from `/etc/tls/internal/`, though the base OpenShift Route does not terminate TLS. The service has no application-level authentication; access control is delegated to the platform. [source: explainability-service/manifests/base/trustyai-deployment.yaml:62-81, 83-145, explainability-service/src/main/resources/application.properties:1-7, 102-131, explainability-service/pom.xml:21]

## Architectural Analysis

TrustyAI Explainability follows an event-driven data collection pattern where inference payloads flow from KServe/ModelMesh model servers into TrustyAI's consumer endpoint, are reconciled into structured dataframes, and stored for subsequent metric computation. The init container pattern for registering the consumer endpoint via a `model-serving-config` ConfigMap creates a tight coupling with the KServe payload processing pipeline — the service must be deployed before models can route inference data to it. [source: explainability-service/manifests/base/trustyai-deployment.yaml:62-81, explainability-service/src/main/java/org/kie/trustyai/service/endpoints/consumer/ConsumerEndpoint.java:29-32]

The service supports dual storage backends: a PVC-based flat file store (default) mounted at `/inputs` and an optional Hibernate ORM-backed relational database (MariaDB/MySQL). The storage backend selection is runtime-configurable via the `QUARKUS_HIBERNATE_ORM_ACTIVE` environment variable. This architectural flexibility allows operators to choose between simplicity (PVC) and scalability (database) based on data volume. MinIO is also available as an alternative storage backend. [source: explainability-service/src/main/resources/application.properties:63-71, explainability-service/manifests/base/trustyai-deployment.yaml:141-151, explainability-service/pom.xml:142-144]

The RHOAI distribution profile significantly reduces the API surface compared to ODH, disabling all explainer endpoints (SHAP, LIME, Counterfactual, TSSaliency, global explainers) and retaining only fairness and drift monitoring capabilities. This profile-driven endpoint gating uses Quarkus `@EndpointDisabled` annotations controlled by `application.properties` feature flags, allowing clean separation of distribution-specific functionality without code branches. [source: explainability-service/src/main/resources/application.properties:102-131, explainability-service/src/main/java/org/kie/trustyai/service/endpoints/metrics/fairness/group/GroupStatisticalParityDifferenceEndpoint.java:32-33]

The explainer subsystem (disabled in RHOAI) communicates with KServe inference services using gRPC via `KServeV2GRPCPredictionProvider`, making the service a gRPC client rather than server. This client connection is used for on-demand explanation generation where TrustyAI calls back into the model for predictions needed by explanation algorithms. [source: explainability-service/src/main/java/org/kie/trustyai/service/endpoints/explainers/ExplainerEndpoint.java:6-38]

A notable security characteristic is the absence of application-level authentication. No JAX-RS security annotations (`@RolesAllowed`, `@Authenticated`) or security context injection were found in any endpoint class. The RBAC configuration grants the `trustyai-serviceaccount` cluster-wide ConfigMap management via a ClusterRole, which the init container uses to create the model-serving-config ConfigMap. Access control to the service's HTTP endpoints is delegated entirely to the OpenShift platform (Route, NetworkPolicy, or service mesh). ## Data Flows

- **Inference payload ingestion:** KServe/ModelMesh model servers send inference input and output payloads to `POST /consumer/kserve/v2`. The init container registers this endpoint by creating a `model-serving-config` ConfigMap with a payloadProcessors URL pointing to `trustyai-service.<namespace>/consumer/kserve/v2`. The ConsumerEndpoint receives `InferencePartialPayload` objects, which the `ModelMeshInferencePayloadReconciler` joins into complete input-output pairs and stores in the configured backend. [source: explainability-service/manifests/base/trustyai-deployment.yaml:67-81, explainability-service/src/main/java/org/kie/trustyai/service/endpoints/consumer/ConsumerEndpoint.java:29-59]
- **Metric computation and export:** The `PrometheusScheduler` periodically computes fairness and drift metrics over stored inference data on a configurable schedule (`SERVICE_METRICS_SCHEDULE`). Results are exported as Prometheus metrics at `/q/metrics`, scraped by Prometheus via `prometheus.io/scrape` annotations on the Service and Deployment. Users can also request one-off metric computations via the `/metrics/group/fairness/*` and `/metrics/drift/*` REST endpoints. [source: explainability-service/src/main/resources/application.properties:109-113, explainability-service/manifests/base/trustyai-deployment.yaml:9-11]
- **Service exposure:** The trustyai-service ClusterIP Service routes external traffic on port 80 to container port 8080. An OpenShift Route named `trustyai` exposes the service externally without TLS termination (`tls: null`). The application itself configures TLS on port 4443 with certificates at `/etc/tls/internal/`, but this internal TLS port is not exposed through the base manifests. [source: explainability-service/manifests/base/trustyai-deployment.yaml:17-25, explainability-service/manifests/base/route.yaml:1-18, explainability-service/src/main/resources/application.properties:3-7]
