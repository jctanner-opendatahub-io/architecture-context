## Purpose

**Short**: Praxis AI is a Rust-based AI-native reverse proxy built on Pingora that provides configurable filter pipelines for inference routing, credential injection, guardrails enforcement, and agentic protocol support (A2A, MCP) across LLM provider backends. **Detailed**: Praxis AI is an AI-native proxy server built on the Praxis proxy framework (which itself wraps Cloudflare's Pingora HTTP engine). It functions as a programmable HTTP reverse proxy purpose-built for AI/LLM workloads, exposing configurable listener addresses with composable filter chains. The server registers HTTP and TCP protocol handlers and provides an admin API on a separate port for health checks and diagnostics. The filter system includes AI-specific capabilities: intelligent routing across model providers, credential injection for upstream API authentication (with AWS SigV4 and experimental Azure AD/GCP ADC support), AI guardrails enforcement, prompt enrichment, token counting and usage tracking, and agentic protocol filters for A2A and MCP. An optional `ext_proc` compatibility layer integrates with llm-d's Envoy External Processing Protocol as a gRPC client. The proxy is configuration-driven via YAML files with hot-reload support through filesystem watching. ## Architectural Analysis

Praxis AI follows a layered proxy architecture: a Pingora-based runtime core (`praxis-core`) handles connection management, TLS termination, and protocol multiplexing, while the AI-specific layer (`praxis-ai-filters`) adds domain-specific request processing through a composable filter pipeline system. Each listener binds an address and protocol (HTTP or TCP) to one or more named filter chains, which are resolved at startup and can be hot-reloaded when the configuration file changes.

The filter system is the primary architectural surface. Security-critical filters like `provider_route` and `credential_inject` are distinguished from non-security filters at registration time, enabling the proxy to enforce that security filter failures default to closed behavior unless explicitly overridden. The `peer_identity_trust` filter validates client mTLS certificates against configured peer digests, establishing a trust boundary for multi-proxy mesh deployments. Credential injection supports static secrets (loaded from configuration) and dynamic provider-specific authentication (AWS SigV4, with experimental Azure AD and GCP ADC filters).

The llm-d integration via `ext_proc` is architecturally notable: rather than exposing a gRPC service, the proxy acts as a gRPC client implementing the Envoy External Processing Protocol, sending request/response data to an llm-d backend for model-aware scheduling decisions. This is explicitly documented as a compatibility layer (not general-purpose ext_proc support), with native Praxis filters preferred for extension work.

The proxy enforces a non-root execution policy by default, refusing to start as UID 0 unless explicitly overridden. It uses `rustls` for TLS with `ring` as the default cryptographic provider. The build produces a statically-linked binary on Alpine/musl, with jemalloc as the memory allocator on Unix platforms. ## Data Flows

- **Inference request flow:** Client requests arrive at the configured listener address (default 8080/TCP), pass through the filter chain (authentication, guardrails, prompt enrichment, routing, token counting), are routed to a configured upstream AI provider cluster, and the response flows back through the response-phase filters. When the `ext_proc` filter is active, request/response data is additionally sent to the llm-d gRPC backend for model-aware scheduling decisions. [source: server/src/server.rs:52-113, server/src/lib.rs:63-71, integrations/llmd/ext-proc/src/lib.rs:1-55]
- **Admin/health flow:** Health probes from the container orchestrator hit the admin endpoint (default 9901/TCP) which checks upstream cluster health via the health registry. [source: server/src/server.rs:216-235, server/src/default.yaml:11-12, Containerfile:122-123]
- **Configuration reload flow:** A filesystem watcher monitors the config file and triggers hot-reload of filter pipelines, health checks, and cluster configuration without restarting the process. [source: server/src/server.rs:191-209]
