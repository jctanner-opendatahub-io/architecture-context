## Purpose

**Short**: odh-model-controller is a Kubernetes operator that orchestrates model serving infrastructure on RHOAI, managing InferenceService lifecycle, serving runtime provisioning, Gateway API routing, NVIDIA NIM account integration, and admission webhook validation for KServe resources. [source: cmd/main.go:90, server/server.go:16, config/crd/bases/nim.opendatahub.io_accounts.yaml:2]

**Detailed**: odh-model-controller runs as two Deployments within the RHOAI platform: the primary `odh-model-controller` manager that hosts 10 reconciliation controllers and 8 admission webhooks, and a companion `model-serving-api` server that exposes a REST API for gateway discovery and LLM sample retrieval. The controller manager reconciles KServe InferenceService, LLMInferenceService, InferenceGraph, ServingRuntime, and NIM Account custom resources, creating the necessary supporting resources (Services, Routes, NetworkPolicies, RBAC bindings, ServiceMonitors, and KEDA TriggerAuthentications) for each model deployment. It watches platform-level DataScienceCluster and DSCInitialization CRs to determine which components are enabled and reads the OpenShift APIServer resource to align TLS profiles with the cluster's cryptographic policy. The operator ships 27 ClusterServingRuntime definitions spanning vLLM (CUDA, ROCm, Gaudi, Spyre, CPU), OVMS, and MLServer runtimes. The model-serving-api server provides Bearer-token-authenticated gateway discovery and unauthenticated static sample endpoints, both served over TLS with OpenTelemetry instrumentation. [source: cmd/main.go:90, 202, server/server.go:16-44, config/rbac/role.yaml:3, pkg/tls/tls.go:98-119]

## Architectural Analysis

odh-model-controller follows a dual-deployment architecture. The primary `odh-model-controller` Deployment runs the controller-runtime manager hosting 10 reconciliation controllers and an admission webhook server on port 9443. A separate `model-serving-api` Deployment runs a standalone HTTP server that provides a gateway discovery API and static LLM sample templates.

**Controller coordination pattern.** The InferenceServiceReconciler is the most interconnected controller, owning or watching 15 Kubernetes resource types including Services, Routes, NetworkPolicies, ServiceAccounts, ClusterRoleBindings, ServingRuntimes, PodMonitors, ServiceMonitors, and KEDA TriggerAuthentications. This breadth reflects the controller's responsibility for assembling the full serving stack around each InferenceService. The GatewayReconciler manages Gateway API resources, EnvoyFilters, PodMonitors, and Kuadrant AuthPolicies, and watches LLMInferenceService and LLMInferenceServiceConfig resources to keep gateway routing synchronized with serving workloads. Both controllers share a ConfigMap watch channel for configuration propagation.

**Admission webhooks as a safety gate.** The operator registers 5 mutating and 3 validating webhooks, all with `failurePolicy: Fail`. This design choice prioritizes correctness over availability — a webhook outage will block resource creation rather than allow invalid resources into the cluster. The Pod mutating webhook intercepts all Pod CREATE operations, giving the controller an injection point for model-serving sidecar configuration.

**TLS profile alignment.** The `ProfileWatcher` controller reads the OpenShift `APIServer` resource to extract the cluster-wide TLS security profile, ensuring all operator-managed TLS listeners use cipher suites and protocol versions consistent with the platform's cryptographic policy. On non-OpenShift clusters, it falls back to the Intermediate profile with ALPN support. [source: cmd/main.go:191-205, pkg/tls/tls.go:98-119, server/server.go:16-44]

**Platform awareness.** The controller watches DataScienceCluster and DSCInitialization CRs to detect which platform components are enabled, and conditionally registers the prometheus-operator ServiceMonitor watch only when monitoring is available. This conditional registration avoids watch errors on clusters where the monitoring CRD is not installed. [source: config/rbac/role.yaml:3, internal/controller/serving/inferenceservice_controller.go:214]

**Serving runtime inventory.** The repository ships 27 ClusterServingRuntime manifests covering vLLM variants across 6 accelerator types (CUDA, ROCm, Gaudi, Spyre on ppc64le/s390x/x86, and CPU/CPU-x86), plus OVMS and MLServer runtimes. Each accelerator variant includes a base runtime and two "fast" variants, providing graduated resource profiles. All runtime images use parameterized references resolved at deployment time by the operator or platform installer. [source: config/runtimes/]

## Data Flows

- **InferenceService lifecycle flow:** A user creates or updates an InferenceService CR → the InferenceServiceReconciler reconciles the desired state by creating/updating the supporting resource set (Service, ServiceAccount, Route, NetworkPolicy, ClusterRoleBinding, ServiceMonitor, TriggerAuthentication) → the ServingRuntimeReconciler ensures the matching ServingRuntime template is provisioned → the GatewayReconciler creates HTTPRoute and Gateway resources for traffic routing and optionally applies Kuadrant AuthPolicies. All controller interactions with the Kubernetes API use ServiceAccount tokens over TLS. [source: config/rbac/role.yaml:3, internal/controller/serving/inferenceservice_controller.go:206-216]
- **Model-serving API flow:** External clients authenticate with a Bearer token → the `model-serving-api` server validates the token via the Auth middleware → the `/api/v1/gateways` handler uses the forwarded token to perform a SelfSubjectAccessReview and list Gateways from the Kubernetes API → results are returned as JSON over TLS. The `/api/v1/samples/llm-d` endpoint serves static embedded YAML templates without authentication. [source: server/server.go:16-44, server/middleware/auth.go:24-41]
- **Admission webhook flow:** The Kubernetes API server sends admission requests to the webhook server on port 9443 → mutating webhooks inject defaults into Pods, InferenceServices, InferenceGraphs, and LLMInferenceServices at creation time → validating webhooks enforce schema and policy constraints on NIM Accounts, InferenceGraphs, and InferenceServices. All webhook traffic is TLS-encrypted with certificates provisioned by the OpenShift service-ca operator. [source: config/webhook/manifests.yaml:2-106, config/webhook/service.yaml:1]
- **Observability flow:** The controller-runtime metrics endpoint on port 8443 is protected by TokenReview and SubjectAccessReview authn/authz filters. The model-serving-api metrics endpoint on port 8080 serves Prometheus metrics over TLS without application-level authentication. When configured, an OTLP/gRPC trace exporter sends spans to an OpenTelemetry Collector with TLS enabled by default. [source: cmd/main.go:191-202, server/observability/observability.go:66-82]
