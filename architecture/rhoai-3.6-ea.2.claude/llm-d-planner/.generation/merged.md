## Purpose

**Short**: llm-d-planner is an LLM deployment planning and recommendation service that helps operators size, configure, and deploy large language models on Kubernetes clusters using benchmark data and GPU-aware capacity analysis. [source: Dockerfile:62, 65, src/planner/api/app.py:59-63]

**Detailed**: llm-d-planner provides a FastAPI-based backend service that assists platform operators in planning LLM deployments. The service exposes a REST API on port 8000 for capacity planning, GPU estimation, workload profiling, SLO specification, and deployment configuration generation. It integrates with multiple LLM providers—Ollama (local), OpenAI-compatible endpoints, and Vertex AI (Anthropic Claude)—for natural-language intent extraction and recommendation generation. A co-deployed Ollama instance provides local LLM inference, while the backend queries the Kubernetes API to detect available GPU types on cluster nodes. A Streamlit-based UI on port 8501 provides a browser interface, and both the UI and backend are exposed externally via OpenShift Routes with TLS termination. The service manages a local benchmark database for performance data and supports administrative operations gated by an optional HMAC password. ## Architectural Analysis

llm-d-planner follows a three-tier deployment topology: a Streamlit UI frontend, a FastAPI backend, and a co-deployed Ollama LLM instance, each running as a separate Kubernetes Deployment. The backend is the architectural core, serving a comprehensive REST API (39 endpoints under `/api/v1/`) that covers the full LLM deployment planning lifecycle—from intent extraction through capacity calculation to Kubernetes manifest generation. [source: src/planner/api/app.py:75-85, deploy/kubernetes/backend.yaml:1, deploy/kubernetes/ui.yaml:1, deploy/kubernetes/ollama.yaml:1]

The LLM integration layer uses a provider-agnostic factory pattern supporting Ollama (default, local), OpenAI-compatible endpoints, and Vertex AI (Anthropic Claude), selected at runtime via the `LLM_PROVIDER` environment variable. This design allows deployment flexibility: local Ollama for development or air-gapped environments, and cloud-hosted models for production. The Ollama sidecar Deployment runs on port 11434 and serves as both a development convenience and a self-contained inference option. [source: src/planner/llm/factory.py:15-69, src/planner/llm/vertex_client.py:20-43]

The backend queries the Kubernetes API to detect GPU types on cluster nodes by reading `nvidia.com/gpu.product` labels, cached with a configurable TTL (default 300s) to reduce API load. This GPU detection drives the capacity planning and hardware recommendation workflows. Access to node resources is scoped through a dedicated `planner-gpu-reader` ClusterRole granting only `list` on `nodes`. [source: src/planner/cluster/gpu_detector.py:38-75, deploy/kubernetes/gpu-reader-rbac.yaml:9]

Authentication is notably absent at the application layer—the FastAPI application registers only CORS middleware with a permissive `allow_origins=["*"]` configuration. The sole exception is the database administration API (`/db/upload-benchmarks`, `/db/reset`, `/db/verify-admin`), which implements an optional HMAC password check via the `X-Admin-Password` header when the `DB_ADMIN_PASSWORD` environment variable is set. External access is mediated by two OpenShift Routes with TLS termination, but no platform-level authentication enforcement (such as OAuth proxy or service mesh AuthorizationPolicy) is configured in the shipped manifests. This represents a significant security gap for production deployments. [source: src/planner/api/app.py:67-73, src/planner/api/routes/database.py:23-34, deploy/kubernetes/route.yaml:1, 19]

The service manages multiple sensitive credentials—API keys for OpenAI, Anthropic, HuggingFace, and a model catalog token—via environment variables and a Kubernetes Secret (`planner-secrets`). TLS trust for internal services uses the OpenShift Service CA operator via a ConfigMap annotation for CA bundle injection. [source: deploy/kubernetes/service-ca-configmap.yaml:3, deploy/kubernetes/secrets.yaml:1]

- **Entry and service surface:** External users access the service through two OpenShift Routes with TLS termination: `planner` routes to the Streamlit UI (port 8501) and `planner-backend` routes to the FastAPI backend (port 8000). Internally, 4 Kubernetes Services expose the backend, UI, Ollama, and a source-defined llm-d-planner service. The backend serves 39 HTTP endpoints under `/api/v1/` covering capacity planning, deployment configuration, GPU estimation, intent extraction, and quality scoring. [source: deploy/kubernetes/backend.yaml:1, 150, deploy/kubernetes/ollama.yaml:1, 90, deploy/kubernetes/route.yaml:1, 19, deploy/kubernetes/ui.yaml:1, 56]
- **LLM inference flow:** The backend delegates natural-language processing to an LLM provider selected at runtime via `LLM_PROVIDER`. The default path sends requests to the co-deployed Ollama instance on port 11434 (HTTP, no encryption). Alternative paths route through the OpenAI SDK (HTTPS, API key auth) or the Anthropic Vertex AI SDK (HTTPS, GCP credentials). The provider factory pattern isolates client construction from business logic. [source: src/planner/llm/factory.py:15-69, src/planner/llm/vertex_client.py:38-43]
- **Cluster interaction flow:** The backend queries the Kubernetes API to list cluster nodes and read `nvidia.com/gpu.product` labels for GPU detection, using a TTL-cached result (300s default) to reduce API load. The `planner-gpu-reader` ClusterRole scopes this access to `list` on `nodes` only. [source: src/planner/cluster/gpu_detector.py:38-75, deploy/kubernetes/gpu-reader-rbac.yaml:9]
- **Security context:** 3 authentication rules and 6 secret references describe the enforcement boundary. The general API surface has no authentication middleware. Database admin operations (`/db/upload-benchmarks`, `/db/reset`, `/db/verify-admin`) are optionally gated by an HMAC password check via the `X-Admin-Password` header. Multiple API keys (OpenAI, HuggingFace, Anthropic, model catalog) are supplied via environment variables and a Kubernetes Secret.
