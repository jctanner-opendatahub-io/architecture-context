## Purpose

**Short**: Training Hub is a Python library providing a unified, algorithm-focused interface for language model training techniques including SFT, LoRA, GRPO reinforcement learning, and gradient-free prompt optimization (GEPA). [source: pyproject.toml:8, src/training_hub/__init__.py:1-51]

**Detailed**: Training Hub is a Python package that abstracts multiple training backends behind a consistent Algorithm/Backend pattern. It supports supervised fine-tuning (SFT) via InstructLab Training, optimized SFT (OSFT) via Mini-Trainer, LoRA-based training via Unsloth, reinforcement learning from verifiable rewards (GRPO) via the ART/OpenPipe framework with co-located vLLM inference, distributed GRPO via VeRL, and gradient-free prompt optimization (GEPA) via both a standalone backend and an MLflow-integrated backend. The library also provides a unified callback abstraction (TrainingHubCallback) that works across all backends, inference-time scaling integration via ITS Hub, and memory estimation utilities. Training Hub is consumed as a library dependency — it does not expose HTTP endpoints, Kubernetes services, or its own deployment manifests. [source: pyproject.toml:8, src/training_hub/__init__.py:1-51, src/training_hub/algorithms/__init__.py:1-97, src/training_hub/callbacks.py:1-116]

## Architectural Analysis

Training Hub implements a pluggable Algorithm/Backend architecture where each training technique (SFT, OSFT, LoRA, GRPO, GEPA) is an Algorithm subclass paired with one or more Backend implementations that delegate to different training frameworks. The AlgorithmRegistry provides factory-based construction, allowing users to select algorithms and backends by name. This design isolates the user-facing API from backend-specific concerns such as torchrun subprocess management, vLLM engine lifecycle, and MLflow experiment tracking.

The GRPO backend is architecturally notable for its co-located inference pattern: it uses the ART (OpenPipe) framework to run a vLLM inference engine alongside LoRA training on the same GPU via time-sharing. The shutdown sequence explicitly manages the vLLM AsyncLLM engine and its spawned EngineCore subprocess to prevent zombie processes and GPU memory leaks. Multi-turn agentic rollouts are supported through custom rollout functions and ITS Hub integration, which can generate thousands of concurrent LLM calls per training iteration.

The GEPA algorithm differs fundamentally from weight-training algorithms: it optimizes textual prompts without modifying model weights, using evolutionary search with Pareto-based selection. It offers two backends — a standalone backend using the gepa library directly, and an MLflow-integrated backend that wraps GEPA with MLflow's prompt registry and scorer framework. Both backends route inference through LiteLLM to OpenAI-compatible endpoints, setting OPENAI_API_BASE and OPENAI_API_KEY environment variables at runtime and restoring them afterward.

As a library, Training Hub has no deployment footprint of its own. It is consumed by notebook environments, training jobs, and other RHOAI components. All network activity (MLflow tracking, LLM inference) is outbound client-side; the library neither binds ports nor exposes services.

## Data Flows

- **Training execution:** Users invoke algorithm functions (sft, osft, lora_sft, lora_grpo, gepa) which dispatch to backend implementations. SFT uses InstructLab Training's torchrun-based distributed training. OSFT uses Mini-Trainer. LoRA/GRPO uses ART/OpenPipe with a co-located vLLM engine for inference and Unsloth for parameter-efficient training. [source: src/training_hub/__init__.py:1-11, src/training_hub/algorithms/sft.py:3-8, src/training_hub/algorithms/lora_grpo.py:1-43]
- **GEPA prompt optimization:** The GEPA algorithm sends inference requests to OpenAI-compatible endpoints via LiteLLM, using OPENAI_API_BASE and OPENAI_API_KEY environment variables. The MLflow backend variant additionally reads prompt templates from MLflow's prompt registry and logs optimization results to the MLflow tracking server. [source: src/training_hub/algorithms/gepa.py:62-97, 150-303]
- **Callback lifecycle:** TrainingHubCallback instances receive normalized training state (step, epoch, loss, metrics) across all backends. For torchrun backends (InstructLab, Mini-Trainer), callbacks cross the subprocess boundary via class-source serialization. [source: src/training_hub/callbacks.py:1-116]
- **Security context:** 1 secret reference (OPENAI_API_KEY) is used for outbound LLM inference authentication; no inbound authentication is required as the component exposes no endpoints. [source: src/training_hub/algorithms/gepa.py:65]
