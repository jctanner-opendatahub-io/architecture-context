## Purpose

**Short**: Container image build repository producing JupyterLab notebook and code-server workbench images for RHOAI, with CPU, CUDA, and ROCm accelerator variants built on UBI9-based Dockerfiles. **Detailed**: The notebooks repository builds the container images that serve as interactive data science workbench environments in Red Hat OpenShift AI. It produces two main categories of workbench images: JupyterLab-based notebooks (minimal, datascience, pytorch, tensorflow, trustyai, and LLM compressor variants) and code-server-based workbenches. Each variant is built from Konflux Dockerfiles with CPU, NVIDIA CUDA, and AMD ROCm accelerator targets on UBI9 with Python 3.12. The JupyterLab images launch via `start-notebook.sh` which invokes `jupyter lab` with platform-injected configuration, while code-server images use `run-code-server.sh` to start code-server with nginx as a reverse proxy. Authentication is entirely platform-delegated: the `odh-notebook-controller` injects an OAuth proxy sidecar and environment variables (NB_PREFIX, NOTEBOOK_ARGS) that route traffic through the platform authentication layer. The repository also includes Go-based build utilities (buildinputs, check-payload) used during image construction and CI validation. [source: jupyter/minimal/ubi9-python-3.12/start-notebook.sh:1-51, codeserver/ubi9-python-3.12/run-code-server.sh:1-147, tests/containers/workbenches/culling_api_test.py:32-47, jupyter/minimal/ubi9-python-3.12/Dockerfile.konflux.cpu:1-30]

## Architectural Analysis

The notebooks repository follows an image-factory pattern: it does not deploy a long-running operator or controller, but instead produces a family of container images that the platform launches on demand as user workbench pods. Each workbench image bundles a complete data science environment—JupyterLab or code-server IDE, pre-installed Python libraries (PyTorch, TensorFlow, scikit-learn, MLflow, KFP SDK, CodeFlare SDK), and supporting system packages—into a single OCI image built via Konflux pipelines.

The architecture splits into two workbench families with distinct entry patterns. JupyterLab images share a layered Dockerfile hierarchy (minimal → datascience → framework-specific) and start via `start-notebook.sh`, which assembles `ServerApp` arguments from platform-injected environment variables (NOTEBOOK_PORT, NOTEBOOK_BASE_URL, NOTEBOOK_ARGS) before launching `jupyter lab`. Code-server images run `run-code-server.sh`, which starts nginx and httpd as reverse proxies in front of code-server on port 8787, using the `NB_PREFIX` environment variable to configure path-based routing. [source: jupyter/minimal/ubi9-python-3.12/start-notebook.sh:18-51, codeserver/ubi9-python-3.12/run-code-server.sh:13-147]

Authentication is a critical architectural boundary: the notebook images themselves explicitly disable all built-in authentication (JupyterLab tokens/passwords, code-server auth), relying entirely on the OAuth proxy sidecar that `odh-notebook-controller` injects into each workbench pod. This design means the images are not safe to expose directly without the platform's authentication layer. The nginx configuration in code-server workbenches processes the `NB_PREFIX` path prefix to ensure correct reverse-proxy routing behind the OAuth proxy. [source: codeserver/ubi9-python-3.12/run-code-server.sh:144, tests/containers/workbenches/culling_api_test.py:32-47, codeserver/ubi9-python-3.12/run-nginx.sh:17-37]

The Go components (buildinputs, check-payload, dockerfile) are build-time utilities rather than runtime services. check-payload validates FIPS compliance of container images during CI, built with CGO_ENABLED=0 for portability as a scanning tool rather than as a shipped runtime binary. [source: scripts/check-payload/Dockerfile:18-19]

### FIPS Compliance

The notebook images are primarily Python-based container images built on UBI9 base images. FIPS compliance relies on the OpenSSL provided by the UBI base and the explicit installation of `compat-openssl11` for FIPS compliance scanning. The Go components (buildinputs, check-payload) are build-time utilities, not shipped runtime binaries.

## Data Flows

- **User access flow:** Users access workbench instances through the RHOAI dashboard, which triggers `odh-notebook-controller` to create a pod running the selected notebook image. HTTP requests from the user's browser reach the workbench via an OpenShift Route → OAuth proxy sidecar (authentication) → JupyterLab (port 8888) or nginx → code-server (port 8787). The OAuth proxy validates the user's identity before forwarding requests to the workbench process. [source: jupyter/minimal/ubi9-python-3.12/start-notebook.sh:48-51, codeserver/ubi9-python-3.12/run-code-server.sh:139-147, codeserver/ubi9-python-3.12/run-nginx.sh:17-37]
- **Platform configuration injection:** The `odh-notebook-controller` injects environment variables (NB_PREFIX for path routing, NOTEBOOK_ARGS for server configuration) into the workbench pod. The startup scripts consume these variables to configure the notebook server's base URL, port, and root directory. [source: tests/containers/workbenches/culling_api_test.py:32-47, jupyter/minimal/ubi9-python-3.12/start-notebook.sh:18-45]
- **Security context:** Authentication is entirely platform-delegated. Notebook images explicitly disable built-in auth mechanisms. The 7 secret references in the analyzer evidence are CI/automation credentials, not runtime notebook secrets. [source: codeserver/ubi9-python-3.12/run-code-server.sh:144, jupyter/minimal/ubi9-python-3.12/start-notebook.sh:48-51]
