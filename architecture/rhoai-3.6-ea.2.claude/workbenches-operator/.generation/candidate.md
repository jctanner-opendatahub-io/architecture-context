## Purpose

**Short**: workbenches-operator is a Kubernetes operator that manages the lifecycle of Kubeflow Notebook workbenches within Red Hat OpenShift AI, including manifest reconciliation, hardware profile injection via mutating webhooks, and platform-coordinated distribution management. [source: cmd/main.go:67, internal/controller/workbenches_controller.go:117-146, internal/platformconfig/config.go:37-48]

**Detailed**: workbenches-operator is a controller-runtime-based Kubernetes operator that reconciles the cluster-scoped `Workbenches` custom resource (`components.platform.opendatahub.io/v1alpha1`). When a Workbenches CR is created or updated, the operator applies upstream Kubeflow Notebook Controller manifests from an embedded `/opt/manifests` directory using server-side apply, managing Deployments, RBAC resources, CRDs, NetworkPolicies, and webhook configurations as owned operands. [source: cmd/main.go:90-91, internal/controller/workbenches_controller.go:152-179]

The operator runs two mutating admission webhooks on port 9443: `connection-notebook.opendatahub.io` injects data connection secrets into notebook pods at creation, and `hardwareprofile-notebook-injector.opendatahub.io` resolves HardwareProfile CRs to inject compute resource requests and tolerations. Webhook TLS certificates are provisioned via OpenShift service-ca or cert-manager, with a periodic ensurer that reconciles certificate state. [source: cmd/main.go:88-89, 158-163, 199-211]

Platform integration is mediated through the `odh-workbenches-config` ConfigMap, which supplies distribution name, version, and a platform version handshake. The operator watches this ConfigMap and re-reconciles when platform configuration changes, supporting both standalone (ODH) and managed (RHOAI) deployment modes. The Workbenches CR spec receives orchestrator-projected fields for gatewayDomain, mlflowEnabled, and platform identity. [source: internal/platformconfig/config.go:37-48, 67-103, cmd/main.go:168-181]

## Architectural Analysis

The operator follows a single-CR reconciliation pattern typical of OpenShift AI module operators. A single cluster-scoped `Workbenches` CR drives the entire component lifecycle, with the reconciler applying upstream manifests via server-side apply and tracking owned operands through controller-runtime ownership watches covering ConfigMaps, Secrets, Services, ServiceAccounts, Roles, RoleBindings, ClusterRoles, ClusterRoleBindings, MutatingWebhookConfigurations, ValidatingWebhookConfigurations, and Deployments. This design cleanly separates what the operator manages (notebook infrastructure) from what the platform orchestrator controls (which components are enabled and their configuration). [source: internal/controller/workbenches_controller.go:152-179]

The webhook architecture is noteworthy: rather than running webhooks unconditionally, the operator gates webhook server startup on the `--enable-webhooks` flag (defaulting to true) and dynamically detects whether a TLS certificate provider (OpenShift service-ca or cert-manager) is available. If no provider is found, webhooks are disabled entirely rather than failing at startup. This defensive behavior allows the same binary to run on both OpenShift and vanilla Kubernetes clusters with graceful degradation. [source: cmd/main.go:88-89, 132-136, 158-163, 199-211]

TLS configuration is derived from the OpenShift APIServer TLS security profile when available, falling back to a hardcoded Mozilla Intermediate cipher set (ECDHE+AES-GCM and ECDHE+ChaCha20) with a TLS 1.2 minimum on non-OpenShift clusters. A `SecurityProfileWatcher` monitors the cluster TLS profile and triggers pod restart on profile changes via context cancellation, ensuring the operator's TLS posture stays aligned with cluster policy. The recent migration to the `ubi9/ubi-minimal-pqc` base image signals early post-quantum cryptography readiness. [source: internal/tlsconfig/tlsconfig.go:41-48, 107-154, cmd/main.go:119-127, 224-226, Dockerfile.konflux:20]

The platform handshake mechanism through the `odh-workbenches-config` ConfigMap provides a clean contract boundary: the platform orchestrator writes distribution name, version, and platform version metadata, and the operator reads it to align its reconciliation behavior and status reporting. The ConfigMap informer is scoped to the applications namespace (or both ODH and RHOAI default namespaces when unset), reducing unnecessary cache pressure. [source: internal/platformconfig/config.go:37-48, 67-103, cmd/main.go:165-181]

## Data Flows

- **Reconciliation flow:** The Workbenches CR triggers the `WorkbenchesReconciler`, which reads the `odh-workbenches-config` ConfigMap from the applications namespace for distribution and platform version handshake, then applies upstream manifests from `/opt/manifests` via server-side apply. Owned operands (Deployments, RBAC, Services, webhook configs) are tracked through controller-runtime ownership watches and reconciled on drift. [source: internal/controller/workbenches_controller.go:117-179, internal/platformconfig/config.go:67-103, cmd/main.go:189-197]
- **Webhook admission flow:** The Kubernetes API server sends admission requests to the operator's webhook server (port 9443, TLS via service-ca or cert-manager) for notebook CREATE/UPDATE operations. The `connection-notebook` webhook injects data connection secrets, and the `hardwareprofile-notebook-injector` webhook resolves HardwareProfile CRs to inject resource requests and tolerations. Both webhooks use a Fail failure policy. [source: cmd/main.go:158-163, 199-204]
- **Platform coordination flow:** The platform orchestrator projects `gatewayDomain`, `mlflowEnabled`, and `platform` fields into the Workbenches CR spec, and writes distribution metadata to the `odh-workbenches-config` ConfigMap. The operator watches both the CR (generation-changed predicate) and the ConfigMap (namespace-scoped predicate), triggering reconciliation on platform configuration changes. [source: internal/controller/workbenches_controller.go:153-172, internal/platformconfig/config.go:37-48]
- **Security surface:** Health and readiness probes on port 8081 are unauthenticated by design. The metrics endpoint on port 8443 uses TokenReview and SubjectAccessReview via the controller-runtime authentication/authorization filter. Webhook traffic uses TLS certificates provisioned by OpenShift service-ca or cert-manager, with the TLS cipher suite and minimum version derived from the cluster's APIServer TLS security profile. [source: cmd/main.go:84-85, 138-146, 213-218, internal/tlsconfig/tlsconfig.go:41-48, 107-154]
