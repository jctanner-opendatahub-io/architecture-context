## Purpose

**Short**: odh-cli (packaged as `rhai-cli`) is a Cobra-based kubectl plugin providing operational CLI commands for managing, diagnosing, and migrating RHOAI platform deployments on Kubernetes clusters. [source: cmd/main.go:28, Dockerfile.konflux:62]

**Detailed**: odh-cli is a Go-based kubectl plugin that provides operational tooling for Red Hat OpenShift AI (RHOAI) platform administrators. The CLI exposes subcommands for component status inspection (`status`), diagnostics with failure classification (`diagnose`), log aggregation (`logs`), event monitoring (`events`), platform linting (`lint`), dependency auditing (`deps`), API discovery (`api`), resource retrieval (`get`), and data migration including TrustYAI metrics backup/restore (`migrate`). All cluster interactions use kubeconfig-based authentication via `k8s.io/cli-runtime` ConfigFlags, which expose standard kubectl flags (`--kubeconfig`, `--context`, `--token`, `--server`, etc.) on every subcommand. The tool performs SelfSubjectAccessReview pre-flight checks before privileged operations and integrates with OLM for operator lifecycle inspection. It also provides a Model Context Protocol (MCP) server mode (`mcp serve`) that exposes CLI operations as structured tool calls for AI agent integration via stdio or SSE transports. The container image is packaged as `/opt/rhai-cli/bin/rhai-cli` on an `ose-cli-rhel9` runtime base. ## Architectural Analysis

odh-cli follows a standard Cobra CLI architecture with a root command that delegates to 13 subcommand groups, each receiving shared `genericclioptions.ConfigFlags` for kubeconfig resolution. The unified client layer (`pkg/util/client`) wraps five Kubernetes client types — dynamic, discovery, API extensions, OLM, and typed core/authorization — behind `Reader`, `Writer`, and `Client` interfaces, providing a clean separation between read-only operations (used by `lint`, `get`, `status`) and write operations (used by `migrate`).

The tool bridges three platform dependencies: it imports `opendatahub-operator` packages for cluster health assessment and failure classification in diagnostics, and for MCP tool definitions. OLM integration uses the operator-lifecycle-manager client to inspect subscriptions and CSVs for operator lifecycle operations. The TrustYAI migration path is architecturally notable — it discovers TrustYAI Service endpoints via OpenShift Route lookups, then makes direct HTTPS requests with bearer token authentication to back up and restore metrics, using TLS 1.2+ with certificate verification skipped for in-cluster self-signed routes.

The optional MCP server mode represents a secondary architectural role: when invoked with SSE transport, the CLI starts an HTTP server on localhost exposing all CLI operations as JSON-RPC tool calls via Server-Sent Events. This transforms the CLI from a one-shot command tool into a persistent process that AI agents can interact with programmatically. The FIPS-compliant build configuration (`GOEXPERIMENT=strictfipsruntime`, `CGO_ENABLED=1`) ensures the binary uses OpenSSL-backed cryptography from the UBI runtime, though the TrustYAI HTTP client's `InsecureSkipVerify` setting weakens TLS verification at the application level. ## Data Flows

- **Kubernetes API interaction:** All cluster operations flow through a unified client (`pkg/util/client`) that constructs dynamic, discovery, metadata, OLM, and typed Kubernetes clients from a shared REST config derived from kubeconfig. ConfigFlags propagate authentication (bearer token, client certificate, OIDC) to every API call. Pre-flight RBAC checks use SelfSubjectAccessReview before privileged operations such as namespace creation or resource patching. [source: pkg/util/client/client.go:70-117, pkg/util/kube/rbac/check.go:37-71, cmd/main.go:29-41]
- **TrustYAI migration:** The `migrate` subcommand discovers TrustYAI Service endpoints by querying OpenShift Routes (by label or name), then makes direct HTTPS GET/POST requests to the service's metrics API for backup and restore. Bearer tokens from the kubeconfig REST config authenticate these requests. TLS uses `MinVersion: tls.VersionTLS12` with `InsecureSkipVerify: true` for in-cluster self-signed certificates. [source: pkg/migrate/actions/trustyai/metrics/http.go:43-68, pkg/migrate/actions/trustyai/metrics/http.go:71-120]
- **Platform diagnostics:** The `diagnose` command imports `opendatahub-operator/pkg/clusterhealth` for condition assessment and `opendatahub-operator/pkg/failureclassifier` for error categorization, combining cluster state queries with operator-provided classification logic. [source: pkg/diagnose/format.go:8, pkg/diagnose/run.go]
- **MCP server mode:** When started with SSE transport, the CLI binds an HTTP server on localhost, exposing all CLI operations as MCP tool calls via JSON-RPC over Server-Sent Events. The MCP tool definitions are sourced from `opendatahub-operator/pkg/mcptools`. [source: pkg/mcp/server.go:81-108, cmd/mcp/mcp.go:57-66]
