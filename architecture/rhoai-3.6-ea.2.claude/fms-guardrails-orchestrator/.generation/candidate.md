## Purpose

**Short**: A Rust-based orchestration service that coordinates content safety detection and text generation by routing requests through configurable detector, chunker, and generation backends via REST and gRPC clients. [source: Cargo.toml:1-7, config/config.yaml:1-70, src/server/routes.rs:70-111]

**Detailed**: fms-guardrails-orchestrator is a Foundation Model Safety orchestration server built with axum (HTTP) and tonic (gRPC client). It exposes a REST API surface on port 8033 with v1 and v2 endpoint families for classification-with-generation, content detection, chat detection, context-document detection, and streaming variants. A separate health server runs on port 8034. The orchestrator coordinates downstream services: TGIS or caikit-nlp for text generation (gRPC), detector services for content safety evaluation (REST), chunker services for text segmentation (gRPC), and optionally an OpenAI-compatible generation server for chat/completions endpoints. TLS is optional across both the inbound server and all outbound connections, with per-service TLS configuration and optional mTLS. Authentication operates via configurable header passthrough to downstream services, with optional X-Forwarded-Access-Token to Authorization Bearer rewriting. The component is built for multi-architecture deployment (amd64, ppc64le, s390x) with Konflux build support. [source: Cargo.toml:1-7, src/args.rs:32-47, src/server/routes.rs:62-111, config/config.yaml:1-70, build.rs:1-25]

## Architectural Analysis

The orchestrator follows a sidecar-style request-coordination pattern: it does not perform detection or generation itself but routes client requests to a configurable mesh of downstream services and aggregates their responses. The generation backend is pluggable between TGIS (gRPC) and caikit-nlp (gRPC), selected by a `provider` key in the YAML configuration, with an optional OpenAI-compatible HTTP backend that conditionally enables the `/api/v2/chat/completions-detection` and `/api/v2/text/completions-detection` endpoints at startup. [source: config/config.yaml:6-18, src/server/routes.rs:97-108]

The security model is layered. The inbound server optionally terminates TLS with client certificate verification (mTLS), configured through CLI flags and environment variables (`tls_cert_path`, `tls_key_path`, `tls_client_ca_cert_path`). Outbound TLS is configured per downstream service through named TLS profiles in the YAML config, allowing independent cert/key/CA and insecure-skip settings per destination. Authentication is passthrough-only: the orchestrator does not validate tokens but forwards configured request headers to downstream services, optionally rewriting `X-Forwarded-Access-Token` into a standard `Authorization: Bearer` header. The health and info endpoints are served on a separate unauthenticated port. [source: src/args.rs:43-47, src/server/routes.rs:62-67, 452-480, config/config.yaml:53-70]

A key architectural trade-off is the explicit selection of `ring` as the cryptographic provider for all TLS operations (rustls, tokio-rustls, hyper-rustls, tonic, rustls-webpki). `ring` is not a FIPS-validated provider, which means the application-level TLS stack cannot achieve FIPS compliance without changing the crypto backend to `aws-lc-rs` with FIPS features or delegating TLS termination to a FIPS-capable proxy. [source: Cargo.toml:33-34, 62-65, 81-83, 85-89, 68]

The component does not expose any gRPC services despite depending on tonic and prost. The build script explicitly sets `build_server(false)`, generating only gRPC client stubs for downstream communication with chunkers, NLP services, TGIS, and health check probes. [source: build.rs:9]

## Data Flows

- **Inbound request flow:** Clients send HTTP POST requests to the guardrails server on port 8033. Requests arrive through the axum router, which registers v1 endpoints for classification-with-generation and v2 endpoints for detection, chat, context, and streaming variants. When TLS is configured, the Rust TLS acceptor terminates TLS (optionally with mTLS client verification) before the request reaches the router. Configured passthrough headers are filtered from the incoming request and forwarded to downstream services; if enabled, `X-Forwarded-Access-Token` is rewritten to `Authorization: Bearer`. [source: src/server/routes.rs:62-111, 452-480, src/args.rs:43-47]
- **Downstream orchestration:** The orchestrator fans out to downstream services based on the request type and configuration. Text is segmented via gRPC calls to chunker services (port 8085), content safety evaluation is performed via REST calls to detector services (port 8080) with health probes on port 8081, and text generation is handled via gRPC to TGIS (port 8033) or optionally via REST to an OpenAI-compatible server. Each downstream connection supports independent TLS configuration through named TLS profiles. [source: config/config.yaml:6-66, build.rs:13-19]
- **Health and observability:** A separate health server on port 8034 exposes `/health` and `/info` endpoints without authentication or TLS. OpenTelemetry traces and metrics can be exported via gRPC or HTTP to a configurable OTLP endpoint. [source: src/server/routes.rs:62-67, src/args.rs:51-73]
- **Security context:** 4 authentication rules cover the inbound surface: optional TLS/mTLS at the transport layer, header passthrough and token rewriting at the application layer, and unauthenticated health endpoints. 4 secret references (TLS server cert/key, client CA cert, API tokens, downstream TLS certs) are provisioned by the platform operator. [source: src/args.rs:43-47, src/server/routes.rs:452-480, config/config.yaml:53-66]
