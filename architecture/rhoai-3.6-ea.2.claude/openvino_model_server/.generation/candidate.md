## Purpose

**Short**: OpenVINO Model Server (OVMS) is a high-performance AI model inference server that exposes TensorFlow Serving v1, KServe v2, and OpenAI-compatible v3 REST and gRPC APIs for serving models in OpenVINO, ONNX, TensorFlow, PyTorch, PaddlePaddle, and vLLM formats on RHOAI. **Detailed**: OpenVINO Model Server is a C++ inference server (`/ovms/bin/ovms`) that serves as a KServe-compatible serving runtime within the RHOAI platform. It provides three API protocol families: TensorFlow Serving v1 REST API for prediction, classification, and regression; KServe v2 inference protocol for model inference, health checks, and metadata; and OpenAI-compatible v3 endpoints for chat completions and generative workloads. The server exposes configurable gRPC and REST ports, with optional Prometheus metrics. Two serving runtime definitions ship with the repository: a cluster-scoped `kserve-openvino` ClusterServingRuntime and a namespace-scoped `kserve-ovms-2026-2` ServingRuntime optimized for GPU workloads with vLLM support. An optional nginx mTLS sidecar pattern provides TLS termination and client certificate authentication. The upstream project is Intel's OpenVINO Model Server, synced through opendatahub-io midstream to the red-hat-data-services downstream. ## Architectural Analysis

OpenVINO Model Server is architected as a standalone, high-performance C++ inference server that integrates into the RHOAI platform as a KServe-compatible serving runtime. The server binary (`/ovms/bin/ovms`) exposes dual network interfaces — a gRPC server and an HTTP REST server — each bound to configurable addresses and ports. The gRPC layer registers three service implementations: TensorFlow Serving PredictionService, TensorFlow Serving ModelService, and KServe GRPCInferenceService. The REST layer mirrors this with regex-routed handlers for TFS v1 (`/v1/models/...`), KFS v2 (`/v2/...`), and OpenAI-compatible v3 (`/v3/...`) endpoints, plus a Prometheus metrics endpoint. [source: src/grpcservermodule.cpp:140-142, src/http_rest_api_handler.cpp:102-129]

The serving runtime definitions define how OVMS integrates with KServe on the RHOAI platform. The `kserve-openvino` ClusterServingRuntime supports OpenVINO, ONNX, TensorFlow, and HuggingFace formats with gRPC on port 9000 and REST on port 8080. The `kserve-ovms-2026-2` ServingRuntime adds GPU support with PyTorch, PaddlePaddle, and vLLM formats, using gRPC on port 8001 and REST on port 8888. Both define a startup probe against `/v2/health/ready` and support KServe v2 and gRPC-v2 protocol versions. [source: extras/kserve/kserve-openvino.yaml:14-47, extras/openshift_AI/ServingRuntime.yaml:17-40]

Authentication follows two distinct patterns. For generative (v3/OpenAI-compatible) endpoints, the server supports API key authentication loaded from a file via `--api_key_file` or the `API_KEY` environment variable; when not configured, these endpoints are unauthenticated. For production mTLS deployments, an optional nginx sidecar (`extras/nginx-mtls-auth/`) wraps OVMS by binding the server to localhost and fronting it with nginx configured for TLS 1.2 with client certificate verification, providing both encryption and mutual authentication on the original ports while proxying to the internal OVMS ports. [source: src/cli_parser.cpp:42,174-177, extras/nginx-mtls-auth/model_server.conf.template:27-35, extras/nginx-mtls-auth/ovms_wrapper:113-133]

The build produces a C++ binary linked against system libraries on a UBI 9 base image. OpenSSL is installed as a build dependency (`openssl-devel`), and the runtime image inherits the UBI-provided OpenSSL. No explicit FIPS build flags or Go crypto configuration are present since the primary binary is C++, not Go; the Go modules in the repository are client-side demo applications and test utilities, not the production server. ## Data Flows

- **Model inference request flow:** Clients submit inference requests via REST (configurable port) or gRPC (configurable port) to the OVMS server. The REST handler routes requests by URI pattern to the appropriate API handler (TFS v1, KFS v2, or OpenAI-compatible v3). For gRPC, the server dispatches to one of three registered services (TFS PredictionService, TFS ModelService, or KFS GRPCInferenceService). In both cases, the request is deserialized, validated, and forwarded to the model manager which loads and manages model instances from the configured model path (`/mnt/models` in serving runtime deployments). [source: src/http_rest_api_handler.cpp:102-129, src/grpcservermodule.cpp:140-142, extras/kserve/kserve-openvino.yaml:16-19]

- **Model loading flow:** OVMS loads models from the path specified by `--model_path` (single model) or `--config_path` (multi-model configuration). The server polls the file system at the interval specified by `--file_system_poll_wait_seconds` to detect model version changes. Models are loaded into OpenVINO runtime for inference. [source: src/cli_parser.cpp:59-60, extras/kserve/kserve-openvino.yaml:16-19]

- **Optional mTLS sidecar flow:** When deployed with the nginx-mtls-auth sidecar, external clients connect to nginx on the original ports with TLS and client certificates. Nginx terminates TLS, verifies client certificates, and proxies gRPC traffic via `grpc_pass` and REST traffic via `proxy_pass` to OVMS bound on localhost. [source: extras/nginx-mtls-auth/ovms_wrapper:113-133, extras/nginx-mtls-auth/model_server.conf.template:27-51]
