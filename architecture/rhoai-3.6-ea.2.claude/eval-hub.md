## Purpose

**Short**: Evaluation orchestration service for RHOAI that manages evaluation job lifecycle, provider configurations, and evaluation collections through a REST API backed by pluggable SQL storage (PostgreSQL or SQLite). [source: internal/eval_hub/server/server.go:456, internal/eval_hub/storage/sql/sql.go:34-37]

**Detailed**: eval-hub is a multi-binary Go application service that provides the evaluation orchestration backend for Red Hat OpenShift AI. The primary `eval-hub` binary exposes a REST API on port 8080 for managing evaluation jobs, collections, and providers, with conditional multi-tenant identity enforcement via X-User and X-Tenant headers. It delegates evaluation execution to Kubernetes Jobs and communicates with MLflow Tracking Server for experiment tracking, S3-compatible storage for test data, and OpenTelemetry Collector for distributed tracing. The repository produces four runtime binaries: the main API server (`eval-hub`), an init container for S3 data download (`eval-runtime-init`), a sidecar proxy for runtime evaluation orchestration (`eval-runtime-sidecar`), and an MCP server (`evalhub-mcp`). The storage layer supports both PostgreSQL (via pgx driver) and SQLite as configurable backends, with OpenTelemetry instrumentation on database queries. All binaries are built with `GOEXPERIMENT=strictfipsruntime` and dynamic linking for FIPS compliance, and the runtime image uses the UBI9 PQC (Post-Quantum Cryptography) minimal base. [source: Dockerfile.konflux:27-52, internal/eval_hub/server/server.go:456-498, internal/eval_hub/storage/sql/sql.go:13-37, internal/eval_hub/config/mlflow_config.go:7-15]

## Architectural Analysis

eval-hub follows a multi-binary architecture with clear separation of concerns: the main API server handles REST endpoints and job orchestration, the init container provisions test data from S3, and the sidecar proxy manages runtime evaluation lifecycle alongside evaluation pods. A fourth binary provides an MCP (Model Context Protocol) server interface.

The API server uses Go's standard `net/http` mux with a layered middleware stack. Identity enforcement is configuration-gated: when `RequiresIdentityHeaders()` returns true (typical in cluster deployments), the `canContinueRequest` guard requires both X-User and X-Tenant headers on evaluation API endpoints, while health, docs, and OpenAPI routes bypass this check. In local/development mode, CORS middleware is also enabled. HTTP metrics middleware wraps all routes when OpenTelemetry metrics are configured. [source: internal/eval_hub/server/server.go:441-498]

The storage layer abstracts over two SQL backends—PostgreSQL (pgx) and SQLite (modernc.org/sqlite)—selected by driver configuration at startup. Both backends share a common `sqlStorage` implementation with backend-specific SQL statement factories, and database queries are instrumented with OpenTelemetry spans via `otelsql`. The PostgreSQL path supports serialization failure retry logic for concurrent transaction conflicts. [source: internal/eval_hub/storage/sql/sql.go:33-78]

Kubernetes integration is centralized in `KubernetesHelper`, which uses both the typed clientset (for ConfigMaps, Secrets, Jobs, and Events) and the dynamic client (for HardwareProfile custom resources at `infrastructure.opendatahub.io/v1`). The helper initializes with in-cluster config and falls back to kubeconfig, and includes an event recorder sourced as `evalhub-server`. [source: internal/eval_hub/runtimes/k8s/k8s_helper.go:41-81, 104-162]

The TLS configuration enforces a minimum of TLS 1.2 and maximum of TLS 1.3 on the API server. When the runtime detects FIPS mode (via `/proc/sys/crypto/fips_enabled`), it rejects any configuration that sets `InsecureSkipVerify`, providing a defense-in-depth guard against accidental certificate verification bypass in FIPS environments. All four binaries are compiled with `GOEXPERIMENT=strictfipsruntime` and `CGO_ENABLED=1` to ensure FIPS-validated cryptography through OpenSSL. [source: internal/eval_hub/server/server.go:532-540, internal/platform/platform.go:18-26, Dockerfile.konflux:27-52]

## Data Flows

- **Inbound requests:** Clients reach the eval-hub API server on port 8080 via HTTP or HTTPS (TLS 1.2–1.3 when enabled). The API serves evaluation job CRUD, collection management, and provider configuration under `/api/v1/`. A dedicated metrics server exposes `/metrics` for Prometheus scraping on a separate port in cluster mode; in local mode, `/metrics` is co-located on the API server. The evalhub-mcp binary serves an MCP endpoint on `/` with a `/health` probe. No Kubernetes Service or Ingress resources are defined in this repository; the deploying operator provisions them. [source: internal/eval_hub/server/server.go:456-498, 507-558, internal/eval_hub/server/metrics_server.go:23-28, internal/evalhub_mcp/server/server.go:222-227]
- **Evaluation job orchestration:** When an evaluation job is submitted, eval-hub creates Kubernetes Jobs (batch/v1) via KubernetesHelper, provisions ConfigMaps with job configuration, and reads HardwareProfile CRs from the `infrastructure.opendatahub.io/v1` API group to determine resource requirements. The eval-runtime-init container downloads test data from S3-compatible storage, and the eval-runtime-sidecar proxy manages the evaluation lifecycle alongside the evaluation pod. [source: internal/eval_hub/runtimes/k8s/k8s_helper.go:104-162, cmd/eval_runtime_init/main.go:114, internal/eval_hub/config/sidecar_config.go:35-47]
- **Downstream integrations:** The service connects to MLflow Tracking Server via HTTP with optional TLS and token authentication for experiment tracking. It exports traces, metrics, and logs to an OpenTelemetry Collector via OTLP/gRPC. The storage backend connects to either PostgreSQL or SQLite depending on runtime configuration. [source: internal/eval_hub/config/mlflow_config.go:7-15, internal/otel/otel_sdk.go:174, internal/eval_hub/storage/sql/sql.go:13-37]
- **Security context:** 7 authentication rules govern API access: evaluation endpoints require X-User and X-Tenant headers when identity enforcement is enabled, while health, docs, and OpenAPI endpoints are unauthenticated. Kubernetes API access uses in-cluster service account credentials or kubeconfig-based authentication. [source: internal/eval_hub/server/server.go:441-454, internal/eval_hub/runtimes/k8s/k8s_helper.go:41-55]
