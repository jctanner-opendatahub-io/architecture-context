## Purpose

**Short**: NeMo-Guardrails is a FastAPI-based guardrails server that applies programmable safety rails (input/output filters, content checks, jailbreak detection, and fact-checking) to LLM-based conversational systems, deployed as a containerized Python service on RHOAI. [source: pyproject.toml:2, nemoguardrails/server/api.py:29, Dockerfile.konflux:84]

**Detailed**: NeMo-Guardrails provides a runtime guardrails layer between clients and LLM inference endpoints. The server exposes an OpenAI-compatible chat completions API (`/v1/chat/completions`, `/v1/checks`, `/v1/guardrail/checks`) that intercepts requests, evaluates them against configured safety rails defined in Colang, and either passes through, modifies, or blocks content before forwarding to downstream LLM providers. The component is upstream NVIDIA NeMo-Guardrails with Red Hat downstream adaptations for Konflux builds and AIPCC base images. It ships auxiliary microservice Dockerfiles for AlignScore fact-checking (port 5000) and jailbreak detection (port 1337). The Konflux production image bundles pre-cached model artifacts (MiniLM, Snowflake Arctic, spaCy, NLTK) from Red Hat modelcar images and runs via uvicorn with optional OpenTelemetry auto-instrumentation. The server has no built-in authentication; access control is platform-delegated. [source: nemoguardrails/server/api.py:29, 91-106, 278-315, scripts/entrypoint.sh:33-47, Dockerfile.konflux:1-11, 41-48, 83-84]

## Architectural Analysis

NeMo-Guardrails follows a plugin-oriented guardrails architecture where safety behaviors are defined declaratively in Colang configuration files and executed by the `LLMRails` engine at request time. The FastAPI server (`GuardrailsApp`) supports both single-config and multi-config deployment modes, routing requests to the appropriate rails configuration based on `config_id`. The server wraps uvicorn and can optionally be launched with OpenTelemetry auto-instrumentation when `OTEL_EXPORTER_OTLP_ENDPOINT` is set. [source: nemoguardrails/server/api.py:91-106, 154-177, scripts/entrypoint.sh:39-47]

The component exposes three primary API surfaces: the upstream OpenAI-compatible `/v1/chat/completions` endpoint, a standalone `/v1/checks` endpoint for Colang 1.0 rail evaluation, and a downstream-added `/v1/guardrail/checks` endpoint that provides role-based message routing to input, output, or tool rails. Health checking is available at `/healthz` and `/v1/health`. The server delegates LLM inference to external providers (OpenAI, Azure OpenAI, and others) configured at runtime through YAML-based configuration, making it provider-agnostic. [source: nemoguardrails/server/api.py:278-315, 772-818, nemoguardrails/server/checks.py:479-491]

A significant architectural characteristic is the absence of built-in authentication. The server's FastAPI application includes only exception-handling and optional CORS middleware; no request authentication, API key validation, or token verification is enforced at the application level. In RHOAI deployments, authentication must be provided by the platform's service mesh, gateway, or network policy layer. The Dockerfile.konflux build uses the AIPCC CPU base image and pre-caches embedding models from Red Hat modelcar images, enabling offline inference for guardrails evaluation without runtime model downloads. [source: nemoguardrails/server/api.py:225-261, Dockerfile.konflux:1, 36-48]

### FIPS Compliance

NeMo-Guardrails is a Python-only application with no Go binaries; check-payload build-time FIPS validation (dynamic linking, CGO) does not apply. The application depends on `cryptography==46.0.7` which delegates TLS operations to OpenSSL provided by the UBI-based AIPCC base image (`quay.io/aipcc/base-images/cpu:3.5.0`). The Dockerfile.konflux sets `SSL_CERT_FILE` and `REQUESTS_CA_BUNDLE` to the system certificate store, ensuring outbound HTTPS connections use the platform's CA trust chain. No explicit FIPS mode configuration (`OPENSSL_FIPS=1`, cipher suite restrictions, or FIPS provider selection) is present in the application code or container configuration. FIPS compliance is inherited from the base image and host OpenSSL configuration; the application itself does not opt in or opt out of FIPS mode. ## Data Flows

- **Client request ingress:** Clients send OpenAI-compatible chat completion or guardrail check requests to port 8000 (exposed by Dockerfile.konflux). The FastAPI server receives requests without authentication and routes them to the appropriate rails configuration based on `config_id` or the default configuration. [source: Dockerfile.konflux:83, nemoguardrails/server/api.py:262, scripts/entrypoint.sh:33-36]
- **Guardrails evaluation pipeline:** The `LLMRails` engine evaluates incoming messages against Colang-defined safety rails (input rails for user/system messages, output rails for assistant messages, tool_input rails for tool messages). The `/v1/guardrail/checks` endpoint performs role-based routing to the appropriate rail type without forwarding to an LLM. [source: nemoguardrails/server/checks.py:479-491, nemoguardrails/server/api.py:772-818]
- **LLM provider egress:** For chat completion requests, the server forwards approved messages to configured LLM providers (OpenAI, Azure OpenAI, or other OpenAI-compatible endpoints) via HTTPS using the `openai` and `httpx` Python SDKs. Provider selection and credentials are runtime-configured via YAML and environment variables. [source: nemoguardrails/embeddings/providers/azureopenai.py:49-53, nemoguardrails/server/api.py:29]
- **Security credential flow:** 15 environment variable secrets support optional third-party guardrail provider integrations (ActiveFence, AI Defense, Prompt Security, etc.). These credentials are consumed by guardrail action plugins at runtime and are not required for core server operation. [source: nemoguardrails/library/prompt_security/actions.py:67-68]
