## Purpose

**Short**: HTTP gateway that provides route-specific OpenAI-compatible chat completion endpoints with configurable detector-based content filtering, proxying requests to a TrustyAI Orchestrator backend. [source: src/main.rs:84-109, config/config.yaml:1-18, Dockerfile.konflux:58]

**Detailed**: vllm-orchestrator-gateway is a Rust application service that acts as an HTTP routing layer for OpenAI-compatible chat completions with safety and content detection capabilities. At startup, it reads a YAML configuration file defining routes and detectors, then dynamically creates POST endpoints at `/{route_name}/v1/chat/completions` for each configured route. When a client sends a chat completion request, the gateway enriches the payload with route-specific detector configurations (input and output detectors with parameters) and forwards it to a TrustyAI Orchestrator backend at `/api/v2/chat/completions-detection`. If detectors flag content, the gateway substitutes a configurable fallback message. The gateway supports both streaming (SSE) and non-streaming response modes and optionally uses mTLS for orchestrator communication when TLS certificates are mounted. Authorization headers are forwarded to the orchestrator without gateway-level enforcement. [source: src/main.rs:58-136, src/main.rs:154-199, src/main.rs:351-406, src/config.rs:6-53]

## Architectural Analysis

vllm-orchestrator-gateway follows a reverse-proxy pattern specialized for AI safety guardrails. Rather than implementing detection logic itself, it acts as a thin routing layer that transforms standard OpenAI-compatible chat completion requests into orchestrator-enriched requests by injecting detector configurations from its YAML-driven route table. This design separates policy definition (which detectors to apply, what fallback message to return) from policy enforcement (handled by the downstream TrustyAI Orchestrator and its detector services).

The gateway's route configuration is loaded once at startup and drives dynamic endpoint creation via axum's `Router`. Each route produces a POST handler at `/{name}/v1/chat/completions`, meaning the set of exposed endpoints is determined entirely by the config file rather than compiled into the binary. The default listening port is 8090 (overridable via `HTTP_PORT`). Both streaming (SSE) and non-streaming paths proxy to the same orchestrator endpoint (`/api/v2/chat/completions-detection`), differing only in response handling — streaming responses are parsed as SSE chunks while non-streaming responses are deserialized as complete JSON.

For orchestrator communication, the gateway builds an `reqwest::Client` with optional mTLS support. When TLS certificates exist at `/etc/tls/private/tls.crt` and `/etc/tls/private/tls.key` with a CA at `/etc/tls/ca/service-ca.crt`, the client uses HTTPS with mutual TLS. Certificate loading uses the `openssl` crate to construct a PKCS#12 identity, converted to a `native-tls` identity for `reqwest`. The gateway does not terminate TLS for inbound requests — it listens on plain HTTP. Authentication is passthrough: `Authorization` and `X-Forwarded-*` headers from clients are forwarded to the orchestrator, but the gateway itself performs no token validation or access control. ### FIPS Compliance

The gateway uses the `openssl` (0.10.73) and `native-tls` (0.2.12) crates for TLS, which delegate to the system OpenSSL library rather than using pure-Rust crypto (e.g., rustls). The Konflux Dockerfile installs `openssl-devel` at build time and `openssl-libs` at runtime, and the release image is based on `ubi9/ubi-minimal-pqc` (post-quantum cryptography variant). The `reqwest` dependency is configured with `default-features = false` and the `native-tls` feature, ensuring it uses system OpenSSL rather than a bundled TLS stack. However, no explicit FIPS mode configuration is present in the application code — the gateway does not call `openssl::fips::enable()` or set `OPENSSL_FIPS` environment variables. Whether the runtime OpenSSL library operates in FIPS-validated mode depends on the container base image and platform configuration, not on the application. The non-Konflux Dockerfile uses `compat-openssl11` instead of `openssl-libs`, which may have different FIPS posture. FIPS validation status: not verified.
