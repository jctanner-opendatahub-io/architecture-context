The service exposes a single POST endpoint (`/api/v1/text/contents`) that accepts text content and detector parameters, applies built-in PII detectors (email addresses, social security numbers, credit cards) and arbitrary custom regex patterns, and returns detection results with position, type, and score metadata. ## Architectural Analysis

guardrails-regex-detector follows a minimal single-binary, single-endpoint architecture. The entire service is a Tokio-based async Rust application that binds a plain TCP listener on a configurable port (default 8080, via `HTTP_PORT` environment variable) and serves two Axum routes: a health probe and the detection endpoint. [source: src/main.rs:21-45]

The detection handler implements a dispatch pattern: incoming requests carry a list of regex identifiers in `detector_params.regex`, and the handler resolves each against a HashMap of built-in detectors (email, SSN, credit card) before falling back to treating unrecognized entries as raw regex patterns. All detection runs purely in-process with no external I/O, making the service fully stateless and side-effect-free. [source: src/detectors.rs:96-137]

The service has no application-level authentication, no TLS termination, and no outbound network calls. It is designed to be called by an upstream guardrails orchestrator, with authentication and encryption delegated entirely to the platform service mesh or gateway layer. The `compat-openssl11` package installed in the container image provides shared library compatibility for the UBI9 runtime environment but is not used by the application for cryptographic operations — the Rust binary has no OpenSSL or TLS crate dependencies. [source: src/main.rs:31-38, Cargo.toml:6-15, Dockerfile:42]

The component carries no gRPC surface, no CRDs, no RBAC requirements, and no persistent storage. Its operational footprint is intentionally narrow, consistent with a sidecar or backend detector pattern where the guardrails orchestration layer manages routing, authentication, and policy enforcement. ## Data Flows

- **Inbound detection request:** An upstream guardrails orchestrator sends a POST request to `/api/v1/text/contents` containing a JSON body with `contents` (text strings to scan) and `detector_params.regex` (list of detector names or raw regex patterns). The service processes the request entirely in-memory, applying each regex to each content string, and returns a JSON array of detection results with start/end positions, matched text, detection type, and score. No data is persisted or forwarded. [source: src/main.rs:33, src/detectors.rs:20-30, 96-137]
- **Health probe:** A GET request to `/health` returns a static `"healthy"` string. No authentication, no state inspection. [source: src/main.rs:32]
- **No egress:** The service makes no outbound network calls. All detection logic runs locally using the `regex` crate. [source: src/detectors.rs:74-94, Cargo.toml:8]
