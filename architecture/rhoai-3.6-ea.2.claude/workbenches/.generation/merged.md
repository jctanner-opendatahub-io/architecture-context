## Purpose

**Short**: Kubernetes controller and REST backend for managing interactive development workspaces (Jupyter, VS Code, RStudio) as Workspace and WorkspaceKind custom resources on RHOAI. [source: workspaces/controller/api/v1beta1/workspace_types.go:385, workspaces/controller/api/v1beta1/workspacekind_types.go:917, workspaces/backend/api/app.go:84-166]

**Detailed**: The workbenches component provides a three-tier architecture for managing interactive development environments on Red Hat OpenShift AI. A Go controller-runtime operator reconciles Workspace and WorkspaceKind custom resources into StatefulSets, Services, ServiceAccounts, RoleBindings, and networking resources (HTTPRoute or VirtualService depending on the ingress mode). A Go REST backend exposes an authenticated HTTP API on port 4000 that serves workspace CRUD operations, PVC management, secret management, and metrics, enforcing per-request Kubernetes SubjectAccessReview authorization against the caller's identity extracted from upstream proxy headers. A React/nginx frontend serves the UI on port 8080. The controller manages the full lifecycle of workspace pods including culling, pausing, and image resolution through WorkspaceKind definitions. [source: workspaces/backend/cmd/main.go:170-208, workspaces/backend/api/app.go:84-166, workspaces/controller/internal/controller/workspace_controller.go:174-501, workspaces/backend/internal/auth/authentication.go:31-81]

## Architectural Analysis

The workbenches component follows a controller-runtime operator pattern with a companion REST API backend, splitting concerns between Kubernetes resource reconciliation and user-facing HTTP interactions.

**Controller design.** Two reconcilers run in a single controller-runtime manager binary (`/manager`): WorkspaceReconciler owns StatefulSets, Services, ServiceAccounts, and RoleBindings for each Workspace CR, while WorkspaceKindReconciler manages the cluster-scoped WorkspaceKind templates that define available workspace images and resource options. The controller watches Pods to track workspace readiness and supports both Gateway API HTTPRoutes and Istio VirtualServices for workspace ingress routing, selectable per deployment mode. Validating admission webhooks enforce create/update/delete constraints on both CRDs, and a conversion webhook handles CRD version migration. [source: workspaces/controller/internal/controller/workspace_controller.go:174-1349, workspaces/controller/internal/webhook/workspace_webhook.go:44, workspaces/controller/internal/webhook/workspacekind_webhook.go:65]

**Backend authentication model.** The REST backend delegates authentication to an upstream proxy (e.g., Istio/OAuth2 Proxy) that sets user identity headers. It extracts the user ID and groups from configurable request headers using Kubernetes `headerrequest` authenticator, then authorizes every API call via Kubernetes SubjectAccessReview against the caller's identity. This ensures that workspace operations respect the platform RBAC model without the backend managing credentials directly. TLS is optional and configured via cert/key flags, using TLS 1.3 minimum when enabled. [source: workspaces/backend/internal/auth/authentication.go:31-81, workspaces/backend/internal/auth/authorization.go:41-74, workspaces/backend/internal/server/server.go:100-107]

**FIPS posture.** The controller Dockerfile.konflux builds with `CGO_ENABLED=1`, `GOEXPERIMENT=strictfipsruntime`, and `-tags strictfipsruntime` on a UBI9 PQC (Post-Quantum Cryptography) base image, meeting check-payload requirements for dynamic linking and OpenSSL presence. The backend has no Konflux Dockerfile in this checkout; its upstream Dockerfile uses `CGO_ENABLED=0` with a distroless base, which would not pass FIPS validation. [source: workspaces/controller/Dockerfile.konflux:27-30, workspaces/backend/Dockerfile:25-28]

**Networking.** Three ClusterIP services expose the component: the webhook service on port 443 for admission traffic, the backend on port 4000 for the REST API, and the frontend on port 8080 for the UI. A prometheus metrics service exposes controller metrics on port 8080. The controller reconciles HTTPRoute or VirtualService resources to route external traffic to workspace pods through a configured gateway. [source: workspaces/controller/manifests/kustomize/base/webhook/service.yaml:1-13, workspaces/backend/manifests/kustomize/base/service.yaml:1-10, workspaces/frontend/manifests/kustomize/base/service.yaml:1-9]

## Data Flows

- **User request flow:** External users reach the frontend (nginx on port 8080) through the platform ingress gateway. The frontend SPA makes API calls to the backend (port 4000), which authenticates the caller via request headers set by an upstream proxy, authorizes each operation via Kubernetes SubjectAccessReview, and then performs the requested Kubernetes API operations (workspace CRUD, PVC management, secret management). [source: workspaces/backend/api/app.go:84-166, workspaces/backend/internal/auth/authentication.go:31-81, workspaces/backend/internal/auth/authorization.go:41-74]
- **Controller reconciliation:** The controller watches Workspace and WorkspaceKind CRs and reconciles them into StatefulSets, Services, ServiceAccounts, RoleBindings, and ingress resources (HTTPRoute or VirtualService). It also watches Pods to track workspace readiness, and manages ClusterRoleBindings for workspace access control. [source: workspaces/controller/internal/controller/workspace_controller.go:174-1349, workspaces/controller/internal/controller/workspacekind_controller.go:285-286]
- **Admission flow:** Webhook requests arrive at the webhook service (port 443), where validating webhooks enforce Workspace and WorkspaceKind constraints, and a conversion webhook handles CRD version migration for WorkspaceKind resources. [source: workspaces/controller/manifests/kustomize/base/webhook/service.yaml:1-13, workspaces/controller/internal/webhook/workspace_webhook.go:44, workspaces/controller/internal/webhook/workspacekind_webhook.go:65]
- **Security context:** The backend enforces 4 authentication rules: health/readiness probes are unauthenticated, admission webhooks use Kubernetes admission authentication, and the backend REST API uses request-header authentication with SubjectAccessReview authorization. The controller uses TLS for webhook serving. [source: workspaces/backend/api/auth.go:33-69, workspaces/backend/internal/server/server.go:100-107]
