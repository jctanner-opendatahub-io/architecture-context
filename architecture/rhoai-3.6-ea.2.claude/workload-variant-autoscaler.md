## Purpose

**Short**: Kubernetes controller that performs intelligent autoscaling for inference model servers by querying Prometheus metrics, evaluating GPU saturation, and adjusting replica counts for Deployments, LeaderWorkerSets, and KEDA ScaledObjects. **Detailed**: workload-variant-autoscaler is a controller-runtime operator that implements saturation-based autoscaling for AI/ML inference workloads on OpenShift. It watches HorizontalPodAutoscalers, InferencePools (from the Gateway API inference extension), ScaledObjects (from KEDA), and ConfigMaps to discover autoscaling targets and their configuration. At runtime, it queries a Prometheus instance for workload metrics, computes saturation signals through a pluggable engine pipeline that includes Kalman filtering and GPU rebalancing, and actuates scaling decisions by patching Deployment or LeaderWorkerSet scale subresources. The controller supports scale-from-zero via dynamic client discovery of workload kinds. Configuration is driven by ConfigMaps that are bootstrapped at startup and reconciled live, enabling runtime tuning of autoscaling parameters without restarts. ## Architectural Analysis

The workload-variant-autoscaler follows a controller-runtime operator pattern with four reconciliation loops — ConfigMap, HPA, InferencePool, and ScaledObject — each watching a distinct Kubernetes resource type. The ConfigMap reconciler bootstraps and live-updates autoscaling configuration, gating the readiness probe until initial sync completes. The HPA, InferencePool, and ScaledObject reconcilers track active autoscaling targets and feed them into a shared datastore that the optimization engine consumes.

The core scaling pipeline queries Prometheus via an HTTP API client with configurable TLS (minimum TLS 1.2, optional CA cert and mutual TLS) and bearer token authentication. Metrics flow through a source registry, are processed by pluggable engines — including a Kalman-filter-based predictor and a GPU rebalancing coordinator that reads ResourceQuota and Node resources — and produce scaling decisions that the DirectActuator applies by patching `autoscaling/v1/Scale` subresources. A scale-from-zero engine uses dynamic client discovery to handle workloads that have been scaled to zero replicas.

The operator's security model uses controller-runtime's built-in authn/authz filter for the `:8443/metrics` endpoint, backed by TokenReview and SubjectAccessReview with self-signed TLS certificates. Health and readiness probes on `:8081` are intentionally unauthenticated. All cluster access uses a single `controller-manager` ServiceAccount bound to a `manager-role` ClusterRole with least-privilege RBAC covering the specific resource types the controller reads and writes. Leader election via Lease objects prevents duplicate scaling in multi-replica deployments.
