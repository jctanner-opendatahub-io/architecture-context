## Purpose

**Short**: Envoy External Processor (ExtProc) gRPC server that executes Praxis AI filter pipelines for request and response mutation within the MaaS ingress gateway. [source: Cargo.toml:1-9, src/bin/praxis_extproc.rs:27-28]

**Detailed**: praxis-extproc is a Rust-based Envoy ExtProc server that implements the `envoy.service.ext_proc.v3.ExternalProcessor` gRPC service. It receives bidirectional streaming gRPC calls from the Envoy sidecar in the MaaS default gateway, runs configurable Praxis filter pipelines (including AI-specific filters from praxis-ai-filters) over request and response headers and bodies, and returns header/body mutations or immediate rejection responses. The server exposes three listeners: a gRPC ExtProc endpoint (port 9004 in deployment), a gRPC health check service (port 50052), and a Prometheus metrics HTTP endpoint (port 9090). It is deployed as the `payload-processing` Deployment in the `openshift-ingress` namespace, positioned in the Envoy filter chain relative to Kuadrant's authorization WasmPlugin via an EnvoyFilter resource with priority 10. [source: src/bin/praxis_extproc.rs:27-50, 93-110, deploy/base/instance/deployment.yaml:1-68, deploy/overlays/odh/envoy-filter.yaml:1-75]

## Architectural Analysis

praxis-extproc implements the Envoy External Processing protocol as a standalone gRPC server built on tonic and tokio. The binary loads a YAML configuration file that defines named filter chains, each containing an ordered list of Praxis filters. At startup, it builds a shared `FilterPipeline` from the `praxis-ai-filters` registry (which includes AI-specific filters such as `model_to_header`) and the core `praxis-filter` framework, then launches three concurrent servers: the primary ExtProc gRPC service, a tonic-health gRPC health reporter, and a hyper-based HTTP/1.1 Prometheus metrics exporter. [source: src/bin/praxis_extproc.rs:72-123, src/config.rs:36-124, src/metrics.rs:60-72]

The ExtProc service processes bidirectional gRPC streams from Envoy. Each stream carries request/response headers and buffered bodies through the filter pipeline, which may mutate headers, rewrite bodies, or issue immediate rejection responses. The server supports optional TLS via the OpenSSL crate (`openssl` + `tokio-openssl`), with three modes: plaintext (default), self-signed ephemeral certificates, or provided certificate/key files with optional mTLS client verification via a CA certificate. TLS uses `SslAcceptor::mozilla_intermediate` with ALPN h2 negotiation. [source: src/server.rs:1-120, src/tls.rs:40-60, 224-338]

The component is deployed into the `openshift-ingress` namespace as a sidecar-adjacent workload to the MaaS default Istio gateway. An EnvoyFilter resource (priority 10) inserts two ext_proc filter instances into the gateway's HTTP filter chain relative to Kuadrant's authorization WasmPlugin: a pre-processing filter (`ipp-pre`) positioned before auth with `failure_mode_allow: true`, and a post-processing filter (`ipp`) positioned after auth with `failure_mode_allow: false`. A DestinationRule configures SIMPLE TLS with explicit SNI for the Envoy-to-ExtProc connection. The deployment reads Kubernetes ConfigMaps, Secrets, and `inference.opendatahub.io` CRDs (ExternalProviders, ExternalModels) via a ClusterRole. [source: deploy/overlays/odh/envoy-filter.yaml:1-75, deploy/overlays/odh/after/destination-rule.yaml:1-13, deploy/overlays/odh/rbac/clusterrole.yaml:1-15]

## Data Flows

- **Envoy ExtProc request flow:** The MaaS default Istio gateway receives inbound HTTP requests and routes them through an EnvoyFilter-configured ext_proc filter chain. The pre-processing filter (`ipp-pre`) sends request headers and buffered bodies to the payload-pre-processing ExtProc instance before Kuadrant auth. After Kuadrant authorization, the post-processing filter (`ipp`) sends request headers, response headers, and buffered request/response bodies to the payload-processing ExtProc instance. Each ExtProc instance runs its configured Praxis filter pipeline and returns header/body mutations or immediate responses via the bidirectional gRPC stream. [source: deploy/overlays/odh/envoy-filter.yaml:19-75, src/server.rs:105-120]
- **Kubernetes API reads:** The payload-processing service account reads ConfigMaps and Secrets from the Kubernetes API server, as well as ExternalProviders and ExternalModels custom resources from the `inference.opendatahub.io` API group, to configure filter behavior and model routing. [source: deploy/overlays/odh/rbac/clusterrole.yaml:6-15]
- **Metrics scraping:** Prometheus scrapes the `/metrics` HTTP endpoint on port 9090 for ExtProc operational metrics (request counts, immediate response counts, and request duration histograms). [source: src/metrics.rs:25-33, deploy/overlays/odh/networking/networkpolicy.yaml:37-48]
