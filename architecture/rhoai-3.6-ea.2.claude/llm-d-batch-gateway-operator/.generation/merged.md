## Purpose

**Short**: Kubernetes operator that reconciles LLMBatchGateway custom resources to deploy and manage batch inference gateway stacks using embedded Helm charts for the batch-gateway and async-processor components. [source: cmd/main.go:104-105, config/crd/bases/batch.llm-d.ai_llmbatchgateways.yaml:2]

**Detailed**: The llm-d-batch-gateway-operator manages the lifecycle of batch inference gateway deployments on OpenShift. When a user creates an LLMBatchGateway CR (batch.llm-d.ai/v1alpha1), the operator's LLMBatchGatewayReconciler renders two embedded Helm charts—batch-gateway and async-processor—to provision the required Deployments, Services, ServiceAccounts, ConfigMaps, HTTPRoutes, cert-manager Certificates, and ReferenceGrants. The operator watches for drift via a configurable sync period and reconciles owned resources back to the desired state. A separate MetricsController dynamically manages the operator's own metrics Service, ServiceMonitor, and PrometheusRule resources for Prometheus-based observability. The operator integrates with the OpenShift TLS profile API to enforce cluster-wide TLS policy on its metrics endpoint and propagate TLS settings into the Helm-rendered workloads, restarting gracefully when the profile changes. [source: cmd/main.go:95-198, internal/tls/profile.go:57-120, internal/monitoring/controller.go:42-49]

## Architectural Analysis

The operator follows a Helm-rendering reconciler pattern: rather than constructing Kubernetes objects inline, it embeds two Helm charts (batch-gateway and async-processor) and renders them with values derived from the LLMBatchGateway CR spec and the cluster's TLS profile. This design isolates chart evolution from operator logic and allows the same charts to be used standalone or by the operator. The charts are either fetched at build time (upstream) or supplied as pre-fetched artifacts in the Konflux hermetic build path. [source: cmd/main.go:104-105, 157-167, Dockerfile.konflux:24-32]

The operator deploys four managed container images (apiserver, processor, gc, and async) resolved from environment variables at startup, giving the downstream build pipeline control over image provenance without code changes. Leader election is supported but disabled by default. [source: config/manager/manager.yaml:29-41, cmd/main.go:108]

TLS handling is a notable architectural feature. At startup, the operator reads the OpenShift APIServer TLS profile (falling back to Intermediate defaults on non-OpenShift clusters) and applies the resolved cipher suites and minimum TLS version to both the metrics server and the Helm-rendered workloads. A SecurityProfileWatcher triggers a graceful shutdown and restart when the cluster TLS profile or adherence policy changes, ensuring the operator does not serve with stale cryptographic settings. [source: internal/tls/profile.go:57-151, cmd/main.go:125-138]

The metrics endpoint on port 8443 is served over HTTPS with authentication and authorization filters (TokenReview and SubjectAccessReview), consistent with the operator's RBAC permissions for `authentication.k8s.io/tokenreviews` and `authorization.k8s.io/subjectaccessreviews`. The MetricsController further provisions an OpenShift serving-cert-annotated Service and a ServiceMonitor for automated Prometheus scraping. [source: cmd/main.go:133-139, internal/monitoring/controller.go:120-148, config/rbac/role.yaml:2]

Gateway API integration is conditional: the controller watches HTTPRoute and ReferenceGrant resources only when the corresponding CRDs are installed, allowing the operator to run on clusters without the Gateway API. Similarly, prometheus-operator CRD watches are gated behind runtime CRD discovery. [source: internal/monitoring/controller.go:108-115]

## Data Flows

- **CR-to-workload reconciliation:** A user or platform operator creates an LLMBatchGateway CR. The LLMBatchGatewayReconciler watches the CR, renders the batch-gateway and async-processor Helm charts with values from the CR spec and the cluster TLS profile, and applies the resulting Deployments, Services, ServiceAccounts, ConfigMaps, HTTPRoutes, Certificates, and ReferenceGrants to the target namespace. Owned resources are watched for drift and re-reconciled on a configurable sync period (default 5 minutes). [source: cmd/main.go:104-110, 157-176, internal/controller/llmbatchgateway_controller.go:146, 545-550]
- **Secret synchronization:** The operator watches Secrets referenced by LLMBatchGateway CRs and synchronizes them into the workload namespace, enabling cross-namespace secret sharing via ReferenceGrants for Gateway API integration. [source: internal/controller/secret_sync.go:62, internal/controller/llmbatchgateway_controller.go:550, 568]
- **Metrics and monitoring:** The MetricsController creates a ClusterIP Service (`llm-d-batch-gateway-operator-metrics`) on port 8443 with an OpenShift serving-cert annotation for automatic TLS certificate provisioning. A ServiceMonitor and PrometheusRule are applied alongside the Service for Prometheus scraping and alerting. The metrics endpoint uses authentication (TokenReview) and authorization (SubjectAccessReview) filters. [source: internal/monitoring/controller.go:120-148, cmd/main.go:133-139]
- **TLS profile propagation:** At startup, the operator fetches the cluster TLS profile from the OpenShift APIServer config and applies it to the metrics server and Helm-rendered workloads. A SecurityProfileWatcher triggers a graceful restart when the profile changes. [source: internal/tls/profile.go:57-151, cmd/main.go:125-138, 155]
