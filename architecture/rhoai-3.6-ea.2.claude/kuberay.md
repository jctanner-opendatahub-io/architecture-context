## Purpose

**Short**: KubeRay is a Kubernetes operator that manages the lifecycle of Ray clusters, jobs, and services on OpenShift, providing CRD-driven orchestration with integrated OAuth/OIDC authentication via kube-rbac-proxy, mTLS between Ray components via cert-manager, and OpenShift TLS profile-aware FIPS-compliant configuration. [source: ray-operator/controllers/ray/authentication_controller.go:47-53, ray-operator/controllers/ray/raycluster_mtls_controller.go:24-39, ray-operator/pkg/tls/tls.go:65-69, ray-operator/Dockerfile.konflux:30]

**Detailed**: KubeRay operates as a controller-runtime-based Kubernetes operator managing four custom resources — RayCluster, RayJob, RayService, and RayCronJob — through dedicated reconcilers. Beyond the primary resource controllers, the operator includes an AuthenticationController that injects a kube-rbac-proxy sidecar (port 8443) into Ray clusters to enforce OpenShift OAuth or OIDC authentication on dashboard access, and a RayClusterMTLSController that provisions cert-manager Certificate and Issuer resources for mutual TLS between Ray head and worker nodes. The operator reads the OpenShift cluster-wide TLS security profile from `apiservers.config.openshift.io/cluster` and configures cipher suites accordingly, falling back to hardened Intermediate defaults on non-OpenShift clusters. The repository also contains an API server (gRPC + HTTP gateway), a history server for Ray dashboard data, and an experimental security proxy, though the primary RHOAI deployment artifact is the ray-operator built with FIPS-compliant settings (`GOEXPERIMENT=strictfipsruntime`, `CGO_ENABLED=1`). [source: ray-operator/controllers/ray/authentication_controller.go:76-84, 147-161, ray-operator/controllers/ray/raycluster_mtls_controller.go:9, 24-39, ray-operator/pkg/tls/tls.go:65-69, 91-110, ray-operator/Dockerfile.konflux:30-32]

## Architectural Analysis

KubeRay's architecture follows a multi-controller pattern built on controller-runtime, with each controller owning a distinct concern. The primary reconcilers (RayClusterReconciler, RayJobReconciler, RayServiceReconciler, RayCronJobReconciler) manage their respective CRDs and the Kubernetes resources they produce — Pods, Services, Secrets, and batch Jobs. Three auxiliary controllers extend the operator's capabilities on OpenShift: the AuthenticationController manages OAuth/OIDC authentication by injecting a kube-rbac-proxy sidecar container into Ray cluster head pods and creating Gateway API HTTPRoute resources for authenticated dashboard access; the NetworkPolicyController generates NetworkPolicy resources per RayCluster for pod-level network isolation; and the RayClusterMTLSController provisions cert-manager Certificate and Issuer resources to establish mutual TLS between Ray head and worker nodes within a cluster. [source: ray-operator/controllers/ray/authentication_controller.go:76-84, 147-161, ray-operator/controllers/ray/raycluster_mtls_controller.go:24-39]

The authentication design is notable for its dual-mode support: on OpenShift clusters, the AuthenticationController detects whether to use Integrated OAuth or standalone OIDC and configures the kube-rbac-proxy sidecar accordingly, with the proxy image configurable via the `RELATED_IMAGE_ODH_KUBE_RBAC_PROXY_IMAGE` environment variable to support disconnected installations. The controller uses a finalizer pattern (`ray.io/authentication-resources`) to ensure cleanup of cross-namespace resources such as HTTPRoutes and ReferenceGrants when a RayCluster is deleted. On OpenShift, the controller enforces `enableIngress: false` to prevent creation of legacy Route/Ingress resources, ensuring all external access routes through the Gateway API. [source: ray-operator/controllers/ray/authentication_controller.go:37-74, 176-202, 244-268]

The operator's TLS configuration integrates with the OpenShift platform TLS profile by reading `apiservers.config.openshift.io/cluster` at startup via the `tls.Resolve` function. The resolved profile is mapped to Go `crypto/tls` cipher suites and minimum TLS version, with a hardened Intermediate fallback (AES-GCM and ChaCha20-Poly1305 cipher suites, TLS 1.2 minimum) when the OpenShift API is unavailable or on non-OpenShift clusters. This ensures the operator's webhook and health endpoints conform to the cluster-wide cryptographic policy. The RHOAI build uses `GOEXPERIMENT=strictfipsruntime` with dynamic linking (`CGO_ENABLED=1`), producing a FIPS-validated binary on a UBI 9 Minimal PQC base image. [source: ray-operator/pkg/tls/tls.go:28-56, 65-110, ray-operator/Dockerfile.konflux:30-32]

The operator exposes a single ClusterIP Service on port 8080 for Prometheus metrics scraping via standard `prometheus.io/*` annotations. Health and readiness probes are served on port 8082 (`/healthz` and `/readyz`) and are unauthenticated by design. Admission webhooks (one mutating for RayCluster, three validating for RayCluster, RayJob, and RayService) enforce resource validation with a `fail` failure policy, ensuring invalid Ray resources are rejected at admission time. [source: ray-operator/config/manager/service.yaml:3-7, ray-operator/config/manager/manager.yaml:1]

## Data Flows

- **CRD reconciliation loop:** Users or platform controllers create RayCluster, RayJob, RayService, or RayCronJob custom resources. The corresponding reconciler watches for changes and creates/updates dependent Kubernetes resources — Pods, Services, ServiceAccounts, Secrets, batch Jobs, and networking resources (Routes, Ingresses, NetworkPolicies). The operator communicates with the Kubernetes API server over TLS using an in-cluster ServiceAccount token bound to the `kuberay-operator` ClusterRole. [source: ray-operator/controllers/ray/authentication_controller.go:97-112, ray-operator/config/manager/service.yaml:1]
- **Authentication injection:** When a RayCluster is created with authentication enabled, the AuthenticationController injects a kube-rbac-proxy sidecar container (port 8443) into the head pod, creates a ServiceAccount with appropriate RoleBindings, and provisions Gateway API HTTPRoute and ReferenceGrant resources to route authenticated traffic to the Ray dashboard. The authentication mode (Integrated OAuth or OIDC) is detected from the cluster environment, and the proxy image is resolved from the `RELATED_IMAGE_ODH_KUBE_RBAC_PROXY_IMAGE` environment variable for disconnected support. [source: ray-operator/controllers/ray/authentication_controller.go:45-74, 147-161, 204-268]
- **mTLS certificate provisioning:** The RayClusterMTLSController creates a self-signed CA Issuer, CA Certificate, and per-node Certificates via cert-manager for mutual TLS between Ray head and worker nodes. Certificates are stored in Kubernetes Secrets (`ray-head-secret`, `ray-worker-secret`) and mounted into Ray pods. [source: ray-operator/controllers/ray/raycluster_mtls_controller.go:24-39]
- **Metrics and observability:** The operator exposes a Prometheus metrics endpoint at `/metrics` on port 8080 via the kuberay-operator ClusterIP Service, annotated with `prometheus.io/scrape: "true"` for automatic discovery. Health probes on port 8082 provide liveness (`/healthz`) and readiness (`/readyz`) signals. [source: ray-operator/config/manager/service.yaml:3-7]
- **Platform TLS integration:** At startup, the operator reads the cluster TLS security profile from `apiservers.config.openshift.io/cluster` and configures its webhook server and internal TLS connections with the platform-mandated cipher suites and minimum TLS version. On non-OpenShift clusters, hardened Intermediate defaults are applied. [source: ray-operator/pkg/tls/tls.go:65-110]
