## Purpose

**Short**: Preflight validation CLI for xKS clusters that verifies GPU availability, RDMA connectivity, network bandwidth, required CRDs, and inference readiness before AI workload deployment. [source: Dockerfile.konflux:19, cmd/agent/main.go:30-39]

**Detailed**: rhaii-cluster-validation is a Go CLI tool (`rhaii-validator`) designed as a kubectl plugin (`kubectl-rhaii_validate`) that performs preflight cluster validation for Red Hat AI Infrastructure (RHAII) workloads. The tool deploys ephemeral Kubernetes Jobs to GPU-equipped nodes to validate hardware readiness across multiple dimensions: GPU driver version, ECC status, and health; RDMA device availability, NIC status, GPU-NIC topology, and connectivity mesh; TCP bandwidth and latency; and CRD/operator prerequisites. The controller runs locally under the invoking administrator's kubeconfig credentials, creating a dedicated `rhaii-validation` namespace with a ServiceAccount bound to the OpenShift privileged SCC so that probe Jobs can access host sysfs for PCI topology and InfiniBand device discovery. Results are collected into a ConfigMap-based report. The tool has no HTTP endpoints, no long-running services, and no internal platform component dependencies — it operates as a standalone validation utility against the Kubernetes API. [source: cmd/agent/main.go:24-39, Dockerfile.konflux:16-22, deploy/rbac.yaml:13-14, pkg/controller/controller.go:114-145]

## Architectural Analysis

rhaii-cluster-validation follows a controller-agent pattern: the CLI controller runs on the operator's workstation using their kubeconfig, while ephemeral Job pods (agents) execute on target GPU nodes inside the cluster. The controller orchestrates a multi-phase validation lifecycle — cleanup of prior runs, namespace/RBAC provisioning, Job deployment, result collection, and reporting — using the Kubernetes batch/v1 and core/v1 APIs exclusively. Each validation dimension (GPU, RDMA node checks, RDMA ping mesh, RDMA bandwidth, TCP network) maps to a dedicated Cobra subcommand and can run independently or combined via the `all` subcommand. [source: cmd/agent/main.go:42-50, pkg/controller/controller.go:148-159]

The tool's security model splits privileges: the controller itself authenticates to the Kubernetes API via the administrator's kubeconfig (standard client-go credential chain) and performs all cluster-mutating operations — creating Namespaces, ServiceAccounts, ClusterRoles, ClusterRoleBindings, Jobs, and ConfigMaps. The workload pods never call the Kubernetes API; they run under a ServiceAccount (`rhaii-validator`) whose ClusterRole has an empty rules set. The SA exists solely as an SCC subject — on OpenShift, it receives the `system:openshift:scc:privileged` binding so that probe Jobs can access host-level device files (`/sys/class/infiniband`, PCI topology). This is an intentional least-privilege design: the elevated SCC grants host device access without granting any Kubernetes API permissions to the workload pods. [source: deploy/rbac.yaml:12-14, deploy/rbac.go:139-158, pkg/controller/controller.go:115-128]

The Konflux build uses `GOEXPERIMENT=strictfipsruntime` with `CGO_ENABLED=1` on a UBI9 base, producing a dynamically linked binary that delegates cryptographic operations to the system OpenSSL. The application does not import `crypto/tls` directly or configure custom cipher suites — all TLS is inherited from the client-go Kubernetes client, which uses the Go runtime's FIPS-validated crypto backend when `strictfipsruntime` is active. [source: Dockerfile.konflux:11, Dockerfile.konflux:14]

## Data Flows

- **Validation lifecycle:** The operator invokes `rhaii-validator` (or `kubectl rhaii-validate`) from their workstation. The controller authenticates to the Kubernetes API via kubeconfig, creates the `rhaii-validation` namespace and RBAC resources, deploys probe Jobs to GPU nodes, waits for completion, collects results from Job logs and ConfigMaps, and produces a validation report. [source: pkg/controller/controller.go:148-159, deploy/rbac.go:30-92]
- **Agent execution:** Probe Jobs run the same `rhaii-validator` binary in agent mode (`run` subcommand) inside the cluster. Agents perform hardware checks (GPU driver, ECC, RDMA devices, bandwidth) using host-level device access via the privileged SCC. Results are written to stdout (captured by the controller via Kubernetes log API) and to ConfigMaps for mesh-topology results. [source: cmd/agent/main.go:52-53, deploy/rbac.go:139-158]
- **Kubernetes resource flow:** The controller creates and manages Namespaces, ServiceAccounts, ClusterRoles, ClusterRoleBindings, Jobs, and ConfigMaps. All resource operations flow through the Kubernetes API (port 6443, TLS 1.2+) using the administrator's kubeconfig credentials. No other external or internal services are contacted. [source: pkg/controller/controller.go:115-128, deploy/rbac.yaml:1-32]
