## Purpose

**Short**: Garak red-teaming evaluation adapter that integrates NVIDIA's Garak security testing framework with the eval-hub evaluation platform, running as a Kubernetes Job to assess LLM safety and vulnerability. [source: pyproject.toml:2-4, src/llama_stack_provider_trustyai_garak/evalhub/garak_adapter.py:1-18]

**Detailed**: llama-stack-provider-trustyai-garak is an eval-hub `FrameworkAdapter` that runs as a Kubernetes Job to execute Garak red-teaming scans against large language models. It supports two execution modes: **simple mode**, which runs Garak as a subprocess inside the K8s Job pod, and **kfp mode**, which delegates scan execution to a Kubeflow Pipeline using S3 (via an OpenShift AI Data Connection secret) for artifact transfer. The adapter reads its `JobSpec` from a mounted ConfigMap, builds and executes Garak CLI commands based on configurable scan profiles (OWASP LLM Top 10, AVID taxonomy, CWE, intents-based risk assessment), parses results from Garak's JSONL reports, persists artifacts to an OCI registry, and reports results back to eval-hub via sidecar callbacks. The component does not expose any HTTP endpoints or Kubernetes Services; it is a batch execution adapter, not a long-running service. [source: pyproject.toml:2-4, 13-23, src/llama_stack_provider_trustyai_garak/evalhub/garak_adapter.py:1-18, 79, 1844-1848, 1868-1881]

## Architectural Analysis

This component follows the eval-hub adapter pattern: it implements the `FrameworkAdapter` interface from `evalhub.adapter` and runs as a short-lived Kubernetes Job rather than a persistent service. The `main()` entry point reads a `JobSpec` from a mounted ConfigMap (default path `/meta/job.json`), instantiates the `GarakAdapter`, executes the benchmark, and reports results back via `DefaultCallbacks` before exiting. This batch-job architecture means the component has no inbound HTTP endpoints, no Kubernetes Services, and no ingress — all communication is outbound. [source: src/llama_stack_provider_trustyai_garak/evalhub/garak_adapter.py:33-44, 79, 1844-1881]

The dual execution mode design is the key architectural decision. In simple mode, Garak runs in-process as a subprocess. In KFP mode, a six-step Kubeflow Pipeline handles validation, taxonomy resolution, synthetic data generation, prompt preparation, the Garak scan itself, and result publishing — with S3 artifact transfer via Data Connection secrets injected into KFP pods through `kubernetes.use_secret_as_env`. This allows the adapter to scale scan execution beyond the Job pod's resources while maintaining a consistent result-reporting interface. [source: src/llama_stack_provider_trustyai_garak/evalhub/kfp_pipeline.py:1-25, 48-54, 57-75]

Authentication for outbound integrations follows a multi-tier resolution chain: direct API key values, named keys from mounted model auth secrets (via `evalhub.adapter.auth.read_model_auth_key`), environment variables, role-convention keys, and a final `"DUMMY"` fallback. This design accommodates varied deployment patterns — from development environments with direct key injection to production configurations using Kubernetes Secrets. The `cryptography` and `pyjwt` dependencies are transitive (from eval-hub-sdk and garak) rather than directly invoked by this adapter. [source: src/llama_stack_provider_trustyai_garak/evalhub/garak_adapter.py:1534-1588, src/llama_stack_provider_trustyai_garak/core/pipeline_steps.py:155-169]

## Data Flows

The adapter operates as a batch Kubernetes Job with purely outbound communication:

1. **Job initialization:** The adapter reads a `JobSpec` from a mounted ConfigMap (`/meta/job.json`) containing the benchmark configuration, model endpoint, and scan profile selection. [source: src/llama_stack_provider_trustyai_garak/evalhub/garak_adapter.py:1844-1870]

2. **Simple mode execution:** Garak runs as a subprocess within the Job pod. The adapter builds CLI commands from the resolved scan profile, executes the scan against the target LLM endpoint (authenticated via API keys from mounted secrets or environment variables), and parses JSONL report output. [source: src/llama_stack_provider_trustyai_garak/evalhub/garak_adapter.py:1-18]

3. **KFP mode execution:** The adapter submits a six-step Kubeflow Pipeline, injecting S3 Data Connection credentials via `kubernetes.use_secret_as_env`. KFP pods execute validation, taxonomy resolution, SDG generation, prompt preparation, the Garak scan, and result publishing. The adapter polls for pipeline completion and downloads results from the shared S3 bucket. [source: src/llama_stack_provider_trustyai_garak/evalhub/kfp_pipeline.py:1-25, 48-54]

4. **Result reporting:** Parsed results are persisted as OCI artifacts and reported back to the eval-hub service via sidecar callbacks (`DefaultCallbacks.report_results`). [source: src/llama_stack_provider_trustyai_garak/evalhub/garak_adapter.py:1874-1881]

5. **Security context:** 4 secret references (API_KEY, KFP_AUTH_TOKEN, OPENAICOMPATIBLE_API_KEY, AWS_SECRET_ACCESS_KEY) provide credentials for outbound integrations. No inbound authentication is required as the adapter exposes no endpoints. [source: src/llama_stack_provider_trustyai_garak/evalhub/garak_adapter.py:1534-1588, src/llama_stack_provider_trustyai_garak/core/pipeline_steps.py:155-169]
