## Purpose

**Short**: MLServer is a Python-based inference server implementing the KServe V2 Inference Protocol, providing REST (FastAPI on port 8080) and gRPC (port 8081) interfaces for multi-framework model serving on RHOAI. [source: mlserver/rest/app.py:60-162, mlserver/grpc/server.py:81-89, mlserver/settings.py:429-435]

**Detailed**: MLServer serves as a general-purpose model serving runtime within the Red Hat OpenShift AI platform. It implements the KServe V2 Inference Protocol over both REST (via FastAPI/uvicorn on port 8080) and gRPC (via grpc.aio on port 8081), supporting inference, streaming inference, model lifecycle management, and health monitoring. The server supports multiple ML frameworks through pluggable runtime backends including Scikit-Learn, XGBoost, LightGBM, ONNX, MLflow, HuggingFace, CatBoost, Spark MLlib, Alibi Detect, and Alibi Explain, each packaged as a separate Python module that registers with the core server.

MLServer is deployed as a container within KServe InferenceService pods on OpenShift, with authentication delegated to the platform's kube-rbac-proxy sidecar. The downstream distribution builds two Konflux container variants — a CPU image (from `quay.io/aipcc/base-images/cpu:3.6.0-ea.1`) and a CUDA GPU image (from `quay.io/aipcc/base-images/cuda-12.9-el9.6:3.6.0-ea.1`) — both based on AIPCC base images. Observability is provided through OpenTelemetry tracing integration and Prometheus metrics export on a dedicated metrics port (8082). [source: mlserver/rest/app.py:60-181, mlserver/grpc/server.py:81-89, mlserver/settings.py:429-451, Dockerfile.konflux:1, Dockerfile.konflux.cuda:1]

## Architectural Analysis

MLServer follows a dual-protocol server architecture implementing the KServe V2 Inference Protocol. The REST layer is built on FastAPI with Starlette, served via uvicorn, while the gRPC layer uses the Python grpc.aio async server with a ThreadPoolExecutor. Both protocols share a common DataPlane handler abstraction that delegates to framework-specific model runtimes. [source: mlserver/rest/app.py:52-56, mlserver/grpc/server.py:75-86]

The runtime plugin system uses Python's import machinery to dynamically load model implementations. In production mode (RHOAI container images), a trusted-runtimes allowlist (`/etc/mlserver/trusted-runtimes.json`) is baked into the container image at build time via an inline Python script in the Dockerfile, restricting which model implementations can be loaded. This security boundary prevents arbitrary code execution through untrusted runtime paths. The CPU image trusts LightGBM, ONNX, Scikit-Learn, and XGBoost runtimes; the CUDA image trusts only the ONNX runtime. [source: Dockerfile.konflux:3, 35-52, Dockerfile.konflux.cuda:3, 38-55, mlserver/settings.py:140-166]

The server exposes three distinct network listeners: HTTP inference on port 8080, gRPC inference on port 8081, and Prometheus metrics on port 8082. The gRPC server binds with `add_insecure_port`, confirming that TLS termination is delegated to the platform rather than handled at the application level. Authentication is not implemented at the application layer — the gRPC interceptors handle only logging (`LoggingInterceptor`) and Prometheus metrics collection (`PromServerInterceptor`), and the REST middleware stack includes only CORS, GZip compression, and Prometheus metrics. All authentication enforcement is platform-delegated to the kube-rbac-proxy sidecar injected by KServe. [source: mlserver/settings.py:429-451, mlserver/grpc/server.py:88-89, mlserver/grpc/interceptors.py:27-43, 46-68, mlserver/rest/app.py:208-237]

The streaming inference endpoints (`infer_stream`, `generate_stream`) and the bidirectional gRPC `ModelStreamInfer` RPC extend the V2 protocol for scenarios requiring incremental response delivery, such as text generation with large language models. Custom model handlers can dynamically register additional REST routes at runtime through the `add_custom_handlers` mechanism on the RESTServer. [source: mlserver/rest/app.py:93-113, mlserver/rest/server.py:38-47]

## Data Flows

- **Inference request path:** Client requests arrive at either the REST interface (port 8080/TCP via FastAPI/uvicorn) or the gRPC interface (port 8081/TCP via grpc.aio). REST requests are routed through the V2 Inference Protocol endpoints defined in the FastAPI application to the shared DataPlane handler, which dispatches to the appropriate framework-specific model runtime. gRPC requests follow the same pattern through the GRPCInferenceService servicer. All versioned endpoint variants (e.g., `/v2/models/{model_name}/versions/{model_version}/infer`) share the same handlers as their non-versioned counterparts. [source: mlserver/rest/app.py:60-162, mlserver/grpc/server.py:81-86]
- **Model lifecycle management:** The V2 Model Repository API (`/v2/repository/index`, `/v2/repository/models/{model_name}/load`, `/v2/repository/models/{model_name}/unload`) and corresponding gRPC ModelRepositoryService RPCs manage model loading, unloading, and discovery. Models are loaded from the directory specified by `MLSERVER_MODELS_DIR` (default `/mnt/models`). [source: mlserver/rest/app.py:164-181, mlserver/grpc/server.py:84-86, Dockerfile.konflux:12]
- **Observability pipeline:** Request metrics are collected via PrometheusMiddleware (REST) and PromServerInterceptor (gRPC), exposed on a dedicated metrics endpoint (`/metrics` on port 8082/TCP). OpenTelemetry tracing is optionally enabled when `tracing_server` is configured, with health check endpoints excluded from trace collection. [source: mlserver/rest/app.py:192-205, 226-236, mlserver/grpc/interceptors.py:46-68, mlserver/settings.py:445-451]
- **Security enforcement:** No application-level authentication or authorization is implemented. All gRPC service endpoints rely on platform-delegated authentication via kube-rbac-proxy sidecar in the KServe pod. REST endpoints follow the same platform-delegated pattern. The application-level gRPC interceptors handle only logging and metrics. [source: mlserver/grpc/interceptors.py:27-43, 46-68, mlserver/rest/app.py:208-237]
