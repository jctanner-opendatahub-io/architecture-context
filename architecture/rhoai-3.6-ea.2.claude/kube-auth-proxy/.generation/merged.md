## Purpose

**Short**: kube-auth-proxy is a FIPS-compliant reverse authentication proxy that gates access to upstream RHOAI services using OAuth2/OIDC, OpenShift OAuth, Kubernetes ServiceAccount token validation, and basic authentication. [source: main.go:17, Dockerfile.konflux:51, providers/openshift.go:46, pkg/authentication/k8s/tokenreview.go:30-33]

**Detailed**: kube-auth-proxy is a fork of oauth2-proxy, customized for Red Hat OpenShift AI, that acts as a reverse proxy providing authentication and authorization in front of upstream application services. It supports multiple authentication mechanisms: OAuth2/OIDC providers (with OpenShift OAuth as a first-class provider), Kubernetes ServiceAccount token validation via the TokenReview API, htpasswd-based basic authentication, and JWT bearer token passthrough. The proxy manages user sessions via cookie-based session stores or Redis-backed distributed sessions, and exposes a standard set of OAuth2 endpoints (`/oauth2/sign_in`, `/oauth2/start`, `/oauth2/callback`, `/oauth2/sign_out`, `/oauth2/auth`, `/oauth2/userinfo`) alongside a health check endpoint. It is built with FIPS-compliant settings (`CGO_ENABLED=1`, `GOEXPERIMENT=strictfipsruntime`) on a UBI9 PQC base image and uses `crypto/tls` with configurable TLS 1.2+/1.3 for both its own listeners and Redis connections. The proxy integrates with the Kubernetes API server for TokenReview-based authentication and can optionally use Redis/Valkey for scalable session storage. [source: main.go:17-88, oauthproxy.go:47-65, 342-380, Dockerfile.konflux:51-54, pkg/http/server.go:142-144, pkg/sessions/redis/redis_store.go:160-178]

## Architectural Analysis

kube-auth-proxy follows a middleware-chain architecture built on `gorilla/mux` and `justinas/alice`. Every incoming request passes through a pre-auth chain (health checks, HTTPS redirect, logging, metrics) before reaching the session-aware chain that enforces authentication. The proxy supports four authentication mechanisms in parallel: (1) OAuth2/OIDC authorization code flow via a configurable provider, with OpenShift OAuth as a first-class option that auto-discovers endpoints from the cluster's `/.well-known/oauth-authorization-server`; (2) Kubernetes ServiceAccount token validation via the TokenReview API, using a singleflight-deduplicated, TTL-cached client (`defaultCacheTTL=10s`, `defaultReviewTimeout=30s`); (3) htpasswd-based basic authentication; and (4) JWT bearer token passthrough with configurable issuer validation. [source: oauthproxy.go:229-234, main.go:60-78, pkg/authentication/k8s/tokenreview.go:36-47, 63-66]

The TLS layer is configurable on both the main application server and a separate metrics server. The application server supports TLS 1.2–1.3 with optional custom cipher suite selection and certificate loading. Redis session storage connections support TLS with optional custom CA and skip-verify modes. The proxy delegates token verification to the Kubernetes API server (for ServiceAccount tokens) and to the configured OIDC/OAuth provider (for user tokens), meaning it does not perform local cryptographic token validation for ServiceAccount tokens. [source: pkg/http/server.go:142-163, pkg/sessions/redis/redis_store.go:182-217, providers/openshift.go:34-35]

A notable design choice is the MLflow-specific auth-denied handler (`authdeny.NewMLflowHandler()`), which returns structured error responses for non-browser API clients, indicating RHOAI-specific integration with the MLflow tracking server. The proxy's Dockerfile.konflux build uses `GOEXPERIMENT=strictfipsruntime` with dynamic linking (`CGO_ENABLED=1`) on a `ubi9/ubi-minimal-pqc` base image, targeting post-quantum cryptography readiness. [source: oauthproxy.go:266, Dockerfile.konflux:51-59]

## Data Flows

- **Client authentication flow:** External clients connect to kube-auth-proxy via OpenShift Route (TLS) or the ClusterIP Service (port 80→4180). Unauthenticated browser requests are redirected to `/oauth2/sign_in` and then to the configured OAuth2/OIDC/OpenShift OAuth provider via `/oauth2/start`. After provider authentication, the callback at `/oauth2/callback` establishes a session cookie. API clients may authenticate via Kubernetes ServiceAccount bearer tokens (validated via TokenReview API), JWT bearer tokens (validated against configured OIDC issuers), or basic auth (validated against htpasswd). [source: oauthproxy.go:342-380, main.go:60-78, pkg/authentication/k8s/tokenreview.go:138-207]
- **Upstream proxying:** Authenticated requests are forwarded to configured upstream services via the `gorilla/mux` router. The session chain injects request headers (`X-Forwarded-User`, `X-Forwarded-Email`, `X-Forwarded-Groups`) and response headers as configured. Configurable skip-auth routes allow certain paths to bypass authentication. [source: oauthproxy.go:363, pkg/apis/options/legacy_options.go:18-22]
- **Session persistence:** Sessions are stored either in encrypted cookies (default) or in a Redis/Valkey backend. Redis connections support TLS with custom CA certificates, username/password authentication, Sentinel, and Cluster topologies. Session state includes user identity, groups, access token, and expiry. [source: oauthproxy.go:147-149, pkg/sessions/redis/redis_store.go:160-178]
- **Kubernetes API interactions:** When K8s token validation is enabled, the proxy creates TokenReview resources against the Kubernetes API server using the pod's ServiceAccount credentials or a configured kubeconfig. Concurrent TokenReview calls for the same token are deduplicated via singleflight, and successful results are cached for a configurable TTL (default 10s). [source: pkg/authentication/k8s/tokenreview.go:84-130, 219-249]
