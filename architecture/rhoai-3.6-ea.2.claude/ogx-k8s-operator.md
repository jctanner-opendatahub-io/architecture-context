## Purpose

**Short**: ogx-k8s-operator is a Kubernetes operator that manages the lifecycle of OGX (formerly LlamaStack) inference servers, providing CRD-driven deployment, autoscaling, networking, and admission validation for OGXServer resources on OpenShift and ODH platforms. [source: Dockerfile.konflux:41-43, main.go:213-237, config/crd/bases/ogx.io_ogxservers.yaml:2]

**Detailed**: ogx-k8s-operator is a two-binary operator system that manages OGX inference server deployments on Kubernetes and OpenShift. The primary operator binary (`ogx-k8s-operator`) reconciles `OGXServer` custom resources (ogx.io/v1beta1) into complete deployment stacks including Deployments, Services, NetworkPolicies, Ingresses, HorizontalPodAutoscalers, PodDisruptionBudgets, and RBAC resources. It also manages `LlamaStackDistribution` resources (llamastack.io/v1alpha1). A validating admission webhook enforces resource constraints on OGXServer creation and updates. The companion `ogx-module` binary operates as an ODH platform component controller, reconciling the cluster-scoped `OGX` resource (components.platform.opendatahub.io/v1alpha1) to deploy and manage the ogx-k8s-operator itself, handling kustomize-based manifest rendering, RBAC setup, CRD lifecycle, and webhook configuration. Both binaries follow OpenShift TLS profile conventions for webhook and metrics serving, and integrate with prometheus-operator for monitoring via ServiceMonitor and PrometheusRule CRDs. [source: main.go:27-33, ogx-module/internal/controller/ogx/reconciler.go:12-19, 47-56, config/rbac/role.yaml:2, config/webhook/manifests.yaml:2-27]

## Architectural Analysis

ogx-k8s-operator follows a two-tier controller architecture. The outer tier is the **ogx-module** controller, which acts as an ODH platform component manager: it watches a cluster-scoped `OGX` custom resource and uses kustomize-based manifest rendering (via `odh-platform-utilities`) to deploy the inner-tier operator, its CRDs, RBAC, webhooks, and monitoring resources. This design allows the ODH/RHOAI platform operator to manage the OGX operator's lifecycle declaratively, with separate kustomize overlays for ODH and RHOAI distributions. [source: ogx-module/internal/controller/ogx/reconciler.go:47-56]

The inner tier is the **OGXServer controller** (`OGXServerReconciler`), which reconciles namespaced `OGXServer` resources into a full deployment stack. Each OGXServer produces a Deployment, Service, optional HPA, PDB, NetworkPolicy, Ingress, ConfigMap, and PersistentVolumeClaim — all owned by the OGXServer CR and garbage-collected via controller-runtime ownership. The controller also manages ServiceAccount and RoleBinding resources for workload identity. A `configgen` utility generates default configurations for OGX server deployments. [source: controllers/ogxserver_controller.go:822-839, main.go:239-263]

The operator enforces admission validation through a `ValidatingWebhookConfiguration` at `/validate-ogx-io-v1beta1-ogxserver` with a `Fail` failure policy, rejecting invalid OGXServer CREATE and UPDATE requests. TLS for the webhook and metrics endpoints is configured dynamically by reading the OpenShift APIServer TLS profile via `openshift/controller-runtime-common`, falling back to the Intermediate profile on non-OpenShift clusters. When `--metrics-cert-path` is set, the metrics server at `:8443` enables secure serving with token review and subject access review authentication. [source: main.go:149-211, 265-276, config/webhook/manifests.yaml:2-27]

The operator integrates with the prometheus-operator ecosystem by managing `ServiceMonitor` and `PrometheusRule` CRDs, enabling platform-level observability. Legacy resource adoption logic handles migration from prior naming conventions. The `ogx-module` controller additionally manages `ValidatingWebhookConfiguration` and `CustomResourceDefinition` resources as owned objects, ensuring the inner operator's admission and API surface are kept in sync with the platform state. [source: ogx-module/internal/controller/ogx/reconciler.go:141-150, main.go:33]

Both operator and ogx-module Dockerfiles use `CGO_ENABLED=1` for dynamic linking and the `ubi9/ubi-minimal-pqc` runtime base image, which provides OpenSSL and post-quantum cryptography libraries. Neither build specifies `GOEXPERIMENT=strictfipsruntime`, so Go's strict FIPS runtime enforcement is not enabled. The dynamically linked binary will use the system OpenSSL via the Go runtime's CGO crypto backend, but without explicit strict FIPS mode opt-in. [source: Dockerfile.konflux:6, 29, 33; ogx-module/Dockerfile.konflux:5, 21, 24]
