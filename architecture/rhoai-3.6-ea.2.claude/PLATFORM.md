## Platform Overview

Red Hat OpenShift AI (RHOAI) 3.6-ea.2 is an AI/ML platform deployed on OpenShift Container Platform via OLM. The platform operator (`rhods-operator`) acts as a lifecycle orchestrator, reconciling a `DataScienceCluster` CR to deploy and configure approximately 76 components spanning model serving, training, pipelines, feature stores, guardrails, observability, and developer tooling. Components are organized into module operators (kserve, feast-module-operator, mlflow-operator, trainer-operator, workbenches-operator, spark-operator, ai-gateway-operator, etc.) that rhods-operator enables or disables based on the cluster's `DataScienceCluster` specification.

The platform's ingress architecture uses two primary Gateways in the `openshift-ingress` namespace. The `data-science-gateway` is the central shared Gateway for model serving and notebooks: rhods-operator creates the Gateway and an EnvoyFilter that routes authentication subrequests via `ext_authz` to `kube-auth-proxy`'s `/oauth2/auth` endpoint, enforcing OAuth2/OIDC authentication at the gateway level before requests reach backend services. A second Gateway, `maas-default-gateway`, serves the Models-as-a-Service (MaaS) API with Kuadrant AuthPolicy-based authentication (supporting both API keys and OpenShift tokens) and a dual-stage Praxis ExtProc pipeline for payload processing. Legacy OpenShift Routes coexist with Gateway API resources for observability endpoints and some component-specific services.

The security posture is defense-in-depth: gateway-level authentication (ext_authz or Kuadrant AuthPolicy), per-pod kube-rbac-proxy sidecars for metrics and notebook endpoints, RBAC enforcement via Kubernetes TokenReview and SubjectAccessReview, TLS everywhere with cipher suites derived from the OpenShift APIServer TLS profile, and FIPS-compliant Go binaries built with `GOEXPERIMENT=strictfipsruntime` on UBI9 PQC base images. All webhook configurations use `failurePolicy: Fail`, prioritizing data consistency over availability.

### Central Components

**rhods-operator** is the platform root: it creates the `DataScienceCluster` and `DSCInitialization` CRs that gate all other component deployments, manages the `data-science-gateway` Gateway infrastructure, and watches across 14+ CRD types including FeatureStore, InferenceService, and Gateway API resources.

**kserve** is the most interconnected serving component: it defines 13 CRDs (InferenceService, LLMInferenceService, LLMInferenceServiceConfig, ServingRuntime, ClusterServingRuntime, InferenceGraph, TrainedModel, LocalModelCache, LocalModelNamespaceCache), runs 30 webhooks, and is depended upon by data-science-pipelines-operator, models-as-a-service, and odh-model-controller.

**odh-model-controller** bridges the gap between KServe and the platform gateway: it creates HTTPRoutes, EnvoyFilters, Kuadrant AuthPolicies, and Gateway resources, and exposes a model-serving-api for gateway and sample management.

**odh-dashboard** is the primary user-facing component: its operator manages workspace creation, and 11 Go BFF (Backend-for-Frontend) sidecars proxy domain-specific APIs (model serving, pipelines, connections, storage, accelerator profiles, etc.) to the Kubernetes API server.

**kubeflow** (notebook-controller) manages Notebook CR lifecycles and injects kube-rbac-proxy sidecars via a mutating webhook on every Notebook pod, creating HTTPRoutes targeting `data-science-gateway` for per-notebook ingress.

### Ingress Analysis

RHOAI 3.6-ea.2 operates two primary ingress paths through the `openshift-ingress` namespace, reflecting the platform's dual model-serving architecture.

The **data-science-gateway** path is the central shared ingress surface for traditional model serving and interactive workloads. rhods-operator creates the Gateway, a GatewayClass (`data-science-gateway-class`), and an EnvoyFilter that intercepts every request with an `ext_authz` subrequest to `kube-auth-proxy`'s `/oauth2/auth` endpoint (source: `rhods-operator/internal/controller/services/gateway/resources/envoyfilter-authn.tmpl.yaml`). kube-auth-proxy validates OAuth2/OIDC sessions and returns identity headers (`x-auth-request-user`, `x-auth-request-email`, `x-auth-request-access-token`). A Lua filter in the same EnvoyFilter chain strips OAuth2 proxy cookies and forwards access tokens. After gateway-level authentication, requests reach backend services: for notebooks, a kube-rbac-proxy sidecar (injected by kubeflow's mutating webhook) enforces per-user Kubernetes RBAC; for InferenceServices, odh-model-controller may attach Kuadrant AuthPolicies for additional authorization. This two-layer authentication (gateway ext_authz + pod kube-rbac-proxy) is a deliberate design: the gateway provides SSO-style session validation while pod-level proxies enforce resource-specific authorization.

The **maas-default-gateway** path serves the Models-as-a-Service API and external-provider model inference. This gateway uses a different GatewayClass (`openshift-default`) and a different authentication model: Kuadrant AuthPolicies backed by Authorino support dual authentication (API keys with `sk-oai-*` prefix and OpenShift bearer tokens). The gateway's request path includes a dual-stage Praxis ExtProc pipeline: `ipp-pre` (pre-authentication, `failure_mode_allow: true`) extracts model identifiers for routing, and `ipp` (post-authentication, `failure_mode_allow: false`) applies the full payload-processing filter chain. The ai-gateway-controller manages the ExtProc filter installation, performing kustomize build, placeholder substitution (namespace, gateway name, route names), and server-side-apply of the dataplane manifests. The MaaS HTTPRoute (`maas-api-route`) defines four rules (models, subscriptions, api-keys, maas-api catchall) with per-rule ExtProc disabling for the management API routes.

**Legacy Routes** coexist with Gateway API: odh-observability uses three OpenShift Routes for Prometheus and Thanos Querier (TLS passthrough with backend kube-rbac-proxy), distributed-workloads exposes MinIO via Routes, and model-registry-operator creates both HTTPRoutes and legacy Routes for each registry instance. This parallel ingress generation reflects a transition from OpenShift Routes to Gateway API that is not yet complete across all components.

**Unresolved ingress relationships**: The workbenches component references a `kubeflow-gateway` Gateway resource and supports both HTTPRoute and VirtualService routing; the exact gateway lifecycle (whether created by workbenches or pre-existing) is configuration-dependent and partially unresolved. OpenShell's GRPCRoute has a configurable `parentRef` that can target any gateway, making its production gateway binding deployment-specific.

## Deployment Architecture

### Deployment Topology

The platform deploys across four namespace tiers. The **operator namespace** (`opendatahub`) hosts the platform operator (rhods-operator), module operators, and core controllers. Each module operator reconciles its domain-specific CRDs and deploys workloads into the appropriate namespace. The **ingress namespace** (`openshift-ingress`) hosts the gateway infrastructure: two Istio-backed Gateways (data-science-gateway, maas-default-gateway), the kube-auth-proxy OAuth2 authentication proxy, and the praxis-extproc payload-processing service. The **monitoring namespace** (`redhat-ods-monitoring`) hosts the Prometheus stack, OpenTelemetry collector, and kube-rbac-proxy proxies for metrics access. **User namespaces** host workloads: notebooks, InferenceServices, model servers, pipeline runs, training jobs, feature stores, and TrustyAI services are created per-user or per-project.

The kserve controller namespace (`kserve`) is a notable exception to the operator-namespace pattern: kserve runs its own manager, llmisvc controller, localmodel controller, and kserve-module controller in a dedicated namespace, reflecting its upstream Kubernetes-native deployment model. Similarly, model-registry-operator runs in `model-registry-operator-system`.

The platform comprises 76 analyzed components with approximately 420 container entrypoints, 78 Go executables, 77 controllers, 62 Deployments, 54 Python packages, 48 Go controller-runtime operators, 15 Rust services, and 10 Go BFF sidecars. The structured inventory includes 146 CRDs across 31 components, 213 webhooks across 18 components, 138 Kubernetes Services, and 142 gRPC service definitions.

## Platform Architectural Analysis

RHOAI 3.6-ea.2 represents a platform at an inflection point between two architectural generations. The traditional KServe-based model serving path (data-science-gateway → ext_authz → kube-auth-proxy → KServe InferenceService) coexists with the newer MaaS-based path (maas-default-gateway → Kuadrant AuthPolicy → Praxis ExtProc → maas-api → external/internal models) and the LLM-D disaggregated inference path (Envoy → ExtProc EPP → InferencePool → vLLM backends). Each path has its own gateway, authentication model, and routing mechanism, reflecting intentional architectural separation rather than accidental complexity.

**Authentication fragmentation** is the most significant cross-cutting tension. The platform uses at least four distinct authentication mechanisms at different enforcement points: (1) gateway ext_authz → kube-auth-proxy for OAuth2/OIDC session validation, (2) Kuadrant AuthPolicy → Authorino for API key and token validation, (3) kube-rbac-proxy sidecars for per-pod TokenReview+SAR enforcement, and (4) application-level bearer token validation delegating to the Kubernetes API server. While each mechanism is well-implemented, the composition across components creates operational complexity: a request to a notebook traverses ext_authz + kube-rbac-proxy, a request to a MaaS model traverses Kuadrant AuthPolicy + Praxis ExtProc, and a request to a model-registry traverses an as-yet partially resolved path. The fragmentation is not a defect—each mechanism serves a different trust model—but it complicates unified audit logging and policy enforcement.

**Webhook density** is notable: 213 webhooks across 18 components, with kueue-operator alone contributing 70 (34 mutating + 36 validating) to cover its broad workload admission surface. All webhooks use `failurePolicy: Fail`, meaning any webhook server outage blocks resource creation for its target types. The kserve pod-mutator intercepts all Pod CREATE operations in watched namespaces, creating a wide blast radius. The cascading reconciliation chains (DataScienceCluster → module operator CRs → component CRDs → workload resources) combined with cross-component webhook interception create a complex admission topology where a single CR change can trigger reconciliation and webhook evaluation across multiple controllers.

**The module operator pattern** (`components.platform.opendatahub.io/v1alpha1`) is a unifying architectural success: 15+ components register as modules that rhods-operator can enable/disable declaratively. This enables selective capability deployment (e.g., enabling MaaS without training, or training without feature stores) and provides a clean extension point for new capabilities. However, module operators vary significantly in maturity: some (kserve, kubeflow) have deep CRD surfaces with multiple controllers, while others (feast-module-operator, trainer-operator) are thin wrappers that delegate most logic to upstream operators.

**TLS and FIPS posture** is largely consistent across Go components (strictfipsruntime + UBI9 PQC base images + OpenShift TLS profile inheritance) but has notable gaps in Rust components. The fms-guardrails-orchestrator uses the `ring` cryptographic crate (not FIPS-validated), and OpenShell uses `rustls/ring`. This creates a FIPS compliance boundary between the Go and Rust component populations that operators deploying in FedRAMP or DISA-regulated environments should be aware of.

**Observability integration** follows a consistent pattern: all operators expose Prometheus metrics on dedicated ports (typically 8443, proxied through kube-rbac-proxy), and the odh-observability component deploys Prometheus with ServiceMonitor-based service discovery. OpenTelemetry tracing is available but optional across components (maas-api, odh-model-controller, odh-dashboard, trustyai-service-operator). The three-route observability pattern (cluster proxy, namespace proxy, Thanos querier) via OpenShift Routes with kube-rbac-proxy backends provides scoped access but adds operational complexity.

**Database management** is per-component: data-science-pipelines-operator deploys MariaDB per DSPA instance, model-registry-operator deploys PostgreSQL per registry, maas-api uses PostgreSQL (pgx client), and kserve's LocalModelCache uses PersistentVolumes. No shared database or distributed consensus system spans the platform, which is architecturally clean but means each stateful component manages its own backup, migration, and availability.
