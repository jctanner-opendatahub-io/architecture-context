## Purpose

**Short**: Guardrails detectors provide text content analysis microservices — including regex-based pattern matching, HuggingFace model inference, and LLM-as-Judge evaluation — deployed as KServe serving runtimes within RHOAI for use with the FMS Guardrails Orchestrator. [source: detectors/pyproject.toml:5, detectors/Dockerfile.konflux.builtIn:32-37]

**Detailed**: The guardrails-detectors repository packages three distinct detector types as independently deployable FastAPI microservices. The **built-in detector** runs regex and file-type pattern matching via a compiled shell script entrypoint, exposing content analysis and a detector registry API. The **HuggingFace detector** loads AutoModelForSequenceClassification or GraniteForCausalLM models for inference-based text classification. The **LLM Judge detector** delegates content evaluation to a remote vLLM inference server via the `vllm-judge` library, supporting configurable evaluation metrics including safety, toxicity, accuracy, and helpfulness. Each detector exposes a `/api/v1/text/contents` POST endpoint conforming to a shared content analysis request/response schema. The HuggingFace and LLM Judge detectors are packaged as KServe ServingRuntime definitions for deployment via the RHOAI model serving infrastructure. [source: detectors/built_in/app.py:42, detectors/llm_judge/app.py:36-41, detectors/llm_judge/detector.py:4, detectors/huggingface/deploy/servingruntime.yaml:1, detectors/llm_judge/deploy/servingruntime.yaml:1]

## Architectural Analysis

Guardrails-detectors follows a plugin-style architecture where each detector type is an independent FastAPI application sharing a common base class (`DetectorBaseAPI`) that provides standardized error handling, health endpoints, and Prometheus instrumentation counters for detections, requests, errors, and runtime latency. [source: detectors/common/app.py:33-64]

The three detector variants — built-in, HuggingFace, and LLM Judge — share a common request/response schema (`ContentAnalysisHttpRequest` / `ContentsAnalysisResponse`) but differ significantly in their compute patterns. The built-in detector performs local regex and file-type matching with minimal resource requirements. The HuggingFace detector loads ML models locally, requiring GPU or substantial CPU/memory. The LLM Judge detector makes outbound HTTP calls to a vLLM inference server configured via `VLLM_BASE_URL`, introducing a runtime dependency on an external model serving endpoint. [source: detectors/llm_judge/detector.py:25-37, detectors/built_in/app.py:42-65]

Deployment is via KServe ServingRuntime CRDs that package each detector as a model serving container. The HuggingFace runtime uses a MinIO sidecar deployment for model storage, while the LLM Judge runtime requires network access to a pre-deployed vLLM predictor service (e.g., `qwen2-predictor:8080`). The built-in detector is self-contained with no external model dependencies. [source: detectors/huggingface/deploy/servingruntime.yaml:1, detectors/llm_judge/deploy/servingruntime.yaml:34-35, detectors/huggingface/deploy/model_container.yaml:27-30]

No authentication middleware is registered at the application level — the FastAPI instances are created with empty dependency lists, and the `DetectorBaseAPI` class adds no auth filters. Transport security (TLS) is configurable via the uvicorn server configuration when `ssl_ca_certs` is present, but is not enforced by default. Authentication and authorization are expected to be delegated to the platform service mesh or KServe infrastructure. [source: detectors/common/app.py:21-29, detectors/common/app.py:181-182]

## Data Flows

- **Content analysis request flow:** The FMS Guardrails Orchestrator sends POST requests to `/api/v1/text/contents` on port 8000 (HuggingFace, LLM Judge) or 8080 (built-in). For the built-in detector, the request is processed locally using regex and file-type pattern matching. For the HuggingFace detector, the request triggers local model inference using a pre-loaded model from MinIO storage. For the LLM Judge detector, the request is forwarded to a vLLM inference server at `VLLM_BASE_URL` (default `http://qwen2-predictor:8080`) via the `vllm-judge` library for evaluation. [source: detectors/built_in/app.py:42-65, detectors/llm_judge/detector.py:25-37, detectors/llm_judge/deploy/servingruntime.yaml:34-35]
- **Model serving deployment:** Detectors are deployed as KServe ServingRuntime containers. The HuggingFace deployment includes a MinIO sidecar (`minio-guardrails-guardian` on port 9000/TCP) that provides model artifact storage via a PersistentVolumeClaim. The LLM Judge runtime requires network connectivity to an existing vLLM predictor service. [source: detectors/huggingface/deploy/model_container.yaml:1-12, detectors/huggingface/deploy/servingruntime.yaml:1, detectors/llm_judge/deploy/servingruntime.yaml:1]
- **Observability:** All detectors expose Prometheus metrics. The built-in detector serves `/metrics` via `prometheus_client` multiprocess collector. The LLM Judge detector uses `prometheus-fastapi-instrumentator` to auto-expose `/metrics`. The `DetectorBaseAPI` tracks per-detector counters for detections, requests, errors, and runtime latency. [source: detectors/built_in/app.py:35-40, detectors/llm_judge/app.py:33, detectors/common/app.py:37-58]
- **Security context:** No authentication middleware is registered at the application level. TLS is configurable via server config but not enforced by default. The HuggingFace deployment references an opaque secret (`aws-connection-minio-data-connection-guardrails-guardian`) for MinIO credentials. [source: detectors/common/app.py:21-29, detectors/huggingface/deploy/model_container.yaml:94]
