## Purpose

**Short**: kubeflow-sdk is a Python client library providing a unified interface for managing ML workloads across Kubeflow Trainer, Katib, Spark, Pipelines, and Model Registry, with RHAI (Red Hat AI) downstream extensions for speculative decoding, training hub integration, and instrumentation. [source: pyproject.toml:2, 10, 28-53, kubeflow/trainer/backends/kubernetes/backend.py:27-39]

**Detailed**: kubeflow-sdk is the Kubeflow Python SDK, providing programmatic access to the Kubeflow ML platform for defining, submitting, and managing training jobs, hyperparameter tuning experiments, Spark workloads, ML pipelines, and model registry operations. The SDK's Kubernetes backend authenticates using the kubernetes Python client library (kube-config or in-cluster service account) and interacts with the Kubernetes API server to create and manage custom resources such as TrainJobs. The RHOAI distribution extends the upstream SDK with RHAI modules including SpeculativeDecodingTrainer, TrainingHubTrainer, and JIT checkpoint injection utilities, which provide Red Hat AI-specific training workflows for large language model fine-tuning and inference optimization. [source: pyproject.toml:2, 10, 28-53, kubeflow/trainer/backends/kubernetes/backend.py:27-60, kubeflow/common/types.py:16-27]

## Architectural Analysis

kubeflow-sdk follows a backend-abstraction pattern where training operations are defined through high-level Python types (CustomTrainer, HuggingFaceTrainer, SpeculativeDecodingTrainer) and dispatched through pluggable backends. The Kubernetes backend (`kubeflow.trainer.backends.kubernetes`) translates these training definitions into Kubernetes custom resources (TrainJob CRs managed by the Kubeflow Trainer controller) via the `kubeflow_trainer_api` models and the `kubernetes` Python client library. Authentication is fully delegated to the Kubernetes API server — the SDK uses kube-config for development access and in-cluster service account tokens for pod-based execution, with no SDK-level authentication middleware. [source: kubeflow/trainer/backends/kubernetes/backend.py:27-60, kubeflow/common/types.py:16-27]

The RHOAI distribution adds the `kubeflow.trainer.rhai` package as a downstream extension, providing SpeculativeDecodingTrainer for Eagle3 draft model training, TrainingHubTrainer for centralized training workflows with callback support, and JIT checkpoint injection for model checkpoint management during distributed training. These RHAI modules are assembled at the parent module level and are architecturally separate from upstream Kubeflow SDK functionality. [source: kubeflow/trainer/backends/kubernetes/backend.py:36-39]

The SDK's dependency architecture uses optional dependency groups (`docker`, `podman`, `rhai`, `spark`, `hub`, `pipelines`) to allow consumers to install only the integration surfaces they need. Core dependencies include `kubernetes>=27.2.0,<36.0.0` for Kubernetes API access, `kubeflow-trainer-api` for Trainer CRD models, and `kubeflow-katib-api` for hyperparameter tuning models. The `cryptography` and `pyjwt` packages appear in the resolved dependency tree as transitive dependencies of `pygithub` (a development/release tool dependency), not as direct SDK crypto or auth dependencies. [source: pyproject.toml:28-53, requirements.txt:416, 466, 1412, 1415]

## Data Flows

- **SDK-to-Kubernetes API flow:** The SDK submits training job definitions (TrainJob custom resources) to the Kubernetes API server through the `kubernetes` Python client library. Authentication uses kube-config credentials or in-cluster service account tokens. The Kubernetes backend creates CustomObjectsApi and CoreV1Api calls to manage TrainJobs in the target namespace. [source: kubeflow/trainer/backends/kubernetes/backend.py:53-60, kubeflow/common/types.py:16-27]
- **RHAI extensions:** RHAI-specific trainers (SpeculativeDecodingTrainer, TrainingHubTrainer) construct specialized TrainJob configurations that extend the upstream training flow with additional parameters for draft model training, callbacks, and checkpoint injection. These configurations are submitted through the same Kubernetes backend. [source: kubeflow/trainer/backends/kubernetes/backend.py:36-39]
- **Pipeline integration:** When the optional `pipelines` dependency group is installed, the SDK provides a compatibility layer over the Kubeflow Pipelines SDK (`kfp`), enabling pipeline definition and execution through the `kubeflow.pipelines` namespace. [source: kubeflow/pipelines/__init__.py:83-95, pyproject.toml:53]
- **Platform dependency context:** The SDK operates as a client library without its own runtime services, ingress, or persistent state. All network communication, authentication, and encryption are delegated to the Kubernetes API server and the platform's networking layer. [source: kubeflow/trainer/backends/kubernetes/backend.py:53-56]
