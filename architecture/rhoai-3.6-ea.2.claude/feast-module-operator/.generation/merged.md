## Purpose

**Short**: Kubernetes operator that manages the lifecycle of Feast feature store deployments within the RHOAI platform, reconciling FeastOperator custom resources into Feast FeatureStore instances with associated RBAC, monitoring, and workload resources. [source: cmd/main.go:29, config/crd/bases/components.platform.opendatahub.io_feastoperators.yaml:2, internal/controller/feastoperator/feastoperator_controller.go:90]

**Detailed**: The feast-module-operator is a controller-runtime-based Kubernetes operator that implements the RHOAI modular component pattern. It watches FeastOperator custom resources (components.platform.opendatahub.io/v1alpha1) and reconciles them into complete Feast feature store deployments using kustomize-based manifest rendering. The operator is built on the opendatahub-operator reconciler framework, which provides standardized actions for manifest rendering, deployment, garbage collection, and status reporting. It manages a broad set of owned resources including Deployments, Services, ConfigMaps, RBAC objects, Jobs, and ServiceMonitors. The operator also watches external CRDs (Feast FeatureStore, Kubeflow Notebooks, MLflow) and platform ConfigMaps to coordinate with other RHOAI components. The binary is a Cobra CLI application with two subcommands: `operator` (the main controller loop) and `chartgen` (manifest generation tooling). [source: cmd/main.go:31-43, pkg/manager/manager.go:66-151, internal/controller/feastoperator/feastoperator_controller.go:79-146]

## Architectural Analysis

The feast-module-operator follows the RHOAI modular operator pattern, where each platform component is managed by a dedicated module operator rather than a monolithic controller. The operator delegates its reconciliation logic to the opendatahub-operator framework, importing the reconciler, action pipeline, and status-reporting infrastructure from `github.com/opendatahub-io/opendatahub-operator/v2`. This creates a tight coupling to the platform operator's SDK — the controller constructs its reconciliation loop using `reconciler.ReconcilerFor()` and chains actions for kustomize rendering, deployment, garbage collection, and status updates. [source: internal/controller/feastoperator/feastoperator_controller.go:90-137, pkg/manager/manager.go:134-137]

The operator scopes its cache to the configured applications namespace for namespace-scoped resources (Deployments, Services, ServiceAccounts, Roles, RoleBindings), while watching FeastOperator CRs and CRDs cluster-wide. ConfigMaps and Secrets are excluded from the cache and read directly from the API server, which avoids stale reads for configuration data but increases API server load. The controller watches CustomResourceDefinitions filtered by component label and a named platform ConfigMap to trigger reconciliation when external platform state changes. [source: pkg/manager/manager.go:86-119, internal/controller/feastoperator/feastoperator_controller.go:101-114]

A notable architectural characteristic is the operator's broad RBAC scope: the manager-role grants 27 rule entries spanning core resources, CRDs, batch workloads, RBAC objects, Feast FeatureStore CRs, OpenShift Routes, Spark applications, and Prometheus ServiceMonitors. This breadth reflects the operator's responsibility for deploying and managing a complete Feast ecosystem rather than just a single workload. The finalizer performs explicit cleanup of cluster-scoped ClusterRoles and ClusterRoleBindings that cannot use ownerReferences for garbage collection. [source: internal/controller/feastoperator/feastoperator_controller.go:148-181, config/rbac/role.yaml:2]

The operator uses GOEXPERIMENT=strictfipsruntime with CGO_ENABLED=1 for FIPS-compliant builds, and the runtime image is based on ubi9/ubi-minimal-pqc (post-quantum cryptography variant), indicating preparation for both current FIPS requirements and future PQC readiness. [source: Dockerfile.konflux:7,25,30]

## Data Flows

- **Reconciliation trigger:** FeastOperator CR creation or updates, CRD changes (filtered by component label), and platform ConfigMap changes trigger the reconciliation loop. The controller uses controller-runtime's `ReconcilerFor` pattern with owned-resource watches and external resource watches with predicates. [source: internal/controller/feastoperator/feastoperator_controller.go:90-114]
- **Manifest rendering and deployment:** The reconciliation pipeline initializes module state, checks upgrade requirements, sets kustomize parameters, reconciles platform version from a ConfigMap, renders manifests via kustomize, deploys resources with caching and apply ordering, reports deployment status, and performs garbage collection of stale resources in the applications namespace. [source: internal/controller/feastoperator/feastoperator_controller.go:115-136]
- **Metrics and observability:** The operator exposes a Prometheus metrics endpoint on port 8443 (HTTPS) protected by TokenReview and SubjectAccessReview authentication. A ServiceMonitor CR is created as an owned resource to integrate with the prometheus-operator monitoring stack. Health and readiness probes are served on port 8081 without authentication. [source: pkg/manager/manager.go:92-148, config/default/metrics_service.yaml:1-17]
- **External API interactions:** The operator reads Feast FeatureStore CRs (feast.dev), Kubeflow Notebooks (kubeflow.org), and MLflow CRs (mlflow.opendatahub.io) as cross-component coordination points. It manages OpenShift Routes and Spark applications as part of Feast ecosystem deployments. All Kubernetes API interactions use the operator's service account with TLS 1.2+ encryption. [source: internal/controller/feastoperator/feastoperator_controller.go:72-76, config/rbac/role.yaml:2]
