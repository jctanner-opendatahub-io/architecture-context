## Purpose

**Short**: llm-d is a disaggregated LLM inference serving framework that deploys vllm-based model servers with Envoy/EPP-based request routing and optional RDMA KV-cache transfer for prefill-decode disaggregation. [source: docker/Dockerfile.cpu:142, guides/recipes/router/base.values.yaml:4-8, guides/recipes/modelserver/base/single-host/pd/base/prefill-deployment.yaml:28-29]

**Detailed**: llm-d provides Kubernetes deployment recipes for large language model inference using vllm as the serving backend. The framework supports both single-host decode-only deployments and disaggregated prefill-decode architectures where prefill and decode workloads run on separate pods and transfer KV-cache state via nixl over RDMA on port 5600. Request routing is handled by an Envoy sidecar proxy (listening on port 8081) that delegates routing decisions to an Endpoint Picker Plugin (EPP) via the ext_proc gRPC protocol on port 9002. The EPP evaluates model server load and routes requests to optimal backends using the Gateway API InferencePool abstraction. The model server container runs the vllm OpenAI-compatible API server on port 8000/TCP, exposing standard inference endpoints. Dockerfiles are provided for CPU, ROCm (AMD GPU), XPU (Intel), and RDMA-tools variants. Security is platform-delegated: the model server has no built-in authentication, but guides provide Istio strict mTLS with AuthorizationPolicy for inter-component gRPC traffic. Observability is supported through OpenTelemetry tracing (OTLP export) and Prometheus metrics scraping via PodMonitor. [source: docker/Dockerfile.cpu:142, guides/recipes/modelserver/base/single-host/default/decode-deployment.yaml:17-38, guides/no-kubernetes-deployment/router/envoy/envoy.yaml:29-76, guides/modelexpress-p2p/security/istio-mtls-authz.yaml:1-42]

## Architectural Analysis

llm-d adopts a disaggregated inference architecture where prefill and decode phases can run on separate Kubernetes Deployments. In the default single-host mode, a single `decode` Deployment runs the vllm OpenAI-compatible API server on port 8000. In disaggregated (prefill-decode) mode, a `prefill` Deployment exposes an additional nixl port (5600/TCP) for KV-cache transfer via RDMA, and a routing sidecar (with `--kv-connector=nixlv2`) intercepts traffic on port 8000 to coordinate cache handoff between prefill and decode pods. [source: guides/recipes/modelserver/base/single-host/pd/base/prefill-deployment.yaml:28-29, guides/recipes/modelserver/base/single-host/pd/vllm/patch-sidecar.yaml:12-13]

Request routing follows an ext_proc pattern: an Envoy sidecar proxy accepts client traffic on port 8081, forwards request and response headers/bodies to the EPP (Endpoint Picker Plugin) over gRPC on port 9002, and the EPP selects a model server backend via the `x-gateway-destination-endpoint` header for ORIGINAL_DST routing. The EPP operates within the Gateway API InferencePool abstraction, and its proxy type is configurable between Envoy and agentgateway. [source: guides/no-kubernetes-deployment/router/envoy/envoy.yaml:29-101, guides/recipes/router/base.values.yaml:17-28]

Security is entirely platform-delegated. The vllm model server has no built-in authentication or authorization. When Istio service mesh is present, the ModelExpress guide demonstrates strict mTLS with PeerAuthentication scoped to the broker workload and an AuthorizationPolicy that restricts gRPC port 8001 to the decode ServiceAccount only. RDMA-based weight transfers bypass the mesh entirely. The routing sidecar can be deployed with `--secure-proxy=false`, explicitly disabling TLS on the sidecar-to-vllm path. [source: guides/modelexpress-p2p/security/istio-mtls-authz.yaml:1-42, guides/recipes/modelserver/base/single-host/pd/vllm/patch-sidecar.yaml:14]

No FIPS compliance signals were found at any layer. The primary workload is a Python-based vllm server; no Go build flags, GOEXPERIMENT settings, or explicit FIPS crypto configuration are present in the repository. [source: docker/Dockerfile.cpu:130-142]

## Data Flows

- **Inference request flow:** Client requests arrive at the Envoy proxy on port 8081, which forwards headers and body to the EPP via ext_proc gRPC on port 9002. The EPP selects a target model server based on InferencePool membership and load, sets the `x-gateway-destination-endpoint` header, and Envoy routes via ORIGINAL_DST to the selected vllm model server on port 8000/TCP. The model server responds with OpenAI-compatible JSON via /v1/completions or /v1/chat/completions. [source: guides/no-kubernetes-deployment/router/envoy/envoy.yaml:29-101, guides/recipes/router/base.values.yaml:20-21]
- **Disaggregated KV-cache transfer:** In prefill-decode mode, prefill pods expose port 5600/TCP for nixl-based KV-cache transfer over RDMA. A routing sidecar with `--kv-connector=nixlv2` intercepts port 8000 traffic on decode pods to coordinate cache handoff. RDMA weight transfers bypass the Istio mesh. [source: guides/recipes/modelserver/base/single-host/pd/base/prefill-deployment.yaml:28-29, guides/recipes/modelserver/base/single-host/pd/vllm/patch-sidecar.yaml:12-14]
- **Observability pipeline:** Model servers and EPP export traces via OTLP gRPC (port 4317) to an OpenTelemetry Collector, which batches and forwards to Jaeger on jaeger-collector:4317. Prometheus scrapes metrics via PodMonitor. [source: guides/recipes/observability/tracing/otel-collector.yaml:9-14, guides/recipes/router/base.values.yaml:60-64]
