## Purpose

**Short**: Batch inference gateway for RHOAI that accepts asynchronous batch inference requests, manages file uploads, and orchestrates job processing against llm-d inference endpoints. [source: cmd/apiserver/main.go:34, internal/apiserver/server/server.go:86-100, charts/batch-gateway/values.yaml:98-99]

**Detailed**: batch-gateway provides a REST API for submitting and managing asynchronous batch inference jobs in Red Hat OpenShift AI. The system comprises three cooperating Go binaries: an API server that accepts batch and file management requests over HTTP (optionally TLS-terminated), a background processor that dequeues pending jobs and forwards inference requests to llm-d gateway endpoints, and a garbage collector that periodically removes expired jobs and files. State is persisted in PostgreSQL, job coordination uses Redis/Valkey as a message exchange, and input/output files are stored on either local PVCs or S3-compatible object storage. The component integrates with the llm-d ecosystem via both the llm-d-async Go library and direct HTTP calls to inference gateway endpoints, with the `Authorization` header passed through to downstream services. Observability is provided through Prometheus metrics, OpenTelemetry tracing (OTLP/gRPC), and structured logging. ## Architectural Analysis

batch-gateway follows a three-process architecture where each binary handles a distinct concern: the API server manages external HTTP traffic, the processor handles asynchronous job execution, and the garbage collector performs periodic cleanup. All three share a common internal library for database access, file storage, Redis/Valkey messaging, and TLS configuration, but they are built and deployed as separate container images with independent Konflux Dockerfiles.

The API server exposes two separate HTTP listeners — an API mux on port 8000 (configurable, with optional TLS) and an observability mux on port 8081 (always plain HTTP). The API mux applies a middleware chain of panic recovery, request context enrichment (request ID, tenant header extraction, OTel tracing, metrics), and security response headers, but does not enforce authentication at the application layer. The `X-MaaS-Username` header is extracted for tenant identification, and the `Authorization` header is passed through to downstream inference calls, indicating that authentication is expected to be enforced externally by a platform gateway or service mesh. The Helm chart includes an optional HTTPRoute resource that attaches to an `llm-d-inference-gateway` Gateway, which would provide the external auth boundary.

The TLS subsystem is configurable with minimum version (default TLS 1.2), cipher suites, and ALPN protocol negotiation, all resolved through a dedicated `internal/tls` package that produces `crypto/tls` configuration functions. All Konflux builds use `GOEXPERIMENT=strictfipsruntime` with `CGO_ENABLED=1`, enabling FIPS-validated cryptography through the Go runtime's OpenSSL integration on UBI9 base images.

Storage is abstracted behind pluggable backends: PostgreSQL for relational state (job metadata, status tracking), Redis/Valkey for job coordination and messaging via the llm-d-async producer library, and either filesystem PVCs or S3-compatible object storage for batch input/output files. All external connections support configurable TLS and retry policies. ## Data Flows

- **Batch job submission:** External clients submit batch inference requests to the API server's HTTP endpoint (port 8000, optional TLS). The API server validates the request, persists job metadata to PostgreSQL, and enqueues the job via Redis/Valkey using the llm-d-async producer library. The `Authorization` header is captured and stored for downstream passthrough. [source: internal/apiserver/server/server.go:86-100, charts/batch-gateway/values.yaml:186-201]
- **Batch job processing:** The processor polls Redis/Valkey for pending jobs, retrieves input files from the configured file store (PVC or S3), and forwards inference requests to the llm-d inference gateway over HTTP/HTTPS. Results are written back to the file store, and job status is updated in PostgreSQL. [source: cmd/batch-processor/main.go:44, charts/batch-gateway/values.yaml:74-96]
- **File management:** Input and output files are managed via the API server's file endpoints. Files are stored in either a local filesystem (PVC-backed) or S3-compatible object storage, with configurable size limits (default 200 MB) and expiration (default 90 days). [source: charts/batch-gateway/values.yaml:74-96, 202-205]
- **Garbage collection:** The GC process periodically scans PostgreSQL for expired batch jobs and files, removing associated data from both the database and the file store. [source: cmd/batch-gc/main.go:49]
- **Observability:** All three components export Prometheus metrics on a dedicated observability port (default 8081). OpenTelemetry traces are exported via OTLP/gRPC to a configurable collector endpoint, with per-connection tracing available for Redis and PostgreSQL. [source: charts/batch-gateway/values.yaml:49-69, internal/util/otel/otel.go:203]
