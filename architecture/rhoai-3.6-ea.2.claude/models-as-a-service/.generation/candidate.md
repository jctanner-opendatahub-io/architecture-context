## Purpose

**Short**: Models-as-a-Service (MaaS) provides a multi-tenant API gateway and controller platform for managing AI model subscriptions, API key authentication, and Gateway API routing within Red Hat OpenShift AI. [source: maas-api/internal/auth/tenant_auth_middleware.go:17-19, maas-controller/pkg/controller/maas/maasauthpolicy_controller.go:989, deployment/base/maas-api/networking/httproute.yaml:1-60]

**Detailed**: Models-as-a-Service is a two-component system comprising a REST API server (maas-api) and a Kubernetes controller manager (maas-controller). The maas-api server exposes OpenAI-compatible endpoints for model discovery, subscription management, and API key lifecycle, authenticating requests via Kubernetes TokenReview and SubjectAccessReview APIs. The maas-controller manages the platform's CRD-driven resource model—including AITenant, MaaSSubscription, MaaSModelRef, MaaSAuthPolicy, and ExternalModel—and dynamically creates Kuadrant AuthPolicy and Gateway API HTTPRoute resources to enforce per-tenant authentication and routing policies at the ingress layer. The system integrates with KServe InferenceService for model serving state and relies on a PostgreSQL database for persistent storage of API keys and subscription metadata. [source: maas-api/internal/auth/tenant_auth_middleware.go:17-19, maas-controller/pkg/controller/maas/maasauthpolicy_controller.go:989, deployment/base/maas-api/networking/httproute.yaml:1-60, maas-api/Dockerfile.konflux:15]

## Architectural Analysis

Models-as-a-Service follows a split-plane architecture: the maas-api server handles synchronous user-facing REST traffic while the maas-controller asynchronously reconciles the platform's declarative resource model. This separation allows the API server to remain responsive to client requests while the controller independently manages complex multi-resource reconciliation workflows spanning seven custom resource types.

The authentication architecture operates at two layers. At the application level, the maas-api's `TenantAuthMiddleware` validates Bearer tokens via Kubernetes TokenReview and confirms authenticated-user membership through SubjectAccessReview, enforcing a 5-second timeout on all Kubernetes API calls to prevent hangs. At the gateway level, the MaaSAuthPolicy controller dynamically constructs Kuadrant/Authorino AuthPolicy resources that enforce API key validation, Kubernetes TokenReview, and optional OIDC JWT authentication—with CEL expressions governing per-request identity extraction and subscription-scoped authorization headers (X-MaaS-Username, X-MaaS-Group, X-MaaS-Subscription). This dual-layer design means authentication is enforced both at the ingress gateway and within the API server, providing defense in depth. [source: maas-api/internal/auth/tenant_auth_middleware.go:17-90, maas-controller/pkg/controller/maas/maasauthpolicy_controller.go:900-1060]

The ingress architecture routes external traffic through a Gateway API HTTPRoute (`maas-api-route`) targeting the `maas-default-gateway` in the `openshift-ingress` namespace. The route exposes `/v1/models`, `/v1/subscriptions`, `/v1/api-keys`, and `/maas-api/*` paths with backend port 8443 (HTTPS), while explicitly excluding `/v1/tenants` from gateway routing to restrict it to internal-only access via the maas-api Service directly. An EnvoyFilter integration for payload processing operates on per-route indices, creating a tight coupling between HTTPRoute rule ordering and the EnvoyFilter configuration. [source: deployment/base/maas-api/networking/httproute.yaml:1-60]

The controller employs a rich watch topology where six reconcilers (AITenant, MaaSAuthPolicy, MaaSModelRef, MaaSSubscription, Tenant, Lifecycle) share cross-cutting watches on common resources—particularly AITenant and MaasTenantConfig—creating cascading reconciliation chains. The MaaSModelRef controller conditionally watches KServe InferenceService resources to track model serving state, enabling the system to reflect model availability in the subscription and routing layers. [source: maas-controller/pkg/controller/maas/maasauthpolicy_controller.go:989, maas-controller/pkg/controller/maas/maasmodelref_controller.go:559]

## Data Flows

- **External client requests:** Clients access the MaaS API through the Gateway API HTTPRoute (`maas-api-route`), which routes `/v1/models`, `/v1/subscriptions`, `/v1/api-keys`, and `/maas-api/*` paths through the `maas-default-gateway` in `openshift-ingress` to the maas-api backend on port 8443 (HTTPS). The Kuadrant/Authorino AuthPolicy enforces authentication (API key, Kubernetes TokenReview, or OIDC JWT) at the gateway before requests reach the application. The `/v1/tenants` path is intentionally excluded from gateway routing and accessible only via the internal maas-api Service. [source: deployment/base/maas-api/networking/httproute.yaml:1-60, maas-controller/pkg/controller/maas/maasauthpolicy_controller.go:989]
- **API server processing:** The maas-api server handles authenticated requests using Gin HTTP routes for model listing, subscription management, API key CRUD, and tenant operations. For gateway-authenticated requests, identity headers (X-MaaS-Username, X-MaaS-Group, X-MaaS-Subscription) are injected by the AuthPolicy's CEL-based response processing. For direct internal access, the `TenantAuthMiddleware` validates Bearer tokens through Kubernetes TokenReview and SubjectAccessReview. [source: maas-api/internal/auth/tenant_auth_middleware.go:17-90, maas-controller/pkg/controller/maas/maasauthpolicy_controller.go:994-1059]
- **Controller reconciliation:** The maas-controller manages the declarative resource model through six reconcilers watching seven CRD types. Changes to AITenant, MaaSSubscription, or MaaSModelRef resources trigger cascading reconciliation that creates or updates HTTPRoute, AuthPolicy, and TokenRateLimitPolicy resources. The MaaSModelRef controller conditionally watches KServe InferenceService to reflect model availability. [source: maas-controller/pkg/controller/maas/maasauthpolicy_controller.go:989, maas-controller/pkg/controller/maas/maasmodelref_controller.go:559]
- **Security context:** 11 authentication rules and 1 secret reference describe the extracted enforcement and credential inputs applied around these interactions; unknown values remain explicit in the tables. Both binaries are built with FIPS-compliant settings (CGO_ENABLED=1, GOEXPERIMENT=strictfipsruntime) on UBI9 ubi-minimal-pqc base images. [source: maas-api/Dockerfile.konflux:5, 15, 17, maas-controller/Dockerfile.konflux:5-6, 16, 18, maas-api/internal/config/tls.go:49-54]
