## Purpose

**Short**: Kubernetes operator that manages the lifecycle of Data Science Pipelines (DSP) deployments on RHOAI, reconciling DataSciencePipelinesApplication custom resources into a complete pipeline stack including API server, workflow controller, database, and object storage services. [source: main.go:165, controllers/dspipeline_controller.go:892-903]

**Detailed**: The data-science-pipelines-operator is a controller-runtime-based Kubernetes operator that watches DataSciencePipelinesApplication (DSPA) custom resources and reconciles them into a full Data Science Pipelines stack. For each DSPA instance, the operator deploys and manages an API server (with HTTP port 8888, gRPC port 8887, and an optional OAuth proxy on port 8443), an Argo Workflow controller, a MariaDB database (or external database connection), and a MinIO object store (or external S3-compatible storage). The operator uses manifestival to apply Go templates from `config/internal/` as Kubernetes resources, applying label-based filtering to scope its cache to operator-managed resources only. It integrates with the OpenShift TLS security profile API to configure TLS on its webhook and metrics servers, watches for TLS profile changes, and performs graceful restarts when the profile is updated. The operator also manages RBAC aggregation for Argo Workflow CRDs and DSPA resources, creates NetworkPolicy resources for workload isolation, and supports per-DSPA webhook validation for PipelineVersion resources. [source: main.go:165-415, controllers/dspipeline_controller.go:892-903, config/internal/apiserver/default/service.yaml.tmpl:1-30]

## Architectural Analysis

The data-science-pipelines-operator follows a single-controller reconciliation pattern: one `DSPAReconciler` watches the primary `DataSciencePipelinesApplication` CRD and owns all child resources (Deployments, Services, ServiceAccounts, ConfigMaps, Secrets, PVCs, Roles, RoleBindings, Routes, and NetworkPolicies). The controller uses manifestival to render Go templates from `config/internal/` into Kubernetes manifests, applying a `dsp-version` label to all managed resources. This label is used to scope the controller-runtime cache, ensuring the operator only watches resources it created rather than all cluster-wide resources of those types. [source: main.go:215-300, controllers/dspipeline_controller.go:892-903]

The operator deploys a multi-component stack per DSPA instance: an API server exposing both REST (8888) and gRPC (8887) interfaces, an optional OAuth proxy (8443) gated by `EnableRoute`, an Argo Workflow controller with its own RBAC and metrics service, and optional MariaDB and MinIO instances for users who do not bring external database or storage. Service-serving certificates are provisioned via OpenShift's `service.beta.openshift.io/serving-cert-secret-name` annotation, and pod-to-pod TLS for MariaDB is configurable through the DSPA CR. [source: config/internal/apiserver/default/service.yaml.tmpl:1-30, config/internal/mariadb/default/service.yaml.tmpl:1-21, config/internal/webhook/service.yaml.tmpl:1-19]

TLS configuration is derived from the OpenShift `APIServer` TLS profile at startup and applied to both the webhook server (port 9443) and the metrics server (port 8080). A `SecurityProfileWatcher` detects profile changes at runtime and triggers a graceful pod restart so the operator always reflects the cluster-wide TLS policy. On non-OpenShift clusters, the operator falls back to the `Intermediate` TLS profile. [source: tls_profile.go:22-64, main.go:224-408]

The MLflow integration uses direct API reads (bypassing the controller-runtime client cache) so that behavior does not depend on whether the MLflow CRD existed at operator startup. This pattern allows the operator to gracefully handle clusters where MLflow is not installed. [source: main.go:329-330, controllers/dspipeline_controller.go:28]

## Data Flows

- **Operator control plane:** The controller-manager exposes health probes on `:8081` (healthz, readyz), TLS-secured metrics on `:8080`, and a TLS-secured webhook server on `:9443`. The webhook validates PipelineVersion resources. All TLS configuration is derived from the OpenShift APIServer TLS profile. [source: main.go:170-171, 265-275, tls_profile.go:22-64]
- **DSPA reconciliation:** When a DataSciencePipelinesApplication CR is created or modified, the DSPAReconciler renders Go templates from `config/internal/` via manifestival and applies them as owned Kubernetes resources. The operator watches Deployments, Services, Secrets, ConfigMaps, ServiceAccounts, PVCs, NetworkPolicies, Roles, RoleBindings, and Routes as owned resources. [source: controllers/dspipeline_controller.go:892-903]
- **Per-DSPA service stack:** Each DSPA instance results in an API server (ports 8888 HTTP, 8887 gRPC, optional 8443 OAuth proxy), a workflow controller (metrics on 9090), and optionally a MariaDB (3306, with optional pod-to-pod TLS) and MinIO (9000). Service-serving certificates are provisioned via OpenShift annotation. [source: config/internal/apiserver/default/service.yaml.tmpl:1-30, config/internal/mariadb/default/service.yaml.tmpl:1-21, config/internal/minio/default/service.yaml.tmpl:1-26]
- **External integrations:** The operator reads MLflow CRs (direct API, bypassing cache), watches KServe InferenceService and OpenShift Route status, manages prometheus-operator ServiceMonitors, and has RBAC for Kubeflow Notebook CRDs.
