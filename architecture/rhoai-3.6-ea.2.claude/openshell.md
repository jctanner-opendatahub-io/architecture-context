## Purpose

**Short**: OpenShell provides sandboxed execution environments for autonomous AI agents, governed by declarative YAML policies that enforce file access, network connectivity, process privileges, and inference routing.

**Detailed**: OpenShell is NVIDIA's safe, private runtime for autonomous AI agents. It consists of two primary components: a control-plane **gateway** that manages sandbox lifecycle, authentication, authorization, policy delivery, and credential injection; and a **supervisor** binary that is injected into arbitrary user containers to enforce policy at the filesystem, network (L7-aware), process, and inference layers.

The gateway exposes a gRPC API (with HTTP bridging) for sandbox CRUD operations, provider/credential management, workspace isolation, inference routing, and real-time sandbox observation. It supports multiple compute backends — Docker, Podman, Kubernetes, and MicroVM — through a pluggable compute-driver interface. On Kubernetes, the supervisor binary is sideloaded into sandbox pods via init containers or Kubernetes ImageVolumes, and enforces egress policy using nftables/iptables rules combined with an L7-aware proxy.

Within the RHOAI platform, OpenShell is deployed via Helm chart as a StatefulSet (with SQLite) or Deployment (with external PostgreSQL) and integrates with OpenShift Routes for TLS passthrough ingress, cert-manager for PKI automation, OIDC providers (Keycloak) for user authentication, and SPIFFE/SPIRE for workload identity. The three Konflux container images (gateway, supervisor, CLI) are built hermetically on UBI9 with fully locked Cargo, RPM, and generic artifact dependencies.

## Architectural Analysis

OpenShell employs a defense-in-depth architecture with four distinct enforcement layers — filesystem, network, process, and inference — each independently configurable through declarative YAML policies. The gateway acts as a centralized control plane that distributes policies to per-sandbox supervisor instances, creating a hub-and-spoke model where policy updates are hot-reloadable without sandbox restart.

The authentication chain follows a first-match-wins pattern with three authenticator types: OIDC/Bearer tokens for user-facing API calls, gateway-minted Ed25519 JWTs for supervisor-to-gateway communication (using SPIFFE-style `spiffe://openshell/sandbox/{uuid}` subjects), and compute-driver-native bootstrap credentials for initial sandbox token issuance. Authorization is layered on top with workspace-scoped roles (user/admin) and global roles (platform_admin), enforced through protobuf method annotations that declare required auth mode, scope, and role directly in the `.proto` service definition.

A notable architectural decision is the supervisor's static linkage strategy: the supervisor binary is compiled with `-C target-feature=+crt-static` to produce a fully-static glibc binary that can be injected into arbitrary user containers (Alpine, Debian, distroless, UBI) regardless of their libc. This eliminates runtime library dependencies but carries LGPL relinking obligations for glibc-static distributions. The CLI binary uses the same static linkage approach.

The network enforcement layer is particularly sophisticated, implementing L7 policy evaluation with protocol-aware rules for HTTP, WebSocket, GraphQL, SQL, JSON-RPC, and MCP protocols. It includes AWS SigV4 re-signing support for transparent credential injection and formal policy verification using the Z3 SMT solver (bundled as `z3-sys` in the gateway build). The policy validation uses a fail-closed default (`fail_closed` mode), meaning any policy parse failure blocks sandbox operation rather than falling back to a permissive posture.

For Kubernetes deployments, OpenShell supports three workspace modes — `shared` (single namespace), `managed` (gateway creates/deletes per-workspace namespaces), and `operator` (external namespace lifecycle with label/file selectors) — providing flexibility for multi-tenant platform deployments. The credential storage architecture encrypts credentials at rest using AES-256-GCM with a Key Encryption Key (KEK) stored as a Kubernetes Secret, with optional Vault and Kubernetes Secrets credential driver backends.

The FIPS posture is notable: the Rust TLS stack uses `rustls` with `ring` as the crypto provider (not OpenSSL). While the UBI9 base images include `openssl-fips-provider` packages, the gateway and supervisor binaries use rustls/ring for their own TLS operations, meaning application-level TLS does not go through OpenSSL's FIPS-validated module. No `GOEXPERIMENT=strictfipsruntime` or equivalent Rust FIPS configuration is present, as this is a Rust (not Go) codebase. The `jsonwebtoken` crate is configured with the `aws_lc_rs` feature for JWT operations.
