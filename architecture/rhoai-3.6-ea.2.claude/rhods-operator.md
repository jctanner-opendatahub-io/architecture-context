## Purpose

**Short**: rhods-operator is the central lifecycle operator for Red Hat OpenShift AI (RHOAI), managing installation, configuration, and reconciliation of platform components including model serving, data science pipelines, workbenches, and gateway infrastructure through CRD-driven controllers with FIPS-compliant builds. [source: cmd/main.go:301, Dockerfiles/Dockerfile.konflux:58, Dockerfiles/Dockerfile.konflux:79]

**Detailed**: rhods-operator is the Kubernetes operator that orchestrates the entire RHOAI platform lifecycle. It ships as a single `/manager` binary (built from `cmd/main.go`) alongside a separate `cloudmanager` binary for multi-cloud Kubernetes engine provisioning (AWS, Azure, CoreWeave). The operator uses a DAG-based registration system to manage three categories of reconcilers: components (DataSciencePipelines, Kueue, Ray, TrustyAI, and others), services (Auth, Gateway), and modules, each registered with configurable run-levels and suppression flags. [source: cmd/main.go:301-335, Dockerfiles/Dockerfile.konflux:58-61]

The operator exposes 14 CRDs spanning component lifecycle (`DataScienceCluster`, `DSCInitialization`), platform services (`Auth`, `GatewayConfig`), infrastructure management (`HardwareProfile`, cloud engine CRDs), and feature tracking (`FeatureTracker`). Its gateway service controller creates and manages the complete ingress chain: Gateway API resources, kube-auth-proxy deployments with OIDC support, OpenShift Routes, EnvoyFilters, and DestinationRules. The auth service controller manages namespace-scoped RBAC for admin and allowed groups, reconciling on namespace changes for models-as-a-service and kuadrant integration. All webhook and metrics endpoints use TLS derived from the cluster's OpenShift TLS security profile. [source: cmd/main.go:478-504, internal/controller/services/gateway/gateway_controller.go:50-109, internal/controller/services/auth/auth_controller.go:56-87]

## Architectural Analysis

The rhods-operator follows a layered controller architecture built on controller-runtime with three distinct reconciler categories: components, services, and modules. Each category uses a DAG-based registration system with configurable run-levels, allowing the operator to sequence initialization and honor suppression flags for individual controllers. The main entrypoint wraps the standard controller-runtime manager with `odh-platform-utilities/framework/manager`, adding manifest and chart base path management. [source: cmd/main.go:29, 543, 301-335]

The gateway service is architecturally the most complex controller, owning a full ingress stack: it creates Gateway API resources, kube-auth-proxy deployments (with OIDC variants), HTTPRoutes, OpenShift Routes, EnvoyFilters, DestinationRules, and NetworkPolicies. It dynamically watches for the Dashboard CRD, certificate secrets, and cluster TLS security profile changes, triggering reconciliation when any of these external signals change. This design couples the gateway controller to both Istio service mesh resources (EnvoyFilter, DestinationRule) and OpenShift-specific routing, with dynamic guards that skip Istio resources when the CRDs are absent. [source: internal/controller/services/gateway/gateway_controller.go:50-109]

The auth service controller manages data-science admin and allowed group RBAC, creating ClusterRoles, Roles, and their bindings from Go templates. It watches two specific namespace names: `models-as-a-service` and `kuadrant-system`, reconciling auth permissions when either namespace appears or disappears. This establishes runtime dependencies on both the MaaS subsystem and the Kuadrant API gateway policy engine, even though neither is directly imported as a Go library by the auth controller itself. [source: internal/controller/services/auth/auth_controller.go:56-87]

The operator uses combined sequential initialization guarded by leader election to avoid race conditions between cleanup and DSCI/DSC creation (RHOAIENG-48054). TLS configuration is derived from the OpenShift APIServer TLS security profile at startup, and a `SecurityProfileWatcher` cancels the manager context on profile changes, forcing a pod restart to pick up new cipher suite requirements. This means the operator cannot dynamically rotate its TLS configuration; it relies on pod restart for TLS profile changes. [source: cmd/main.go:478, 593-604, 621-628]

Build-time FIPS compliance is enforced through `GOEXPERIMENT=strictfipsruntime` and `CGO_ENABLED=1` for the main manager binary, with the runtime image using `ubi9/ubi-minimal-pqc` (post-quantum crypto variant). The cloudmanager binary uses `-tags strictfipsruntime` but relies on a build-arg for `CGO_ENABLED`, which may not be explicitly set to 1 in all build contexts. [source: Dockerfiles/Dockerfile.konflux:58-63]

The cloudmanager binary has a potential gap: it uses `CGO_ENABLED=${CGO_ENABLED}` as a build-arg rather than an explicit `CGO_ENABLED=1`, and while `-tags strictfipsruntime` enables the FIPS runtime tag, dynamic linking to OpenSSL depends on CGO being enabled. ## Data Flows

- **Admission and webhook surface:** The Kubernetes API server sends admission requests to the operator's webhook server on port 9443 over TLS (certificate provisioned by OpenShift service-ca). The operator processes 10 webhook handlers: 3 conversion webhooks for CRD version migration, 4 validating webhooks for DataScienceCluster, DSCInitialization, AcceleratorProfile, and HardwareProfile resources, and 3 mutating webhooks for DataScienceCluster defaults and PodMonitor injection. [source: cmd/main.go:501-504, config/webhook/service.yaml:1]
- **Controller reconciliation loop:** Each controller (component, service, module) watches its primary CR plus owned and referenced resources through the Kubernetes API. Changes to watched resources trigger reconciliation, which applies desired state using template-based resource generation and cached deployment. The gateway controller additionally watches certificate Secrets, HTTPRoutes, Dashboard CRDs, and the APIServer TLS profile, creating the full ingress chain on each reconciliation cycle. [source: internal/controller/services/gateway/gateway_controller.go:50-109, cmd/main.go:551-589]
- **Auth and RBAC propagation:** The auth service controller watches namespace lifecycle events for `models-as-a-service` and `kuadrant-system` namespaces. When these namespaces are created or deleted, the controller reconciles ClusterRoles and RoleBindings from Go templates to grant data-science admin and allowed groups appropriate access to platform resources including ModelRegistry, Feast, KServe, HardwareProfile, and NIM Account CRs. [source: internal/controller/services/auth/auth_controller.go:63-76, internal/controller/services/auth/resources/data-science-admingroup-clusterrole.tmpl.yaml:1]
- **Metrics and health:** The operator exposes health probes at `:8081/healthz` and `:8081/readyz` (unauthenticated by design) and a metrics endpoint at port 8443 with optional authentication and authorization filtering when `MetricsSecure` is enabled. Both the metrics server and webhook server derive their TLS configuration from the cluster's OpenShift TLS security profile, fetched at startup. [source: cmd/main.go:478, 487-498, 612-616]
