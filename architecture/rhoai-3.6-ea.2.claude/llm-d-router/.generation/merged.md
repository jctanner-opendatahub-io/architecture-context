## Purpose

**Short**: llm-d-router implements the Endpoint Picker (EPP) for the llm-d inference serving stack, routing LLM inference requests through an Envoy External Processor using scheduling plugins, KV-cache awareness, and model rewriting to select optimal backend model server pods. [source: pkg/epp/server/runserver.go:238, pkg/epp/server/options.go:44, Dockerfile.konflux.epp:53]

**Detailed**: llm-d-router is the core routing and scheduling component of the llm-d inference serving stack within RHOAI. It operates as an Envoy External Processing (ExtProc) gRPC service that intercepts inference requests and applies configurable scheduling policies — including prefix-aware routing, KV-cache utilization, queue depth balancing, and latency prediction — to select optimal backend model server pods. The component also includes a coordinator binary for multi-EPP orchestration and a pd-sidecar proxy for per-pod DNS-based routing with NIXL KV-cache transfer support. [source: pkg/epp/server/runserver.go:238, Dockerfile.koordinator:46, cmd/pd-sidecar/main.go:30]

The system is driven by three custom resources: EndpointPickerConfig (scheduling and plugin configuration), InferenceModelRewrite (model alias translation), and InferenceObjective (autoscaling objectives). Controllers reconcile these CRDs alongside InferencePool and Pod resources from the Gateway API inference extension to maintain an in-memory datastore of available endpoints and their metrics. The EPP uses this datastore to make real-time routing decisions during Envoy's external processing callout flow. [source: apix/config/v1alpha1/endpointpickerconfig_types.go:33, config/crd/bases/llm-d.ai_inferencemodelrewrites.yaml:1, config/crd/bases/llm-d.ai_inferenceobjectives.yaml:1, pkg/epp/controller/pod_reconciler.go:54]

## Architectural Analysis

llm-d-router follows a plugin-based processing pipeline architecture. The EPP's request handling is organized into a framework of composable plugins that operate across four phases: request control (scheduling, flow control), data production (metrics scraping, tokenization, latency prediction), data layer (Redis, in-memory, and HTTP-based caching), and parsing (OpenAI-compatible request/response parsing). An EndpointPickerConfig CRD drives plugin selection and parameterization at runtime, allowing operators to tune scheduling behavior without redeployment. [source: apix/config/v1alpha1/endpointpickerconfig_types.go:33, pkg/epp/server/runserver.go:233]

The component ships three distinct binaries: `epp` (the main Envoy ExtProc service on port 9002), `coordinator` (multi-EPP coordination with health and metrics endpoints), and `pd-sidecar` (a per-pod DNS proxy that intercepts model server traffic for NIXL-aware KV-cache transfers). Each binary runs as a controller-runtime manager, sharing the same reconciler framework for CRD and Pod watches. [source: Dockerfile.konflux.epp:46-51, Dockerfile.konflux.sidecar:39, Dockerfile.coordinator:46]

TLS is configurable but not enforced by default on the gRPC ExtProc surface. When `--secure-serving` is enabled, the EPP loads certificates from a mounted path or generates self-signed certificates, with optional certificate reloading and configurable TLS minimum version and cipher suites. No application-level authentication interceptors are applied to the ExtProc or Health gRPC services; authentication is delegated to the network transport layer and upstream Envoy configuration. The metrics endpoint supports optional authentication and client-certificate verification via controller-runtime's metrics server. [source: pkg/epp/server/runserver.go:175-208, pkg/epp/server/options.go:115-124, internal/tls/tls.go:34]

The Konflux build pipeline enforces FIPS compliance through `GOEXPERIMENT=strictfipsruntime` and dynamic linking (`CGO_ENABLED=1`) against the UBI9 PQC minimal runtime image, which provides system OpenSSL. All cryptographic operations route through the Go FIPS runtime backed by the system crypto provider. [source: Dockerfile.konflux.epp:31-33, Dockerfile.konflux.sidecar:27-28]

No Kubernetes Service manifests are shipped in this repository. Service definitions for the EPP, coordinator, and sidecar are expected to be managed by the deploying operator (llm-d operator or RHOAI platform operator) rather than bundled with the component itself. [source: deploy/environments/kubernetes-base/openshift/route.yaml:1]

## Data Flows

- **Inference request routing:** Envoy forwards incoming LLM inference requests to the EPP via the External Processing gRPC API (default port 9002). The EPP inspects request headers and body, applies scheduling plugins to select a backend model server pod, and returns routing metadata to Envoy for upstream forwarding. When TLS is enabled via `--secure-serving`, the gRPC transport uses certificates loaded from disk or self-signed certificates generated at startup. [source: pkg/epp/server/runserver.go:238, pkg/epp/server/options.go:44, Dockerfile.konflux.epp:47]
- **Controller reconciliation:** Four controllers maintain an in-memory datastore by watching Kubernetes resources: PodReconciler tracks model server pods, InferencePoolReconciler watches pool configuration from the Gateway API inference extension, InferenceObjectiveReconciler monitors autoscaling objectives, and InferenceModelRewriteReconciler manages model alias mappings. All watches use controller-runtime's cached client against the kube-apiserver over TLS. [source: pkg/epp/controller/pod_reconciler.go:54, pkg/epp/controller/inferencepool_reconciler.go:79, pkg/epp/controller/inferenceobjective_reconciler.go:100, pkg/epp/controller/inferencemodelrewrite_reconciler.go:88]
- **Metrics and observability:** Each binary exposes a Prometheus `/metrics` endpoint. The EPP optionally exports distributed traces via OTLP/gRPC (default localhost:4317) or OTLP/HTTP (default localhost:4318) to a configured OpenTelemetry Collector, selectable via `OTEL_EXPORTER_OTLP_PROTOCOL` environment variable. [source: cmd/epp/runner/runner.go:1235, pkg/common/observability/tracing/telemetry.go:307, pkg/common/observability/tracing/telemetry.go:326-328]
- **Sidecar proxy:** The pd-sidecar intercepts DNS and HTTP traffic on model server pods to enable NIXL-aware KV-cache transfers between pods, proxying requests through a local HTTP listener. [source: pkg/sidecar/proxy/proxy.go:635, Dockerfile.konflux.sidecar:39]
