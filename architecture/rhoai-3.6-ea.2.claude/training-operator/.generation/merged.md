## Purpose

**Short**: Kubernetes operator that orchestrates distributed training jobs across six ML frameworks (PyTorch, TensorFlow, MPI, JAX, XGBoost, PaddlePaddle) via corresponding CRDs, with validating admission webhooks and OpenShift TLS profile integration. [source: manifests/base/crds, cmd/training-operator.v1/main.go:100-106]

**Detailed**: Training-operator manages the lifecycle of distributed machine learning training workloads on Kubernetes. It provides six custom resource definitions — PyTorchJob, TFJob, MPIJob, JAXJob, XGBoostJob, and PaddleJob — that abstract distributed training orchestration across their respective frameworks. Each job type has a dedicated reconciler that creates and manages worker pods, services, and supporting resources (ConfigMaps, ServiceAccounts, Roles, NetworkPolicies) for the training workload. The operator includes validating admission webhooks for all six job types, enforcing schema correctness at create and update time with a Fail policy. On OpenShift clusters, the operator reads the cluster-wide APIServer TLS profile (`config.openshift.io/v1/APIServer`) to align its webhook server TLS configuration with cluster policy, falling back to a hardened intermediate profile (TLS 1.2, AEAD cipher suites) on non-OpenShift environments. [source: cmd/training-operator.v1/main.go:100-137, manifests/base/webhook/patch.yaml:1] The Konflux build uses `GOEXPERIMENT=strictfipsruntime` and `CGO_ENABLED=1` for FIPS-compliant dynamic linking on a UBI9 base. [source: build/images/training-operator/Dockerfile.konflux:17] Prometheus metrics are exposed on port 8080 via service annotations. [source: manifests/base/service.yaml:5-7]

## Architectural Analysis

Training-operator follows the controller-runtime multi-reconciler pattern, with a dedicated controller for each of the six supported training frameworks (JAX, MPI, PaddlePaddle, PyTorch, TensorFlow, XGBoost). All reconcilers share common lifecycle patterns — creating worker pods, tracking replica status, and cleaning up resources on job completion — but framework-specific reconcilers handle unique semantics: MPIJobReconciler additionally manages ConfigMaps, ServiceAccounts, Roles, and RoleBindings to set up the MPI communication fabric; PyTorchJobReconciler supports HorizontalPodAutoscaler management for elastic training; and all reconcilers create per-job NetworkPolicies for workload isolation. [source: manifests/base/rbac/role.yaml:7-303, cmd/training-operator.v1/main.go:436-458]

The operator's TLS posture is notable: rather than accepting default Go TLS settings, it reads the OpenShift `config.openshift.io/v1/APIServer` resource to derive the cluster's TLS profile (cipher suites and minimum version), applying those constraints to its webhook server. On non-OpenShift clusters or when the APIServer resource is unavailable due to transient errors, it falls back to an intermediate profile with TLS 1.2 minimum and six AEAD cipher suites (AES-GCM and ChaCha20-Poly1305 variants). If a custom TLS profile specifies ciphers but none are supported by Go, the operator refuses to start. [source: cmd/training-operator.v1/main.go:100-172]

The webhook server listens on port 9443 (fronted by a ClusterIP Service on port 443) and implements five validating webhooks — one per supported framework excluding MPI — with a Fail policy that blocks non-conforming job submissions. The readiness probe deliberately waits for webhook certificate readiness before advertising the pod as ready, preventing early API requests from being rejected during startup. [source: cmd/training-operator.v1/main.go:448-458, manifests/base/service.yaml:17-19]

The operator integrates with two optional gang-scheduling systems — Volcano (`scheduling.volcano.sh`) and scheduler-plugins (`scheduling.x-k8s.io`) — managing PodGroup resources for coordinated scheduling of training worker replicas. RBAC grants are cluster-scoped, reflecting the operator's design to manage training jobs across all namespaces. [source: manifests/base/rbac/role.yaml:260-283]

## Data Flows

- **Job submission flow:** Users submit training job CRs (PyTorchJob, TFJob, MPIJob, JAXJob, XGBoostJob, PaddleJob) to the Kubernetes API. The validating admission webhooks intercept CREATE and UPDATE operations on port 9443 (via Service port 443) to enforce schema correctness before persistence. Each webhook uses a Fail policy, so malformed jobs are rejected at admission time. [source: manifests/base/webhook/patch.yaml:1, manifests/base/service.yaml:17-19]
- **Reconciliation loop:** The framework-specific reconciler watches its CRD and creates worker Pods, Services, and supporting resources (ConfigMaps, ServiceAccounts, Roles, RoleBindings for MPI; NetworkPolicies for all frameworks). The reconciler tracks replica status via Pod watches and updates the job CR status accordingly. PyTorchJobReconciler additionally manages HorizontalPodAutoscalers for elastic training. [source: manifests/base/rbac/role.yaml:7-303]
- **TLS configuration flow:** At startup, the operator reads the OpenShift `config.openshift.io/v1/APIServer` "cluster" resource via the Kubernetes API to derive the cluster TLS profile. The derived cipher suites and minimum TLS version are applied to the webhook server's TLS configuration. If the APIServer resource is not found (non-OpenShift), the operator applies a hardened intermediate profile. [source: cmd/training-operator.v1/main.go:100-137]
- **Observability:** Prometheus scrapes metrics from port 8080 via `prometheus.io/scrape: "true"` service annotations. Health and readiness probes are served on port 8081 at `/healthz` and `/readyz` respectively, with readyz gated on webhook certificate readiness. [source: manifests/base/service.yaml:5-7, cmd/training-operator.v1/main.go:436-458]
