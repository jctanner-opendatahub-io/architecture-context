## Purpose

**Short**: Asynchronous inference processor that consumes requests from message queue transports (Redis or Google Cloud Pub/Sub), dispatches them to model servers via HTTP, and returns results through the same messaging layer. [source: cmd/main.go:14, pkg/server/runner.go:43, pkg/server/options.go:106]

**Detailed**: llm-d-async is a Go-based asynchronous inference processing worker built on controller-runtime. It bridges message queue transports (Redis Pub/Sub, Redis Sorted Set, or Google Cloud Pub/Sub) with downstream model-serving endpoints. The processor subscribes to request queues, applies configurable merge policies and flow-control gates (including metric-based gating via Prometheus), and dispatches inference requests to model servers over HTTP with optional mTLS. It exposes health probes on port 8081 and authenticated Prometheus metrics on port 9090 via the controller-runtime metrics server. The component supports configurable worker pool concurrency, request body transforms via a plugin system, and hot-reload of queue configuration. It integrates with the gateway-api-inference-extension for flow-control primitives and exports OpenTelemetry traces for distributed observability. [source: cmd/main.go:14, pkg/server/runner.go:43-217, pkg/server/options.go:57-69, internal/health/health.go:33-49]

## Architectural Analysis

llm-d-async follows an event-driven worker architecture where a pluggable transport layer decouples request ingestion from inference dispatch. The transport abstraction (`pipeline.Flow`) unifies three backends — Redis Pub/Sub, Redis Sorted Set, and Google Cloud Pub/Sub — behind a common interface that surfaces request channels, retry channels, and result channels. Each transport is instantiated via a `--transport` flag with inline or file-based JSON configuration, and the Redis Sorted Set and GCP Pub/Sub transports support hot-reload of queue definitions at a configurable watch interval. [source: pkg/server/runner.go:290-331, pkg/server/options.go:105-108]

Worker concurrency is organized into named pools, each with an optional metric-based gate backed by Prometheus queries. Gates throttle dispatch based on real-time metrics (e.g., GPU utilization or queue depth), providing backpressure without blocking the transport layer. A request merge policy (defaulting to random-robin) governs how queued requests are distributed across pools. [source: pkg/server/runner.go:92-161, pkg/server/options.go:143]

The outbound inference path uses a standard `net/http` client instrumented with OpenTelemetry and wrapped in configurable TLS. When `--tls-ca-cert`, `--tls-cert`, and `--tls-key` are supplied, the client establishes mTLS connections to downstream inference gateways with a minimum TLS version of 1.2. The component does not terminate inbound TLS on its own HTTP servers (health and metrics). [source: pkg/server/runner.go:374-438, pkg/server/options.go:152-155]

The health server (port 8081) and metrics server (port 9090) are isolated from the inference data path. The metrics server delegates authentication and authorization to the controller-runtime `filters.WithAuthenticationAndAuthorization` middleware by default, which validates bearer tokens against the Kubernetes API server. This protects the Prometheus scrape endpoint without application-level auth code. [source: pkg/server/runner.go:334-371, pkg/server/options.go:96-98]

## Data Flows

- **Request ingestion:** The async processor subscribes to request queues via a pluggable transport layer (Redis Pub/Sub, Redis Sorted Set, or Google Cloud Pub/Sub). Incoming inference requests are delivered through message channels to a configurable merge policy that distributes them across named worker pools. [source: pkg/server/runner.go:105-141, pkg/server/options.go:105-108]
- **Inference dispatch:** Worker goroutines consume merged request channels and forward inference requests to downstream model servers via an HTTP client with optional mTLS. Flow-control gates backed by Prometheus metric queries throttle dispatch based on real-time conditions. Results and retry messages are routed back through the transport's result and retry channels. [source: pkg/server/runner.go:163-177, pkg/server/runner.go:374-392]
- **Observability surface:** Health probes (/healthz, /readyz) are served on port 8081 without authentication. Prometheus metrics are exposed on port 9090 with controller-runtime authentication and authorization. OpenTelemetry traces are exported via gRPC to a configurable collector. [source: internal/health/health.go:33-49, pkg/server/runner.go:334-371, pkg/server/runner.go:220-227]
- **Security context:** 3 authentication rules govern the API surface: health probes are unauthenticated by design, and the metrics endpoint is protected via Kubernetes API bearer token validation. The outbound inference client supports mTLS with configurable CA certificates and client certificates. [source: pkg/server/runner.go:353-361, pkg/server/runner.go:410-438]
