## Purpose

**Short**: Python SDK for submitting and managing distributed compute workloads on Kubernetes via KubeRay and Kueue, providing a simplified client interface for RayJob and RayCluster custom resources. [source: pyproject.toml:2, 8, src/codeflare_sdk/ray/rayjobs/rayjob.py:17, src/codeflare_sdk/ray/client/ray_jobs.py:16-18]

**Detailed**: CodeFlare SDK is a Python client library that enables data scientists and developers to submit, monitor, and manage distributed compute workloads on OpenShift and Kubernetes clusters. The SDK wraps the KubeRay operator's RayJob and RayCluster custom resources through a vendored KubeRay Python client (`kuberay_job_api.RayjobApi`, `kuberay_cluster_api.RayClusterApi`), providing a simplified interface for creating managed Ray clusters with Kueue-based queue scheduling and priority class support. [source: src/codeflare_sdk/ray/rayjobs/rayjob.py:27-35, 58-64]

The SDK also exposes a `RayJobClient` wrapper around Ray's `JobSubmissionClient` for direct HTTP-based job submission to existing Ray Dashboard endpoints, with configurable TLS verification, headers, and cookies for authentication. Kubernetes authentication is handled through `kube-authkit` with auto-detection of kubeconfig and in-cluster credentials, with deprecated legacy classes (`TokenAuthentication`, `KubeConfigFileAuthentication`) still supported for backward compatibility. [source: src/codeflare_sdk/ray/client/ray_jobs.py:20-67, src/codeflare_sdk/common/kubernetes_cluster/auth.py:30-31, 225-268]

## Architectural Analysis

CodeFlare SDK operates as a client-side Python library rather than a deployed service, meaning it runs within the user's environment (notebooks, workbench pods, or local machines) and authenticates outward to the Kubernetes API server. The architecture provides two distinct job submission paths: a CRD-based path that creates RayJob custom resources managed by the KubeRay operator with optional Kueue integration for queue scheduling, and a direct HTTP path that connects to Ray Dashboard endpoints via `JobSubmissionClient` for clusters not managed through KubeRay. [source: src/codeflare_sdk/ray/rayjobs/rayjob.py:58-64, src/codeflare_sdk/ray/client/ray_jobs.py:25-67]

The authentication layer is transitioning from legacy token and kubeconfig classes to `kube-authkit`, a shared OpenDataHub library for unified Kubernetes authentication. The `config_check()` function implements a priority chain: existing client → kube-authkit auto-detection → legacy kubeconfig/in-cluster fallback. Custom CA certificate paths are resolved through explicit parameter, `CF_SDK_CA_CERT_PATH` environment variable, or the OpenShift workbench default at `/etc/pki/tls/custom-certs/ca-bundle.crt`. [source: src/codeflare_sdk/common/kubernetes_cluster/auth.py:225-291, 316-325]

The SDK vendors the KubeRay Python client (`python-client`) directly rather than declaring it as an external dependency, coupling it to a specific KubeRay API version. This vendoring pattern avoids PyPI version conflicts but requires manual synchronization with upstream KubeRay releases. The `cryptography` library is used for generating self-signed TLS certificates (RSA 3072-bit, x509) for Ray cluster internal communication, relying on the platform's OpenSSL backend rather than implementing custom cryptographic primitives. [source: src/codeflare_sdk/vendored/pyproject.toml:2, src/codeflare_sdk/common/utils/generate_cert.py:21-24, 56-59, pyproject.toml:41]

## Data Flows

- **CRD-based job submission (KubeRay path):** The SDK authenticates to the Kubernetes API server via `kube-authkit` (Bearer token, kubeconfig, or in-cluster service account), then creates RayJob custom resources through the vendored KubeRay Python client (`RayjobApi`). The KubeRay operator reconciles these CRs into Ray cluster pods. When Kueue integration is enabled, the SDK annotates the RayJob CR with a local queue name and optional priority class, delegating scheduling to the Kueue controller. [source: src/codeflare_sdk/ray/rayjobs/rayjob.py:27-35, 43, 66-78, src/codeflare_sdk/common/kubernetes_cluster/auth.py:225-268]
- **Direct job submission (Ray Dashboard path):** The `RayJobClient` wrapper connects directly to a Ray Dashboard HTTP endpoint, bypassing KubeRay CRDs. Authentication is caller-configured via HTTP headers and cookies parameters, with TLS verification enabled by default. This path is used for submitting jobs to existing Ray clusters not managed by the SDK. [source: src/codeflare_sdk/ray/client/ray_jobs.py:20-67]
- **Certificate generation:** The SDK generates self-signed CA and server certificates (RSA 3072-bit) using the `cryptography` library for securing Ray cluster internal TLS communication. Certificates are stored as Kubernetes Secrets via the Kubernetes API client. [source: src/codeflare_sdk/common/utils/generate_cert.py:21-24, 35-59]
- **Security context:** RBAC roles for Kueue and Ray CRD operations are defined in test infrastructure manifests. The SDK itself does not deploy RBAC resources in production; it relies on the user's existing Kubernetes credentials and cluster-level RBAC policies. [source: images/tests/rbac-test-user-permissions.yaml:58, 93, 127]
