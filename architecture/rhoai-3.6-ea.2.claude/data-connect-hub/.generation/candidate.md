## Purpose

**Short**: Data Connect Hub is a Kubernetes operator that manages data connection lifecycle, deploying Rust-based REST and Arrow Flight services with kube-rbac-proxy authentication to provide a unified API for creating, testing, and exporting data connections across multiple backend systems. [source: dc-controller/cmd/main.go:197-243, services/rest/src/main.rs:42-69]

**Detailed**: Data Connect Hub consists of a Go controller-runtime operator (`dc-controller`) and a suite of Rust services that together provide a managed data connectivity layer for the RHOAI platform. The operator reconciles three custom resources — DataConnectService, InitDataConnection, and InitDataConnectionType — to deploy and configure REST and Arrow Flight service pods with kube-rbac-proxy sidecars for token-based authentication. [source: dc-controller/cmd/main.go:197-243, dc-controller/internal/controller/dataconnectservice_controller.go:354-367]

The REST service (actix-web) exposes a tenant-scoped CRUD API for connection types and connections under `/api/{version}/data/*`, enforcing tenant isolation via a required `X-Tenant-ID` header middleware. The Flight service provides Apache Arrow Flight protocol access for high-throughput data transfer. Backend connectivity is implemented through a pluggable connector architecture with support for PostgreSQL, Elasticsearch, Milvus, Neo4j, S3, SQLite, and URI-based sources. The operator manages Gateway API HTTPRoute resources to expose services through the platform's ingress infrastructure. [source: services/rest/src/main.rs:42-69, services/rest/src/rest/middleware.rs:16-57, dc-controller/internal/controller/dataconnectservice_controller.go:340-372]

## Architectural Analysis

Data Connect Hub follows a two-tier architecture: a Go operator tier that manages lifecycle and platform integration, and a Rust services tier that handles data operations and API serving.

**Operator tier.** The `dc-controller` operator uses controller-runtime with five reconcilers. The primary `DataConnectServiceReconciler` renders Kustomize manifests to deploy REST service, Flight service, and kube-rbac-proxy containers as Deployments in the CR's namespace. It also manages ConfigMaps, Services, ServiceAccounts, NetworkPolicies, and Gateway API HTTPRoutes as owned resources. The `InitDataConnectionTypeReconciler` and `ConfigMapWatcherReconciler` both use HTTP clients to communicate with the deployed REST service for connection-type synchronization, while the `SecretWatcherReconciler` uses a migration HTTP client to propagate secret changes. Leader election is configured via Lease resources. [source: dc-controller/cmd/main.go:173-243, dc-controller/internal/controller/dataconnectservice_controller.go:340-372]

**Services tier.** The REST service is built on actix-web and exposes tenant-scoped CRUD endpoints for data connections and connection types. All data API routes are gated by a `validate_headers` middleware that requires a non-empty `X-Tenant-ID` header and optionally extracts the `Authorization` header for downstream passthrough. The Flight service provides Arrow Flight protocol access with Prometheus metrics. Both services are fronted by kube-rbac-proxy sidecars that perform Kubernetes TokenReview-based authentication with configurable audiences. [source: services/rest/src/main.rs:42-69, services/rest/src/rest/middleware.rs:16-57, dc-controller/internal/controller/dataconnectservice_controller.go:354-367]

**Platform integration.** The operator reads OpenShift Ingress configuration (`config.openshift.io/v1/Ingress`) and IngressController resources (`operator.openshift.io/v1/IngressController`) to determine the cluster's routing domain, and resolves Gateway API Gateway resources for HTTPRoute creation. RBAC is tiered: a `manager-role` ClusterRole grants the operator broad resource management permissions, while `admin`, `editor`, and `viewer` ClusterRoles provide graduated access to DataConnectService resources for platform users. [source: dc-controller/internal/controller/dataconnectservice_controller.go:530-538, dc-controller/config/rbac/role.yaml:2]

**Cryptographic posture.** The Rust services use rustls with `aws_lc_rs` as the explicitly selected cryptographic provider (`default-features = false, features = ["aws_lc_rs"]`). The `ring` crate is present as a transitive dependency in `Cargo.lock` but is not the selected provider for rustls. FIPS validation requires the `fips` feature on aws-lc-rs and a FIPS-validated build of aws-lc, neither of which are configured in the current Cargo.toml; FIPS compliance status is therefore not verified. [source: Cargo.toml:78, Cargo.toml:76]

| Step | Source | Destination | Port | Protocol | Encryption | Auth |
|------|--------|-------------|------|----------|------------|------|

| 2 | Kubernetes API | dc-controller-manager | N/A | Watch event | TLS 1.2+ | ServiceAccount |
