## Purpose

**Short**: GitOps configuration repository packaging Helm charts and Kustomize overlays for installing RHOAI platform dependencies and operator configurations on OpenShift and non-OpenShift Kubernetes clusters. [source: charts/rhai-on-openshift-chart/Chart.yaml:3, charts/rhai-on-xks-chart/Chart.yaml:3]

**Detailed**: odh-gitops is a declarative configuration repository that provides two primary Helm charts for deploying Red Hat AI (RHAI) platform prerequisites. The `rhai-on-openshift-chart` packages operator subscriptions and configurations for OpenShift-based deployments via OLM, while the `rhai-on-xks-chart` targets non-OpenShift Kubernetes services (AWS EKS, Azure AKS, CoreWeave) where OLM is unavailable, bundling operator installations directly as Helm sub-charts. The repository also maintains a parallel Kustomize structure under `components/`, `configurations/`, and `dependencies/` that installs and configures platform-level operators including Kueue, JobSet, LeaderWorkerSet, cert-manager, RHCL (Kuadrant/Authorino), observability stack (OpenTelemetry, Tempo), and GPU-related operators (NFD, NVIDIA). The upstream source is `opendatahub-io/odh-gitops`, synced downstream via auto-merge with a `helm-sync.yml` workflow. [source: kustomization.yaml:4-5, dependencies/operators/kustomization.yaml:4-17, charts/rhai-on-xks-chart/Chart.yaml:3-4]

## Architectural Analysis

odh-gitops follows a dual-packaging strategy that reflects the divergent installation models between OpenShift and vanilla Kubernetes. On OpenShift, operators are installed through OLM Subscriptions and then configured via custom resources; the Kustomize tree under `components/operators/` and `configurations/` handles this by composing operator subscriptions and post-install configuration (e.g., the Kuadrant CR and Authorino CR for API gateway authentication). On non-OpenShift clusters, the `rhai-on-xks-chart` Helm chart embeds dependency operators (cert-manager, RHCL/Kuadrant, Sail/Istio, Gateway API CRDs, LeaderWorkerSet) as sub-charts, since OLM is not available to manage their lifecycle.

The authentication architecture is centered on Kuadrant and Authorino. The Authorino CR is deployed cluster-wide in the `kuadrant-system` namespace with TLS enabled on the listener (using a `authorino-server-cert` secret) but OIDC server TLS disabled. This positions Authorino as the central authorization enforcement point for RHOAI service mesh traffic. The optional `tls-enabled` overlay adds the Authorino CR with explicit TLS listener configuration, providing a layered security posture.

The repository does not contain runtime application code, container builds, or service binaries. As a pure GitOps configuration artifact, FIPS compliance and HTTP endpoints are not directly applicable — those concerns are delegated to the individual operator and service component repositories whose deployments this repository orchestrates. The dependency graph is intentionally broad: the repository provisions the foundational operator layer (scheduling via Kueue/JobSet/LeaderWorkerSet, networking via Sail/Gateway API, security via cert-manager/RHCL, observability via OpenTelemetry/Tempo) that other RHOAI components depend on at runtime.
