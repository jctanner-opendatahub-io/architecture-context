## Purpose

**Short**: Kubernetes operator that manages distributed training workloads on RHOAI through TrainJob, TrainingRuntime, and ClusterTrainingRuntime CRDs, orchestrating JobSet-based distributed jobs with pluggable gang-scheduling support. [source: cmd/trainer-controller-manager/main.go:74, manifests/base/crds/trainer.kubeflow.org_trainjobs.yaml:16, manifests/base/crds/trainer.kubeflow.org_trainingruntimes.yaml:16]

**Detailed**: The trainer component is a controller-runtime operator that implements the Kubeflow Trainer v2 API for RHOAI. It defines three core CRDs -- TrainJob (namespaced workload submission), TrainingRuntime (namespaced runtime templates), and ClusterTrainingRuntime (cluster-scoped shared templates) -- plus a Configuration CRD for operator settings. The controller reconciles TrainJobs into downstream JobSet resources for distributed execution, with pluggable runtime framework plugins for Flux, MPI, CoScheduling (scheduler-plugins), and Volcano gang-scheduling backends. Admission webhooks validate and default TrainJob and runtime resources with a Fail policy. The operator also manages per-TrainJob NetworkPolicies for workload network isolation and tracks training progression status through pod inspection. TLS configuration for webhook and metrics servers is dynamically resolved from the OpenShift TLSSecurityProfile, falling back to hardened Intermediate defaults. Python initializer containers for dataset and model preparation are shipped alongside the Go controller. ## Architectural Analysis

The trainer operator follows a plugin-based runtime framework architecture. The controller manager registers schemes for its own CRDs alongside JobSet, scheduler-plugins PodGroups, and Volcano PodGroups at startup, then initializes a runtime map that resolves TrainJob specs into concrete distributed training configurations. Each scheduling backend (Flux for basic workloads, MPI for message-passing, CoScheduling and Volcano for gang scheduling) is implemented as a framework plugin that watches its own ancillary resources -- ConfigMaps and Secrets for Flux/MPI, PodGroup CRDs for the scheduler backends. [source: cmd/trainer-controller-manager/main.go:65-72, pkg/runtime/framework/plugins/flux/flux.go:244, pkg/runtime/framework/plugins/coscheduling/coscheduling.go:270, pkg/runtime/framework/plugins/volcano/volcano.go:343]

The RHOAI distribution adds several operational capabilities on top of the upstream Kubeflow Trainer. A NetworkPolicy reconciler creates per-TrainJob ingress policies scoped by `jobset.sigs.k8s.io/jobset-name` labels, providing workload-level network isolation. A progression tracker lists training pods by namespace and label selectors to identify the primary/launcher pod for status reporting. The operator reads the OpenShift `config.openshift.io/v1/apiservers` resource to resolve the cluster TLSSecurityProfile, applying the resulting cipher suites and minimum TLS version to both the webhook and metrics servers. When the OpenShift API is unavailable, it falls back to a hardened Intermediate profile with ECDHE+AES-GCM and CHACHA20-POLY1305 ciphers at TLS 1.2 minimum. [source: pkg/rhai/networkpolicy.go:39-49, pkg/rhai/networkpolicy.go:152-180, pkg/rhai/progression/progression.go:130-168, pkg/tls/tls.go:39-60, pkg/tls/tls.go:88-134]

Certificate management is optionally handled by the OPA cert-controller (`github.com/open-policy-agent/cert-controller`), which rotates webhook certificates and updates the webhook configurations. The readiness probe gates on both certificate readiness and the webhook server's started state, ensuring that admission requests are not served before TLS is established. The operator exposes three service ports -- webhook (443), metrics (8443), and status-server (10443) -- all internal to the cluster. User-facing RBAC is tiered through training-view, training-edit, and training-admin ClusterRoles, while a public ConfigMap role provides read access to authenticated users for runtime discovery. ## Data Flows

- **Training workload submission:** Users create TrainJob CRs referencing a TrainingRuntime or ClusterTrainingRuntime. The mutating webhook defaults unset fields, and validating webhooks enforce schema and semantic constraints. The controller resolves the runtime reference, selects the appropriate framework plugin, and creates a downstream JobSet with the computed pod templates, volumes, and scheduling directives. - **Distributed execution orchestration:** Each framework plugin manages its own ancillary Kubernetes resources. The Flux and MPI plugins watch ConfigMaps and Secrets for per-job configuration and credentials. CoScheduling and Volcano plugins create and watch PodGroup CRDs to coordinate gang scheduling. The controller reconciles JobSet status back onto the TrainJob status. - **RHOAI operational flows:** The NetworkPolicy reconciler creates ingress rules scoped to each TrainJob's JobSet pods, and the progression tracker polls training pod status to update TrainJob status conditions. The operator reads the OpenShift APIServer resource at startup to configure TLS for its webhook (port 443), metrics (port 8443), and status-server (port 10443) endpoints. - **Security surface:** Health and readiness probes on port 8081 are unauthenticated by design. Webhook and metrics endpoints use TLS derived from the cluster TLSSecurityProfile.
