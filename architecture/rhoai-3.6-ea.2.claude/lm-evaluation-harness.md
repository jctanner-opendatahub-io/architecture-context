## Purpose

**Short**: Batch-oriented Python framework for evaluating language models, packaged as a container job image for the RHOAI LMEval evaluation pipeline. [source: Dockerfile.konflux.lmes-job:47-49, pyproject.toml:6, 11, 57]

**Detailed**: lm-evaluation-harness is a downstream fork of the EleutherAI lm-evaluation-harness framework, adapted for Red Hat OpenShift AI. It provides a standardized runtime for one-shot language model evaluations, integrating the Unitxt framework for task definitions and supporting multiple model backends including local HuggingFace Transformers, OpenAI-compatible APIs, Anthropic, IBM WatsonX, and vLLM. The component is packaged as a container image (`odh-ta-lmes-job-rhel9`) designed to run as a Kubernetes batch Job, created and managed by the trustyai-service-operator (LMES operator). It does not expose HTTP endpoints or Kubernetes Services; instead, it consumes model inference APIs as an outbound client, authenticating via environment-variable API keys. The repository ships two Dockerfile variants: `Dockerfile.konflux.lmes-job` for Konflux CI with parameterized CUDA/CPU base images, and `Dockerfile.lmes-job` for development builds based on UBI9 Python 3.11. [source: Dockerfile.konflux.lmes-job:1-50, Dockerfile.lmes-job:1-6, 234, pyproject.toml:6, 19, 57, lm_eval/models/openai_completions.py:104, lm_eval/models/anthropic_llms.py:178-179, lm_eval/models/ibm_watsonx_ai.py:60-63]

## Architectural Analysis

lm-evaluation-harness follows a batch-job architecture pattern: the trustyai-service-operator creates Kubernetes Jobs using the `odh-ta-lmes-job-rhel9` container image, which runs `lm-eval` evaluations to completion and writes results to a configured output path. The harness itself is stateless—it receives evaluation parameters at invocation, executes benchmark tasks against a target model, and exits. This design delegates lifecycle management, scheduling, and result collection entirely to the platform operator.

The model backend abstraction is the central architectural pattern. Each backend (local HuggingFace, OpenAI-compatible, Anthropic, WatsonX, vLLM) is a registered model class inheriting from a common `LM` or `TemplateAPI` base. Authentication is handled per-backend through environment variables (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `WATSONX_API_KEY`, `HF_TOKEN`), with no centralized credential management within the harness. This means the operator must inject the correct secrets into the Job's environment for each evaluation target. [source: lm_eval/models/openai_completions.py:104, lm_eval/models/anthropic_llms.py:178-179, lm_eval/models/ibm_watsonx_ai.py:59-63, lm_eval/__main__.py:307-308]

The Konflux build (`Dockerfile.konflux.lmes-job`) uses parameterized base images (`CUDA_BASE_IMAGE`, `CPU_BASE_IMAGE`) selected per target architecture (amd64/arm64 use CUDA, ppc64le/s390x use CPU), enabling multi-architecture builds with GPU acceleration where available. The development build (`Dockerfile.lmes-job`) uses a multi-stage approach starting from UBI9 Python 3.11, compiling architecture-specific dependencies (PyArrow, Torch) from source for s390x and ppc64le. Both images run as non-root user (UID 65532) and set up writable directories for HuggingFace cache, output, and custom task definitions. [source: Dockerfile.konflux.lmes-job:1-9, 41, Dockerfile.lmes-job:1-6, 233-234]

The `eval-hub-sdk[adapter]` dependency (constrained to `~=1.0.0`) connects the harness to the RHOAI evaluation hub, though the SDK integration is at the library level rather than a runtime service call. External integrations include S3-compatible storage via boto3 for dataset and artifact management, and the HuggingFace datasets server for benchmark data retrieval.
