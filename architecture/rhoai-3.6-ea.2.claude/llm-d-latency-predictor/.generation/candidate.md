## Purpose

**Short**: llm-d-latency-predictor provides online ML-based latency prediction for llm-d inference workloads, using a two-server architecture (training + prediction) with XGBoost/LightGBM models for TTFT and TPOT estimation. [source: prediction/prediction_server.py:28-29, training/training_server.py:31, Dockerfile.konflux.prediction:19, Dockerfile.konflux.training:14]

**Detailed**: llm-d-latency-predictor is a Python FastAPI application comprising two cooperating servers: a **training server** (port 8000) that collects inference telemetry data, trains XGBoost and LightGBM regression models for Time To First Token (TTFT) and Time Per Output Token (TPOT) prediction, and serves trained model artifacts; and a **prediction server** (port 8001) that periodically syncs trained models from the training server and serves low-latency prediction requests. The prediction server supports single, bulk, and strict-bulk prediction modes, with configurable quantile regression objectives and optional queue-gated ensemble models. Both servers are deployed as Kubernetes Deployments with dedicated ClusterIP Services, using AIPCC CPU base images and uvicorn as the ASGI transport. The component exposes 24 HTTP endpoints across the two servers and uses no authentication middleware. [source: prediction/prediction_server.py:28-29, 64-100, training/training_server.py:31, 64-100, deploy/base/prediction/service.yaml:2, deploy/base/training/service.yaml:2]

## Architectural Analysis

llm-d-latency-predictor follows a two-pod microservice pattern where the training server acts as the stateful model factory and the prediction server acts as the stateless inference front-end. The prediction server maintains a background `ModelSyncer` thread that polls the training server at a configurable interval (`MODEL_SYNC_INTERVAL_SEC`, default 10s) to download updated model artifacts via HTTP, comparing server-side timestamps against local file modification times before downloading. This polling-based model distribution avoids the need for shared persistent storage or a model registry, though it creates a runtime dependency on the training server's availability during model refresh cycles. [source: prediction/prediction_server.py:68, 132-179, 1189-1199]

Both servers use FastAPI with ORJSONResponse for high-throughput JSON serialization and expose health/readiness probes at `/healthz` and `/readyz`. The prediction server supports three prediction modes — single (`/predict`), bulk (`/predict/bulk`), and strict-bulk (`/predict/bulk/strict`) — with configurable quantile regression via XGBoost or LightGBM estimators. An ensemble mode enables queue-gated models that split predictions by whether requests are queued or unqueued. [source: prediction/prediction_server.py:29, 76-79, 87, 997, 1017, 1070]

The component has no authentication middleware on either server. All 24 HTTP endpoints are exposed without token validation, bearer authentication, or any request-level authorization checks. Platform-level network isolation (e.g., NetworkPolicy, Service mesh) would be the expected enforcement boundary for production deployments. [source: prediction/prediction_server.py:28-29, training/training_server.py:31]

Both Konflux Dockerfiles use the AIPCC CPU base image (`quay.io/aipcc/base-images/cpu:3.5.0`), inheriting the RHEL AI Python environment with system OpenSSL. The prediction server uses `hashlib.md5()` for file integrity checksums during model sync, which is not a security-critical use but may raise warnings in strict FIPS audits. [source: Dockerfile.konflux.prediction:1, Dockerfile.konflux.training:1, prediction/prediction_server.py:15, 125]

## Data Flows

- **Telemetry ingestion:** External clients (llm-d inference proxies or monitoring systems) POST inference telemetry data to the training server at `/add_training_data_bulk` (port 8000). The training server accumulates this data in memory, partitioned by model, and periodically retrains TTFT and TPOT regression models using XGBoost or LightGBM. [source: training/training_server.py:31, 64-100, 1870]
- **Model distribution:** The prediction server's `ModelSyncer` background thread periodically polls the training server via HTTP at `TRAINING_SERVER_URL` (default `http://training-service:8000`). It queries `/model/{name}/info` for last-modified timestamps and downloads updated model artifacts from `/model/{name}/download` when the server has a newer version. Downloaded models are written to local disk paths and loaded by the predictor. [source: prediction/prediction_server.py:68, 155-179, 1189-1199]
- **Prediction serving:** Clients POST prediction requests to the prediction server at `/predict`, `/predict/bulk`, or `/predict/bulk/strict` (port 8001). The server applies the synced ML models to estimate TTFT and TPOT latency for given request parameters. No authentication is enforced at either the training or prediction entry points. [source: prediction/prediction_server.py:997, 1017, 1070, deploy/base/prediction/service.yaml:2]
- **Observability:** The training server exposes a Prometheus-compatible `/metrics` endpoint (port 8000) and both servers provide `/healthz` and `/readyz` probes for Kubernetes liveness and readiness checks. [source: training/training_server.py:1970, prediction/prediction_server.py:1159, 1164, deploy/base/prediction/deployment.yaml:2, deploy/base/training/deployment.yaml:2]
