## Purpose

**Short**: Kubernetes operator that manages Apache Spark application lifecycle through SparkApplication, ScheduledSparkApplication, and SparkConnect CRDs, handling driver/executor pod creation, scheduling, monitoring, and webhook-based validation and mutation. [source: Dockerfile.konflux:25, cmd/operator/main.go:44, spark-operator-module/pkg/apis/v1alpha1/types.go:26]

**Detailed**: spark-operator automates Apache Spark workload management on OpenShift. It provides three custom resource APIs: SparkApplication for one-time Spark jobs, ScheduledSparkApplication for cron-scheduled Spark workloads, and SparkConnect for Spark Connect server deployments. The operator runs as two Kubernetes Deployments — a controller that reconciles these CRDs into driver pods, executor pods, services, and supporting resources, and a webhook server that validates and mutates SparkApplication submissions and injects Spark configuration into pods via admission webhooks with failurePolicy=Fail. In RHOAI, the operator is deployed through the spark-operator-module, an ODH platform module controller that manages the full operator lifecycle including CRDs, RBAC, cert-manager Certificates, and NetworkPolicies. The module implements the `common.PlatformObject` interface from odh-platform-utilities, enabling the ODH Operator to manage SparkOperator instances through the `components.platform.opendatahub.io/v1alpha1` API. TLS is enforced on webhook endpoints via cert-manager-provisioned certificates, and the operator respects the cluster-wide OpenShift TLS security profile for cipher suite and minimum version configuration. [source: spark-operator-module/pkg/apis/v1alpha1/types.go:7-18, pkg/tls/profile.go:49, Dockerfile.konflux:25]

## Architectural Analysis

spark-operator follows a dual-deployment architecture with a controller and webhook server running as separate Kubernetes Deployments, each with its own service account and RBAC scope. The controller reconciles SparkApplication, ScheduledSparkApplication, and SparkConnect resources, creating and managing driver/executor pods, services, ConfigMaps, PodDisruptionBudgets, and Ingress resources. The webhook server runs seven admission webhooks — four mutating (pods, SparkApplication, ScheduledSparkApplication, SparkConnect) and three validating — all with `failurePolicy: Fail`, ensuring that misconfigured Spark submissions are rejected before pod creation. A conversion webhook handles CRD version migration for ScheduledSparkApplication resources. [source: config/webhook/webhook-validating-selector-patch.yaml:9, internal/webhook/sparkapplication_validator.go:37, internal/webhook/sparkpod_defaulter.go:43]

The RHOAI-specific module controller (spark-operator-module) adds a second management layer. It watches the cluster-scoped SparkOperator CR (singleton named `default-sparkoperator`) and reconciles the complete operator stack — deployments, RBAC roles and bindings, CRDs, webhook configurations, services, NetworkPolicies, and cert-manager Certificates/Issuers. This two-tier controller pattern (platform module → operator → workload) is consistent with the ODH modular operator architecture. The SparkOperator type implements `common.PlatformObject` from odh-platform-utilities, providing a uniform status/conditions/release interface that the ODH Operator uses for lifecycle coordination across all platform components. [source: spark-operator-module/pkg/apis/v1alpha1/types.go:15-18, spark-operator-module/go.mod:8]

Authentication follows standard Kubernetes patterns: webhook endpoints are secured via TLS certificates provisioned by cert-manager, and all Kubernetes API interactions use ServiceAccount tokens with RBAC enforcement. The operator reads the OpenShift APIServer TLS profile (`config.openshift.io/v1 APIServer`) at startup to align its TLS configuration with cluster security policy, falling back to an Intermediate profile (TLS 1.2 with AEAD cipher suites) when the profile is unavailable or on non-OpenShift clusters. Health and readiness probes on port 8081 are intentionally unauthenticated. The webhook RBAC limits secret access to only the named `spark-operator-webhook-certs` secret via resourceNames restriction. [source: pkg/tls/profile.go:49-112, pkg/tls/tls.go:26-51, config/webhook/role.yaml:1]

FIPS compliance is enforced at build time through `GOEXPERIMENT=strictfipsruntime` and `CGO_ENABLED=1` in the Konflux Dockerfile, ensuring the Go binary uses the system OpenSSL for cryptographic operations rather than Go's pure-Go crypto. The AIPCC base image provides the FIPS-validated OpenSSL library. At the application level, the operator's TLS configuration uses only AEAD cipher suites (AES-GCM, ChaCha20-Poly1305) and delegates cipher selection to the cluster TLS profile when available. [source: Dockerfile.konflux:25, pkg/tls/profile.go:160-167]

## Data Flows

- **SparkApplication submission flow:** Users create SparkApplication CRs → mutating webhooks inject defaults (SparkApplicationDefaulter, SparkPodDefaulter) → validating webhooks check field constraints and ResourceQuota compliance → the SparkApplication controller reconciles the CR by creating driver pods, executor pods, services, ConfigMaps for monitoring, and optional PodDisruptionBudgets → the controller monitors pod lifecycle through watches and updates CR status/finalizers. ScheduledSparkApplication follows the same path but adds cron-triggered SparkApplication creation. [source: internal/webhook/sparkapplication_defaulter.go:30, internal/webhook/sparkapplication_validator.go:37, internal/controller/sparkapplication/controller.go:284, internal/controller/sparkapplication/monitoring_config.go:50]
- **Module lifecycle flow:** ODH Operator creates a cluster-scoped SparkOperator CR → spark-operator-module reconciles by deploying the controller and webhook Deployments, RBAC (ClusterRoles, ClusterRoleBindings, Roles, RoleBindings), CRDs, cert-manager Certificate/Issuer resources, Services, and NetworkPolicies → cert-manager provisions TLS certificates for webhook endpoints → the module controller monitors child deployment health and updates SparkOperator status through the `common.PlatformObject` interface. [source: spark-operator-module/pkg/apis/v1alpha1/types.go:15-18, spark-operator-module/pkg/sparkoperatormodule/setup.go:22-32]
- **Webhook TLS flow:** cert-manager issues TLS certificates to the `spark-operator-webhook-certs` Secret (access restricted by RBAC resourceNames) → webhook deployment mounts certificates at `/etc/k8s-webhook-server/serving-certs` → at startup, both controller and webhook read the OpenShift TLS profile from `config.openshift.io/v1 APIServer` resource → TLS options (minimum version, cipher suites) are applied to webhook and metrics HTTPS listeners, defaulting to Intermediate profile (TLS 1.2, AEAD ciphers) when the cluster profile is unavailable. [source: pkg/tls/profile.go:49-112, config/webhook/role.yaml:1, Dockerfile.konflux:81]
- **Egress:** All Kubernetes API interactions use in-cluster ServiceAccount tokens over HTTPS/WSS to port 6443, with RBAC scoped to the operator's required resource set. The operator creates no external egress beyond the Kubernetes API server. [source: cmd/operator/controller/start.go:345]
