**Detailed**: MLflow is deployed as a tracking server within Red Hat OpenShift AI, packaging the upstream MLflow Python library with a Node.js web UI into a container image that runs on port 5000 via gunicorn/uvicorn. The server is configured with the `kubernetes-auth` authentication plugin (from `mlflow-kubernetes-plugins==1.5.0`), workspace support via Kubernetes namespace isolation (`--enable-workspaces --workspace-store-uri kubernetes://`), and artifact serving (`--serve-artifacts`). The component exposes 48 HTTP endpoints spanning the tracking API, model registry, AI gateway proxy, MCP server, assistant API, and job execution. External integrations include AWS S3-compatible storage (via boto3), Google Cloud Storage, and AI provider APIs (OpenAI, Bedrock). The Kubernetes Python client enables MLflow project execution as Kubernetes Jobs via `BatchV1Api`. The repository follows a three-tier lineage from upstream MLflow through opendatahub-io to the downstream red-hat-data-services fork. ## Architectural Analysis

MLflow is deployed as a multi-function tracking server built on Flask and FastAPI, served via gunicorn or uvicorn behind a UBI 9 container. The container entrypoint (`Dockerfile.konflux:CMD`) starts `mlflow server` on port 5000 with three key deployment flags: `--app-name kubernetes-auth` loads the `kubernetes-auth` authentication plugin from the externally packaged `mlflow-kubernetes-plugins==1.5.0` wheel, `--enable-workspaces` activates per-namespace workspace isolation, and `--serve-artifacts` enables the artifact proxy. [source: Dockerfile.konflux:80, requirements/konflux-pypi.in:13]

Authentication is handled at two layers. Server-side, the `kubernetes-auth` app plugin is resolved via `_find_app()` which queries `mlflow.app` entry points at startup. Client-side, the `KubernetesRequestAuthProvider` injects Kubernetes service account bearer tokens from `/var/run/secrets/kubernetes.io/serviceaccount/token` (or kubeconfig) into the `Authorization` header, with an optional `X-MLFLOW-WORKSPACE` header derived from the pod namespace for workspace-scoped operations. Tokens are cached with a 60-second TTL. [source: mlflow/server/__init__.py:218-226, mlflow/tracking/request_auth/kubernetes_request_auth_provider.py:39-42, 137-141, 203-258]

The 48 HTTP endpoints span several functional domains: core tracking and model registry APIs under `/ajax-api/`, AI gateway proxy routes at `/gateway/` and `/v1/` that forward to upstream LLM providers (OpenAI, Bedrock, Cohere, etc.), MCP server endpoints for model context management, an assistant API for AI-assisted workflows, and job execution endpoints. The gateway architecture uses provider-specific Python SDK clients with API key credentials passed via environment variables. [source: mlflow/gateway/app.py:301-457, mlflow/server/mcp_server_api.py:622-908]

The Kubernetes integration in `mlflow/projects/kubernetes.py` creates `BatchV1Api` Jobs for remote project execution, loading kubeconfig from in-cluster service accounts or `~/.kube/config`. The component installs a `mlflow_kubernetes_plugins` wheel that is not built from this repository's source tree but is prefetched during the Konflux build. [source: mlflow/projects/kubernetes.py:59-88, Dockerfile.konflux:54-58]

The container image is built in a three-stage Dockerfile: a Node.js builder compiles the React UI, a Python builder produces wheels for mlflow, mlflow-skinny, and mlflow-tracing, and the final stage assembles everything on `ubi9/ubi-minimal-pqc` with packages from both the AIPCC Python package index and Konflux-prefetched PyPI wheels. The use of `--require-hashes --no-deps` throughout ensures hermetic, hash-verified dependency installation. [source: Dockerfile.konflux:1-63]

## Data Flows

- **Request authentication flow:** HTTP requests arrive at the MLflow tracking server on port 5000. The `kubernetes-auth` app plugin (loaded via `--app-name` and resolved through `_find_app()`) authenticates requests using Kubernetes service account bearer tokens before routing to API handlers. The client-side `KubernetesRequestAuthProvider` reads tokens from `/var/run/secrets/kubernetes.io/serviceaccount/token` or kubeconfig and attaches `Authorization: Bearer <token>` and optionally `X-MLFLOW-WORKSPACE: <namespace>` headers. [source: Dockerfile.konflux:80, mlflow/server/__init__.py:218-226, mlflow/tracking/request_auth/kubernetes_request_auth_provider.py:39-42, 137-141, 229-258]
- **Gateway proxy flow:** The AI gateway endpoints (`/gateway/proxy/`, `/v1/chat/completions`, `/v1/completions`, `/v1/embeddings`) forward requests to upstream AI providers (OpenAI, AWS Bedrock, Google Cloud, Cohere, etc.) using provider-specific SDK clients. API credentials are passed via environment variables (OPENAI_API_KEY, AWS_SECRET_ACCESS_KEY, ANTHROPIC_API_KEY, etc.). [source: mlflow/gateway/app.py:419-457, mlflow/gateway/providers/bedrock.py:212, mlflow/deployments/openai/__init__.py:175]
- **Kubernetes Job execution:** MLflow project execution creates Kubernetes Jobs via `BatchV1Api.create_namespaced_job()`, pushing container images to a registry and polling job status at 5-second intervals through the Kubernetes API. [source: mlflow/projects/kubernetes.py:70-88, 102-138]
- **Runtime inventory:** 6 runtime components serve the application: the container entrypoint runs `mlflow server`, gunicorn/uvicorn provide the ASGI/WSGI transport, and the mlflow, mlflow-skinny, and mlflow-tracing packages deliver the tracking, registry, and tracing functionality respectively. [source: Dockerfile.konflux:80, libs/skinny/pyproject.toml:2, libs/tracing/pyproject.toml:2]
- **Security context:** 19 secret references (API keys, tokens, credentials) supply authentication for upstream AI providers, cloud storage, and workspace management. The `kubernetes-auth` plugin enforces bearer token authentication at the server boundary. [source: mlflow/tracking/request_auth/kubernetes_request_auth_provider.py:39-42, Dockerfile.konflux:80]
