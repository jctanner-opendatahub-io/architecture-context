## Purpose

**Short**: odh-dashboard is the RHOAI web console, combining a Kubernetes operator for lifecycle management with a federated micro-frontend architecture that uses per-domain Go BFF sidecars and a shared React/TypeScript SPA. [source: Dockerfile.konflux:52, Dockerfile.konflux.dashboard-operator:34, distributions/core-bff/bff/internal/api/app.go:1]

**Detailed**: odh-dashboard provides the primary web interface for Red Hat OpenShift AI. Its architecture has three tiers: (1) a controller-runtime-based Go operator (`dashboard-operator`) that reconciles Dashboard custom resources and manages the deployed console's Deployments, Services, Routes, RBAC, and NetworkPolicies; (2) a Node.js Fastify backend that serves the React SPA, proxies Kubernetes API calls via user impersonation, and exposes WebSocket endpoints for real-time resource watches; and (3) a set of domain-specific Go BFF (backend-for-frontend) services—agent-ops, automl, autorag, core-bff, data-registry, eval-hub, gen-ai, maas, mlflow, and model-registry—each shipped as a separate container image and loaded into the frontend via Webpack Module Federation. The operator also includes embedded Workspace and WorkspaceKind controllers for the Kubeflow Notebooks workspace subsystem. The dashboard integrates with over a dozen RHOAI platform components including KServe, TrustyAI, MLflow, ModelRegistry, DataScience Pipelines, Feast, and Gateway API, and supports both user-token and internal-ServiceAccount authentication modes across its BFF surface. [source: Dockerfile.konflux.dashboard-operator:18-20, backend/src/utils/constants.ts:18, packages/agent-ops/bff/internal/api/middleware.go:34-56, dashboard-operator/config/rbac/role.yaml:1]

## Architectural Analysis

odh-dashboard follows a **federated micro-frontend pattern** with per-domain backend services. The React/TypeScript SPA acts as a Webpack Module Federation host, dynamically loading feature-specific remote entries (gen-ai, model-registry, agent-ops, etc.) at `/_mf/:name/*`. Each remote has a corresponding Go BFF service that handles domain-specific API calls, Kubernetes resource operations, and upstream service integrations. This architecture allows independent development and deployment of feature domains while sharing a unified user experience through the PatternFly component library and a common `plugin-core` TypeScript SDK. [source: backend/src/routes/module-federation.ts:1, distributions/core-bff/bff/internal/api/app.go:1-23]

The **authentication model** is layered. At the outer boundary, kube-rbac-proxy terminates TLS on port 8443 and forwards authenticated requests to the Node.js backend, which reads user identity from `x-forwarded-access-token` headers. The Go BFF services support a configurable `--auth-method` flag with three modes: `user_token` (extracts Bearer tokens from the Authorization header), `internal` (uses the pod's ServiceAccount token), and `disabled` (for development). The `InjectRequestIdentity` middleware extracts and validates the caller's identity on every `/api/v1/*` request, with additional per-route authorization via `RequireAccessToService` (namespace-scoped RBAC check) and `RequireAuthenticatedForAgents` (SubjectAccessReview-based per-agent authorization). [source: backend/src/utils/constants.ts:18-19, packages/agent-ops/bff/internal/api/middleware.go:34-56, packages/agent-ops/bff/internal/api/middleware.go:160-168]

The **operator subsystem** uses controller-runtime to reconcile Dashboard CRs, managing the full deployment lifecycle including Deployments, Services, Routes, RBAC objects, NetworkPolicies, PodDisruptionBudgets, and OAuthClients. It also embeds the Kubeflow Workspaces controllers (WorkspaceReconciler and WorkspaceKindReconciler) which manage StatefulSets, Services, HTTPRoutes (via Gateway API), and VirtualServices for interactive workspace environments. The operator's RBAC surface is broad (59 rules across the ClusterRole), reflecting its role as the deployment orchestrator for the entire dashboard stack. [source: dashboard-operator/config/rbac/role.yaml:1, dashboard-operator/config/webhook/manifests.yaml:1]

The component has **no gRPC service endpoints**. While the gen-ai BFF acts as a gRPC-web proxy client to ML Metadata (MLMD), no gRPC servers are registered within odh-dashboard itself. The service surface is entirely HTTP/WebSocket-based. [source: coverage:grpc_services]

All Go components are built with `CGO_ENABLED=1` and `-tags strictfipsruntime` on UBI9 base images, establishing FIPS-compliant dynamic linking. The Node.js backend runs on UBI9/nodejs-22 and inherits OpenSSL from the base image but does not have an equivalent explicit FIPS build tag. TLS configuration uses the Go `crypto/tls` standard library across all BFF services and the operator. [source: Dockerfile.konflux.dashboard-operator:18-20, Dockerfile.konflux.core-bff:80, Dockerfile.konflux:1-4]

## Data Flows

- **User request flow:** External HTTPS requests arrive at the OpenShift Route, pass through kube-rbac-proxy (port 8443) for TLS termination and authentication, and reach the Node.js Fastify backend. The backend serves the React SPA for browser requests, proxies Kubernetes API calls at `/api/k8s/*` using user impersonation (Bearer Token to K8s Impersonation), and relays WebSocket connections at `/wss/k8s/*` for real-time resource watches. Module federation remotes are served at `/_mf/:name/*`. [source: backend/src/app.ts:4, backend/src/utils/constants.ts:18, backend/src/routes/wss/k8s/index.ts:73]
- **BFF service flows:** Each Go BFF sidecar (core-bff, gen-ai, maas, model-registry, etc.) runs on port 8080 with its own HTTP router, health check, and authentication middleware. BFFs communicate with upstream platform services (KServe, MLflow, TrustyAI, DataScience Pipelines, Prometheus) using Bearer Token or ServiceAccount authentication over HTTPS. Inter-BFF communication uses a shared `bffclient` factory with configurable TLS root CAs. [source: distributions/core-bff/bff/internal/api/app.go:1-50, Dockerfile.konflux.core-bff:94]
- **Operator reconciliation:** The dashboard-operator reconciles Dashboard CRs by creating and managing Deployments, Services, Routes, RBAC objects, NetworkPolicies, and OAuthClients. The embedded Workspace controllers reconcile workspace environments by managing StatefulSets, Services, HTTPRoutes, and PodDisruptionBudgets. All operator-to-API-server communication uses the operator's ServiceAccount token with RBAC enforced via the `odh-dashboard-operator-role` ClusterRole (59 rules). [source: dashboard-operator/config/rbac/role.yaml:1, dashboard-operator/cmd/manager/main.go:101, dashboard-operator/config/webhook/manifests.yaml:1]
- **Admission webhooks:** Validating webhooks intercept Dashboard CR creates, Workspace creates/updates, and WorkspaceKind creates/updates/deletes. A conversion webhook handles WorkspaceKind CRD version conversions. All webhook traffic is served over TLS on port 9443 via the webhook Service. [source: dashboard-operator/config/webhook/manifests.yaml:1-64]
