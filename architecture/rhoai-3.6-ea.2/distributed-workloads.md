## Purpose

**Short**: E2E test suite and example workloads for distributed training on Red Hat OpenShift AI, covering Kubeflow Training Operator v1, Kubeflow Trainer v2, and KubeRay.

**Detailed**: The distributed-workloads repository serves as the comprehensive test and example hub for distributed machine learning workloads on RHOAI. It provides integration tests for three primary orchestration frameworks — Kubeflow Training Operator v1 (KFTO) for legacy PyTorchJob-based training, Kubeflow Trainer v2 (TrainJob) for modern JobSet-based training, and KubeRay (RayCluster/RayJob) for Ray-based distributed training. The repository contains production-ready example workflows (LLM fine-tuning, hyperparameter optimization, stable diffusion training), runtime base images for CPU/GPU/ROCm accelerators (with OpenMPI 4.1 and PyTorch variants), benchmarking harnesses (MPI microbenchmarks, LLM training), and a shared test infrastructure library that provides unified client abstractions and resource helpers for Kubernetes, Kubeflow, KubeRay, and Kueue APIs.

## Architectural Analysis

The distributed-workloads repository exhibits a **test-driven architecture** with four distinct but integrated layers:

1. **Test Infrastructure Layer** (`tests/common/support/`): A shared library of ~40 Go source files providing a unified abstraction for managing test lifecycle, namespace isolation, and client access to multiple Kubernetes APIs (core K8s, Kubeflow Training Operator, Trainer v2, KubeRay, Kueue, JobSet, OpenShift). Tests use gomega assertions and automatic cleanup via `t.Cleanup` to ensure isolation and determinism.

2. **Test Suite Layer**: Four parallel test suites — **kfto** (PyTorchJob v1), **trainer** (TrainJob v2, the primary and most actively developed), **odh** (KubeRay), and **fms** (foundation model fine-tuning via both kfto and trainer paths). Each suite imports the shared support library and adds suite-specific utilities via embedded test resources and Prometheus query helpers.

3. **Example & Benchmark Layer**: Production-ready examples (`examples/`) and benchmarks (`benchmarks/`) that demonstrate real-world training workflows. Examples range from hyperparameter optimization with Ray Tune to multi-modal fine-tuning (Stable Diffusion DreamBooth, LLM SFT with Feast RAG). Benchmarks include both OSU MPI microbenchmarks and end-to-end LLM training with Qwen models.

4. **Runtime Image Layer** (`images/`): Two distinct image families — **runtime images** (Pipfile/Pipfile.lock, public PyPI) for on-demand execution, and **universal images** (pyproject.toml/requirements.txt, AIPCC PyPI) for RHOAI-curated environments. Images come in CPU/CUDA/ROCm variants with OpenMPI 4.1 pre-installed for multi-node distributed training.

**Key Design Observations**:

- **API Versioning Strategy**: The go.mod shows an intentional migration path from Training Operator v1 (`github.com/kubeflow/training-operator v1.9.3`) to Trainer v2 (`github.com/kubeflow/trainer/v2 v2.3.0`). A replace directive keeps v1 tests functioning during the transition, indicating this is a long-running deprecation.
- **Accelerator-First Design**: Test suites assume GPU availability for certain workloads (`TEST_TIER` environment variable gates smoke/tier1/tier2/tier3/GPU tests). Multi-GPU and multi-node testing is explicitly tracked via test tags (`MultiNode`, `Gpu`).
- **MinIO S3 Integration**: Examples consistently use MinIO as the S3-compatible storage backend for model/dataset staging. Service manifests expose both API (port 9000) and console (port 9001/9090) on OpenShift Routes with TLS termination.
- **Namespace Isolation**: Test infrastructure creates per-test namespaces with automatic cleanup, enabling parallel test execution without cross-contamination.
- **Vendor-Specific Credentials**: Tests for fms-hf-tuning GPU variants and Training Hub RayJob require HuggingFace tokens and S3 credentials (AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY), indicating external model/dataset dependencies.

The repository is **actively maintained** as evidenced by recent commits involving dependency updates (Konfluex base images, AIPCC base image updates), Kueue integration (post-codefreeze gatekeeper workflows), and test additions (e.g., Kueue scheduling directives in TrainJob pods).
