## Purpose

**Short**: Installs and periodically reapplies the Praxis ext-proc data-plane manifests used by the AI Gateway.

**Detailed**: `ai-gateway-controller` is the control-plane companion to the `praxis-extproc` data plane. In the implemented Phase 1 path, a controller-runtime manager builds a vendored Kustomize overlay, rewrites namespace, gateway, route, and image placeholders, and server-side-applies the resulting Kubernetes objects. The manager performs one install at startup and retries on a five-minute resync interval; it does not currently reconcile a Custom Resource.

The repository also defines the RHOAI `inference.opendatahub.io/v1alpha1` `ExternalModel` and `ExternalProvider` API types and corresponding permissions. Those types describe the planned EA2 control plane for model/provider routing, namespace-local credentials, and status, but the checkout documents that the watch/reconcile path is still in progress and deferred from the current Phase 1 implementation.

## Architectural Analysis

The component is deliberately a thin, leader-elected manifest installer rather than a conventional CR-driven operator. Its main architectural boundary is between a small Go manager and a commit-pinned, vendored Praxis Kustomize overlay. `Build`, `PostRender`, and `Apply` separate rendering, placeholder substitution, and SSA application, which permits the same data-plane manifests to be installed into a gateway namespace selected by the consuming platform controller.

The generated data plane has two ext-proc stages around the platform gateway's authentication filters: a pre-auth model-header stage that allows failure and a post-auth request/response stage that fails closed. Istio `EnvoyFilter` patches support several Kuadrant/Istio filter naming variants, while dedicated HTTP/2 TLS clusters avoid Istio metadata-exchange behavior that the non-mesh Praxis service does not accept. This is powerful but tightly coupled to gateway labels, route naming, Istio versions, and self-signed certificate behavior.

The Phase 2 API and RBAC shape points toward namespace-scoped model/provider reconciliation and per-tenant fan-out, but it should not be read as implemented runtime behavior in this revision. The most material current risks are that the data-plane TLS configuration explicitly accepts untrusted certificates, the controller's broad cluster role can create or modify cluster-scoped RBAC objects, and live end-to-end wiring through `ai-gateway-operator` is documented as unverified.
