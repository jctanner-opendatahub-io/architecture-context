## Purpose

**Short**: Installs and manages the praxis-extproc Envoy ExtProc dataplane manifests for request/response processing in the AI Gateway.

**Detailed**: `ai-gateway-controller` is a lightweight controller deployed by `ai-gateway-operator` as a sibling of `maas-controller`. Its sole responsibility in Phase 1 is to render vendored `praxis-extproc` manifests with environment-specific values (namespace, gateway name, target image) and apply them to the cluster via server-side apply (SSA). It combines static kustomize builds with placeholder post-rendering to handle cross-repo, commit-pinned manifest vendoring patterns. The controller runs once at startup and periodically (default 5-minute resync) without watching any custom resource; configuration comes purely from command-line flags. This design separates the "install dataplane" concern from the "watch ExternalModel CR" concern, which remains on `maas-controller`.

## Architectural Analysis

`ai-gateway-controller` exemplifies a minimal, stateless installer pattern: it is a `controller-runtime` manager with exactly one `Runnable` component (`Installer`), no API types, no webhooks, and no CR watches. The architecture is deliberately constrained to reduce dependencies and deployment complexity. The controller uses three sequential stages:

1. **Build** (`kustomize build`) — Reads the vendored overlay at `/config/manifests/praxis-extproc/overlays/odh` and produces unstructured Kubernetes resources.
2. **PostRender** — Substitutes placeholders (`openshift-ingress` → `--namespace` flag value, `maas-default-gateway` → `--gateway-name`, image digest, HTTPRoute names) and normalizes JSON types for SSA compatibility.
3. **Apply** — Uses Kubernetes server-side apply with a dedicated field owner (`ai-gateway-controller`) to reconcile resources declaratively, allowing parallel reconciliation without race conditions.

Key constraints: the vendored overlay is baked into the container image at build time (via `COPY` in `Dockerfile.konflux`), ensuring reproducible, pinned deployments. No dynamic configuration watch exists; the 5-minute resync interval is the only retry trigger besides process restart. The `Installer` requires leader election when deployed with multiple replicas, ensuring only one replica applies at a time.

The RBAC surface is broad but intentional: the controller must create/update/delete every Kubernetes resource the vendored overlay contains (Services, ConfigMaps, Deployments, EnvoyFilters, DestinationRules, NetworkPolicies, HTTPRoutes, ServiceEntries, and a custom ClusterRole/ClusterRoleBinding for `payload-processing-reader`). An escalation-check comment in the ClusterRole mirrors these permissions to detect if the vendored overlay ever grants permissions the controller itself lacks.
