## Purpose

**Short**: WVA is a Kubernetes controller that derives GPU- and performance-aware replica recommendations for LLM inference workloads and exposes them to HPA or KEDA.

**Detailed**: WVA monitors inference workload resources, endpoint-picker metrics, Prometheus time series, node GPU capacity, and queueing/saturation signals. Its optimization engines select replica counts across workload variants, while the actuator updates Kubernetes scale subresources or emits `wva_desired_replicas` metrics consumed by an external autoscaler.

The controller supports namespace-scoped and cluster-scoped operation. It discovers HPAs by WVA annotations, optionally discovers KEDA `ScaledObject` resources, resolves Gateway API InferencePool resources to endpoint-picker services, and optionally handles LeaderWorkerSet-backed workloads. ConfigMaps provide live or bootstrapped saturation, queueing, scale-to-zero, and coordinator settings.

## Architectural Analysis

WVA is a leader-elected controller-runtime process with several cooperating loops: resource reconcilers populate a local datastore, Prometheus-backed collectors obtain workload observations, optimization engines calculate desired capacity, and actuators write scale targets or metrics. The design deliberately delegates final replica management to HPA/KEDA in the normal path, allowing those systems to retain stabilization and policy behavior.

The deployment supports both a cluster-wide cache and a namespace-restricted cache. In cluster mode, ConfigMaps are filtered by the WVA label and namespace-local configuration is enabled by namespace labels; in namespace mode, `--watch-namespace=$(POD_NAMESPACE)` narrows observation. Optional CRDs are detected at startup and can trigger an automatic restart when installed later.

The principal deployment risk is the split between secure runtime configuration and development-oriented defaults. OpenShift overlays verify Prometheus and metrics-server certificates, while the base ServiceMonitor explicitly skips verification for self-signed metrics certificates. The container is statically linked with `CGO_ENABLED=0` and uses a distroless static image, so it does not provide the dynamic OpenSSL/CGO properties expected by the documented check-payload FIPS gate.
