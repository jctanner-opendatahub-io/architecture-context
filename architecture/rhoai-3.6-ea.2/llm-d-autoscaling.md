## Purpose

**Short**: A Kubernetes-based global autoscaler for inference model servers serving LLMs that optimizes replica counts by considering GPU availability, energy budget, and performance constraints across hardware variants.

**Detailed**: The Workload Variant Autoscaler (WVA) is a Kubernetes controller that drives intelligent scaling decisions for LLM inference deployments. It introduces the concept of **variants**—multiple model servers in an InferencePool that serve the same base model but differ in hardware configuration (GPU type), serving configuration (tensor parallelism, max batch size, quantization), or both. WVA continuously monitors request rates and server performance via Prometheus metrics, uses capacity models to determine desired replica counts by observing KV cache utilization and queue depth, and emits optimization metrics that external autoscalers (HPA/KEDA) consume to scale deployments. The controller supports multiple deployment patterns including P/D disaggregation (prefill vs. decode variants), batch-gateway integration for mixed workloads, and cost optimization by selecting among competing serving configurations.

## Architectural Analysis

WVA is a production-grade Kubernetes operator designed to bridge the gap between LLM inference workload characteristics and Kubernetes' native autoscaling primitives. Rather than implementing autoscaling directly, it operates as a "metric producer" that feeds Prometheus custom metrics to external autoscalers (HPA and KEDA), maintaining separation of concerns and allowing operators to leverage existing Kubernetes autoscaling infrastructure.

**Key Design Patterns:**

1. **Metric-Driven Architecture**: WVA publishes desired replica counts as Prometheus metrics (`wva_desired_replicas`) which external autoscalers consume. This decouples the autoscaling logic from the scaling orchestration, allowing flexible scaling policies and multiple simultaneous autoscalers.

2. **Multi-Engine Design**: The controller contains multiple optimization engines (saturation engine, scale-from-zero engine, and experimental coordinator) that can be configured and selected independently via ConfigMaps without controller restart.

3. **Variant-Centric Modeling**: Unlike generic Kubernetes workloads, WVA models LLM inference through the lens of "variants"—explicit representations of different serving configurations for the same model. This enables cost optimization by selecting among competing configurations and P/D disaggregation patterns.

4. **Pluggable Saturation Analysis**: The saturation engine supports multiple analyzer implementations (V1 percentage-based, V2 token/capacity-based, optional throughput analyzer) selected dynamically via ConfigMap, allowing operators to switch analysis strategies without restart.

5. **Prometheus-First Dependency**: The controller requires persistent Prometheus connectivity for capacity modeling and performance observation. This is validated at startup and failure is fatal, reflecting that autoscaling decisions depend entirely on telemetry fidelity.

6. **Leader Election with Aggressive Timeouts**: Configured with extended lease durations (60s) and renewal deadlines (50s)—significantly longer than controller-runtime defaults—to tolerate network latency and API server delays in production environments.

7. **Dynamic CRD Support**: Optional CRD support for KEDA ScaledObjects and LeaderWorkerSet deployments can be enabled post-startup without restart (when `--disable-crd-auto-restart` is not set), with graceful degradation to HPAs-only mode if CRDs are absent.

**Security Posture:**

- Static binary (CGO_ENABLED=0) using distroless base image, minimizing attack surface
- TLS configuration for metrics and webhooks with certificate watchers that reload certs without restart
- RBAC: Fine-grained permissions scoped to resources the controller must observe (Deployments, HPA, KEDA ScaledObjects, LeaderWorkerSets, InferencePools, Prometheus ServiceMonitors) with no cluster admin privileges
- Metrics endpoint secured via HTTPS with authentication and authorization filtering
- ServiceAccount token used for Prometheus authentication (bearer token pattern)

**Observability:**

WVA emits extensive Prometheus metrics (distinct metrics for each engine phase, replica counts, optimizer decisions, cluster inventory) and supports structured logging with configurable verbosity. Health endpoints (`/healthz`, `/readyz`) provide Kubernetes-native liveness and readiness probes.

**Flow Description**:

4. Saturation engine (or coordinator) emits desired replica count metric back to Prometheus
5. HPA (or KEDA, via Prometheus adapter) reads the desired replica metric and patches the Deployment's scale subresource
