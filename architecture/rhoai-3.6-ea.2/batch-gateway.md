## Purpose

**Short**: Provides an OpenAI-compatible API and asynchronous workers for submitting, processing, tracking, and cleaning up large batch inference jobs.

**Detailed**: The API server accepts OpenAI-compatible batch and file operations, persists job/file metadata, queues work, and stores input and output files. The processor consumes queued jobs, groups requests by model and system-prompt characteristics, applies global and per-model concurrency control, sends requests to llm-d inference gateways, writes results, and updates status. An optional asynchronous dispatcher integration is supplied by `llm-d-async`.

The deployment is deliberately split into independently scalable API-server, processor StatefulSet, and garbage-collector workloads. PostgreSQL stores metadata, Redis/Valkey supplies queue/event/status primitives, and either a filesystem/PVC or S3-compatible object store holds files. Prometheus and OpenTelemetry instrumentation provide operational visibility.

## Architectural Analysis

Batch Gateway is a shared-state, worker-oriented architecture. The API server and workers communicate indirectly through PostgreSQL and Redis/Valkey rather than through an internal REST endpoint. The processor's StatefulSet identity is used by the GC reconciler to detect live processors and recover orphaned work. The processor uses local `emptyDir` work space for plan files and can use a shared file-storage volume when configured.

The API and observability planes are separate: business routes receive recovery, request/tenant context, security-header, metrics, and tracing middleware, whereas health, readiness, metrics, and optional pprof are served on a plain HTTP observability listener. This is operationally useful but means observability exposure must remain network-restricted. Authentication is intentionally platform/ingress-oriented; the application propagates an injected tenant header and can pass `Authorization` to downstream inference, but does not implement a JWT/OIDC verifier.
