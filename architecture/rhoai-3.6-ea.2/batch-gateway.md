## Purpose

**Short**: High-performance system for processing large-scale batch inference jobs in Kubernetes environments with OpenAI-compatible API, supporting up to 50,000 requests per job with model-aware scheduling and adaptive concurrency control.

**Detailed**: Batch Gateway provides infrastructure for efficient batch processing of inference workloads while minimizing interference with interactive traffic. The system comprises three independently scalable components: (1) an API server handling REST endpoints for batch job submission, status tracking, and file management; (2) a batch processor pulling jobs from a priority queue and executing inference requests with per-model and global concurrency control; and (3) a garbage collector performing periodic cleanup of expired jobs and files. The architecture is storage-agnostic, supporting pluggable backends (PostgreSQL for metadata, Redis/Valkey for queues, and S3 or filesystem for files). Design priorities include cost optimization through differential billing for batch vs. interactive workloads, KV-cache reuse via model-aware grouping, and fault tolerance with automatic recovery from processor crashes.

## Architectural Analysis

Batch Gateway follows a clean separation of concerns across three independently deployable services, enabling efficient resource scaling based on workload patterns. The API server implements an OpenAI-compatible `/v1/batches` and `/v1/files` API, delegating persistence to pluggable storage backends rather than embedding database logic. The batch processor implements adaptive concurrency control via AIMD (Additive Increase, Multiplicative Decrease) flow control, dynamically adjusting downstream request rates based on real-time success/failure signals without manual tuning.

Key architectural patterns:
- **Priority Queue-Based Dispatch**: Jobs are enqueued in Redis/Valkey with priority metadata, allowing the processor to pull and process jobs at its own rate without API server coupling.
- **Per-Model Execution Plans**: The processor pre-processes batch files to extract model IDs and system prompts, grouping requests by model and prompt hash to maximize prefix cache locality and avoid eviction-triggered KV-cache rebuilds.
- **Hermetic Build**: Conflict-free Go builds with `go.sum` pinning, `GOEXPERIMENT=strictfipsruntime`, `CGO_ENABLED=1` dynamic linking, and UBI 9 minimal base images enable FIPS compliance validation via Konflux's check-payload gate.
- **Health & Observability**: All components expose `/health`, `/ready`, and `/metrics` endpoints on dedicated observability ports (8081 for API server, 9090 for processor) with pprof profiling support (opt-in via `enablePprof` config).
- **Multi-Tenancy via Namespace Scoping**: The system does not implement application-level tenant isolation; tenancy is delegated to the deployment layer (Kubernetes namespace per tenant) and enforced upstream by the gateway layer (Kuadrant/Authorino) at authentication/authorization boundaries.

Risks and observations:
- **Unauthenticated observability endpoints**: `/health`, `/ready`, `/metrics`, and `/debug/pprof/*` are exposed without authentication. While common practice for observability, these should be restricted via NetworkPolicy or Ingress to trusted monitoring infrastructure.
- **API server routes have no built-in auth**: The API server routes themselves (batch and file endpoints) enforce no authentication; all auth is delegated to the gateway layer (e.g., Kuadrant admission). This is intentional per the security boundary documented in the deployment guide.
- **Processor inference mTLS optional**: Processor-to-llm-d-router connections support mTLS and custom CAs but are optional; configurations without TLS are supported.

## Multi-Tenancy

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| **Tenant boundary** | Per-namespace | Kubernetes namespace scoping via Helm chart deployment; no application-level tenant isolation |
| **Deployment model** | Multi-instance (one instance per namespace/tenant) | Each tenant deploys its own batch-gateway instances in its namespace |
| **Tenant identifier** | Kubernetes namespace name | Derived from deployment namespace; no explicit tenant ID column in schema |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Gateway-layer RBAC (Kuadrant/Authorino) | Kubernetes + upstream gateway | API server trusts upstream auth decision; no local re-verification |
| Data storage | Namespace-scoped Secrets; PostgreSQL database shared across tenants but schema isolation via namespace naming conventions | Kubernetes + application | Risk: If multiple namespaces share one database, cross-namespace queries are possible without schema-level constraints |
| Network traffic | Kubernetes NetworkPolicy per namespace | Kubernetes | Requires cluster admin to define policies; not enforced by the application |
| Compute & resources | ResourceQuota per namespace | Kubernetes | Pod resource requests/limits set in Helm values but not enforced at the application level |
| Configuration & secrets | Secrets mounted read-only per deployment | Kubernetes | Each deployment mounts its own secret; shared database/queue means shared data unless schema isolation is configured |
| API scoping | No tenant filter in query logic; relies on namespace isolation | Deployment architecture | Risk: If a user compromises credentials, no API-level tenant filtering prevents cross-tenant reads |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| PostgreSQL database | Per-tenant (table prefix or schema per namespace) | Application must enforce schema isolation or table prefixing (not verified in source) |
| Redis / Valkey queue | Per-tenant (key prefix per namespace) | Application must enforce key prefixing (not verified in source) |
| S3 bucket / Filesystem storage | Per-tenant (bucket or directory per namespace) | Helm chart parameterization via `fsRootPath` or S3 bucket naming |
| llm-d Router | Shared inference endpoint (not isolated by tenant) | Inference API key is shared across batch jobs; router enforces model access control separately |

**Tenant Isolation Summary**: Batch Gateway does not implement application-level tenant isolation. Multi-tenancy is achieved via Kubernetes namespace scoping and upstream gateway filtering. If a single PostgreSQL database is shared across namespaces, schema isolation (e.g., table prefixes) must be enforced by deployment automation, not the application. Similarly, Redis keys and S3 paths must be prefixed per tenant at the infrastructure layer. This is a reasonable architecture for on-premises deployments but requires careful configuration to avoid cross-tenant data leakage.
