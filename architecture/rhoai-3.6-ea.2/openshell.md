## Purpose

**Short**: OpenShell is the safe, private runtime for autonomous AI agents, providing sandboxed execution with policy-enforced isolation and credential management.

**Detailed**: OpenShell is NVIDIA's comprehensive sandboxing solution for AI agent workloads. It provides defense-in-depth protection across four policy domains: filesystem access, network egress, process execution, and model inference routing. The platform operates through a gateway control plane that orchestrates sandbox lifecycle across multiple compute drivers (Docker, Podman, Kubernetes, MicroVM), while embedding policy enforcement directly into each sandbox via an injected supervisor process. This architecture enables declarative YAML-based security policies that protect data, credentials, and infrastructure from unauthorized access without requiring centralized proxying for every request. OpenShell integrates with major AI agent platforms (Claude, OpenCode, Copilot) and is designed for both standalone usage and integration into Kubernetes-based platforms like RHOAI.

## Architectural Analysis

OpenShell employs a distributed control-plane + sandboxed-runtime architecture optimized for security isolation and multi-tenancy. The system breaks into three primary deployable components:

1. **Gateway** (Rust, gRPC/HTTP): The control plane responsible for sandbox lifecycle (create/start/stop/delete), credential provider management, policy coordination, and authentication/authorization. It exposes a large gRPC service surface (102 total RPC endpoints) covering sandbox management, provider operations, inference routing, and workspace/team administration. The gateway acts as the authentication boundary and coordinates with multiple pluggable compute drivers.

2. **Supervisor** (Rust, fully-static binary): An embedded process injected into every sandbox container that enforces runtime policies at the application layer (network proxy, filesystem enforcement, process syscall filtering). The supervisor is built as a static glibc binary (no libc dependency) to ensure it can be injected into arbitrary container images (Alpine, Debian, distroless, UBI). Network enforcement is implemented via an in-process proxy that intercepts all outbound connections and applies L7 (HTTP method/path) policy decisions without requiring external proxying infrastructure.

3. **CLI** (Rust): Command-line interface for end users to manage sandboxes, providers, policies, and inference configuration. It also includes a real-time terminal UI (TUI) for monitoring gateway health and sandbox status.

The design separates concerns cleanly: the gateway manages orchestration and state; the supervisor handles enforcement and isolation; the CLI provides user interaction. This allows hot-reloadable network and inference policies without restarting sandboxes (only static filesystem and process policies are locked at creation). The architecture supports multiple credential driver backends (database, Kubernetes Secrets, Vault) and compute drivers (Docker, Podman, Kubernetes, MicroVM, Windows MXC), making it highly pluggable for different deployment contexts.

Security is achieved through a defense-in-depth approach: sandboxes start with minimal outbound access, policies are declarative and auditable, credentials are never written to the sandbox filesystem (injected as environment variables), and the supervisor enforces policies from the application layer down to kernel syscalls. The formal policy verification crate (`openshell-prover`) allows pre-flight validation of policies before deployment.

#### Enforcement Layers

| Layer | Mechanism | Timing |
|-------|-----------|--------|
| **Filesystem** | Regex-based path allowlist enforcement via eBPF or seccomp (locked at container creation) | Static (immutable) |
| **Network** | In-process HTTP/1.1 proxy intercepting all outbound TCP; L7 policy decisions via HTTP method, path, host | Hot-reloadable |
| **Process** | Seccomp/eBPF syscall filtering blocking privilege escalation and dangerous operations | Static (immutable) |
| **Inference** | Policy-based routing that preserves caller context, strips credentials, injects backend credentials | Hot-reloadable |

| **Auth & AuthZ** | OIDC token validation (tenant identity from JWT subject claim); workspace membership checked in gateway before resource access | Tonic gRPC interceptor + gateway handler logic | Token validation via JWKS (public key set). No explicit group-based RBAC; relies on OIDC provider to issue correct claims. Tenant isolation depends on OIDC issuer security. |
| **Data storage** | Sandboxes are scoped to workspace; provider profiles are per-workspace; logs/metrics are workspace-labeled | Gateway state management (in-memory or persistent backing store) | Persistent storage backend (if used) must enforce workspace isolation at the storage layer (e.g., per-workspace database schema or row-level filtering). |
| **Network traffic** | Sandboxes in different workspaces can coexist on same compute cluster; network policies are per-sandbox, not per-workspace. Supervisor network proxy enforces per-sandbox policy (no cross-sandbox leakage). | Kubernetes NetworkPolicy (if K8s driver) + Supervisor in-process proxy | Cross-sandbox traffic within the same cluster is NOT restricted by network policies (supervisor policies are per-sandbox). Workspaces sharing a Kubernetes cluster must rely on node isolation or separate cluster namespaces if strong network isolation is required. |
| **Compute & resources** | Kubernetes ResourceQuota / LimitRange per namespace (if K8s driver); or compute driver plugin provides per-workspace quotas | Kubernetes (K8s driver) / Compute driver plugin | No built-in workspace-level resource quotas in the gateway; compute drivers implement quotas independently. |
| **Configuration & secrets** | Provider credentials are per-workspace; sandboxes inherit provider list from workspace. Supervisor middleware can access workspace-level configuration via supervisor middleware gRPC. | Gateway + Supervisor middleware gRPC | Credentials are stored by credential driver backends (K8s Secrets, Vault, Database); isolation depends on backend (K8s Secrets uses namespace isolation; Vault uses auth paths; Database uses tenant column + queries). |
| **API scoping** | All gateway gRPC calls are scoped to the authenticated tenant's workspace. Provider lookups, sandbox creation, policy management are workspace-scoped. | Gateway gRPC interceptor + handler business logic | No explicit namespace-scoped watches like in Kubernetes controllers. API calls are scoped at the handler level (not at the storage layer). A compromised gateway handler could bypass scoping. Formal verification (openshell-prover) can validate policy correctness but not API scoping. |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Gateway state (in-memory or persistent) | per-workspace | Workspace membership check before resource access |
| Credential driver backend (K8s Secrets, Vault, Database) | per-workspace (or per-tenant in storage layer) | Backend-specific isolation (Vault auth paths, K8s namespace, DB schema/column) |
| Compute cluster (Kubernetes) | per-workspace (sandboxes coexist) | Namespace isolation (if each workspace gets a namespace) OR node/taint isolation (if shared namespace) |
| Inference routing service (shared model backend) | per-workspace | Inference router rewrites requests with workspace-scoped credentials |
| OpenTelemetry Collector (shared) | per-workspace (traces labeled with workspace/sandbox ID) | Collector relabeling rules to tag traces with workspace context |
| Observability/Metrics (shared Prometheus) | per-workspace (metrics labeled with workspace/sandbox ID) | Prometheus label-based isolation (no hard tenancy; depends on metric labels for filtering) |

**Multi-Tenancy Summary**: OpenShell is designed as a multi-tenant system with logical tenant boundaries (workspaces) enforced at the gateway API layer. Strong isolation requires careful configuration of the backing credential store (Vault or K8s Secrets with namespace separation). Network isolation between sandboxes is per-sandbox, not per-workspace; shared compute clusters require namespace-level isolation or additional network policies. No formal multi-tenancy guarantees (e.g., "malicious tenant cannot access another tenant's data"); isolation depends on correct implementation of API scoping and storage backend configuration.

## Data Flows

### Flow 1: Sandbox Creation and Execution

| Step | Source | Destination | Port | Protocol | Encryption | Auth |
|------|--------|-------------|------|----------|------------|------|
| 1 | CLI / user | Gateway | 8080 | gRPC | TLS 1.3 | OIDC bearer token |
| 2 | Gateway | Compute driver | 50051 | gRPC | mTLS | mTLS certificate |
| 3 | Compute driver | Scheduler (Docker/K8s) | varies | Native | TLS (K8s APIServer) | K8s API token |
| 4 | Scheduler | Registry | 443 | HTTPS | TLS 1.3 | Bearer (if private registry) |
| 5 | Sandbox container | Supervisor (init) | loopback | -- | -- | -- |
| 6 | Supervisor | Credential driver | 50052 | gRPC | mTLS | mTLS certificate |
| 7 | Credential driver | Secret backend (Vault/DB/K8s) | varies | HTTPS/TCP | TLS | Backend-specific auth |

### Flow 2: Network Policy Enforcement (Egress from Sandbox)

| Step | Source | Destination | Port | Protocol | Encryption | Auth |
|------|--------|-------------|------|----------|------------|------|
| 1 | App in sandbox | Supervisor proxy (loopback) | 8888 (config) | HTTP | None | None (loopback) |
| 2 | Supervisor network component | OPA (if policy uses Rego) | 8181 | HTTP | TLS (optional) | Bearer (optional) |
| 3 | Supervisor network component | Inference router | (in-process) | -- | -- | -- |
| 4 | Supervisor network component | External endpoint (if allowed) | 443 (typical) | HTTPS | TLS 1.3 | Bearer (original caller's token, rewritten if inference) |

### Flow 3: Inference Routing (Privacy-Aware LLM Call)

| Step | Source | Destination | Port | Protocol | Encryption | Auth |
|------|--------|-------------|------|----------|------------|------|
| 1 | App in sandbox | Supervisor network proxy | 443 | HTTPS | TLS 1.3 | (requests sent to proxy) |
| 2 | Supervisor network proxy | Inference router (in-process) | -- | gRPC (in-memory) | -- | -- |
| 3 | Inference router | Managed LLM endpoint (e.g., Claude API) | 443 | HTTPS | TLS 1.3 | Bearer (backend API key injected by router) |
| 4 | Managed LLM endpoint | (response) | 443 | HTTPS | TLS 1.3 | N/A |
| 5 | Supervisor network proxy | App in sandbox (response) | 443 | HTTPS | TLS 1.3 | N/A |

**Key Security Property**: Caller's original API key is NOT sent to the external endpoint. Inference router strips caller credentials, injects backend credentials, and returns response to caller. This prevents model providers from seeing the caller's API key and allows single-tenant or restricted inference endpoints.
