## Purpose

**Short**: OpenVINO Model Server (OVMS) is a high-performance inference serving system that deploys machine learning models over REST and gRPC APIs in Kubernetes environments.

**Detailed**: OVMS enables inference workloads in Kubernetes by hosting trained models (TensorFlow, PyTorch, ONNX, OpenVINO IR formats) and exposing them via standardized KServe protocols. The component is deployed via KServe `ServingRuntime` custom resources, which define how models are containerized, what inference frameworks are supported, and how inference traffic is routed. OVMS is implemented in C++ for performance, optimized for Intel CPU architectures, and supports GPU acceleration (NVIDIA, AMD) via driver integration. It serves as a foundational runtime adapter in RHOAI's model serving stack, enabling users to deploy inference workloads without directly managing container orchestration.

## Architectural Analysis

OVMS adopts a **multi-protocol, adapter-based serving model** characteristic of KServe runtimes. The component implements KServe protocol endpoints (`v2` and `grpc-v2`) and augments them with OpenAI-compatible APIs for generative models, enabling broad client compatibility. The deployment uses Kubernetes `ServingRuntime` CRs to specify model format support, container images, and port configurations—a pattern that centralizes inference runtime definition and makes model serving declarative rather than imperative.

The architecture emphasizes **remote model loading**: models are fetched at runtime from URLs (local volumes, S3, HuggingFace Hub) rather than baked into images, reducing image bloat and enabling A/B testing of model versions. gRPC and REST ports are independently configurable, allowing teams to choose protocols per deployment. Startup probes validate inference readiness via the KServe health endpoint (`/v2/health/ready`), ensuring Kubernetes only routes traffic after models are fully loaded.

Security follows **least-privilege patterns**: the container runs as non-root (uid 5000), drops all Linux capabilities, disables privilege escalation. The base image is UBI 9 Minimal, reducing attack surface. OpenSSL is installed for crypto operations, though FIPS compliance signals are not explicitly configured in the Konflux Dockerfile.

Scaling is **stateless and horizontal**: each OVMS pod independently loads models, and Kubernetes ReplicaSets handle load distribution. The metrics endpoint (`/metrics`) exports Prometheus-compatible counters for inference latency, throughput, and framework-specific metrics.

## Multi-Tenancy

OVMS is **single-tenant per deployment**. Multi-tenancy managed at Kubernetes level via KServe controller and namespace isolation.

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| **Tenant boundary** | per-namespace | KServe controller deploys `InferenceService` into user namespace |
| **Deployment model** | per-namespace instance | KServe `InferenceService` controller creates pod(s) in target namespace |
| **Tenant identifier** | namespace name | Kubernetes namespace acts as tenant identifier |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Kubernetes RBAC on InferenceService CRDs; Istio AuthorizationPolicy optional | Kubernetes / Istio | OVMS does not enforce auth |
| Data storage | PVC per InferenceService; models namespace-scoped | Kubernetes PVC | Accessible to any pod in namespace with volume permissions |
| Network traffic | NetworkPolicy per namespace; Istio VirtualService optional | Kubernetes / Istio | No egress restrictions on OVMS pod |
| Compute & resources | ResourceQuota, LimitRange per namespace | Kubernetes | OVMS must specify requests/limits for quota |
| Configuration & secrets | Kubernetes Secrets per namespace | Kubernetes | Secrets accessible to any pod in namespace |
| API scoping | InferenceService CRD namespace-scoped | KServe controller | No cross-namespace discovery |
