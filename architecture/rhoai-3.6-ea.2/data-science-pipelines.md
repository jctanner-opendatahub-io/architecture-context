## Purpose

**Short**: Production-grade ML pipeline orchestration platform for RHOAI, built on Kubeflow Pipelines, providing DAG-based workflow execution, metadata persistence, and artifact management on Kubernetes.

**Detailed**: Data Science Pipelines is the RHOAI distribution of Kubeflow Pipelines, a complete ML workflow orchestration system that enables data scientists and MLOps engineers to define, execute, and monitor end-to-end ML pipelines on Kubernetes. The platform consists of a multi-component backend (API server, cache server, persistence agent, scheduled workflow controller) alongside a Python SDK and TypeScript frontend. It manages pipeline definitions, runtime execution via Argo Workflows, artifact storage via S3-compatible backends (SeaweedFS or Minio), and metadata persistence via MySQL. The component integrates deeply with the Kubernetes ecosystem through CRDs (Pipeline, PipelineVersion), webhooks for admission control, RBAC-based access, and Istio networking policies.

## Architectural Analysis

Data Science Pipelines demonstrates a **multi-service, Kubernetes-native architecture** with clear separation of concerns:

1. **API Tier**: The `apiserver` (Go, TCP 8887/gRPC + 8888/HTTP + 8443/webhook) is the principal API surface, exposing 27 HTTP endpoints and 10 gRPC services. It uses gRPC-Gateway for HTTP/JSON-to-gRPC proxying and webhook admission control for Pipeline/PipelineVersion validation. TLS configuration is pluggable via certificate paths; webhook TLS is enforced separately.

2. **Data Persistence**: MySQL (v8.4) stores pipeline definitions, run history, and experiment metadata. SeaweedFS provides S3-compatible artifact storage with optional Istio authorization policies. A dedicated metadata-grpc-deployment bridges to ML Metadata (version 1.14.0) for lineage tracking via gRPC.

3. **Execution Controllers**: 
   - **Persistence Agent**: Reacts to Argo Workflow completion, syncing final status and logs back to ML Pipelines metadata.
   - **Scheduled Workflow Controller**: Manages recurring pipeline executions via cron-like triggers.
   - **Viewer CRD Controller**: Renders pipeline visualization artifacts.
   - **Cache Server**: Implements artifact caching across pipeline runs to avoid redundant computation.

4. **Frontend**: A Node.js TypeScript application (port 3000) provides the web UI, served through a dedicated ml-pipeline-ui service.

5. **Security Posture**:
   - **FIPS Build**: Go binaries (apiserver, driver, persistence agent, scheduler, launcher) use `GOFIPS140=v1.0.0` and `CGO_ENABLED=1` for FIPS mode. The API server uses `CGO_ENABLED=1` without `-tags no_openssl` to dynamically link OpenSSL.
   - **Admission Control**: Validating and mutating webhooks on PipelineVersion enforce schema and policy constraints before CRD persistence.
   - **RBAC**: Service accounts (ml-pipeline, ml-pipeline-persistenceagent, ml-pipeline-scheduledworkflow, ml-pipeline-ui) have minimal role bindings; viewer controller has separate RBAC for CRD watches.
   - **TLS Configuration**: Webhook and API server TLS are configurable; no cipher suite restrictions are enforced in code (relies on OpenSSL defaults via GOFIPS140).
   - **Certificate Handling**: Certificates are loaded from mounted secrets; no hardcoded certs detected.

6. **Multi-Tenancy**: Pipelines are namespace-scoped (namespaced CRDs). Each namespace can run independent pipelines with isolated Argo Workflows and metadata. Tenant isolation is enforced via Kubernetes RBAC and optionally Istio AuthorizationPolicy per namespace.

7. **Integration Vectors**:
   - **Argo Workflows**: Core execution engine (v3.7.14), invoked via SDK submit or dashboard triggers.
   - **Istio**: Optional virtual-service ingress for metadata-envoy; AuthorizationPolicy for MySQL access control.
   - **Kubernetes API**: Controllers use in-cluster ServiceAccount credentials for Pod creation, ConfigMap/Secret access, and CRD watches.
   - **ML Metadata**: Optional metadata store (gRPC) for lineage and artifact provenance.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | RBAC on ml-pipeline, ml-pipeline-persistenceagent, ml-pipeline-ui service accounts; optional Kubernetes API role restrictions per namespace | Kubernetes RBAC | No network-level isolation unless Istio NetworkPolicy or Calico is deployed; shared API server may have privilege escalation risks if service accounts are misconfigured |
| Data storage | MySQL: single shared database with implicit namespace partitioning via pipeline_name; Secrets scoped per namespace | MySQL / Kubernetes | **Gap**: No explicit row-level isolation in MySQL schema; relies on application logic to filter by namespace. Shared database across tenants is a schema-level risk. |
| Network traffic | Optional Istio VirtualService + AuthorizationPolicy per namespace; default: no NetworkPolicy | Istio / Kubernetes | **Gap**: Default deployment has no NetworkPolicy; all pods can reach all services (mysql, seaweedfs) unless explicitly restricted. |
| Compute & resources | ResourceQuota and LimitRange per namespace (optional) | Kubernetes | **Gap**: Not enforced in manifests; admin must configure per-namespace ResourceQuota for pod limits. |
| Configuration & secrets | Secrets per namespace (mlpipeline-minio-artifact, mysql-secret) | Kubernetes | Secrets are namespace-scoped; good isolation. Configurable via ConfigMaps also per-namespace. |
| API scoping | Pod watches and CRD queries filtered by NAMESPACE env var (controllers); API server returns pipelines/runs from all namespaces unless auth config restricts | Application / Kubernetes API | **Gap**: Shared API server serves all namespaces; namespace filtering is enforced via NAMESPACE env var for controllers but not for API queries. Recommend auth middleware (e.g., OIDC with namespace-scoped claims) to restrict API access per tenant. |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| MySQL | Shared database, implicit namespace partition | Application-level query filters on pipeline_name / namespace; no row-level security |
| SeaweedFS / S3 | Shared bucket, implicit namespace partition | Application-level path prefixes (e.g., s3://bucket/namespace-name/run-id/artifact) |
| Argo Workflows | Shared cluster, namespace-isolated | Workflows scoped to Kubernetes namespace; apiserver submits workflows with namespace from request context |

_Multi-tenancy is **namespace-scoped** but with shared backend infrastructure (MySQL, S3). Production deployments should enforce Kubernetes NetworkPolicy, implement auth middleware to restrict API access per tenant, and consider per-tenant MySQL databases or row-level security for sensitive workloads._
