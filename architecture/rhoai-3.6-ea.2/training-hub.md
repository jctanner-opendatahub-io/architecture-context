## Purpose

**Short**: Training Hub is an algorithm-focused Python library providing unified interfaces for Language Model (LLM) training, continual learning, and reinforcement learning techniques.

**Detailed**: Training Hub abstracts common LLM post-training workflows (Supervised Fine-Tuning, Continual Learning, Low-Rank Adaptation, Group Relative Policy Optimization, and Prompt Optimization) behind simple, consistent Python APIs. Rather than deploying as a Kubernetes service or operator, it is distributed as a PyPI package used by practitioners in research and development environments. It bridges multiple specialized backends (InstructLab, Unsloth, ART, verl, GEPA, MLflow) and integrates with distributed training frameworks like Hugging Face Accelerate and FSDP. The component is part of Red Hat's AI Innovation Team offering and supports integration with RHOAI environments through documentation and plugin support (Claude Code, Codex).

## Architectural Analysis

Training Hub operates as a unified training orchestration library rather than a deployed service. Its architecture is defined by:

1. **Backend Abstraction Pattern**: The library implements a backend registry (`Backend`, `AlgorithmRegistry`) that allows swapping training implementations (e.g., GEPA backend for prompt optimization vs. verl backend for multi-GPU GRPO). This enables the same user-facing API (`gepa()`, `lora_grpo()`) to dispatch to different computational backends.

2. **Multi-Algorithm Support**: Six core algorithms are exposed as top-level functions (sft, osft, lora_sft, lora_grpo, grpo, gepa), each with its own configuration schema and backend choices. The verl backend comment reveals a significant distinction: "Volcano Engine Reinforcement Learning for LLMs" (verl framework), which requires multi-GPU FSDP distribution and vLLM for rollout generation.

3. **Supply Chain Acknowledgment**: The pyproject.toml explicitly excludes compromised litellm versions (1.82.7-1.82.8) due to the TeamPCP supply chain attack (2026-03-24), demonstrating security awareness and proactive dependency management.

4. **Credential and API Integration**: The GEPA (prompt optimization) backend integrates with external LLM endpoints via litellm, managing OpenAI API keys and optional local endpoints (via OPENAI_API_BASE environment variables). This is not a backend service requirement but a development-time credential pattern for API-based optimization.

5. **Dependency Complexity**: Training Hub depends on 50+ PyPI packages spanning compute (torch, transformers, accelerate), optimization (peft, unsloth, xformers), efficiency (flash-attn, liger-kernel, bitsandbytes), data handling (datasets, pandas, pyarrow via fsspec), and experiment tracking (mlflow). No direct Kubernetes or networking libraries are present—the component is framework-agnostic regarding deployment infrastructure.

## Sub-Component Details

### sft (Supervised Fine-Tuning)

**Intent**: Standard supervised fine-tuning workflow via InstructLab-Training backend. Single entry point for multi-node distributed SFT on instruction-following datasets.

**Backend**: InstructLab-Training (instructlab-training >=0.16.2)

**Language**: Python

**Dependencies**: transformers, datasets, accelerate, torch, peft, CUDA extras (flash-attn, einops, etc.)

**Configuration Parameters**:
- `model_path`: Hugging Face model identifier or local path
- `data_path`: Training data path (JSONL or Parquet format)
- `ckpt_output_dir`: Checkpoint output directory
- `num_epochs`, `effective_batch_size`, `learning_rate`, `max_seq_len`, `max_tokens_per_gpu`

### osft (Orthogonal Subspace Fine-Tuning)

**Intent**: Continual learning workflow that tunes models while controlling preservation of existing behavior via orthogonal subspace constraints.

**Backend**: RHAI Innovation Mini-Trainer (rhai-innovation-mini-trainer >=0.8.3)

**Language**: Python

**Configuration Parameters**:
- `model_path`: Path to model (local or Hugging Face)
- `data_path`: Training data (JSONL format)
- `ckpt_output_dir`: Output directory
- `unfreeze_rank_ratio`: Fraction of parameters to unfreeze in subspace
- `effective_batch_size`, `max_tokens_per_gpu`, `max_seq_len`, `learning_rate`

### lora_sft (Low-Rank Adaptation + SFT)

**Intent**: Memory-efficient supervised fine-tuning using LoRA adapters. Supports single-GPU and multi-GPU training with Unsloth optimizations.

**Backend**: Unsloth (unsloth >=2026.1.1), with optional xformers acceleration

**Language**: Python

**Additional Features**:
- QLoRA support (4-bit quantization)
- Messages and Alpaca dataset format compatibility
- 2x faster training, 70% less memory via Unsloth

**Configuration Parameters**:
- `lora_r`, `lora_alpha`: LoRA rank and scaling
- Standard SFT parameters (model_path, data_path, learning_rate, num_epochs)

### lora_grpo (LoRA + Group Relative Policy Optimization)

**Intent**: RLVR training for tool-calling agents with two backend choices: ART (single-GPU time-sharing) or verl (multi-GPU distributed). Both backends decompose multi-turn tool-call traces into verification rewards without external API cost.

**Backends**:
- **ART**: OpenPipe ART + Unsloth GRPO (single-GPU, fast iteration)
- **verl**: Distributed verl framework (multi-GPU, multi-node, scales to 70B+ models)

**Language**: Python

**Kubernetes Integration** (verl backend): The lora_grpo_verl.py source file references "Volcano" in a docstring context ("Volcano Engine Reinforcement Learning"). This is NOT a direct dependency on Volcano cluster scheduler, but rather a descriptive reference to the verl framework. No Volcano CRDs or pod scheduling configurations are present; distribution is handled by torch.distributed and FSDP.

**Configuration Parameters**:
- `backend`: "art" or "verl"
- `n_gpus`: Number of GPUs (verl mode)
- `lora_r`, `lora_alpha`: LoRA configuration
- `num_iterations`: Training iterations
- `group_size`: Batch grouping for verl
- `data_path`: Tool-call trace data (JSONL)
- `reward_type`: "tool_call" or custom reward function

### grpo (Full Fine-Tuning GRPO)

**Intent**: Full-parameter GRPO training (vs. LoRA adapters). Requires multi-GPU setup and verl backend.

**Backend**: verl (verl >=0.7)

**Language**: Python

**Configuration Parameters**:
- `model_path`: Full-weight model path
- `data_path`: Tool-call traces
- `ckpt_output_dir`: Output directory
- `n_gpus`: Number of GPUs
- `num_iterations`: Training iterations

### gepa (Genetic-Pareto Prompt Optimization)

**Intent**: Gradient-free prompt optimization via evolutionary search. Does NOT modify model weights; optimizes textual prompts by calling external LLM endpoints (hosted APIs or local vLLM servers via litellm).

**Backends**:
- **gepa**: Direct GEPA optimize() API
- **mlflow**: MLflow prompt registry, scorers, and experiment tracking

**Language**: Python

**Key Credential Handling**: GEPA requires an LLM endpoint (e.g., OpenAI GPT-4, local vLLM). Credentials are managed via environment variables:
- `OPENAI_API_KEY`: API key for the task and reflection LMs
- `OPENAI_API_BASE`: Optional local endpoint (e.g., vLLM server)

The implementation defensively sets OPENAI_API_KEY to "dummy" when using local endpoints (api_base set) if no real key is provided, accommodating local vLLM servers that still require a token placeholder.

**Configuration Parameters**:
- `seed_candidate`: Initial prompt dictionary
- `task_lm`, `reflection_lm`: LLM model identifiers (litellm format, e.g., "openai/gpt-4o")
- `data_path`: Evaluation data (JSONL)
- `output_dir`: Results output
- `max_metric_calls`: Budget for LLM calls

**API Integration**: litellm library abstracts multiple LLM providers (OpenAI, Anthropic, local endpoints, etc.). The dependency excludes versions 1.82.7 and 1.82.8 due to the TeamPCP supply chain attack.

## Data Flows

Training Hub data flows are synchronous and purely within the user's process:

1. **Model Loading**: User specifies model_path (Hugging Face hub or local file) → transformers library loads weights → GPU memory
2. **Data Pipeline**: User provides data_path (JSONL, Parquet, or raw path) → datasets library loads data → batched iteration
3. **Training Loop**: Batches → backend (InstructLab, Unsloth, verl, etc.) → gradient updates → checkpoint saves
4. **GEPA Prompt Optimization** (special case):
   - Initial prompt → GEPA backend → genetic search loop
   - Each generation calls external LLM via litellm (OpenAI API or local vLLM)
   - Evaluation data → LLM API call → rewards → next generation
   - No persistent data storage; results saved to output_dir as JSON/CSV

No external data stores (databases, message queues, caches) are directly used by Training Hub. Some backends (mlflow, verl) may write to external systems, but this is handled within the backend implementations.
