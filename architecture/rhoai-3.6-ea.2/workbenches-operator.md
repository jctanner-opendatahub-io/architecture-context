## Purpose

**Short**: Reconciles the cluster-scoped `Workbenches` resource and deploys the notebook/workbench controller stack and notebook manifests for OpenShift.

**Detailed**: The operator is a standalone platform module. The platform orchestrator creates or updates the singleton `default-workbenches` `Workbenches` CR and projects platform, gateway, and MLflow configuration into it. When managed, the controller resolves the applications namespace, renders committed manifests from `opt/manifests`, injects CR-derived parameters and `RELATED_IMAGE_*` image overrides, and applies the resulting resources with Kubernetes server-side apply.

The controller tracks operand deployments and publishes module lifecycle status, release metadata, and distribution alignment. It owns the applied resources where possible, cleans them up on removal/deletion using a finalizer, and watches operand changes for drift and availability. Two mutating webhooks enrich Kubeflow Notebook resources with connection secrets and hardware-profile scheduling settings.

## Architectural Analysis

This is a cluster-scoped control-plane operator with a namespace-scoped operand data plane. Its committed manifest tree makes image and manifest rendering hermetic at runtime, while the `OpenDataHub` versus `SelfManagedRhoai` platform value selects the notebook overlay and UI configuration. A notable boundary is that `Workbenches` is cluster-scoped and singleton-constrained, but the created notebooks and operand deployments live in the resolved applications namespace.

The admission layer is intentionally fail-closed (`failurePolicy=Fail`) for Notebook create/update requests. Connection references are constrained to the Notebook namespace and checked with SubjectAccessReview; hardware profiles are read from the annotated namespace and can set resources, node selection, tolerations, and Kueue queue labels. TLS setup is dynamic: OpenShift service CA is preferred, cert-manager is a fallback, and the webhook is disabled when neither provider is available.

The operator has broad cluster permissions because it applies the upstream controller stack, including CRDs, RBAC, namespaces, deployments, NetworkPolicies, notebook resources, and webhook configurations. Bind/escalate permissions are resource-name restricted in a separate role, but the resulting service account remains a high-impact cluster administrator for the managed workbench domain.
