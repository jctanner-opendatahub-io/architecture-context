## Purpose

**Short**: Kubernetes operator that reconciles a cluster-scoped `Workbenches` CR and deploys the notebook controller stack (Kubeflow notebook controller, ODH notebook controller, and notebook manifests) on OpenShift.

**Detailed**: The Workbenches Operator is a module operator designed to run within the Open Data Hub (ODH) / Red Hat OpenShift AI (RHOAI) platform orchestration model. It manages the complete notebook infrastructure by:

1. Watching a singleton cluster-scoped `Workbenches` custom resource (`default-workbenches`).
2. Reconciling and deploying upstream Kustomize manifests for notebook controllers (Kubeflow notebook controller and ODH notebook controller).
3. Injecting platform-specific parameters (gateway domain, MLflow enablement, section title) into operand manifests.
4. Managing three key notebook-related webhooks: two mutating webhooks for connection and hardware profile injection, and one conversion webhook for Notebook resources.
5. Applying resources using Server-Side Apply (SSA) with hermetic, committed manifests (no network fetch at build time).
6. Reporting lifecycle status via the ModuleStatus lifecycle model with conditions, phases, and release metadata.

The operator integrates with the platform ConfigMap (`odh-workbenches-config`) to detect platform state and coordinate version handshakes, and auto-detects TLS providers (OpenShift, cert-manager, or none) for webhook certificate provisioning.

## Architectural Analysis

This is a tightly-scoped, single-responsibility operator focused on notebook infrastructure provisioning. Key architectural decisions:

**Manifest Management**: Upstream manifests are committed in `opt/manifests/` to enable hermetic container builds — the Dockerfile copies them into the image at build time, avoiding runtime GitHub fetches which would fail in airgapped environments. A scheduled GitHub Action refreshes ODH manifests daily and opens PRs for review.

**Kustomize Rendering**: The operator uses `sigs.k8s.io/kustomize/api` to render manifests by overlaying CR-derived and platform-projected parameters (`gateway-url`, `mlflow-enabled`, `section-title`) onto committed manifests. Rendered resources are applied via Server-Side Apply, enabling drift reconciliation and concurrent updates by other components.

**ModuleStatus Lifecycle**: The operator implements the platform's ModuleStatus specification with six phases (Pending, Initializing, Ready, Upgrading, Degraded, Failed) and eight conditions (Ready, ProvisioningSucceeded, DeploymentsAvailable, Degraded, ReleaseMetadataAvailable, ImageStreamsAvailable, WorkbenchesV2Ready, plus foreign conditions from orchestrators).

**Webhook TLS Auto-Detection**: The operator probes cluster API groups at startup to detect available TLS providers:
- **OpenShift** (highest priority): annotates Service and MutatingWebhookConfiguration for automatic cert generation via OpenShift's `service.beta.openshift.io/serving-cert-secret-name`.
- **cert-manager**: creates ClusterIssuer + Certificate resources and annotates webhooks for injection.
- **None**: disables webhooks entirely by deleting the MutatingWebhookConfiguration.

A periodic retry (30s) handles resources that appear after startup.

**Hardware Profile Injection**: The hardware profile webhook reads `HardwareProfile` CRs as unstructured objects to avoid importing the platform operator API. It applies resource requests/limits, node selectors, tolerations, and Kueue LocalQueue labels. When Kueue is active, node-based scheduling is skipped.

**Multi-Tenancy**: Single-tenant operator per cluster. Tenancy is delegated to namespace-scoped `Notebook` CRs. The operator ensures two namespaces: the applications namespace (resolved from `APPLICATIONS_NAMESPACE` env var or platform defaults: `opendatahub` for ODH, `redhat-ods-applications` for RHOAI) for operands and platform ConfigMap, and a legacy workbench namespace (for backward compatibility with JupyterHub-era notebooks). Component labels (`app.opendatahub.io/workbenches=true`, `app.kubernetes.io/part-of=workbenches`) ensure only managed resources are owned and cleaned up.

**Finalization**: A finalizer (`components.platform.opendatahub.io/workbenches-cleanup`) ensures operand resources are deleted when the CR is removed or when `spec.managementState=Removed`.

**FIPS Build**: The Dockerfile uses `CGO_ENABLED=1` and `-tags strictfipsruntime` to enable Go's FIPS runtime mode. The operator runs in a UBI9 minimal image with OpenSSL pre-installed, satisfying Konflux's check-payload validation.

| Aspect | Value | Source |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Operator RBAC on Workbenches CR + webhook RBAC (GET hardwareprofiles, CREATE events) | Kubernetes RBAC (workbenches-operator-manager-role, escalate role for upstream) | Webhook runs in operator namespace; no multi-tenant isolation at webhook level; all Notebook mutations are operator-wide |
| Data storage | Operand manifests (Deployments, ConfigMaps, RBAC, webhooks) scoped to single applications namespace; platform ConfigMap is per-namespace (default: opendatahub or redhat-ods-applications) | Kubernetes namespacing | Notebook CRs are namespace-scoped; data is isolated per namespace in the cluster |
| Network traffic | No explicit NetworkPolicy; operator communicates with kube-apiserver and probes OpenShift/cert-manager APIs | Kubernetes DNS, mTLS to kube-apiserver | No NetworkPolicy defined; operator has broad outbound access to cluster APIs |
| Compute & resources | Operator Deployment replicas: 1 (no scaling) | Kubernetes (single replica) | Operator is single-instance, non-scalable; no resource quotas defined |
| Configuration & secrets | Operator env (APPLICATIONS_NAMESPACE) and Helm values (webhooks.tlsProvider); operand ConfigMap (odh-workbenches-config) per namespace | Kubernetes ConfigMap + Environment variables | Configuration is operator-wide; Notebook operands read platform ConfigMap |
| API scoping | Workbenches CR is cluster-scoped (singleton); Notebook CR mutations are cluster-wide (all namespaces); webhook intercepts all kubeflow.org/v1 Notebook CREATE/UPDATE | Kubernetes admission webhooks (by API group/version/resource) | Webhook applies to ALL Notebooks in all namespaces; no per-tenant scoping (by design — workbenches-operator manages cluster-wide infrastructure) |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Notebook Controllers (kf-notebook-controller, odh-notebook-controller) | per-namespace (deployed once per cluster in applications namespace) | Shared controllers; Notebook CRs are namespace-scoped; controllers reconcile Notebook → Jupyter pod mapping per namespace |
| Hardware Profile Webhook | cluster-wide (single webhook mutates all Notebooks) | Webhook reads HardwareProfile CRs from target namespace; resource injection is per-Notebook (no shared state) |
| Connection Webhook | cluster-wide (single webhook injects all connections) | Webhook reads connection secrets from Notebook namespace; injections are per-Notebook |
| Platform ConfigMap (odh-workbenches-config) | per-namespace | Operator watches ConfigMap in resolved applications namespace; one copy per platform instance (opendatahub or redhat-ods-applications) |

**Assessment**: The operator is designed for single-cluster, single-tenant deployments. Multi-tenancy (multiple Notebook users, projects, etc.) is delegated to:
- **Namespace isolation** (Kubernetes-native): different projects use different namespaces.
- **Notebook-level controllers**: downstream kubeflow notebook controller and odh-notebook-controller handle per-user Jupyter instance lifecycle and resource isolation.
- **HardwareProfile CRs**: namespace-scoped, allowing per-namespace hardware configurations.
- **Connection secrets**: namespace-scoped, allowing per-namespace credential management.

The operator itself has no multi-tenant awareness; it is a cluster-wide infrastructure manager.
