## Purpose

**Short**: `llmdbenchmark` renders, deploys, exercises, observes, and tears down llm-d inference benchmark stacks and converts their results into benchmark reports.

**Detailed**: The component is primarily a Python command-line application and library. Its lifecycle commands (`plan`, `standup`, `smoketest`, `run`, `teardown`, `experiment`, and `results`) turn scenario specifications into Kubernetes manifests and commands, deploy model-serving stacks through several deployment modes, run workload harnesses, collect telemetry and artifacts, and analyze results.

It integrates with Kubernetes/OpenShift through the Python Kubernetes clients and `kubectl`/`helm` tooling. Supported paths include standalone vLLM, llm-d modelservice, fast model actuation, kustomize, and a no-Kubernetes local-container mode. It also includes a separate stack-discovery package that inspects Kubernetes resources and Gateway API/OpenShift Route objects to produce benchmark-report-compatible output.

## Architectural Analysis

This is an orchestration and measurement layer rather than an inference server or operator. The main control plane is a step executor driven by rendered scenario configuration; the data plane is supplied by the selected llm-d/vLLM/modelservice stack and temporary benchmark harness pods or local containers. The repository therefore describes many possible deployment topologies, while its own application does not register a stable HTTP or gRPC API.

The optional kustomize deployment resources create a namespaced single-replica StatefulSet, ClusterIP Service, edge-terminated OpenShift Route, and a narrowly named `pods/exec` Role. The static analyzer found the Service and Route but could not establish a complete Service-to-workload selector relationship because the templates use generated names and labels. The discovery image is a separate cluster-inspection workload with broad read-only access to pods, services, ConfigMaps, nodes, Routes, and Gateway API resources.

The build is not currently aligned with the AIPCC ecosystem: the primary image uses Debian Python 3.13 and the s390x image uses UBI 9 with extensive source builds, while neither Dockerfile uses AIPCC base-image or `rhaipcc` tooling. Python dependencies are also not represented by a repository lock file. These are supply-chain and reproducibility gaps for a productized RHOAI build.
