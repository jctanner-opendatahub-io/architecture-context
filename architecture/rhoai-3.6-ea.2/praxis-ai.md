## Purpose

**Short**: Praxis AI is an AI-native proxy gateway that classifies, transforms, routes, and enables observability for AI inference traffic across multiple providers and protocols.

**Detailed**: Praxis AI extends the Praxis proxy framework with specialized filters, provider integrations, and agentic protocol support for building AI gateways. It handles multi-provider routing (OpenAI, Anthropic, etc.), protocol translation, request enrichment, response storage via SQLite/PostgreSQL, OpenAI Responses/Conversations API support, Model Context Protocol (MCP) brokering, Agent-to-Agent (A2A) classification, token usage tracking, and external guardrails integration. The component separates from the core Praxis framework to provide rapid iteration on AI-specific features while maintaining clean separation of concerns between core proxy technology and domain-specific AI extensions.

## Architectural Analysis

Praxis AI is structured as a modular Rust workspace with ten architecture components organized by concern: the proxy server (`praxis-ai-proxy`), AI provider APIs (`praxis-ai-apis`), filter implementations (`praxis-ai-filters`), protocol integrations (`praxis-ai-llmd-ext-proc`), build infrastructure (`praxis-ai-build-support`), test harnesses, and development tooling. The server is a Pingora-based reverse proxy that loads YAML configuration, instantiates filter pipelines at startup, and delegates to Praxis core for base networking (listeners, TLS, load balancing, rate limiting, compression, CORS, health checks, WebSocket support). The component's architectural philosophy emphasizes clean separation of concerns: AI-specific logic remains isolated from core proxy technology, enabling rapid AI feature iteration without destabilizing the proxy foundation or imposing AI dependencies on non-AI deployments. Configuration is purely declarative (YAML), allowing operators to compose filters into request pipelines without code changes. Deployment as a single Alpine Linux container with no external runtime dependencies (SQLite for response storage is embedded; PostgreSQL is optional) simplifies operational footprint.

### FIPS Compliance

#### Build-Time FIPS (check-payload gate)

| Aspect | Value | Source |
|--------|-------|--------|
| **Build flags** | Not explicitly set (GOEXPERIMENT, strictfipsruntime not applicable to Rust) | Rust build, not Go |
| **Linking** | Dynamic (Rust runtime dynamically links OpenSSL via rustls/aws-lc-rs) | Containerfile: openssl-dev, openssl-libs-static installed; rust binary uses system OpenSSL |
| **OpenSSL in image** | Yes, installed via Alpine apk in builder and runtime stages | Containerfile:11 (openssl-dev, openssl-libs-static); Containerfile:98 (ca-certificates, no explicit openssl in runtime) |
| **OLM FIPS annotation** | Not applicable (no OLM Operator) | N/A |

Containerfile uses Alpine Linux base. Alpine does not ship system OpenSSL by default; the builder stage installs openssl-dev and openssl-libs-static for static linking during build. The runtime Alpine image (3.24) includes ca-certificates but relies on rustls bundled crypto. FIPS validation does not apply unless explicitly configured via environment variables or runtime flags.

#### Application-Level Crypto

| Aspect | Value | Source |
|--------|-------|--------|
| **TLS configuration** | Pure Rust TLS via rustls (default) or aws-lc-rs (Cargo.lock). No FIPS enforcement flags set at build time. | Cargo.toml: rustls, tokio-rustls dependencies; Cargo.lock: aws-lc-rs selected as crypto provider |
| **Crypto libraries** | Rustls (pure Rust, FIPS-compatible if aws-lc-rs is configured), aws-lc-rs (FIPS-validated, depends on runtime flags), ring (not FIPS-validated, fallback). Secrecy crate for sensitive data. | Cargo.toml:51 (rustls), Cargo.lock:281 (aws-lc-rs), Cargo.lock:3950 (ring); Cargo.toml:37 (secrecy) |
| **Certificate handling** | System trust store (ca-certificates in Alpine) for upstream connections; custom CA bundles via config. | Containerfile:98 (ca-certificates); reqwest library respects system store by default |
| **Non-FIPS crypto risks** | Ring crate (selected in Cargo.lock) is not a FIPS-validated provider. If ring is used at runtime, FIPS claims are unsupported. Rustls + aws-lc-rs combination can achieve FIPS compliance if explicitly enabled, but no build-time enforcement gate (like check-payload) validates this. | Cargo.lock:3950 (ring dependency); No GOEXPERIMENT=strictfipsruntime or equivalent Rust flag |

**Summary:** Praxis AI uses rustls (pure Rust) by default, which does not integrate with system OpenSSL. For FIPS compliance, the runtime must explicitly select aws-lc-rs as the crypto provider and validate that runtime configuration matches. This is not enforced at build time; Konflux check-payload does not apply to Rust binaries. Absence of FIPS enforcement at the binary level is a significant finding: operators must manually verify crypto provider configuration if FIPS compliance is required.

### Build Hermeticity

| Layer | Lock File | Present | Tool | Source |
|-------|-----------|---------|------|--------|
| **OS packages (RPM)** | rpms.lock.yaml | No | rpm-lockfile-prototype | Not applicable; Alpine uses apk (binary lock implicit in layer) |
| **Language deps** | Cargo.lock | Yes | cargo | /data/checkouts/.../Cargo.lock (148 KB, pinned versions for all 90+ transitive deps) |
| **Artifacts** | artifacts.lock.yaml | No | Hermeto | Not applicable; no artifact layer |
| **Hermeto prefetch** | cachi2.env | No | Hermeto | Not sourced in Containerfile; Docker layer caching used instead (buildkit mount directives on lines 59, 83) |

**Findings:**
- Rust dependency graph is fully locked via Cargo.lock.
- Alpine OS packages (apk) are not explicitly locked; builder stage `RUN apk add --no-cache openssl-dev openssl-libs-static pkgconf cmake make g++` fetches latest available versions of those packages on image rebuild. This is a hermeticity gap: OS package versions are not pinned.
- Docker BuildKit mount caching (lines 59, 83) provides layer-level caching but not hermetic provenance.
- No hermeto-style artifact provenance at the OS layer.
- For RHOAI downstream releases, rpm.lock.yaml or equivalent OS layer locking should be added.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Filter-based per route (credential_inject, custom auth filters). No built-in multi-tenant RBAC. | Application / Filter layer | Routes are not tenant-aware; same backend may serve multiple logical tenants if misconfigured. Auth is per-route, not per-tenant. |
| Data storage | Response storage via SQLite (co-located) or PostgreSQL (remote). No schema-level isolation; shared database requires application-level row-level filtering. | Application (filter config) | If multiple instances share a PostgreSQL backend, no database-level tenant isolation. Response cache is not tenant-scoped. |
| Network traffic | Outbound requests to upstreams are per-route (no tenant-aware firewall). Inbound requests are untagged with tenant info. | Application / Network | No NetworkPolicy per tenant. All outbound traffic routes through the same Praxis instance; egress filtering must be route-level. |
| Compute & resources | No tenant-specific resource quotas. Rate limiting is global or per-route, not per-tenant. | Application | High-volume tenant can starve others via token usage or request count. No built-in QoS. |
| Configuration & secrets | Secrets are global (single credential_inject config). Multiple tenants sharing an instance would share secrets. | Configuration | Credential leakage risk if multiple unrelated tenants share an instance. |
| API scoping | No tenant-scoped API watches or filtering. All routes see all configured backends. | Configuration | Route misconfiguration can expose tenant traffic to wrong backend. |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| PostgreSQL response cache (optional) | None (shared database) | Application-level query filtering by tenant_id column (if implemented at app layer); no database-level enforcement |
| Redis caching (optional) | None (shared instance) | Key namespacing via filter config; no Redis ACL per tenant |
| Upstream provider backends | Route-level (per route config) | YAML route configuration must isolate tenants to different upstreams |

**Summary:** Praxis AI is fundamentally single-tenant per deployment instance. Multi-tenancy is not a native feature. Operators deploying multi-tenant scenarios must:
1. Run separate Praxis AI instances per tenant, or
2. Implement application-level routing and isolation in downstream systems, or
3. Rely on external identity providers and filter-layer enforcement (high risk).
