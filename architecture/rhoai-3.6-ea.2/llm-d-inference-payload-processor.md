## Purpose

**Short**: IPP is an Envoy External Processing gRPC service that inspects and mutates inference request and response payloads through configurable plugins.

**Detailed**: The Inference Payload Processor (IPP) runs in the llm-d data plane beside an inference gateway proxy. Envoy streams request and response headers, bodies, and trailers to IPP over the External Processing API; IPP executes ordered request/response plugins and returns mutations such as routing headers.

The service loads a `PayloadProcessorConfig` from inline text, a file, or a Helm-rendered ConfigMap. Its framework supports profiles, payload processors, model selection, data-layer collectors/extractors, and model-to-header routing. The base-model plugin additionally watches labeled ConfigMaps and maintains an in-memory adapter-to-base-model mapping. The repository also contains development/e2e model-server simulators and Envoy resources, but the primary deployable artifact is the IPP binary.

## Architectural Analysis

IPP combines a controller-runtime manager with a data-plane gRPC server in one process. The manager supplies lifecycle, Kubernetes client/cache, metrics, and the ConfigMap reconciliation loop; separate non-leader-election runnables serve External Processing and health gRPC traffic. This permits a single IPP instance per gateway while keeping plugin configuration and adapter mappings hot-reloadable.

The default configuration extracts `model` from the request body into `X-Gateway-Model-Name` and resolves adapter names into `X-Gateway-Base-Model-Name`. The plugin registry makes the request/response pipeline extensible, while the model selector uses Filter → Score → Pick stages for model-level choice. This is a payload-aware routing layer, not an inference server.

The deployment defaults are intentionally development-oriented: one replica, plaintext ext-proc, unauthenticated metrics, a NodePort in the raw e2e manifests, and a static distroless image. Production operators should supply transport security and traffic policy through the provider integration and should review the cluster-wide ConfigMap RBAC granted to the service account.
