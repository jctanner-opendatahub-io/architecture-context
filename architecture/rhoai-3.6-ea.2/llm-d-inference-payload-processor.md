## Purpose

**Short**: A pluggable framework for inspecting and mutating inference request and response payloads in the llm-d data plane via Envoy's External Processing API.

**Detailed**: The Inference Payload Processor (IPP) is a critical component in the llm-d inference data plane that runs as a sidecar to the inference gateway's proxy. It implements the Envoy External Processing (ext-proc) protocol to intercept, inspect, and mutate both incoming requests and outgoing responses in real time. IPP's primary use case is payload-aware routing: extracting signals from request bodies (such as model names or input parameters) and injecting routing headers that allow a single gateway endpoint to intelligently route requests to multiple backend models and LoRA adapters. The component is built around a pluggable framework where users define request processors, response processors, model selectors, and profile pickers via a declarative YAML configuration (`PayloadProcessorConfig`). This design allows operators to extend IPP without forking the codebase.

## Architectural Analysis

The Inference Payload Processor exemplifies a lightweight, pluggable sidecar architecture optimized for the inference data plane. Rather than implementing a monolithic routing engine, IPP delegates routing decisions to the llm-d Router's Endpoint Picker (EPP) and focuses narrowly on payload inspection and header injection. This separation of concerns aligns with the Gateway API Inference Extension design, which partitions routing into multiple stages: IPP handles request-level signals (e.g., extracting the model name from the request body), and the downstream EPP selects which pod serves the request within a chosen pool.

The component's pluggable framework is implemented as a configuration-driven pipeline. At startup, the runner instantiates plugins named in the `PayloadProcessorConfig`, then registers request and response processors in the order they appear in the config. Profiles group these processors by name, and a profile picker (configurable) selects which profile handles each request. This architecture makes it easy to compose preprocessing and postprocessing steps without code changes.

Key architectural signals:

1. **Controller-Runtime Integration**: IPP uses `sigs.k8s.io/controller-runtime` for both Kubernetes client interaction and lifecycle management. A controller reconciles ConfigMap resources to support dynamic configuration updates—plugins can watch ConfigMaps to reload model or routing tables without restarting.

2. **gRPC ExtProc Protocol**: IPP's core interface is gRPC, implementing the Envoy External Processor service. All request/response processing flows through a bidirectional gRPC stream; the component never receives raw HTTP but only processed messages defined by the ext-proc proto schema.

3. **TLS Support**: The ext-proc server supports optional TLS via self-signed certificates. The `--secure-serving` flag toggles between TLS and plaintext; certificates are generated at runtime with a 10-year validity. Default deployment has TLS disabled.

4. **Observability Stack**: The component ships with OpenTelemetry integration (tracing via OTLP gRPC export), structured logging via zap, and Prometheus metrics. Metrics are served on port 9090 with configurable authentication.

5. **Model Selection Framework**: IPP implements a generalized three-stage pipeline—Filter → Score → Pick—for selecting which model serves a request. This mirrors the Scheduler Architecture pattern from the Gateway API Inference Extension but applies it at the model level rather than pod level.

6. **Single-Tenant Deployment**: IPP is deployed once per gateway instance. Tenant isolation relies on namespace scoping and the upstream proxy's request routing; no per-tenant isolation mechanisms exist within IPP.

**Architecture Risks and Gaps**:

- ConfigMap-based configuration without versioning or conflict detection. Concurrent updates to ConfigMaps from different sources could lead to inconsistent state.
- No explicit authentication on the Health gRPC service or metrics endpoint when metrics-endpoint-auth is disabled.
- TLS for ext-proc is optional and defaults to off in the provided manifests; operators must enable `--secure-serving=true` and manage certificate lifecycle.
- No ResourceLimits in deployment manifests; vulnerable to noisy neighbor.
- Base image digest is not pinned; introduces supply-chain variability.

3. Define NetworkPolicies to restrict access to gRPC and metrics ports

_FIPS Assessment_: IPP is built with **pure-Go static linking** (CGO_ENABLED=0) and **no OpenSSL** in the container image. This will **FAIL** the Konflux check-payload FIPS validation gate, which requires:
- Dynamically linked Go binaries (CGO_ENABLED=1)
- OpenSSL installed in the image

However, the application code itself uses FIPS-capable libraries (stdlib crypto/tls). To pass Konflux FIPS enforcement, the build must be changed to:
1. Set CGO_ENABLED=1 in Dockerfile
2. Use UBI base image (or distroless with OpenSSL installed separately)
3. Link against system OpenSSL

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Kubernetes RBAC per namespace; upstream Envoy proxy controls request ingress | Kubernetes / Envoy proxy | No per-request authentication in IPP; trusts Envoy as sole client |
| Data storage | No shared data layer; config via ConfigMap within namespace; in-memory plugin state | Kubernetes | ConfigMap watch is cluster-wide with manual namespace filtering; concurrent updates not version-controlled |
| Network traffic | Namespace scoping; internal ClusterIP for model server discovery | Kubernetes | No explicit NetworkPolicy; relies on namespace isolation and proxy firewall rules |
| Compute & resources | ResourceLimits not set in manifests; relies on cluster-wide defaults | Kubernetes | Manifest specifies no CPU/memory limits; vulnerable to noisy neighbor and resource starvation |
| Configuration & secrets | ConfigMap per namespace; no cross-namespace sharing | Kubernetes | Single ConfigMap per IPP; no versioning or rollback; concurrent updates could cause inconsistency |
| API scoping | ConfigMap watches are namespace-scoped (NAMESPACE env var applied) | Application (controller-runtime) | ConfigMap reconciler filters by namespace; no sub-namespace partitioning |

_Isolation Notes_: IPP is designed for single-tenant per-gateway deployment. Tenant isolation at the cluster level is achieved through namespace scoping; within IPP, there is no explicit per-tenant isolation mechanism. Profiles can be selected per-request, but all profiles share the same plugin instances and in-memory state.
