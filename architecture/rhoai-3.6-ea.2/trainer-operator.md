## Purpose

**Short**: A Kubernetes operator that reconciles the `Trainer` custom resource and deploys upstream Kubeflow Trainer v2 resources via templated kustomize manifests.

**Detailed**: The trainer-operator is a cluster-scoped OpenShift/Kubernetes operator that manages the deployment and lifecycle of Kubeflow Trainer v2 infrastructure. It reconciles the `components.platform.opendatahub.io/v1alpha1/Trainer` custom resource, which is the ODH platform's abstraction for training job orchestration. The operator follows a manifest-template pattern: it ships pre-packaged upstream Kubeflow Trainer manifests, runtime definitions, and image stream configurations that are dynamically rendered at runtime via kustomize overlays, parameter injection, and Server-Side Apply. This design allows the operator to inherit upstream improvements while providing platform-level configuration control (namespace targeting, resource constraints, RELATED_IMAGE overrides). The operator also enforces platform conventions through its use of `odh-platform-utilities` for common patterns (PlatformObject interface, condition management, garbage collection, label-based resource discovery).

## Architectural Analysis

The trainer-operator implements a **manifest templating and reconciliation pattern** with several key design decisions:

1. **Manifest Pipeline**: Upstream Kubeflow Trainer manifests are fetched at build time by `hack/get_trainer_manifests.sh`, embedded into the container image at `/opt/manifests-template/`, and then rendered at runtime by the reconciler. This decouples the operator's build cycle from upstream trainer releases while maintaining hermetic artifact provenance. The runtime rendering process accepts `RELATED_IMAGE` environment variable overrides to support Konflux image substitution and air-gapped environments.

2. **Cache Hardening & Namespace Scoping**: The operator uses a scoped cache strategy to reduce memory footprint and API load. It only watches platform-managed resources (identified by the `platform.opendatahub.io/part-of: trainer` label) and respects the `APPLICATIONS_NAMESPACE` environment variable for multi-tenant deployments where multiple application namespaces may exist. This prevents unintended cluster-wide informer instantiation (a known anti-pattern in Kubernetes operators).

3. **RBAC Escalation Compliance**: The operator holds broad permissions to manage upstream Trainer RBAC policies (Kubeflow's ClusterRoles, RoleBindings, and related resources) because it must create and patch the exact roles that upstream trainer components expect. This is a compliance requirement enforced by Kubernetes RBAC escalation prevention: the operator's service account must already possess all permissions it intends to grant via manifests.

4. **TLS Profile Resolution**: The operator resolves the OpenShift cluster's TLS profile at startup (GOEXPERIMENT=strictfipsruntime in Dockerfile.konflux) and applies it to metrics serving. This ensures metrics endpoints comply with cluster-wide TLS policies—particularly important in FIPS-enforced clusters.

5. **Garbage Collection Pattern**: Resource cleanup uses label-based discovery via `odh-platform-utilities/pkg/controller/gc` rather than ownership chains. This allows the operator to adopt and eventually clean up resources created by upstream trainer (which doesn't know about the `Trainer` CR) by applying the `platform.opendatahub.io/part-of: trainer` label during initial manifest rendering.

6. **Finalization Strategy**: A finalizer (`components.platform.opendatahub.io/trainer-cleanup`) ensures that when a Trainer CR is deleted, the operator has a chance to clean up all discovered resources before the CR itself is removed. This prevents orphaned Deployments, Services, and ClusterRoles if a user accidentally deletes the Trainer.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | RBAC via trainer-operator manager role; per-namespace trainer-admin/viewer roles | Kubernetes RBAC | Users with trainer-admin role in one namespace can impact training jobs in that namespace; cluster-wide admin role grants access to all Trainers |
| Data storage | Trainer-managed resources (Deployments, Services, ConfigMaps) scoped to target namespace | Kubernetes namespace | Upstream trainer may share etcd; no per-tenant schema isolation |
| Network traffic | Network policies can be deployed; no built-in per-namespace network isolation | Kubernetes NetworkPolicy (manual) | Requires explicit NetworkPolicy configuration; not automated by operator |
| Compute & resources | Trainer spec allows per-controller resource constraints; platform can set global ResourceQuota | Kubernetes ResourceQuota / LimitRange | Upstream trainer controllers may not respect all quota constraints |
| Configuration & secrets | Configuration via Trainer.spec; secrets via environment (RELATED_IMAGE_*) | Kubernetes Secrets + RBAC | Upstream trainer may create ClusterRoles readable by all namespaces |
| API scoping | Trainer CR is cluster-scoped; watches are label-filtered to trainer-managed resources | Kubernetes cache filter | Cluster scope limits true multi-tenancy; only one Trainer CR allowed |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Upstream Trainer controller pod | Cluster-wide (single shared instance) | Pod runs in single namespace; namespace-scoped trainer workloads create isolated job pods |
| Kubernetes etcd | Cluster-wide | No per-tenant isolation; RBAC controls access to resources |

**Multi-Tenancy Assessment**: The operator is designed for **single-tenant per cluster** usage. The `APPLICATIONS_NAMESPACE` environment variable allows optional scoping to a single namespace for shared-infrastructure scenarios, but the singleton Trainer CR pattern and cluster-wide scope of the CRD mean true multi-tenancy (multiple isolated tenants on one cluster) is not natively supported. Upstream Kubeflow Trainer itself is single-tenant per cluster.

## Data Flows

### Flow 1: Trainer CR Reconciliation and Manifest Rendering

| Step | Source | Destination | Port | Protocol | Encryption | Auth |
|------|--------|-------------|------|----------|------------|------|
| 1 | Trainer CR (etcd) | trainer-operator manager Pod | (internal) | (cluster internal) | (internal) | RBAC (service account token) |
| 2 | trainer-operator manager Pod | Disk (/opt/manifests-template/, /opt/runtimes-template/) | (local) | (filesystem) | (N/A) | File permissions |
| 3 | trainer-operator manager Pod | Kubernetes API (Server-Side Apply) | 443 | HTTPS | TLS 1.2+ | Bearer token (service account) |
| 4 | Kubernetes API | etcd | (internal) | (internal) | (depends on cluster config) | (internal) |
| 5 | trainer-operator manager Pod | Kubernetes API (watch) | 443 | HTTPS | TLS 1.2+ | Bearer token |
| 6 | Kubernetes API | trainer-operator manager Pod | (internal) | WebSocket | (depends on cluster) | (service account token) |

**Reconciliation Lifecycle**:
1. **Detect Trainer CR change** (watch event): operator's reconcile queue is triggered
2. **Fetch template files** from embedded `/opt/manifests-template/`, `/opt/runtimes-template/`, `/opt/imagestreams-template/`
3. **Render kustomize overlay** using `odh-platform-utilities/pkg/render/kustomize` with RELATED_IMAGE env var substitutions
4. **Apply manifests** via Kubernetes Server-Side Apply (SSA) to ensure convergence without full object replacement
5. **Watch dependent resources** (Deployments, Services, ValidatingWebhookConfigurations) for rollout status
6. **Update Trainer.status** with Ready condition, release versions, and component status
