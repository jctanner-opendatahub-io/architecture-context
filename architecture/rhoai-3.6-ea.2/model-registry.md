## Purpose

**Short**: Kubeflow Hub is a unified platform for model artifact lifecycle management, providing central registry for storing and managing ML model versions, metadata, and catalog-based federated discovery across external catalogs.

**Detailed**: Kubeflow Hub (formerly known as Model Registry) serves as the backbone for model governance in OpenDataHub and RHOAI. The component provides three primary services: (1) a Go-based backend server implementing OpenAPI contract for model registry operations, (2) a Kubernetes controller for integrating with KServe InferenceService for model serving lifecycle, and (3) a TypeScript/React UI with Go BFF (Backend-for-Frontend) for user interactions. The catalog subsystem enables federated model discovery across external repositories. The system supports multiple deployment variants (ODH, RHOAI, standalone) and database backends (MySQL, PostgreSQL, SQLite for development).

## Architectural Analysis

Kubeflow Hub is architected as a multi-tier system with clear separation between data plane, control plane, and user-facing layers. The backend leverages GORM for database abstraction, supporting multiple relational database backends, making it deployable across diverse infrastructure environments. The controller component implements a reconciliation loop watching KServe InferenceService resources, enabling model registry metadata to flow into serving configurations.

Three distinct security boundaries are enforced: (1) Kubernetes RBAC controls component permissions (service account `controller-controller-manager` limited to specific API groups and resources), (2) Istio AuthorizationPolicy gates HTTP endpoints at the ingress, and (3) the BFF implements application-level Bearer token validation for user API requests. The metrics endpoint is secured with self-signed TLS and controller-runtime authn/authz filtering.

Build-time FIPS compliance is demonstrated through `GOEXPERIMENT=strictfipsruntime` and dynamic linking in the Dockerfile.konflux, ensuring dynamically-linked binaries validated by Konflux check-payload gate. The catalog service includes HTTP health endpoints and MCP (Model Context Protocol) server integration for plugin-based extensibility.

## Multi-Tenancy

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| **Tenant boundary** | Per-namespace + per-user (at API layer) | Istio AuthorizationPolicy allows specific namespace (kubeflow); BFF enforces Bearer token per-user |
| **Deployment model** | Multi-tenant with shared backend; single instance of model-registry-server per cluster; multiple controller instances possible via leader election | cmd/controller/main.go:118-119, manifests/kustomize/options/istio/istio-authorization-policy.yaml |
| **Tenant identifier** | Kubernetes namespace (from Istio context) + user identity (from Bearer token in Authorization header) | Istio AuthorizationPolicy, clients/ui/bff/cmd/main.go:56 |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-namespace Istio AuthorizationPolicy + per-user Bearer token validation | Kubernetes Istio sidecar + application middleware | No explicit user-to-model RBAC; multitenancy is coarse-grained (namespace level) |
| Data storage | Shared relational database (MySQL/PostgreSQL/SQLite) with no tenant column filtering | Application query logic (implicit) | Risk: No row-level filtering in GORM queries; database schema lacks tenant_id columns; potential for cross-tenant data leakage if RBAC is misconfigured |
| Network traffic | Istio AuthorizationPolicy per service; NetworkPolicy can be layered by operator | Istio + Kubernetes | Depends on cluster-wide NetworkPolicy setup; defaults to allow all intra-cluster traffic if not explicitly configured |
| Compute & resources | ResourceQuota per namespace (operator-managed) | Kubernetes | No hardcoded limits in deployment manifests; relies on cluster administrator to set |
| Configuration & secrets | Per-namespace Secrets and ConfigMaps | Kubernetes | Secrets scope to namespace; BFF reads from current namespace; risk if BFF uses wrong namespace context |
| API scoping | Namespace-scoped watches on InferenceService; Istio blocks cross-namespace traffic | controller-runtime watches + Istio | Namespace-scoped CRD watches prevent cross-namespace enumeration; API endpoints coarse-grained by namespace |

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Relational database (MySQL/PostgreSQL) | Single shared instance; no tenant column in schema | No application-level row-level security; relies on Kubernetes RBAC preventing unauthorized API access |
| Model Registry backend API | Shared service instance; no tenant path parameter | Namespace-level access control via Istio AuthorizationPolicy |
| Async upload job queue | Shared Kubernetes Job queue | Namespace-scoped job creation; no per-user quotas |

**Multi-Tenancy Assessment**: The component is deployed as a shared, single-instance service with namespace-level isolation. True per-user isolation is limited; the BFF validates Bearer tokens but does not enforce per-user model quotas or row-level security in the database. This is suitable for RHOAI environments where Istio and Kubernetes RBAC provide the primary tenant boundary.
