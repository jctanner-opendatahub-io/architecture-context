## Purpose

**Short**: Provides a declarative Kubernetes API for deploying and managing Model Context Protocol (MCP) servers.

**Detailed**: The operator reconciles namespaced `MCPServer` resources and creates a same-name Deployment, ClusterIP Service, and ingress-only NetworkPolicy for each server. It accepts a container image source, runtime configuration, environment/configuration references, storage and pod settings, and MCP transport options.

The controller validates configuration, performs an MCP initialize handshake, publishes Accepted and Ready conditions plus the cluster-internal service address, and reports operational metrics and Kubernetes events. It watches owned workloads so changes and failures converge back to the `MCPServer` specification.

## Architectural Analysis

This is a conventional controller-runtime operator with a narrow, namespaced data-plane contract. A single `MCPServer` is the source of truth for its Deployment, Service, and NetworkPolicy, and owner references provide garbage collection. ConfigMap and Secret reference indexes plus a configuration-hash annotation allow configuration changes to trigger rollout behavior without requiring users to edit unrelated workload fields.

The operator performs an active MCP handshake before declaring the server ready, which makes status more meaningful than Deployment availability alone. It also supports CA-bundle rotation detection and optional propagation of validated TLS environment variables to server containers. The primary architectural risks are the intentionally broad operator ClusterRole, optional certificate verification bypass, self-signed metrics certificate default, and missing RPM/artifact lock evidence for a hermetic release build.

Webhook infrastructure is instantiated in the manager code, but webhook resources and handlers are not enabled in the default kustomization and the analyzer reports no admission or conversion webhook. It should therefore be treated as dormant scaffold/configuration rather than an exposed component API.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Kubernetes RBAC; aggregated admin/edit/view roles for MCPServer users; shared operator ServiceAccount | Kubernetes | Operator ClusterRole can read ConfigMaps/Secrets and manage workloads across namespaces; no per-tenant operator identity. |
| Data storage | No database or persistent data store; generated pods and referenced configuration are namespace-scoped | Kubernetes | Server application data isolation is outside this operator. |
| Network traffic | Per-MCPServer ingress-only NetworkPolicy allowing the configured server port | Kubernetes | Policy does not specify source namespaces/pods, so allowed ingress is broad within the namespace/network-plugin semantics; egress is not restricted. |
| Compute & resources | Per-MCPServer Deployment; pod resources and scheduling may be supplied in the CR | Kubernetes | No ResourceQuota, LimitRange, node isolation, or cross-tenant fairness is created here. |
| Configuration & secrets | ConfigMap/Secret references are resolved in the MCPServer namespace | Kubernetes/controller | Operator has cluster-wide read permissions; user-configured references and `InsecureSkipVerify` require tenant governance. |
| API scoping | Namespaced CRD and namespaced child objects; controller watches MCPServers and owns child resources | Kubernetes/controller-runtime | The operator's cluster-scoped RBAC means isolation depends on Kubernetes authorization and controller correctness. |
