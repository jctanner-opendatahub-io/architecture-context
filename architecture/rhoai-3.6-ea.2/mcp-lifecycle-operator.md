## Purpose

**Short**: A Kubernetes operator that provides a declarative API to deploy, manage, and safely roll out Model Context Protocol (MCP) servers with production-grade lifecycle automation.

**Detailed**: The MCP Lifecycle Operator enables Kubernetes-native management of MCP servers through custom resources (MCPServer CRD). MCPs are standardized protocols that allow AI applications to interact with tools, resources, and prompts exposed by backend services. This operator automates the full lifecycle of MCP server deployments including container image sourcing, configuration injection, health monitoring, and safe rollout patterns. It creates and manages underlying Kubernetes resources (Deployments, Services, NetworkPolicies) on behalf of MCPServer custom resources, providing a declarative abstraction layer that simplifies MCP server integration into Kubernetes clusters.

The operator is part of Kubernetes SIG Apps and serves as the foundation for MCP server discovery and lifecycle management in AI-enabled Kubernetes platforms, particularly RHOAI.

## Architectural Analysis

The MCP Lifecycle Operator follows a standard Kubernetes controller-manager pattern built with kubebuilder. It is a single-purpose operator focused exclusively on the MCPServer CRD lifecycle with no other managed resources. The architecture emphasizes:

- **Minimal API Surface**: One core CRD (MCPServer v1alpha1) in the mcp.x-k8s.io API group. No serving runtimes, no ingress management, and no platform integration CRDs.
- **Declarative Resource Management**: The operator watches MCPServer resources and creates corresponding Deployments, Services, and NetworkPolicies with ownership references. This ensures clean cleanup on CR deletion and prevents silent overwrites of resources managed by other controllers.
- **Health & Readiness Probes**: All deployments created by the operator include HTTP-based liveness and readiness probes on port 8081 (/healthz and /readyz endpoints).
- **Metrics & Observability**: Built-in Prometheus metrics support (port 8443 HTTPS by default, or 8080 HTTP). Metrics endpoint requires authentication via token review and subject access review.
- **Leader Election**: Supports leader election for high-availability deployments in multi-replica scenarios.
- **FIPS Compliance**: Build-time FIPS enforcement via Dockerfile with GOEXPERIMENT=strictfipsruntime and post-quantum-safe UBI base images (ubi-minimal-pqc).

Key design pattern: The operator accepts MCPServer specifications with container image references, port configurations, environment variables, and storage mounts, then synthesizes appropriate Kubernetes resources. NetworkPolicies are generated to restrict traffic by default, defaulting to deny-all with explicit allow rules for the MCP server port.

#### MCPServer API Details

The MCPServer CRD spec includes:
- **Source** (required): Container image reference with validation rules for OCI image format, tags, and digests
- **Config** (required): Runtime configuration including port (required), environment variables, arguments, storage mounts, and health check configuration
- **RuntimeConfig** (optional): Optional runtime metadata and policies
- **SecurityConfig** (optional): Security-related settings for the deployment

Status fields track:
- **conditions**: Accepted (CR is valid) and Ready (deployment is available)
- **address.url**: Cluster-internal URL of the deployed MCP server (e.g., http://server-name.namespace.svc.cluster.local:port/mcp)
- **deploymentName**: Reference to the synthesized Deployment
- **serviceName**: Reference to the synthesized Service

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Namespace-scoped RBAC on MCPServer CRD; kubeadm defaults deny all | Kubernetes RBAC | Standard Kubernetes isolation; no additional tenant-aware auth enforced by operator |
| Data storage | Each MCPServer creates a namespaced Deployment; storage mounts are pod-spec-level | Kubernetes (volumes, PVCs) | No cross-namespace data sharing by design; storage isolation depends on PVC provisioner |
| Network traffic | Default-deny NetworkPolicy per namespace; operator creates NPs scoped to namespace | Kubernetes NetworkPolicy | Strong by default; restricts metrics access to labeled namespaces |
| Compute & resources | Standard Kubernetes ResourceQuota and LimitRange per namespace | Kubernetes | Not enforced by operator; relies on cluster admin configuration |
| Configuration & secrets | Environment variables and secret references in MCPServer spec are pod-level | Kubernetes (Secrets API) | Per-namespace Secret isolation applies; no cross-tenant secret leakage by design |
| API scoping | All CRs and resources created by operator are namespaced | Kubernetes API scoping | Operator does not watch cluster-wide resources; full per-namespace isolation |
