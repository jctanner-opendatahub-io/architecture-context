## Purpose

**Short**: Provides online ML-based latency prediction services (Time-To-First-Token and Time-Per-Output-Token) for the llm-d ecosystem.

**Detailed**: 
The llm-d-latency-predictor component manages a dual-service architecture for predicting LLM inference latency metrics. The prediction server exposes a read-only FastAPI service that accepts LLM request profiles and returns estimated Time-To-First-Token (TTFT) and Time-Per-Output-Token (TPOT) latencies using pre-trained ML models (XGBoost, LightGBM, and AutoML-derived models). The training server accepts observed latency measurement data, retrains the underlying models online, and exports model artifacts for distribution to prediction pods. Both services are stateless FastAPI applications that run as Deployments with independent replica strategies: the prediction server scales to 10 replicas with minimal resource overhead (250m CPU, 512Mi memory per pod), while the training server runs as a singleton (1 replica) with heavier resource allocation (1000m CPU, 2Gi memory) to handle model computation workloads.

## Architectural Analysis

The component implements a **learned latency inference pattern** commonly seen in systems that need to predict queueing and compute delays without running actual inference experiments. The architecture decouples data collection (training server) from serving (prediction server), allowing prediction replicas to independently download and cache pre-trained models while the training server maintains a master copy and retrains on ingested data.

**Key design decisions:**

1. **Dual-server separation**: Training and prediction servers are independent deployments with different scaling strategies. This allows prediction to scale horizontally (10 replicas) without coordinator bottlenecks, while training centralizes model state in a single pod.

2. **Local model caching in prediction pods**: Each prediction pod independently downloads and caches models in `/local_models` (an emptyDir volume). This eliminates shared storage requirements but creates a consistency challenge: new models must be propagated by explicit pod reload or restart. The readiness probe includes a generous failure threshold (10 retries over ~50 seconds) to accommodate model download on cold starts.

3. **Python FastAPI stack**: Both servers use Python with FastAPI, uvicorn, and standard ML libraries (scikit-learn, XGBoost, LightGBM). This choice prioritizes rapid iteration on model algorithms over runtime performance — actual latency prediction is likely lighter-weight than the serving framework overhead.

4. **Stateless model storage**: The training server uses an emptyDir volume (`/models`) for temporary model storage, not a persistent backend. This means restarted training pods lose model history and suggests models are either exported to external storage (S3, model registry) or regenerated on demand.

5. **Environmental configuration via ConfigMap**: Each deployment reads a ConfigMap (`latency-predictor-config` for training, `prediction-server-config` for prediction) at runtime, enabling configuration drift without container rebuild.

**Risks & observations:**

- **Model propagation complexity**: Prediction pods must somehow receive updates to models trained by the training server. The codebase provides an HTTP `/reload` endpoint on the prediction server, but the mechanism for triggering this reload across 10 pods is not visible in the manifests — it likely requires an external service or manual intervention.
- **Training data durability**: Training models are stored in an emptyDir volume. If the training pod crashes, unsaved models are lost. For a production system, this suggests models are immediately exported to persistent storage (S3, Git, model registry).
- **No RBAC or multi-tenancy isolation**: The Deployments use default service accounts with no ClusterRoles or RoleBindings defined. Both servers are accessible via ClusterIP Services with no authentication gates, suitable for internal platform services but requiring ingress-layer or sidecar-based auth if exposed to multi-tenant workloads.
