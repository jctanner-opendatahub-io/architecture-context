## Purpose

**Short**: Feast is an open-source feature store that manages offline and online feature storage, retrieval, and serving for machine learning models.

**Detailed**: Feast abstracts feature infrastructure from ML applications by providing a unified API for feature definition, materialization, and retrieval. The component includes two main deployable artifacts: a Kubernetes operator (Go-based) that manages FeatureStore custom resources, and a Python-based feature server that handles low-latency online feature retrieval. Teams use Feast to decouple ML models from underlying data infrastructure, ensuring consistent feature definitions across training and serving, preventing data leakage through point-in-time correctness, and supporting multi-tenancy through namespace-scoped deployments. The RHOAI distribution includes operator control and integration with OIDC-based authorization, Kubernetes RBAC, and on-demand feature transformations.

## Architectural Analysis

Feast follows a distributed feature store architecture with clear separation between control-plane (operator) and data-plane (feature server) components. The operator reconciles FeatureStore custom resources into workloads, managing initialization, registry setup, and feature materialization jobs. The feature server provides gRPC and HTTP endpoints for real-time feature lookup, with support for multiple online store backends (Redis, DynamoDB, Postgres, etc.).

The RHOAI-specific distribution emphasizes multi-tenancy and security: feature servers run in user namespaces, isolated via Kubernetes RBAC and optional OIDC integration. Authorization is pluggable (Kubernetes RBAC, OIDC, or no-auth), allowing teams to configure least-privilege access. The operator watches FeatureStore CRDs and spawns feature server deployments, registry servers, and batch materialization jobs, supporting cloud-native deployment patterns (GitOps, CronJob triggers, OpenLineage integration).

Network exposure is intentionally scoped: the operator runs cluster-wide, exposing metrics only on internal ports; feature servers expose gRPC/HTTP internally by default, with optional Route/Ingress for external access. Batch processing integrates with Apache Spark or Dask, enabling historical feature computation at scale.

Cryptographic concerns are minimal at runtime: TLS is enforced by platform (HTTPS for external access, mTLS for Kubernetes API interactions). The operator uses Go stdlib crypto (OpenSSL via CGO, FIPS-compliant build flags). The Python feature server inherits OpenSSL from the AIPCC base image and depends on cryptography/pyOpenSSL for JWT validation in OIDC flows.

## Multi-Tenancy

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| **Tenant boundary** | per-namespace | FeatureStore CRD is namespaced; each namespace may deploy its own FeatureStore with isolated service accounts and ConfigMaps |
| **Deployment model** | multi-tenant (per-namespace instances) | Operator watches cluster-wide; each namespace can instantiate a FeatureStore CR that spawns isolated feature server deployment in that namespace |
| **Tenant identifier** | namespace name | Kubernetes namespace isolation via ServiceAccount and RBAC roles bound to namespace |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | per-tenant RBAC roles (feature server service account has minimal permissions per namespace) + optional OIDC per FeatureStore | Kubernetes RBAC + Feature Server authz config | Operator cluster-wide; if multi-team clusters, teams could inspect other teams' CRDs via get/describe (mitigated by namespace isolation if RBAC is tightly configured) |
| Data storage | per-namespace ConfigMaps (feature definitions, online/offline store configs) + per-namespace PVCs (optional, for registry) | Kubernetes RBAC + filesystem | Online/offline store backends are shared if configured globally (e.g., single Snowflake warehouse for all tenants); must be mitigated via backend-level access controls or separate service accounts per tenant |
| Network traffic | per-namespace Service (feature-server service only accessible from its namespace or via explicit NetworkPolicy) | Kubernetes NetworkPolicy (optional, not enforced by default) | No default NetworkPolicy; teams must implement NetworkPolicy to prevent cross-namespace feature server access. OpenShift Routes expose externally; OIDC+Bearer tokens provide auth but not network isolation |
| Compute & resources | per-namespace feature server Deployment + optional ResourceQuota per namespace | Kubernetes ResourceQuota / LimitRange | Operator runs cluster-wide; batch materialization jobs (Spark/Dask) inherit compute policies of their namespace |
| Configuration & secrets | per-namespace ConfigMaps (registry.pb, batch engine config) + per-namespace Secrets (online/offline store credentials) | Kubernetes RBAC on secrets | Shared backends (e.g., single Redis online store) require row-level or keyspace isolation at the backend level; Feast does not enforce per-tenant keyspace prefixing out-of-the-box |
| API scoping | per-namespace feature server listens only on internal ClusterIP; external access via Route or Ingress with OIDC/Bearer token validation | Kubernetes Service + Feature Server authz | Bearer token does not include namespace claim; Feature Server must validate bearer token and authorize based on token subject/scope, not namespace membership (teams can share credentials) |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Online Store Backend (Redis, DynamoDB, Postgres) | None (shared backend) | Application query filter (Feast feature lookups are scoped by feature name, not tenant); must rely on backend access controls (separate Redis databases, IAM policies per DynamoDB table) |
| Offline Store Backend (BigQuery, Snowflake) | Schema per tenant (optional) | Feast does not enforce schema/project isolation; teams must use separate service accounts or Snowflake roles to enforce row-level security |
| Registry Server | None (shared cluster-wide) | Read-only ConfigMap per namespace (feature definitions copied from FeatureStore CR); registry server itself is not multi-tenant but can be configured per FeatureStore |
| Operator | None (cluster-wide) | Single operator instance; no per-tenant operator |

**Multi-tenancy summary**: Feast supports soft multi-tenancy via namespace isolation and RBAC, but strong multi-tenancy requires:
1. Per-tenant service accounts with minimal RBAC permissions
2. Per-tenant backend resources (Redis keyspace, Snowflake schema, BigQuery project) or backend-enforced row-level security
3. Bearer token validation in feature server (must map token to namespace or tenant identity)
4. Optional: NetworkPolicy to prevent cross-namespace traffic
