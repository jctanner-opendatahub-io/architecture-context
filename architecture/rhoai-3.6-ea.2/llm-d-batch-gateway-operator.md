## Purpose

**Short**: A Kubernetes operator that manages the lifecycle and deployment of LLM-D batch gateway infrastructure through reconciliation of the `LLMBatchGateway` custom resource.

**Detailed**: The LLM-D Batch Gateway Operator is a controller-based component that implements declarative infrastructure-as-code for batch processing jobs against LLM APIs. The operator translates a single `LLMBatchGateway` custom resource into a complete Kubernetes deployment by rendering upstream Helm charts at runtime. It manages four primary components: an HTTP API server that accepts batch job submissions, a request processor that executes jobs against inference backends, a garbage collector that expires old jobs and files, and optionally an async processor for non-blocking job tracking. The operator enforces multi-tenant isolation through namespace-scoped CRDs and ReferenceGrant validation, coordinates TLS configuration with OpenShift cluster policies, and exposes integrated monitoring via Prometheus and Grafana. It sits at the intersection of batch processing infrastructure, inference platform integration, and observability systems.

## Architectural Analysis

**Helm-Driven Deployment Model**: Unlike traditional operators that generate resources from scratch, this operator renders two upstream Helm charts (`batch-gateway` and `async-processor`) from a single CRD spec. The `specToHelmValues()` function maps CRD fields to chart values, delegating most component logic to the charts themselves. This architecture trades operator complexity for upstream chart synchronization burden — the operator must stay in sync with Helm chart schema changes, and the batch-gateway chart is fetched on-demand at build time (pinned by `BATCH_GATEWAY_REF` in the Makefile). This is a significant architectural constraint: controller changes cannot be decoupled from upstream chart evolution.

**Multi-Tenant Isolation via ReferenceGrant**: The CRD allows `secretRef` to point to Secrets in different namespaces, but Kubernetes Gateway API `ReferenceGrant` must explicitly permit the cross-namespace access. The controller enforces this validation at reconciliation time, copying the remote Secret into the operator's namespace under a managed name (`<gateway-name>-credentials`). This provides namespace-level tenant isolation without requiring per-tenant controller instances, though it shifts the secret synchronization burden to the controller.

**Conditional Component Rendering**: The `Processor.DispatchMode` field determines whether the async processor is deployed. When set to `"async"`, both the batch-gateway chart and async-processor chart are rendered; otherwise, only the batch-gateway chart is used. Status conditions reflect this: the `AsyncProcessorAvailable` condition only appears when async mode is active. This conditional rendering complicates status tracking and CRD validation (see `+kubebuilder:validation:XValidation` rules checking heartbeat intervals).

**TLS Profile Synchronization**: The operator watches the OpenShift `APIServer` resource for TLS profile changes and triggers a graceful restart via `context.CancelFunc` when the profile is updated. This ensures operator-managed workloads respect cluster-wide TLS policies without manual restarts. The TLS configuration is passed to Helm charts as string values (minVersion, cipherSuites, nextProtos), not enforced by the operator directly.

**Fine-Grained RBAC Surface**: The operator requires broad permissions across multiple API groups:
- Secrets (create, get, list, patch, watch) — credential management and monitoring
- Deployments (full CRUD) — component lifecycle
- Gateway API resources (HTTPRoute, ReferenceGrant) — ingress integration
- cert-manager and monitoring.coreos.com — observability and encryption

The `aggregate_roles.yaml` defines read-only aggregated roles (`llm-d-batch-gateway-admin`, `llm-d-batch-gateway-view`) for cluster role aggregation, enabling downstream components to extend RBAC.

**Supply Chain and Hermeticity**: The Dockerfile.konflux uses `CGO_ENABLED=1` and `GOEXPERIMENT=strictfipsruntime` for FIPS-compliant Go linking, dynamically linking against OpenSSL in the UBI 9 base image. The build is hermetic: `go.sum` is committed and vendored in CI builds (`BUILD_TYPE=CI`), ensuring reproducible Go dependency resolution. OS packages come from UBI 9 base image (no `rpms.lock.yaml` observed), representing a hermeticity gap at the OS layer on this branch.

| **Tenant identifier** | Namespace name + LLMBatchGateway name (namespaced key) | Implicit in Kubernetes reconciliation request (NamespacedName) |

_Multi-tenancy is achieved through Kubernetes namespace isolation, not per-tenant controller instances. The single operator instance manages LLMBatchGateway CRs across all namespaces._

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-namespace RBAC on LLMBatchGateway and child resources | Kubernetes RBAC (namespace-scoped CRD, owned resources inherit namespace) | Depends on cluster RBAC configuration; no per-CR tenant identity at CRD level |
| Data storage | Per-namespace Secrets (via secretRef); cross-namespace Secrets require ReferenceGrant validation | Kubernetes + operator validation (resolveSecret enforces ReferenceGrant) | Secrets can be shared across gateways in same namespace if accessed via same secretRef; no row-level isolation at the Secret level |
| Network traffic | Implicit via namespace isolation + NetworkPolicy (not enforced by operator) | Kubernetes NetworkPolicy (outside operator scope) | Operator does not create NetworkPolicy; tenant isolation depends on cluster NetworkPolicy configuration |
| Compute & resources | Implied via pod namespace + ResourceQuota/LimitRange (not enforced by operator) | Kubernetes ResourceQuota/LimitRange (outside operator scope) | Operator does not set resource limits or quotas; relies on cluster-level configuration |
| Configuration & secrets | Per-namespace Secrets mounted as volumes; cross-namespace access requires ReferenceGrant | Kubernetes + Gateway API ReferenceGrant validation | Cross-namespace Secret access is allowed if ReferenceGrant exists; no restriction on which gateways can reference which Secrets in other namespaces |
| API scoping | Namespace-scoped watches — reconciler watches all LLMBatchGateway CRs in all namespaces, but owned resources stay in their original namespace | controller-runtime watches + RBAC namespace scope | Single reconciler instance for all namespaces; no per-tenant API isolation |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Kubernetes API Server | Namespace | RBAC + namespace scoping of owned resources |
| cert-manager | Cluster-wide (shared CA/issuer) | Separate Certificate CRs per gateway (namespace-scoped), each with unique DNS names |
| prometheus-operator | Cluster-wide (shared Prometheus instance) | ServiceMonitor CRs per gateway with unique label selectors (instance name included in labels) |
| batch-gateway backend services (database, S3, inference API) | Not shared by operator — tenant isolation delegated to secretRef | Per-gateway Secret with backend credentials; backend tenancy depends on backend system |

_The operator does not enforce shared services at the Kubernetes level. Tenancy of upstream backends (database, S3, inference API) is delegated to the secretRef credentials passed to the Helm charts. The operator ensures these credentials are isolated per namespace via RBAC and ReferenceGrant validation, but cannot enforce row-level or bucket-level isolation at the backend._
