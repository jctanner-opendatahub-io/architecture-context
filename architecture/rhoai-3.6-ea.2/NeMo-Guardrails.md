## Purpose

**Short**: NVIDIA NeMo Guardrails is an open-source toolkit for adding programmable guardrails to LLM-based conversational systems.

**Detailed**: NeMo Guardrails provides a framework for developers to implement safety controls, prompt injection protection, jailbreak prevention, and structured conversation flows in LLM-based applications. The component consists of a core Python library and an optional HTTP server (FastAPI + Chainlit) that exposes guardrails as a service. It integrates with various LLM providers (OpenAI, Cohere, local models) and supports guardrails configuration via Colang DSL, enabling declarative definition of conversation rules, fact-checking, output moderation, and tool integration. The RHOAI distribution packages this with pre-downloaded ML models (MinLM, Snowflake embeddings, spaCy, NLTK) in container images and uses AIPCC CPU base images for hermetic builds.

## Architectural Analysis

NeMo Guardrails follows a layered architecture:

1. **Core Library** (`nemoguardrails/`): Python library implementing the guardrails framework, including manifest system for extensible rail definitions, embedding providers (FastEmbed, Cohere, OpenAI, Google), LLM client abstraction supporting multiple providers, server implementation (FastAPI + Chainlit), and datastore abstraction for persistence.

2. **Server Deployment**: Two Dockerfiles support different deployment scenarios. `Dockerfile.konflux` (RHOAI) builds with AIPCC CPU base image (`quay.io/aipcc/base-images/cpu:3.5.0`), pre-downloads ML models via multi-stage build from modelcar image registries, and runs the server via `scripts/entrypoint.sh`. `Dockerfile.server` (generic) uses UBI9 Python base without AIPCC dependencies.

3. **Configuration System**: Guardrails are configured via YAML and Colang DSL. The system supports:
   - Profile-based filtering (`GUARDRAILS_PROFILE=opensource|rhoai`) to customize included providers and dependencies
   - Per-config directory discovery allowing multiple independent guardrails configurations
   - Runtime configuration via environment variables and mounted config volumes

4. **Model Integration**: The component integrates with sentence transformers, fastembed, and transformer models for semantic search and embeddings. Pre-downloaded models are cached in `/app/.cache` to ensure offline availability and deterministic builds.

5. **Hermetic Build Patterns**: The Dockerfile.konflux uses `requirements.txt` (compiled by `uv`) and `pyproject.toml` for dependency specification, multi-stage build separating compile and runtime, venv isolation, and modelcar image references for reproducible model downloads. The `requirements-build.txt` pins the RHAI PyPI index (`https://packages.redhat.com/api/pypi/public-rhai/rhoai/3.5/cpu-ubi9/simple/`), ensuring all dependencies resolve from the Red Hat RHEL AI package repository.

6. **Security Posture**: The server runs as non-root UID 1001 in the runtime container, removes PAM namespace configuration, and sets environment flags (`PYTHONDONTWRITEBYTECODE`, `PYTHONUNBUFFERED`, `DO_NOT_TRACK`). TLS is delegated to ingress/load balancer; internal service communication within containers is HTTP only.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-request bearer token validation | Application (FastAPI middleware) | No RBAC; all authenticated users can access all configs; rely on deployment to enforce isolation via separate instances or proxies |
| Data storage | Per-config directory separation; no shared DB | Kubernetes volume mounts / Application file I/O | Shared venv and model cache if multiple configs coexist; isolation depends on deployment setup |
| Network traffic | No NetworkPolicy defined | (delegated to deployment) | Deployment responsibility; no service-to-service mTLS |
| Compute & resources | No resource isolation | (delegated to deployment) | Deployment responsibility via Kubernetes ResourceQuota/LimitRange |
| Configuration & secrets | Per-config YAML files; environment secrets via mounted Secrets | Kubernetes Secrets / Application | Secrets at process level; no per-request secret scoping |
| API scoping | All configs discoverable if querying /v1/config | Application | No per-tenant filtering of configurations |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Model cache (/app/.cache) | Per-process (shared across configs in same instance) | Filesystem isolation via container volume mounts; deployment must use separate instances for strict tenant isolation |
| venv + Python interpreter | Per-process (shared across configs in same instance) | Filesystem isolation via container volume mounts; deployment must use separate instances for strict tenant isolation |

**Multi-Tenancy Summary**: The component supports multiple independent guardrails configurations within a single process but does not enforce strong isolation. Tenancy is logical (config ID + bearer token) not architectural. For strict multi-tenant deployment, use separate instances per tenant or add reverse-proxy request filtering.
