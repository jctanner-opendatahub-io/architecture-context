## Purpose

**Short**: NeMo Guardrails provides programmable input, dialog, retrieval, execution, and output guardrails around LLM-based conversational systems.

**Detailed**: The repository packages the `nemoguardrails` Python library and an optional FastAPI server. The server loads one or more rail configurations, applies configured Colang flows and Python actions, and exposes health, configuration, OpenAI-compatible completion, and guardrail-check APIs.

The RHOAI fork adds a Konflux image based on the AIPCC CPU image, preloads modelcar assets, and starts the server on port 8000 as an unprivileged user. External model providers, moderation services, embedding providers, and optional telemetry systems are selected through configuration and environment variables rather than Kubernetes resources in this checkout.

## Architectural Analysis

The primary runtime is an ASGI/FastAPI service launched by the `nemoguardrails server` CLI. `scripts/entrypoint.sh` validates a configuration identifier and numeric port, requires a config YAML file, disables the Chat UI for the product image, and optionally wraps the process with OpenTelemetry auto-instrumentation. The application is configuration-driven: models, rail types, Colang flows, actions, datastore behavior, and provider credentials are resolved at runtime.

The product image is a multi-stage build. It uses a digest-pinned AIPCC CPU base, imports four modelcar stages, installs Python dependencies into `/app/.venv`, copies model assets into an application cache, and runs as UID 1001. This gives a reproducible image boundary for the RHOAI distribution, but the checked-in repository does not contain Kubernetes workload manifests, Services, Routes, RBAC, or NetworkPolicies; those deployment controls must be supplied by the consuming platform.

The API forwards selected incoming authorization headers to configured upstream model providers and can also read provider API keys from environment variables. The server health endpoint is a process liveness check, not a dependency/readiness check. TLS is configurable at the HTTP deployment layer; no application-level TLS listener or cipher policy is defined in the inspected Python service.
