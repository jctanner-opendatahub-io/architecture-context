## Purpose

**Short**: A Kubernetes operator that reconciles `ModelRegistry` and `Catalog` Custom Resources to deploy Model Registry instances and shared model catalog services in Kubernetes namespaces.

**Detailed**: The Model Registry Operator is a Kubebuilder-based controller that manages the lifecycle of OpenShift AI Model Registry deployments. It reconciles `ModelRegistry` (v1alpha1, v1beta1), `Catalog` (aihub.opendatahub.io), and `AIHub` (components.platform.opendatahub.io) Custom Resources to provision REST API services, PostgreSQL/MySQL databases, kube-rbac-proxy authentication sidecars, and OpenShift Routes or Kubernetes Gateway HTTPRoutes for external access. The operator supports multiple deployment modes: plain Kubernetes (HTTP), OpenShift OAuth Proxy (HTTPS via service certificates and Routes), and Data Science Gateway mode (HTTPS via HTTPRoute and TLS certificates). It handles database configuration (PostgreSQL or MySQL), namespace isolation, RBAC role generation, NetworkPolicy enforcement, and optional shared Model Catalog deployments. The Model Registry itself is an MLOps backing store that indexes and manages ML model metadata, versions, artifacts, training parameters, deployment status, and audit trails to enable collaboration across data science, DevOps, and engineering teams throughout the ML lifecycle.

## Architectural Analysis

The operator follows a multi-controller architecture pattern with three independent reconciler loops: one for `ModelRegistry` resources, one for `Catalog` resources, and one for `AIHub` platform resources. Each reconciler creates and manages a suite of dependent resources (Deployments, Services, ConfigMaps, Secrets, RBAC, NetworkPolicies, and Routes/HTTPRoutes) from inline YAML templates that are dynamically rendered with CR-specific values.

**Key Design Patterns**:

1. **Template-Driven Resource Generation**: The operator embeds YAML templates in `internal/controller/config/templates/` and renders them at reconciliation time using Go text templates. Templates are namespace-scoped and registry-scoped (e.g., `deployment.yaml.tmpl`, `postgres-deployment.yaml.tmpl`, `service.yaml.tmpl`) allowing per-CR customization of resource names, labels, and configuration.

2. **Multi-Tenancy via Namespaces**: Each `ModelRegistry` CR creates an isolated deployment within its own namespace. RBAC roles and RoleBindings are namespace-scoped, and NetworkPolicies restrict traffic to the registry's own namespace unless explicitly cross-namespace routes are configured (e.g., via HTTPRoute with ReferenceGrant for Gateway API mode).

3. **Database Backend Abstraction**: The operator abstracts database configuration via `PostgresConfig` and `MySQLConfig` types in the CR spec, supporting both user-provided external databases and auto-provisioned in-cluster PostgreSQL pods (via `postgres-deployment.yaml.tmpl`). Database credentials and SSL certificates are mounted as Secrets and ConfigMaps into the REST container.

4. **Dual Ingress Pathways**: The operator supports both OpenShift-native Routes (via `route.yaml.tmpl` templates) and Kubernetes Gateway API HTTPRoutes (via `http-route.yaml.tmpl` templates), with a cross-namespace HTTPRoute cleanup mechanism (`deleteObject`) to prevent stale resources when switching modes. OAuth Proxy routes are supported via `kube-rbac-proxy-https-route.yaml.tmpl` for OpenShift clusters with service certificates.

5. **kube-rbac-proxy Sidecar Pattern**: Every user-facing service (ModelRegistry REST API, Catalog API) runs a kube-rbac-proxy sidecar on port 8443 that enforces Kubernetes RBAC and token authentication. The proxy is configured via `--config-file=/etc/kube-rbac-proxy/config-file.yaml` and mounts TLS certificates from Secrets.

6. **FIPS Compliance Build**: The Dockerfile.konflux uses `GOEXPERIMENT=strictfipsruntime` and `CGO_ENABLED=1` to enable Go's FIPS runtime mode, dynamically linking to OpenSSL in the UBI9 minimal-pqc base image for FIPS-compatible TLS and cryptographic operations.

7. **Controller Watches and Reconciliation Triggers**: The ModelRegistry controller watches routes and HTTPRoutes via map functions (`GetRegistryForRoute`), enabling re-reconciliation when external ingress resources drift or are deleted. The AIHub controller watches release resources and manifest renders to coordinate multi-component deployments.

**Notable Risks and Observations**:

- The operator creates and deletes OpenShift Groups (e.g., `{registry-name}-users`) only when running on OpenShift clusters. Non-OpenShift environments lack this user aggregation mechanism, requiring manual RoleBinding management.
- Database SSL configuration is optional and relies on mounted Secrets for certificates; missing or misconfigured certificates will cause silent SSL failures if the service does not validate the connection error.
- The HTTPRoute-to-Route cleanup mechanism (`deleteObject`) is asynchronous and may leave stale HTTPRoute resources if a cluster transitions from Gateway API mode back to Route mode during operator downtime.
- Catalog deployments use `kube-rbac-proxy` for authentication but internally trust catalog queries from the same namespace without additional service-to-service TLS; inter-namespace catalog access relies solely on NetworkPolicy enforcement.

|-----------|-----------|-------------|--------------|
| Auth & AuthZ | per-namespace RBAC roles (`registry-user-{registry-name}`, `registry-editor-role`, `registry-viewer-role`); kube-rbac-proxy validates Bearer tokens against Kubernetes API | Kubernetes RBAC + kube-rbac-proxy | Users must have explicit role binding to access the service; default deny-all is not enforced (relies on role binding curation by cluster admins) |
| Data storage | per-namespace database (PostgreSQL/MySQL); schema isolation via separate database credentials per registry | Kubernetes Secret (database credentials); database schema | No row-level filtering within database; schema isolation depends on correct database credential assignment and database-level access controls |
| Network traffic | per-namespace Services; NetworkPolicy created per registry (if enabled via spec.networkPolicy) | Kubernetes NetworkPolicy (if deployed) | NetworkPolicy is optional and must be explicitly enabled; default is no network isolation beyond namespace boundaries |
| Compute & resources | No resource quotas or LimitRanges created by operator | (not enforced by operator) | Operator does not create or enforce ResourceQuota or LimitRange; cluster admin must configure these manually |
| Configuration & secrets | per-namespace Secrets for database credentials, TLS certificates, OAuth proxy config; ConfigMaps for catalog sources (if Catalog enabled) | Kubernetes Secret + ConfigMap (namespace-scoped) | Secrets are readable by any pod in the namespace with sufficient RBAC; no encryption at rest unless cluster-level Secret encryption is configured |
| API scoping | per-namespace Service; REST API serves all models within the namespace's database schema | Application (REST service + database schema) | No per-user or per-tenant API filtering within a namespace; all users with access to the service can read all models in the database |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Model Catalog (optional) | cluster-wide (single shared Catalog instance); serves all namespaces | Namespace-scoped sources (ConfigMaps); catalog API requires Bearer token (RBAC-enforced); catalog PostgreSQL is isolated from ModelRegistry databases |
| Operator Metrics (port 8443) | cluster-wide | kube-rbac-proxy enforces RBAC on `/metrics` endpoint |

**Multi-Tenancy Observation**: The operator enforces namespace isolation at the resource level (Kubernetes API) but does not enforce schema-level or row-level isolation within shared databases. If multiple tenants share a single external PostgreSQL instance (via different credentials and schemas), data leakage is possible if database-level access controls are misconfigured. The Model Catalog (when deployed) is a cluster-wide shared service but is RBAC-protected via kube-rbac-proxy and can serve multiple tenants via namespace-scoped source ConfigMaps.
