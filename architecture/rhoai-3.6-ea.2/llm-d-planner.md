## Purpose

**Short**: An SLO-driven LLM deployment planning platform that transforms business requirements into optimized Kubernetes configurations through conversational intent extraction, capacity planning, and GPU recommendation.

**Detailed**: llm-d Planner unifies LLM deployment workflows—traditionally fragmented across model selection, GPU sizing, performance estimation, and Kubernetes configuration—into a single platform accessible as a web UI, REST API, and CLI. Users describe their AI use case in natural language; the platform extracts business intent, maps it to traffic profiles, generates SLO targets, queries benchmark databases, estimates performance where benchmarks are missing, and recommends optimal model+GPU configurations. It then generates validated Kubernetes YAML (KServe/vLLM) and deploys to production or local KIND clusters. The platform includes a specialized Capacity Planner module for GPU memory estimation and a GPU Recommender for inference performance prediction across hardware types. A GPU-free vLLM simulator enables local testing without hardware.

## Architectural Analysis

llm-d Planner is a multi-tier Python application with three main deployment components: a FastAPI backend (port 8000), a Streamlit frontend (port 8501), and an optional Ollama LLM service (port 11434) or external OpenAI API integration. The backend exposes 37 REST endpoints covering intent extraction, capacity planning, GPU recommendation, benchmark management, and Kubernetes integration. Deployment manifests use OpenShift Routes with TLS edge termination, indicating the platform is designed for production OpenShift/RHOAI clusters. The backend reads node information via Kubernetes API using RBAC (nodes:list permission) to detect GPU availability for capacity planning. Secrets are managed via Kubernetes Secrets (planner-secrets, planner-config) for tokens and configuration. The platform supports dual deployment modes: production (real GPU inference via vLLM) and simulator (latency-emulated inference for GPU-free development). All Python containers use standard Python slim images (python:3.14-slim), non-root user execution, and security best practices (seccomp, dropped capabilities). The project uses uv for hermetic Python dependency management with explicit lock files. Cryptographic operations are minimal—hashlib (SHA256) for benchmark config checksums and OpenAI/Anthropic SDK integrations for LLM calls.
