## Purpose

**Short**: An inference payload processing system that provides extensible request/response mutation pipelines for AI Gateway via pluggable External Processor (ExtProc) gRPC integration.

**Detailed**: AI Gateway Payload Processing (part of the llm-d inference framework) enables advanced request/response mutations and model routing decisions in the AI Gateway. It deploys as a controller managing custom resource definitions (ExternalModel and ExternalProvider) that define how external LLM providers are discovered, configured, and routed to. The component registers two gRPC services—an external processor service that Envoy's ExtProc filter invokes per-request, and a health service for lifecycle management. It integrates with Gateway API to automatically create and manage HTTPRoute resources based on ExternalModel specifications, enabling dynamic routing of inference requests to configured providers (OpenAI, Anthropic, Azure, Google Vertex, etc.).

## Architectural Analysis

The component embodies a **plugin-driven architecture** with three key tiers:

1. **Kubernetes Controller Tier**: Two namespaced controllers (ExternalModel and ExternalProvider) reconcile custom resources against the Kubernetes API and manage HTTPRoute ownership. Controllers watch ExternalModel, ExternalProvider, Service, and HTTPRoute resources across a specified namespace (or cluster-wide if NAMESPACE env var is unset), reconciling CRD state into working routing configuration.

2. **gRPC ExtProc Server Tier**: A dynamically-configured request/response processor that receives per-request processing directives from Envoy via the Envoy External Processing API. The processor composes a configurable plugin pipeline (loaded from a YAML config or inline text) that mutates request/response headers and bodies, extracts model identifiers from requests, selects target providers based on weights/scoring, and injects provider-specific authentication credentials.

3. **Plugin Framework Tier**: Built on the llm-d-inference-payload-processor library, the framework provides factories for in-tree plugins (field extractors, model selectors, header injectors, API translators, etc.) and accepts downstream custom plugins via a plugin registration interface. Plugins execute in ordered pre-processing, profile-picking, and post-processing phases.

The architecture prioritizes **separation of concerns**: the controller manages Kubernetes topology and routing configuration, while the ExtProc server handles per-request processing decisions. Configuration is decoupled via the llm-d config loader, allowing the processor to evolve independently of the controller. The design also enables **zero-downtime plugin updates** via ConfigMap-based configuration reloads, though CRD-driven routing changes require controller reconciliation.

A notable architectural choice is the **self-signed certificate generation** for ExtProc gRPC TLS (when `--secure-serving` flag is enabled). This is suitable for cluster-internal communication over mTLS but relies on Envoy sidecar injection to validate the certificate; external mTLS terminators need explicit CA handling.

**Summary**: The component appears FIPS-compliant at both layers (build-time strictfipsruntime + dynamic linking, application-level standard TLS). However, the production deployment should provide externally-signed certificates rather than relying on runtime self-signed generation.

## Additional Notes

**Known limitations from analyzer coverage**:
- Manifest discovery is partial: `deploy/payload-processing/templates/rbac.yaml` is a Helm template and could not be fully parsed for static RBAC configuration.
- Dynamic webhook registration is not fully resolved (webhooks field is null).

**Architectural recommendations**:
1. For strict tenant isolation, deploy with `NAMESPACE` env set to a single namespace and use namespace-scoped Role (set `multiNamespace: false` in Helm values).
2. Provide externally-signed certificates for ext-proc TLS in production rather than relying on runtime-generated self-signed certs.
3. Consider adding `rpms.lock.yaml` to the release branch to ensure hermetic OS package versions (currently only Go module locking is present).
4. Document the optional label `inference.llm-d.ai/ipp-managed: "true"` on credential Secrets to optimize Secret informer caching in multi-namespace mode.
5. Review Prometheus metrics endpoint access control; if `METRICS_ENDPOINT_AUTH=true`, ensure kube-rbac-proxy sidecar is deployed.
