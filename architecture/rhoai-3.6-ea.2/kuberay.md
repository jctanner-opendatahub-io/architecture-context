## Purpose

**Short**: KubeRay runs and manages Ray clusters, jobs, and serving workloads as Kubernetes resources.

**Detailed**: KubeRay provides the Kubernetes control plane for Ray. Its operator reconciles `RayCluster`, `RayJob`, `RayCronJob`, and `RayService` resources into Ray head/worker workloads, services, jobs, secrets, and network policies. RayService supports a Ray cluster plus Ray Serve deployment lifecycle, including upgrades.

The repository also contains optional KubeRay API server, security proxy, history server, SDK, dashboard, and submitter artifacts. The RHOAI deployment path centers on the `ray-operator/Dockerfile.konflux` operator image and OpenShift kustomization, while the generic kustomizations provide upstream defaults and optional admission webhooks.

## Architectural Analysis

KubeRay uses a Kubernetes-native reconciliation model: namespace-scoped Ray custom resources are the user-facing contract, and several controllers materialize the corresponding Ray compute plane. The operator watches Kubernetes pods, services, jobs, secrets, service accounts, routes, and network policies to keep the Ray control and data planes aligned with declared state.

The RHOAI branch adds release-oriented hardening and deployment indirection. The Konflux Dockerfile uses a digest-pinned UBI Go builder, `CGO_ENABLED=1`, `GOEXPERIMENT=strictfipsruntime`, and the `strictfipsruntime` build tag, then runs from a digest-pinned UBI minimal PQC image. The OpenShift kustomization injects namespace and image values from `params.env` and patches TLS, metrics, webhook, and gateway-related settings. This differs materially from the generic scratch/distroless image paths, which should not be treated as equivalent FIPS deployment evidence.

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Namespace-scoped user RBAC plus shared operator service account | Kubernetes | Operator is a cluster-level control-plane principal; role breadth must be reviewed for least privilege. |
| Data storage | Ray pods, services, secrets, and jobs are created in the CR namespace | Kubernetes/controller | No separate storage tenant model was extracted. |
| Network traffic | Controller can create/manage NetworkPolicies; Ray cluster isolation depends on generated policy and user configuration | Kubernetes/controller | Default-deny posture and complete cross-namespace policy behavior are not established by the bounded inventory. |
| Compute & resources | Separate namespaced Ray workloads; resource requests/limits come from Ray pod specifications | Kubernetes/user CR | No operator-wide ResourceQuota or LimitRange enforcement was extracted. |
| Configuration & secrets | Namespaced Secrets and service accounts; per-cluster auth/CA secrets | Kubernetes/controller | Shared operator credentials span managed namespaces by design. |
| API scoping | CRDs are namespaced; API server supports namespace-scoped and all-namespace list paths | Kubernetes/API server | All-namespace API operations require appropriate RBAC and can expose cross-tenant metadata. |
