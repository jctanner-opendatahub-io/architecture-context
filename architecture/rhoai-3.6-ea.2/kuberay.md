## Purpose

**Short**: KubeRay is a Kubernetes operator that simplifies deployment and management of Ray applications on Kubernetes through custom resources (RayCluster, RayJob, RayService) and supporting services.

**Detailed**: KubeRay provides three core components that work together to manage Ray distributed computing workloads on Kubernetes. The operator (deployed as a Kubernetes Deployment) reconciles Ray custom resources and manages cluster lifecycle (creation, scaling, fault tolerance). The APIServer offers a gRPC and REST interface for simplified resource management, while the History Server provides observability into Ray task execution and cluster status. KubeRay integrates with the Kubernetes ecosystem through controllers that watch Ray resources, Pods, Secrets, and Services; manages TLS via cert-manager; handles authentication/authorization for Ray clusters and ingress via Gateway API and OpenShift Routes; and exposes metrics via Prometheus. The operator runs with cluster-scoped permissions to manage resources across namespaces but individual RayCluster CRs are namespaced, enabling per-tenant isolation at the workload level.

## Architectural Analysis

KubeRay's architecture reflects a multi-layered design for managing distributed Ray workloads:

1. **Control Plane (ray-operator)**: A controller-runtime based operator deployed as a single Deployment replica (`kuberay-operator`). It runs four specialized controllers—RayClusterReconciler, RayJobReconciler, RayServiceReconciler, and RayCronJobReconciler—that watch their respective CRs and Kubernetes resources (Pods, Services, Secrets) to maintain cluster state. The operator uses admission webhooks (mutating and validating) to enforce constraints on resource definitions before persistence.

2. **API & Observability Layer**: The APIServer provides gRPC and REST endpoints for cluster and job management, supplementing the native Kubernetes API. The History Server independently scrapes Ray cluster events and exposes web endpoints for task timelines, logs, and cluster metadata—a read-only observability tier not requiring operator privileges.

3. **Authentication & Ingress**: The operator manages TLS certificate lifecycle via cert-manager, creates ConfigMaps and ServiceAccounts for Ray cluster authentication, and coordinates with Gateway API to expose services through HTTPRoute CRs. An experimental security proxy can enforce additional authorization on Ray service traffic.

4. **Multi-Tenancy Boundary**: RayCluster CRs are namespaced; the operator's watch/reconciliation respects namespace scope. Network isolation is configured via NetworkPolicy CRs; authentication isolation relies on per-cluster ServiceAccounts and cert-manager Certificates. The operator itself runs with a cluster-scoped role but delegates tenant workloads to user namespaces.

5. **Supply Chain Considerations**: The ray-operator Dockerfile (RHOAI variant) builds with `CGO_ENABLED=1 -tags strictfipsruntime`, dynamically linking against OpenSSL in the UBI 9 base image—meeting check-payload FIPS build requirements. Dependencies are locked in `go.sum`, though OS package hermicity varies by build variant (Konflux vs. buildx).

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | per-tenant RBAC (ServiceAccount per cluster, ClusterRole with namespace watch scope) | Kubernetes RBAC | Operator has cluster-scoped ClusterRole; namespace isolation relies on watch scope and workload isolation |
| Data storage | per-namespace PVC (Ray cluster stores data in user's PVC) | Kubernetes | No shared database; each cluster's data is isolated by namespace |
| Network traffic | NetworkPolicy per cluster (operator creates NetworkPolicy CR per RayCluster) | Kubernetes NetworkPolicy controller | Requires platform to enforce NetworkPolicy; absent NetworkPolicy enforcement allows cross-namespace traffic |
| Compute & resources | ResourceQuota per namespace + LimitRange | Kubernetes | Operator does not enforce LimitRange; relies on namespace admin to configure |
| Configuration & secrets | per-namespace Secrets (ray-cluster-tls-cert, ray-cluster-ca-cert, ray-token-secret) | Kubernetes | Secrets stored with cluster name prefix; RBAC controls access |
| API scoping | namespace-scoped watches + filtered queries | controller-runtime | Operator reconciliation respects namespace scope; APIServer honors user identity for authorization |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| cert-manager | shared cluster service | per-cluster Certificate/Issuer CRs scoped by name+namespace |
| Gateway API | shared cluster service | per-cluster HTTPRoute CRs scoped by name+namespace |
| Prometheus (optional) | shared cluster service | metrics scraped from per-cluster service annotations |

**Multi-Tenancy Summary**: KubeRay's multi-tenancy model is namespace-scoped. The operator is cluster-scoped (runs in single namespace, watches all namespaces) but workload isolation is delegated to per-namespace CRs. NetworkPolicy CRs (created by operator) provide network isolation if enforced. TLS authentication uses per-cluster ServiceAccounts and certificates, ensuring that Ray cluster communication is isolated. The operator itself carries broad permissions but does not bypass Kubernetes RBAC—each tenant's ServiceAccount (used by their Ray pods) has permissions only to their own cluster's resources. This design is appropriate for managed Kubernetes platforms where namespace isolation is the primary tenancy boundary.
