## Purpose

**Short**: Exposes opt-in vLLM introspection endpoints that report server configuration, hardware, and profiled KV-cache information to llm-d.

**Detailed**: The repository packages the `llm-d-api-extensions-vllm` Python distribution. It integrates with vLLM through the `vllm.endpoint_plugins` entry-point mechanism and does not modify vLLM core. The top-level repository is structured so additional inference-server extension packages can be added as sibling directories; the analyzed checkout currently contains the vLLM implementation only.

The server-introspection family provides three read-only HTTP endpoints. Configuration is assembled from vLLM startup configuration, device properties are collected through `collective_rpc` and a separately configured worker extension, and KV-cache capacity/group metadata is collected after profiling. Results are initialized once and cached in application state for the server lifetime. Plugins are disabled unless explicitly named in `VLLM_PLUGINS`.

## Architectural Analysis

This is a library/plugin rather than a standalone workload: it contributes routes to the vLLM FastAPI application and contributes a worker-side RPC method when the devices plugin is enabled. That explains why the analyzer found no workload, Service, RBAC, or ingress manifests. The consuming vLLM deployment owns process binding, TLS, authentication, Kubernetes resources, and tenant boundaries.

The design separates inexpensive configuration introspection from engine-dependent observations. The config plugin works without an engine, while devices and KV-cache plugins return `503` on a CPU-only render server. KV-cache group support is capability-detected with `hasattr`, preserving compatibility with vLLM builds that do not yet provide `get_kv_cache_group_metadata`; in that case capacity fields remain available and `groups` is empty. Operator-controlled `kv_connector_extra_config` is returned in the response and is explicitly identified by the project as potentially sensitive.
