## Purpose

**Short**: Kubernetes operator that manages the lifecycle of TrustyAI services and related AI/ML evaluation and guardrailing infrastructure within RHOAI clusters.

**Detailed**: TrustyAI Service Operator is a multi-faceted operator managing several AI/ML components within RHOAI:

1. **TrustyAI Service**: A platform component that deploys alongside KServe InferenceServices to collect inference data, enabling model explainability, fairness monitoring, and drift tracking.

2. **FMS Guardrails Orchestrator**: A modular framework for deploying and orchestrating guardrails around Large Language Models (LLMs).

3. **LM-Eval Job Management**: A job-based architecture for deploying and managing LLM evaluations, built on EleutherAI's lm-evaluation-harness library.

4. **EvalHub**: A service for orchestrating AI/ML model evaluations, providing a unified API for running benchmarks across multiple evaluation providers and frameworks, with support for both multi-tenant and single-tenant deployments.

The operator runs within a cluster and dynamically creates Deployments, Services, and ConfigMaps to satisfy user-defined Custom Resources (CRDs). It watches KServe InferenceServices, manages lifecycle events, and integrates with OpenTelemetry for observability and Prometheus for metrics collection.

## Architectural Analysis

The TrustyAI Service Operator exhibits a hub-and-spoke controller architecture typical of Kubernetes operators. The operator core (manager) runs in a deployment with leader election, dynamically creating and managing workloads based on CR definitions. Key architectural patterns:

1. **Multi-CRD Hub**: Manages eight separate CRDs (TrustyAI, EvalHub v1/v1alpha1, GuardrailsOrchestrator, LMEvalJob, NemoGuardrails, TrustyAIService v1/v1alpha1), each with distinct lifecycle responsibilities. This differs from single-purpose operators—TrustyAI is a platform component coordinator.

2. **Dynamic Workload Generation**: Uses template-based manifests (`.tmpl.yaml` files) to dynamically generate Deployments and Services in response to CR changes. This pattern centralizes resource definitions in the operator image, reducing manifest duplication across clusters.

3. **FIPS-Compliant Build**: The primary manager binary (Dockerfile.konflux) uses `CGO_ENABLED=1` with `GOEXPERIMENT=strictfipsruntime` and `-tags strictfipsruntime`, targeting FIPS compliance at the build layer. The runtime image (ubi9/ubi-minimal-pqc) includes cryptographic post-quantum capabilities.

4. **Sidecar-Based Security**: Controller-created Deployments include a `kube-rbac-proxy` sidecar that enforces mTLS and RBAC at the API gateway level, securing the upstream service endpoints (e.g., TrustyAI service at 127.0.0.1:8081).

5. **Observability-First Integration**: Extensive OpenTelemetry instrumentation (SDK 1.45.0) for traces and metrics, with support for multiple OTLP export protocols (gRPC, HTTP). Prometheus operator integration for metrics scraping.

6. **Namespace-Scoped Tenancy**: CRDs are predominantly Namespaced (7 of 8), enabling per-namespace resource isolation. The cluster-scoped TrustyAI CRD likely coordinates platform-wide settings.

### Architectural Risks and Observations

- **Leader Election**: The operator uses `--leader-elect` but runs as a single replica in most deployments, meaning leader election is not tested under typical operating conditions.
- **Dynamic Manifest Templates**: The `/opt/manifests-template` embedded in the trustyai-operator-module image is critical for workload generation. If outdated, all created workloads may inherit stale configurations.
- **Sidecar Dependency**: The proxy sidecar (kube-rbac-proxy) is injected into all workloads, introducing a hard dependency on the proxy image and adding runtime overhead.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | kube-rbac-proxy sidecar on workloads; controller-runtime ServiceAccount RBAC | Kubernetes + Application | No per-tenant RBAC within workloads; all workloads in a namespace share proxy configuration |
| Data storage | Each CR manages namespace-scoped Deployments; ConfigMaps and Secrets are namespace-local | Kubernetes | If shared backend databases are used (e.g., EvalHub backend), tenant isolation is application-level only |
| Network traffic | None enforced (no NetworkPolicy) | None | Pod-to-pod traffic within the operator and workloads is unencrypted by default unless explicitly configured |
| Compute & resources | ResourceQuota and LimitRange must be configured per namespace | Kubernetes policy (not operator) | Operator does not enforce resource quotas; relies on namespace-level configuration |
| Configuration & secrets | ConfigMaps and Secrets are namespace-scoped | Kubernetes | Operator workloads inherit Secrets from their namespace; no explicit encryption at rest |
| API scoping | Operator watches all namespaces; CRs are namespace-scoped | Kubernetes | Operator has no built-in tenant filtering; global watches mean operator sees all CRs |
