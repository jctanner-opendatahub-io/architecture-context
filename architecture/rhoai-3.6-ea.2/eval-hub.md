## Purpose

**Short**: EvalHub orchestrates LLM evaluations, persists their state, and exposes REST and MCP interfaces for evaluation workflows.

**Detailed**: EvalHub is a Go service that accepts evaluation requests, validates provider and collection configuration, persists evaluations through a storage abstraction, and runs them either locally or as Kubernetes Jobs. It supports evaluation providers such as lm-evaluation-harness, RAGAS, Garak, GuideLLM, LightEval, and MTEB, with provider and collection definitions shipped as YAML.

The service uses SQLite for development and PostgreSQL for production, can initialize test data from S3-compatible storage, and optionally integrates with MLflow for experiment tracking and OCI storage for exported result cards. Kubernetes jobs use generated ConfigMaps, Secrets, Jobs, and a runtime sidecar to execute and report benchmark work. In cluster mode, an external kube-rbac-proxy supplies authenticated identity headers; EvalHub itself does not validate bearer tokens.

## Architectural Analysis

The repository is a multi-artifact service distribution rather than a Kubernetes operator. `cmd/eval_hub` is the primary API process; `cmd/eval_runtime_init` prepares job inputs; `cmd/eval_runtime_sidecar` proxies runtime, MLflow, model, and OCI interactions; and `cmd/evalhub_mcp` provides an MCP transport. The main server composes HTTP routing, request-scoped `ExecutionContext`, SQL-backed storage, and a selectable local/Kubernetes runtime.

Tenant context is propagated from `X-Tenant` and `X-User` headers into storage and runtime operations. Evaluation APIs require both headers when identity enforcement is enabled, while local mode bypasses the gate and health/documentation routes remain probe- or tooling-friendly. This makes deployment configuration and the external authentication proxy part of the effective security boundary.

The Konflux build produces dynamically linked, strict-FIPS-runtime Go binaries in a digest-pinned UBI toolset image and runs them as a non-root user in a digest-pinned UBI minimal PQC image. Application TLS is explicitly bounded to TLS 1.2–1.3 and supports system or configured CA pools, but several sidecar/model integrations expose an opt-in `insecure_skip_verify` development path. No repository-native kustomize deployment, NetworkPolicy, RBAC, or Route is present; those controls are supplied by the consuming operator/platform.
