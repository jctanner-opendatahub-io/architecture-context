## Purpose

**Short**: A lightweight REST API service for orchestrating Large Language Model (LLM) evaluations across multiple frameworks like lm-evaluation-harness, RAGAS, Garak, and GuideLLM, integrated with MLflow tracking and designed for native OpenShift deployment.

**Detailed**: eval-hub is a Go-based evaluation orchestration platform that exposes a REST API for submitting LLM evaluation jobs, configuring providers and benchmarks, and tracking results through MLflow. It abstracts multiple evaluation frameworks into a unified interface, with support for both local and Kubernetes runtime execution. The service integrates with the TrustyAI Service Operator for OpenShift deployment and includes sidecar binaries for evaluation job execution (eval-runtime-sidecar, eval-runtime-init) and an MCP (Model Context Protocol) bridge (evalhub-mcp) for external tool integration.

## Architectural Analysis

eval-hub follows a clean layered architecture with clear separation of concerns:

**Core Patterns**:
- **Handler-based routing**: Uses Go's standard `net/http.ServeMux` with per-route handlers, avoiding heavyweight frameworks
- **ExecutionContext pattern**: API handlers receive `ExecutionContext` (request ID, tenant, user, logger) instead of raw HTTP objects, ensuring consistent observability across handlers
- **Pluggable abstractions**: `Storage` (SQL backend), `Runtime` (local or Kubernetes), and `RuntimeStorage` (minimal surface for job workers) interfaces enable runtime selection without tight coupling
- **Multi-tenant scoping**: Namespace-level tenancy delegated to Kubernetes; within-cluster auth via kube-rbac-proxy headers (`X-Tenant`, `X-User`)

**Data Flow**:
1. Client submits evaluation job via REST API
2. Handler validates, writes to storage, optionally registers MLflow experiment
3. Runtime (local or k8s) is selected; job is scheduled
4. Sidecar monitors job progress, updates status via `RuntimeStorage.UpdateEvaluationJob`
5. Results are exported to MLflow and optional OCI registries

**Observability Stack**:
- **Prometheus metrics**: Request counters, duration histograms via middleware
- **Structured logging**: slog with request context enrichment
- **OpenTelemetry**: Optional tracing/metrics from service config, with gRPC and HTTP exporters
- **Metrics server**: Dedicated HTTP server on port 8081 (configurable) for Prometheus scrape without auth

**Deployment Model**:
- Local mode (dev/test): SQLite, process-based runtimes, optional metrics
- Kubernetes mode (production): PostgreSQL, Job/ConfigMap orchestration via Kubernetes API, kube-rbac-proxy for auth

**Notable Design Decisions**:
- Sidecar's `WriteTimeout: 0` to support reverse proxy use: upstream latency is enforced per-client, not server-wide
- `ReadHeaderTimeout: 15s` bounds slow-header attacks while `ReadTimeout: 0` allows large request bodies (inference payloads)
- FIPS-compliant build: `GOEXPERIMENT=strictfipsruntime`, dynamic linking, UBI minimal-pqc runtime
- Configuration: YAML-based with environment variable overrides and optional secret files for credentials

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | per-tenant RBAC via ServiceAccount; X-Tenant header scoping | Kubernetes RBAC + kube-rbac-proxy | Local mode bypasses all tenant auth; dev/test only |
| Data storage | Storage.WithTenant() method chains filters; SQL queries include tenant in WHERE | Application (Storage abstraction) | SQL injection possible if tenant value not sanitized; depends on Viper/config parsing |
| Network traffic | NetworkPolicy per namespace (optional; TrustyAI Operator may provision) | Kubernetes | No default NetworkPolicy; relies on cluster policy |
| Compute & resources | ResourceQuota / LimitRange per namespace (optional) | Kubernetes | Not managed by eval-hub; depends on cluster/operator setup |
| Configuration & secrets | Secrets, ConfigMaps per namespace; kube-rbac-proxy enforces identity | Kubernetes RBAC | Shared MLflow backend not tenant-isolated; shared PostgreSQL database requires table-level scoping |
| API scoping | Storage.WithTenant() wraps all queries; queries include namespace filter | Application | Single PostgreSQL backend shared across tenants; relies on application-level row filtering (not row-level security) |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| PostgreSQL database | Shared schema, tenant column in job/evaluation tables | Application query filter (Storage.WithTenant) |
| MLflow tracking server | Shared (single instance for all tenants) | No tenant isolation in MLflow; relies on experiment naming convention |
| OCI registry for result export | Shared registry, per-tenant image namespace | Image repository path (e.g., registry.io/tenant-ns/evalrun-uuid:latest) |

_Multi-tenancy is strong at the API/RBAC layer (kube-rbac-proxy + ServiceAccount) but weak at the backend layer (shared database, shared MLflow). Tenants are isolated by application query filtering, not by database-level enforcement (row-level security not used)._

**Analysis Notes**:
- eval-hub is a well-structured Go service with clear layered architecture, strong FIPS compliance signals (dynamic linking, GOEXPERIMENT=strictfipsruntime), and multi-tenant scoping via Kubernetes RBAC.
- Multi-tenancy is enforced at the API/authentication layer (kube-rbac-proxy + ServiceAccount) but relies on application-level query filtering at the storage layer (no database-level row-level security).
- Shared backends (PostgreSQL, MLflow, OCI registry) across tenants represent a design trade-off between operational simplicity and data isolation; risk mitigation depends on correct application of Storage.WithTenant() filtering.
- Build is FIPS-compliant; application-level crypto (TLS 1.2+) is explicitly configured. No non-FIPS crypto libraries detected.
- Sidecar TLS configuration is conservative (TLS 1.2+) and proxy-aware (WriteTimeout: 0 to allow upstream latency).
