## Purpose

**Short**: Builds multi-variant container images for Jupyter notebooks, Code-Server IDEs, and Elyra pipeline runtimes used by OpenDataHub (ODH) and Red Hat OpenShift AI (RHOAI).

**Detailed**: The notebooks repository produces a collection of pre-configured container images for interactive data science workbenches. These images provide Python environments with machine learning libraries, scientific computing tools, and IDE capabilities (JupyterLab or VS Code in the browser) for data scientists and developers. Images are published as OpenShift ImageStreams and launched by the ODH Notebook Controller and RHOAI platform as Kubernetes Notebook CRs. The repository manages multiple "flavor" variants (minimal, datascience, PyTorch, TensorFlow, TrustyAI, ROCm) across three accelerator types (CPU, NVIDIA CUDA, AMD ROCm), each with hermetically locked dependencies via Cachi2/Hermeto and locked Python packages via `uv`. Additionally, runtime images support Elyra visual pipeline execution and include optional Code-Server workspace environments with nginx-based idle-culling emulation for non-Jupyter-compatible IDEs.

## Architectural Analysis

### Multi-Layered Image Hierarchy

The repository does **not** use inter-image Docker FROM dependencies. Instead, each Dockerfile is self-contained and rebuilds all ancestor stages internally from a single `${BASE_IMAGE}` external base. This design isolates image builds, avoids implicit version pins from layer dependencies, and allows independent base image updates per variant. The conceptual layer structure is:

```
${BASE_IMAGE} (external)
  ├── cpu-base / cuda-base (OS packages + tools)
  │    └── jupyter-minimal (Python + JupyterLab + basic packages)
  │         └── jupyter-datascience (NumPy, Pandas, SciPy, scikit-learn)
  │              ├── jupyter-pytorch (PyTorch + CUDA/ROCm)
  │              ├── jupyter-pytorch+llmcompressor (PyTorch + LLM Compressor)
  │              ├── jupyter-tensorflow (TensorFlow + CUDA/ROCm)
  │              ├── jupyter-trustyai (TrustyAI explainability)
  │              └── ... (other variants)
```

Each leaf Dockerfile (e.g., `jupyter/pytorch/ubi9-python-3.12/Dockerfile.konflux.cuda`) contains **all stages** from base down to the final stage in a single file. Multi-stage inheritance is logical, not buildtime.

### Build System and Parameterization

The Makefile orchestrates builds with two key parameters:
- **PRODUCT**: Selects variant (`PRODUCT=odh` uses `build-args/<variant>.conf` and `manifests/odh/`; `PRODUCT=rhoai` uses `build-args/konflux.<variant>.conf` and `manifests/rhoai/`)
- **Accelerator variants**: `.cpu`, `.cuda`, `.rocm`, `.gaudi` etc. (via `Dockerfile.konflux.VARIANT` naming and `PYLOCK_FLAVOR` arg)

Both ODH and RHOAI can be built locally or on Konflux/Tekton using the same Dockerfile structure; the product variant switches build-args and manifest sets only.

### Hermetic Build and Dependency Locking

All images build hermeticaly on Konflux via Cachi2/Hermeto:
- **OS packages**: Locked via `rpms.lock.yaml` (root `prefetch-input/odh/` and `prefetch-input/rhds/`) with GPG key imports for signature verification
- **Python packages**: Locked via `uv.lock.d/pylock.${PYLOCK_FLAVOR}.toml` (per image, per variant) with `uv pip install --no-index --strict`
- **Build inputs**: Locked via `artifacts.lock.yaml` (Hermeto)
- **Cachi2 source imports**: Monorepo submodules (mongocli) also hermetically prefetched

Image builds run as non-root (`USER 1001:0`) with `umask 0002` for OpenShift arbitrary UID compatibility, and final permissions are corrected via `ensure-openshift-site-packages.sh`.

### OpenShift Integration and Runtime Trust Model

Images are deployed via Kubernetes ImageStreams and launched as Notebook CRs. The ODH Notebook Controller webhook:
1. Resolves container image from ImageStream annotations
2. Mounts CA certificate bundles and pipeline runtime ConfigMaps
3. Injects kube-rbac-proxy sidecar for OAuth

Platform environment variables (`NB_PREFIX`, `NOTEBOOK_ARGS`) are set by the controller, not validated inside the image. Code-Server lacks a Jupyter-compatible API, so the repo provides an nginx + httpd + bash CGI stack that polls the IDE heartbeat and exposes `/api/kernels/` for idle culling.

### Elyra Pipeline Runtime Integration

This repo publishes separate `runtimes/` images marked with `opendatahub.io/runtime-image: "true"` and annotated with Elyra runtime metadata. The Notebook Controller discovers these and mounts them as ConfigMaps; `setup-elyra.sh` at workbench startup copies the JSON configs into Elyra's metadata directories for pipeline runtime discovery and Data Science Pipelines endpoint configuration.

### Multi-Product Manifest Sets

The repository maintains separate kustomize base and overlay manifests for ODH (`manifests/odh/`) and RHOAI (`manifests/rhoai/`), allowing product-specific ImageStream annotations, labels, and configurations while sharing a common image production codebase.

## Sub-Component Details

### Jupyter Notebook Images

**Dockerfile**: `jupyter/*/ubi9-python-3.12/Dockerfile.konflux.cpu` (and `.cuda`, `.rocm` variants)

**Intent**: Interactive data science workbench environments launched by ODH/RHOAI platforms. These are the primary user-facing images. Three variants produce different dependency sets (minimal, datascience, ML-accelerated).

**Image**: `quay.io/opendatahub/workbench-images` (ODH) or `quay.io/redhat-data-services/notebooks` (RHOAI)

**Language**: Python (runtime), Bash (entrypoint and startup hooks)

**Port**: 8888 (JupyterLab default), exposed via container port 8888

**Key startup behavior**:
- `start-notebook.sh` launches JupyterLab server with `NB_PREFIX` environment variable from platform
- Sources `setup-elyra.sh` to populate Elyra runtime metadata from ConfigMap mounts
- JupyterLab plugins and custom build artifacts applied via `apply.sh`

### Code-Server Images

**Dockerfile**: `codeserver/ubi9-python-3.12/Dockerfile.konflux.cpu`

**Intent**: Browser-based VS Code alternative for users preferring traditional IDE experience. Includes three-process idle-culling stack (nginx + httpd + bash CGI) to emulate Jupyter kernel API.

**Image**: `quay.io/opendatahub/workbench-images` (ODH) or `quay.io/redhat-data-services/notebooks` (RHOAI)

**Language**: Bash (idle-culling logic), TypeScript (Code-Server configuration)

**Port**: 80 (nginx reverse proxy), 8080 (httpd CGI gateway), 8787 (Code-Server UI backend)

**Key idle-culling mechanism**:
- nginx reverse-proxy at port 80 logs all traffic to JSON with ISO 8601 timestamps
- httpd (port 8080) acts as CGI gateway
- bash script `access.cgi` polls `http://localhost:8787/healthz` (Code-Server heartbeat) and exposes `/api/kernels/` endpoint in Jupyter-compatible format
- Notebook Controller's culler periodically hits `/api/kernels/` to check `last_activity`

### Runtime Images

**Dockerfile**: `runtimes/*/ubi9-python-3.12/Dockerfile.konflux.*` (cpu/cuda/rocm variants)

**Intent**: Elyra visual pipeline execution environments. These are **not** interactive IDEs; they are step-worker containers that execute individual notebook cells as part of a pipeline DAG.

**Image**: `quay.io/opendatahub/pipeline-runtime-*` (ODH) or `quay.io/redhat-data-services/notebooks` (RHOAI)

**Language**: Python

**Key metadata**: ImageStream annotations include `opendatahub.io/runtime-image: "true"` and `opendatahub.io/runtime-image-metadata` JSON with Elyra v4 runtime descriptor.

### Base Images (ODH only)

**Dockerfile**: `base-images/cpu/c9s-python-3.12/Dockerfile.konflux`, similar for CUDA and ROCm

**Intent**: ODH-specific custom base images with CentOS Stream 9 + Python 3.12 + accelerator libraries (GPU drivers, CUDA, ROCm).

**Language**: Bash

**Note**: These are NOT used in RHOAI builds, which use AIPCC base images instead. Maintained in this repo for ODH's independent build pipeline.

## Security

### RBAC - Cluster Roles

The images themselves do not define RBAC; RBAC is enforced by:
- **kube-rbac-proxy** sidecar injected by Notebook Controller: Validates HTTP requests against RBAC policies before forwarding to the container
- **Notebook CR namespace scoping**: Each Notebook CR is namespaced; the controller ensures it runs in the user's project namespace

Notebook Container RBAC:
- No cluster roles required; the container is unprivileged and does not access the Kubernetes API
- User's service account is bound to roles in their project namespace (managed by Platform RBAC)

## Multi-Tenancy

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| **Tenant boundary** | Per-namespace (Notebook CR deployed to project namespace) | Kubernetes namespace isolation; Notebook CRs are namespaced resources |
| **Deployment model** | Single-instance per Notebook CR (one pod per workbench) | Notebook Controller spawns one Pod per Notebook CR |
| **Tenant identifier** | Namespace name + Notebook CR name | Kubernetes metadata |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | kube-rbac-proxy sidecar + RBAC policies | Kubernetes (sidecar injection) | User authentication is delegated to controller; image has no auth verification of NOTEBOOK_ARGS |
| Data storage | Namespace isolation via PVC mounts (user's home directory) | Kubernetes RBAC + storage classes | Each Notebook gets its own PVC in its namespace; isolation is per-namespace |
| Network traffic | Namespace NetworkPolicies (if configured) | Kubernetes / Istio (platform policy) | Not enforced by image; depends on platform NetworkPolicy setup |
| Compute & resources | ResourceQuota + LimitRange per namespace | Kubernetes | Not enforced by image; platform sets resource requests/limits on Notebook Pod |
| Configuration & secrets | Notebook CR `.spec` + env vars from controller | Kubernetes API + Notebook Controller | Platform-set env vars are trusted (no validation in image) |
| API scoping | Notebook API access is namespace-scoped (Notebook CRs are namespaced) | Kubernetes API (sidecar + RBAC) | Container itself does not filter or scope; isolation is at Kubernetes layer |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Artifact storage (images) | Cluster-wide (ImageStreams) | Registry RBAC + image pull policies |
| Metadata / ConfigMaps (Elyra runtimes) | Cluster-wide discovery, but mounted per-namespace | Controller mounts only ConfigMaps/Secrets from user's namespace |

Multi-tenancy is achieved via Kubernetes namespace isolation, not by the container itself. Images are shared cluster-wide; tenant separation is enforced at the Platform (Notebook Controller) and Kubernetes API layers.
