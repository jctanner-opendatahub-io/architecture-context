## Purpose

**Short**: Reconciles the platform observability stack from a singleton `Monitoring` custom resource.

**Detailed**: The operator watches the cluster-scoped `services.platform.opendatahub.io/v1alpha1` `Monitoring` resource named `default-monitoring`. It detects installed prerequisite operators and renders only the enabled metrics, tracing, telemetry, logging, alerting, dashboard, and query components. Resources are applied with server-side apply and labeled ownership because a cluster-scoped CR cannot own namespaced operands through normal owner references.

The operator also exposes health and readiness probes and can register a TLS admission webhook. The webhook handles `ServiceMonitor` and `PodMonitor` create/update requests, injecting the monitoring scrape label only in namespaces explicitly opted in and when the singleton Monitoring CR exists. Prometheus query access is exposed through namespace- and cluster-oriented `kube-rbac-proxy` deployments.

## Architectural Analysis

This is a discovery-driven control plane: reconciliation checks both the Monitoring CR and the APIs installed on the cluster, allowing one image to support different operator combinations. Embedded Go templates are the deployment boundary for managed operands, while `odh-platform-utilities` supplies cached server-side apply, ordering, and garbage collection behavior. The resulting architecture is intentionally conditional, but it means the effective resource graph depends on cluster capability discovery rather than only on static chart contents.

The most security-sensitive surface is the Prometheus query proxy. The cluster proxy forwards only `/metrics` and uses `cluster-monitoring-view`; the namespace proxy rewrites a `namespace` query parameter into an authorization resource attribute before forwarding to Prometheus. Both use kube-rbac-proxy and TLS, with upstream service-CA/client certificates where applicable. The mutating webhook is fail-closed and excludes the operator and system namespaces.

Analyzer manifest extraction is partial because most operand resources are Go templates. The tables below therefore combine analyzer facts with direct source/template evidence and mark dynamic names or conditional resources accordingly.
