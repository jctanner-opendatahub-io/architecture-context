## Purpose

**Short**: Kubernetes operator that manages a cluster-scoped `Monitoring` custom resource, declaratively provisioning a full metrics, traces, and dashboarding observability stack on OpenShift clusters.

**Detailed**: odh-observability is a controller-based Kubernetes operator designed to automate the provisioning and lifecycle management of observability infrastructure across ODH and RHOAI platforms. It watches a singleton `Monitoring` CR (`services.platform.opendatahub.io/v1alpha1`) and dynamically detects which prerequisite operators are installed on the cluster (Cluster Observability Operator, Tempo Operator, OpenTelemetry Operator, Perses Operator, and cert-manager). The operator deploys only the subsystems whose CRDs are present, enabling flexible observability stacks. Managed subsystems include Prometheus metrics collection via MonitoringStack, distributed tracing via Tempo, telemetry pipelines via OpenTelemetry Collector, dashboarding via Perses, alerting via PrometheusRules, and label injection for ServiceMonitor/PodMonitor resources via mutating webhooks. The operator also manages proxy deployments for namespace-scoped and cluster-scoped Prometheus access, with TLS encryption and RBAC-enforced access control.

## Architectural Analysis

The odh-observability operator demonstrates a sophisticated multi-component orchestration pattern. The reconciliation loop in `MonitoringReconciler` watches 16 distinct Kubernetes resource types—from core ConfigMaps and Secrets to cluster configuration objects—enabling reactive provisioning when prerequisites appear or disappear. This dynamic detection avoids hard dependencies while maintaining declarative intent: the operator synthesizes manifests for only the subsystems that are actually available.

**Key architectural patterns:**

1. **Prerequisite-driven composition**: The operator scans for CRDs (Prometheus, Tempo, Perses operators) and conditionally deploys corresponding subsystems, avoiding failures on minimal clusters while supporting feature-rich deployments.

2. **Template-driven resource generation**: The controller generates Kubernetes manifests from Go text templates (`internal/controller/resources/*.tmpl.yaml`), decoupling manifest structure from reconciliation logic and enabling parameterization for different target environments.

3. **Proxy-based tenancy enforcement**: Two proxy deployments—`data-science-prometheus-cluster-proxy` (cluster-wide access) and `data-science-prometheus-namespace-proxy` (namespace-scoped access)—enforce RBAC boundaries. `kube-rbac-proxy` validates bearer tokens, while `prom-label-proxy` injects namespace filtering, achieving multi-tenant query isolation on shared Prometheus instances.

4. **Webhook-based label injection**: Mutating webhooks (`podmonitor-injector.opendatahub.io`, `servicemonitor-injector.opendatahub.io`) automatically inject required labels into ServiceMonitor and PodMonitor resources, enforcing platform conventions without requiring user intervention.

5. **TLS-first security**: All proxies and inter-component communication use TLS with dynamically provisioned certificates via controller templates. The operator reads OpenShift APIServer TLS profiles to synchronize cipher suites and TLS versions, ensuring compliance with cluster security policies.

**Potential risks and observations:**

- **Watch predicate resolution gaps**: The controller watches RBAC resources (Role, RoleBinding, ClusterRole, ClusterRoleBinding) and networking policies without explicit named-resource filtering. This means the controller may reconcile in response to any RBAC change in the cluster, which could trigger unnecessary reconciliation cycles on large clusters.

- **Namespace immutability**: The Monitoring CR enforces immutable namespace specification (CEL validation rule `self == oldSelf`), preventing accidental migration or multi-tenancy scenarios. This simplifies operational overhead but eliminates flexibility if namespace names change.

- **Optional subsystem coupling**: Many subsystems are optional (Metrics, Traces, Alerting, UsageLogs, Logs). The spec includes complex validation rules (CEL XValidation) to prevent invalid combinations (e.g., alerting without metrics storage). This reduces configuration errors but increases spec complexity.

- **ControllerReconcile patterns**: The reconciler uses declarative manifest generation for all resources, with no imperative retry or rollback logic. This matches Kubernetes best practices but means failed resource creation surfaces as CR status conditions rather than controller-managed retries.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Namespace RBAC + kube-rbac-proxy + system:auth-delegator | Kubernetes RBAC + kube-rbac-proxy | Cluster admins can bypass proxy authentication; proxies delegate to kube-apiserver but do not enforce per-user quotas |
| Data storage | Namespace-scoped Prometheus via prom-label-proxy (label filtering) | prom-label-proxy sidecar injects namespace=X label | prom-label-proxy is in-process; if compromised, label filtering can be bypassed |
| Network traffic | NetworkPolicy not explicitly created; relies on kube-rbac-proxy TLS enforcement | kube-rbac-proxy TLS termination | No NetworkPolicy detected; east-west traffic between proxies and Prometheus is not explicitly restricted |
| Compute & resources | ResourceQuota/LimitRange configured by user via Monitoring CR (optional) | Kubernetes if user specifies resource limits | No default resource limits; over-provisioning or DoS possible if uncontrolled |
| Configuration & secrets | Per-namespace Secrets (TLS certs, datasource tokens, RBAC configs) | Kubernetes namespace isolation | All secrets stored in monitoring namespace (opendatahub); namespace breach exposes all subsystem credentials |
| API scoping | Namespace-scoped watches via prom-label-proxy label injection | prom-label-proxy runtime filter | Controller watches all Prometheus instances cluster-wide; label isolation is enforced at query time, not at storage time |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Prometheus (cluster-wide) | Namespace (via query label injection) | prom-label-proxy injects namespace=X label; cluster admins can access all namespaces via cluster-proxy |
| Tempo / OpenTelemetry Collector | Namespace (via configuration) | Collector configured per subsystem; log forwarding and trace export scoped to monitoring namespace |
| Perses (dashboarding) | Namespace (single instance per Monitoring CR) | Perses datasources are namespace-scoped; admin dashboards access cluster-wide, user dashboards namespace-scoped |
| LokiStack (log aggregation) | Namespace (via label forwarding) | ClusterLogForwarder routes namespace logs to LokiStack; log filtering is tenant-aware |

**Multi-tenancy assessment**: The operator supports namespace-scoped observability stacks, but tenancy is enforced at the query/access layer (kube-rbac-proxy + prom-label-proxy) rather than storage isolation. Shared Prometheus instances are protected via label-based query filtering, which is appropriate for cross-tenant visibility scenarios but not suitable for hard multi-tenant isolation where data must not be visible across namespaces. The architecture is suitable for team-based observability where teams share cluster infrastructure but require isolated dashboards and alerts.
