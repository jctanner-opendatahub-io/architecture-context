## Purpose

**Short**: kubectl plugin for preflight validation of GPU clusters before deploying AI/ML inference workloads.

**Detailed**: RHAII Cluster Validation runs comprehensive preflight checks on Kubernetes clusters with GPU resources to validate readiness for AI/ML workload deployment. The tool auto-detects GPU vendor (NVIDIA/AMD), cloud platform (AKS, EKS, CoreWeave, OpenShift), and cluster topology. It validates GPU hardware health (driver versions, ECC memory errors), RDMA/networking connectivity (device presence, NIC link status, GPU-NIC NUMA affinity), and cross-node bandwidth performance via TCP (iperf3) and RDMA (ib_write_bw, fi_rma_bw). Results are aggregated into a structured report (JSON or table format) showing per-node, per-GPU, and per-NIC findings with pass/warn/fail status and remediation guidance.

## Architectural Analysis

The validator operates as a two-tier orchestration system. The CLI entry point (Cobra-based `rhaii-validator` binary) runs locally on an admin's machine with kubeconfig access, parsing command-line check modes (`gpu`, `network`, `rdma`, `all`, etc.) and delegating work to an embedded controller. The controller orchestrates namespace-scoped Job deployments into the cluster (`rhaii-validation` namespace), with each Job configured as a privileged per-node or cross-node probe. Per-node GPU checks run a simple pod that `chroot /host` to inspect sysfs, run `nvidia-smi`/`rocm-smi`, and parse output locally. Bandwidth tests (`iperf3`, RDMA) deploy paired server/client jobs configured for ring topology (every node as both sender and receiver) to stress-test interconnect. RDMA job expansion happens per GPU-NIC pair discovered from NUMA affinity. Results flow back to a ConfigMap (`rhaii-validate-report`) in the cluster for persistence and kubectl inspection.

Key design choices:

1. **No operator/deployment**: The validator is ephemeral—runs as a user-facing CLI, not a long-lived cluster component. No CRDs, no Helm charts, no OLM operator.
2. **Privileged pod strategy**: GPU/RDMA checks require host access (sysfs, device files). Runs under OpenShift SCC `system:openshift:scc:privileged` when detected, falling back to container privileges elsewhere.
3. **Auto-detection over configuration**: Platform, GPU vendor, RDMA devices, and topology are discovered at runtime. Minimal static config required; per-platform YAML config (AKS, OCP, EKS, CoreWeave) parameterizes driver versions and bandwidth thresholds.
4. **Embedded manifests**: Default container images, RBAC, and namespace YAML are embedded in the Go binary via `//go:embed` and generated dynamically, overridable via CLI flags or env vars.
5. **Multi-GPU topology awareness**: Bandwidth job expansion is keyed on GPU-NIC NUMA proximity to ensure optimal test placement (e.g., GPU0 pairs with its closest NIC for RDMA tests).

No external observability hooks (no Prometheus, no logging exports). Output is human-readable (stdout) or JSON (`-o json`).
