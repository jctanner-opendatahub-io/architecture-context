## Purpose

**Short**: Kubernetes Operator that deploys and manages Kueue, a job queueing system for batch and AI workloads on OpenShift.

**Detailed**: The Kueue Operator automates the deployment and lifecycle management of Kueue, which provides enterprise-grade workload queuing, scheduling, and resource management for batch jobs and distributed AI training frameworks. The operator installs the Kueue controller manager alongside comprehensive CRD definitions that support multiple job frameworks (Batch Job, MPIJob, RayJob, PyTorchJob, TFJob, XGBoostJob, JobSet, PaddleJob, Deployments, StatefulSets, Pods, and AppWrapper). It manages opt-in webhook admission control for namespace-scoped workload validation and mutation, integrates with cert-manager for TLS certificate provisioning, and enforces RBAC-based access control with granular roles for different job types and queue hierarchies (ClusterQueues, LocalQueues, Cohorts, ResourceFlavors).

## Architectural Analysis

The Kueue Operator follows a standard Kubernetes operator pattern: a CLI-based operator binary runs a single controller process that reconciles a custom `Kueue` CRD (in namespace `openshift-kueue-operator`), determining whether and how to deploy the Kueue workload onto the cluster. Kueue itself is deployed as a controller-manager deployment that handles all workload scheduling logic, while the operator owns the lifecycle of that deployment, its RBAC configuration, webhooks, and bundled CRDs.

**Key architectural decisions:**

1. **Opt-in Webhook Admission**: Webhooks only apply to namespaces labeled with `kueue.openshift.io/managed=true`. This decouples Kueue from cluster-wide enforcement and allows gradual adoption. Both validating and mutating webhooks exist for each supported job framework, and the operator dynamically enables/disables them based on the Kueue CRD's `.spec.integrations.frameworks` list.

2. **Bindata Embedding**: The operator embeds Kueue manifests (CRDs, deployments, RBAC, services) as binary data in the operator image itself via the `bindata/` directory. This ensures the operator can deploy Kueue without external manifest repositories and simplifies upgrade atomicity.

3. **Certificate Management**: The operator injects cert-manager annotations into webhook configurations to auto-provision and rotate TLS certificates. This removes manual secret management and ensures webhooks remain healthy across certificate rotation boundaries.

4. **Framework Flexibility**: Rather than a single hardcoded job framework, the operator's `KueueConfiguration` (via the Kueue CRD) specifies which frameworks to enable. The operator then applies only the corresponding webhooks and RBAC roles, reducing cluster noise and scope.

5. **Dual Deployment Model**: The operator itself runs one deployment (`openshift-kueue-operator`) in its own namespace, while Kueue (the operand) runs its own controller-manager deployment in the kueue namespace, created dynamically by the operator. This separation allows the operator to be updated independently of Kueue version changes.

**Risks and observations:**

- Webhook selector merging logic (in `pkg/webhook/pod_webhook.go`) adds the operator's default `kueueManagedLabel` selector to all dynamic webhooks. Misconfiguration of namespace labels or webhook framework lists could cause unexpected pod rejections.
- The operator depends on cert-manager being installed (documented in README); if cert-manager is not available, webhook TLS certificate provisioning will fail silently, causing webhook service failures.
- No explicit multi-tenancy isolation documented; the operator assumes single-tenant cluster deployment. Multi-tenant scenarios would require namespace-level quota/RBAC enforcement (delegated to platform).

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | per-namespace RBAC (ClusterRoles with user/editor separation; LocalQueue editor limited to namespace) | Kubernetes RBAC + Kueue CRD scope | Cluster-scoped CRDs (ClusterQueue, ResourceFlavor, Cohort) allow cross-namespace policy influence; namespace admin can edit LocalQueue scoped to their namespace |
| Data storage | LocalQueue and Workload stored in etcd by namespace; ClusterQueue shared cluster-wide | Kubernetes CRD scope | Cross-namespace resource sharing via Cohort CRD; namespace isolation delegated to RBAC |
| Network traffic | No explicit NetworkPolicy defined | N/A | Webhook traffic between API server and service is automatic; visibility server access requires explicit mTLS cert |
| Compute & resources | ResourceFlavor defines resource attributes; ResourceQuota/LimitRange delegated to platform | Kubernetes (via quota) | No built-in pod-level compute isolation; platform must enforce via ResourceQuota, LimitRange |
| Configuration & secrets | Kueue config ConfigMap in kueue namespace; webhook certs in kueue namespace | Kubernetes RBAC | Operator configuration isolated in operator namespace; operand configuration in kueue namespace |
| API scoping | LocalQueue is namespaced; Workload is namespaced; ClusterQueue/ResourceFlavor/Cohort are cluster-scoped | CRD scope | Namespace isolation for user jobs; cluster-wide resource definitions require cluster-admin |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| kueue-controller-manager | cluster-wide (single deployment) | Single controller manages all namespaces; namespace isolation enforced via LocalQueue scope and webhook label selector |
| Metrics | cluster-wide (single /metrics endpoint) | Prometheus scrapes single endpoint; no per-namespace metrics isolation |

**Multi-Tenancy Summary**: Kueue Operator supports multi-namespace deployment with per-namespace opt-in (label-based). LocalQueue provides namespace scoping; ClusterQueue/ResourceFlavor/Cohort are cluster-wide shared definitions. Isolation is adequate for namespaced job workloads but not for strict tenant separation (e.g., cross-namespace resource contention possible via Cohort sharing). Recommended for shared-tenant clusters where namespace admin trust is acceptable.
