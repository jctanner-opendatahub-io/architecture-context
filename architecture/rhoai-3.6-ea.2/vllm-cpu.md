## Purpose

**Short**: A CPU-optimized container image for vLLM, providing high-throughput LLM inference serving without GPU requirements.

**Detailed**: vLLM is a fast and efficient library for Large Language Model inference and serving. This component provides a RHEL-based container build optimized for CPU-only execution, supporting multi-architecture deployment (x86_64, ppc64le, s390x, aarch64). The service exposes an OpenAI-compatible REST API for model inference, supporting continuous batching, paged attention optimization, and multiple quantization formats. The downstream vllm-cpu repository maintains synchronization with the upstream vLLM project while adding Red Hat-specific build configurations, packaging optimizations, and architecture-specific compilation flags.

## Architectural Analysis

The vllm-cpu component represents a platform service delivery mechanism for LLM inference. Key architectural characteristics include:

**Multi-Architecture Strategy**: The component maintains parallel Dockerfiles for different CPU architectures (x86_64, ppc64le, s390x) with architecture-specific build scripts (`build_vllm_*.sh`). Each architecture has distinct compilation requirements due to differing instruction set support and vendor library availability.

**Build Strategy**: Uses a multi-stage Dockerfile pattern with separate builder and runtime stages. The builder stage compiles vLLM from source using a virtual environment (`/opt/vllm`), caching dependencies via `uv` package manager with Buildkit cache mounts. The runtime stage copies only the compiled virtual environment, minimizing the final image size while maintaining build hermeticity through `uv.lock` management.

**Python Packaging**: Installs Python packages via `uv` instead of `pip` for improved dependency resolution and performance. The Dockerfile uses BuildKit cache mounts (`--mount=type=cache,target=/root/.cache/uv`) for efficient dependency caching during multi-architecture builds. However, the component does not use AIPCC base images despite installing Python packages, representing a deviation from Red Hat's standardized secure build pipeline. Uses standard UBI9 minimal base (`ubi9/ubi-minimal-pqc`) without AIPCC ecosystem integration.

**OpenAI Compatibility**: The service runs `vllm.entrypoints.openai.api_server` as the primary entrypoint, exposing a comprehensive OpenAI-compatible API with 47 registered HTTP endpoints covering chat completions, text generation, embeddings, and multimodal inference paths.

**Runtime Configuration**: Configures multiple environment variables to control runtime behavior, including `VLLM_USE_V1=1` (V1 API enabled), `VLLM_WORKER_MULTIPROC_METHOD=fork`, and non-root execution as UID 2000.

**Crypto Implementation Details**:
- HTTP server uses FastAPI/Starlette, which wraps Python's `ssl` module.
- If TLS is enabled (via CLI args `--ssl-certfile` and `--ssl-keyfile`), the server enforces TLS 1.2+ by default in Python 3.12.
- Model artifact downloads from Hugging Face use the `requests` library, which validates certificate chains against the system CA store (OpenSSL).
- No custom cipher suite specification detected; reliance on Python/OpenSSL defaults (which are secure for TLS 1.2+).
- Token validation is a basic string comparison (`--api-key` vs. `Authorization` header), NOT JWT signature validation or HMAC.

**FIPS Readiness Assessment**: 
- vllm-cpu can operate in FIPS-compliant mode if: (1) OpenSSL in the UBI base is in FIPS mode (`OPENSSL_FIPS=1`), (2) TLS is enforced (HTTPS, not HTTP), and (3) no legacy cipher suites are hardcoded.
- However, explicit FIPS validation (e.g., FIPS module testing, BoringSSL option) is not configured. The component is **FIPS-adjacent** (uses OpenSSL which is FIPS-capable) but not **FIPS-certified**.
- For RHOAI deployments in FIPS environments, TLS termination must be configured at the platform layer (e.g., Istio sidecar, OpenShift Route with TLS termination).

## Notes

1. **AIPCC Gap**: This component does not use AIPCC base images despite installing Python packages. For secure builds in RHOAI, migration to an AIPCC CPU base image (from overlay 0017) would provide:
   - Pre-configured RHEL AI Python Package Index (`pip.conf` / `uv.toml`)
   - Standardized `/etc/rhaipcc/env` environment metadata
   - `/usr/libexec/rhaipcc/dnf` helper for vendor package repos
   - Centralized security patching across all AIPCC-based components

2. **Build Hermeticity**: The downstream rhoai-3.6-ea.2 branch lacks lock files for OS and Python dependencies. Adding `rpms.lock.yaml` and surfacing `uv.lock` would improve supply chain security and reproducibility.

3. **Multi-Tenancy**: The component itself is single-tenant. RHOAI deployments should enforce namespace isolation, resource quotas, and network policies at the platform layer.

4. **Authentication**: The API server does not enforce authentication. Security depends on platform-layer controls (Istio AuthorizationPolicy, OpenShift Routes with TLS/mTLS, network policies).
