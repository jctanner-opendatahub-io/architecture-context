## Purpose

**Short**: Kubernetes-native distributed AI training platform for large language model (LLM) fine-tuning and model training across multiple frameworks.

**Detailed**: Kubeflow Trainer is a Kubernetes operator that orchestrates distributed AI training jobs on Kubernetes. It provides a unified API for running training workloads using multiple frameworks (PyTorch, TensorFlow, JAX, XGBoost, MLX, DeepSpeed, etc.) with built-in support for distributed training, multi-GPU/multi-node orchestration, and HPC integration. The operator integrates with Kueue for topology-aware scheduling, JobSet for job orchestration, and Volcano for advanced scheduling. It includes support for data caching, model initialization, and training runtime definitions that allow users to define custom training environments.

## Architectural Analysis

Kubeflow Trainer follows a controller-based architecture pattern typical of Kubernetes operators. The controller manager runs a reconciliation loop that watches for TrainJob custom resources and orchestrates their lifecycle. The architecture is layered with multiple CRDs representing different aspects of the training system: TrainJob (the primary user-facing resource defining a training job), TrainingRuntime/ClusterTrainingRuntime (defining reusable training environments), and Configuration (cluster-wide settings).

The design emphasizes extensibility through the runtime framework, allowing users to define custom training environments via YAML manifests. This mirrors patterns seen in KServe and other ML operators. The controller integrates with several Kubernetes ecosystem projects: JobSet and LeaderWorkerSet for distributed job coordination, Kueue for scheduling, and Volcano for advanced scheduling features. This indicates the trainer is designed as a building block within a larger platform rather than a standalone component.

Security and FIPS compliance are explicitly addressed through build-time flags (GOEXPERIMENT=strictfipsruntime, CGO_ENABLED=1) enforcing dynamically-linked Go binaries with OpenSSL. The codebase uses standard Kubernetes control-plane patterns: webhooks for validation and defaulting, RBAC for access control, and dynamic configuration via ConfigMaps.

Multi-tenancy is implicitly scoped to Kubernetes namespaces—TrainJob and TrainingRuntime are namespace-scoped resources, and RBAC enforces per-namespace isolation. The controller does not implement application-level tenant isolation; isolation relies entirely on Kubernetes primitives.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | RBAC via ServiceAccount + ClusterRoleBinding per namespace | Kubernetes | Relies on cluster-wide RBAC; no application-level tenant isolation |
| Data storage | Trainer controller watches only resources in its own namespace; TrainJob pods run in their job's namespace | Kubernetes | TrainingRuntime resources in one namespace are visible to controller globally (watch is cluster-wide); consider namespace isolation if strict multi-tenancy is required |
| Network traffic | Implicit (Kubernetes namespace isolation); no explicit NetworkPolicy | Kubernetes | Default-allow posture; NetworkPolicy not enforced by trainer controller |
| Compute & resources | ResourceQuota and LimitRange per namespace (optional, platform-enforced) | Kubernetes / Platform | Trainer does not enforce per-job compute isolation; relies on platform ResourceQuota |
| Configuration & secrets | Per-namespace Secrets and ConfigMaps for model/dataset credentials | Kubernetes | Secrets are namespace-scoped; sharing across namespaces requires manual setup |
| API scoping | Namespace-scoped watches for TrainJob, TrainingRuntime; ClusterTrainingRuntime is cluster-wide | Kubernetes | ClusterTrainingRuntime is readable across all namespaces; consider RBAC restrictions if needed |
