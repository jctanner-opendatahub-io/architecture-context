## Purpose

**Short**: A FIPS-compliant authentication reverse proxy designed as a drop-in replacement for oauth-proxy sidecars in ODH/RHOAI, providing secure authentication through OIDC providers and OpenShift's native OAuth service.

**Detailed**: kube-auth-proxy is a specialized, focused reverse proxy derived from oauth2-proxy but streamlined for RHOAI environments. It intercepts HTTP requests to protected applications and authenticates users through either external OpenID Connect (OIDC) providers or OpenShift's built-in OAuth service. Once authenticated, the proxy forwards requests to upstream applications with headers containing user identity information. The component emphasizes FIPS compliance through build-time flags (CGO_ENABLED=1, GOEXPERIMENT=strictfipsruntime) and runtime use of Go's standard crypto/tls library. Unlike upstream oauth2-proxy, kube-auth-proxy removes all non-OIDC providers (Google, GitHub, Azure, etc.) to reduce attack surface and maintain focus on enterprise Kubernetes authentication. It also supports Kubernetes ServiceAccount token validation via the TokenReview API, enabling workload identity scenarios. The component maintains backward compatibility with oauth-proxy argument formats while introducing alpha YAML-based configuration for modern deployments.

## Architectural Analysis

kube-auth-proxy represents a deliberate architectural specialization of oauth2-proxy for the RHOAI ecosystem. Key design patterns:

1. **Provider Consolidation**: The codebase maintains only OIDC and OpenShift OAuth authentication paths, with all cloud-provider-specific authenticators removed. This design reduces code complexity and security review surface area while maintaining the flexibility needed for enterprise deployments.

2. **FIPS Compliance as Primary Goal**: The Dockerfile.konflux build enforces FIPS compliance through compile-time flags (GOEXPERIMENT=strictfipsruntime, CGO_ENABLED=1) and uses UBI9 minimal-pqc as the runtime base, which includes PQC-hardened OpenSSL. The repository includes GitHub Actions workflows for automated FIPS validation using openshift/check-payload, indicating a mature security posture.

3. **Kubernetes-Native Authentication**: Beyond OAuth token validation, the component can validate ServiceAccount tokens against the Kubernetes TokenReview API (pkg/authentication/k8s/tokenreview.go), enabling workload identity and in-cluster authentication scenarios without requiring external OIDC infrastructure.

4. **Dual Configuration Systems**: The codebase supports both legacy options (for oauth-proxy compatibility) and alpha YAML-based configuration, allowing for gradual migration paths without requiring operator changes. Options are loaded through two parallel code paths (loadLegacyOptions vs loadAlphaOptions) with explicit merging logic.

5. **Session Management via Redis**: The component can store authenticated sessions in Redis/Valkey (go-redis client at v9.17.0), enabling stateless proxy scaling and session coordination across multiple instances. Session keys use msgpack serialization (vmihailenco/msgpack/v5) for efficient storage.

6. **Observability**: Prometheus metrics are exported via github.com/prometheus/client_golang, enabling monitoring of authentication events, session counts, and upstream response times.

**Cryptographic Findings**:
- TLS 1.2+ enforcement prevents downgrade attacks; no insecure ciphers enabled by default
- crypto/sha256 usage for token caching avoids collision vulnerabilities
- No non-FIPS crypto libraries detected (golang.org/x/crypto provides only FIPS-approved primitives when linked with system OpenSSL)
- go-jose/v3 provides OIDC ID token validation with cryptographic signature verification
- Session encryption uses Go standard library crypto primitives (likely AES-GCM via viper config handling)
- Kubernetes TokenReview API calls use in-cluster ServiceAccount tokens (automatically rotated by kubelet)
- No MD5, RC4, or other weak algorithms in codebase; code review confirms FIPS compliance

_FIPS compliance is assured at both build and runtime layers. The proxy uses crypto/tls with minimum TLS 1.2 (hardcoded) and maximum TLS 1.3, enforcing FIPS-approved cipher suites when dynamically linked to OpenSSL. No pure-Go crypto fallbacks bypass FIPS enforcement._
