## Purpose

**Short**: kube-auth-proxy authenticates requests for OpenShift/RHOAI applications and proxies authenticated traffic to an upstream service.

**Detailed**: kube-auth-proxy is a focused fork of oauth2-proxy for OpenDataHub and Red Hat OpenShift AI. It supports external OIDC providers and OpenShift's internal OAuth service, then forwards authenticated requests while preserving compatible identity and authorization headers for the upstream application.

The process can also validate Kubernetes service-account bearer tokens through the Kubernetes TokenReview API. Successful reviews are cached briefly and concurrent reviews for the same token are deduplicated. Session state is held in signed/encrypted cookies or a Redis-compatible store, depending on configuration. The project provides a standard root Go entrypoint and a FIPS-oriented Konflux image build.

## Architectural Analysis

kube-auth-proxy is a single deployable Go binary with a configurable HTTP and optional HTTPS listener. Its central boundary is an authentication reverse proxy: provider-specific OIDC or OpenShift OAuth code establishes a session, middleware validates the session or bearer token, and the reverse proxy sends the request to a configured upstream. The application intentionally provides authentication rather than Kubernetes RBAC or SubjectAccessReview authorization; Kubernetes TokenReview is used for token validity and identity extraction.

The RHOAI-facing example is a conventional Deployment and ClusterIP Service, with an OpenShift Route terminating external TLS before forwarding to the proxy's HTTP listener. The proxy itself can terminate TLS when configured. It uses in-cluster Kubernetes configuration and service-account credentials for TokenReview and OpenShift OAuth discovery, while Redis is an optional external session backend. The short-lived hashed-token cache reduces API-server load but means token-review results are intentionally cached for a bounded interval.

The Konflux Dockerfile is a multi-stage, multi-architecture build using a pinned UBI Go toolset builder and a pinned UBI minimal PQC runtime. The FIPS build enables CGO and `strictfipsruntime`, runs as UID 1001, and embeds only an empty JWT key placeholder; runtime secrets are expected from configuration or mounted files. The repository has a Go module checksum lock but no RPM, artifact, or Hermeto lock metadata in this checkout.
