## Purpose

**Short**: Grid discovers and scores inference providers across Kubernetes sites and publishes routing overlays consumed by Praxis gateways.

**Detailed**: Grid is a Kubernetes operator and distributed control plane for a multi-site inference mesh. It watches GridNetwork, GridSite, InferenceProvider, and AgentToolProvider resources, discovers peers with SWIM, propagates provider state with CRDTs, probes provider health, and selects provider candidates using configurable scoring strategies.

Grid is not in the request path. It writes versioned routing and consumer-configuration ConfigMaps into the namespaces of referenced Praxis gateways. Praxis gateways perform request routing, gateway-to-gateway mTLS, credential injection, and backend communication using that precomputed state. The repository also contains certificate generation, an overlay-sync sidecar, mock providers, and development orchestration crates.

## Architectural Analysis

The principal boundary is a cluster-scoped GridNetwork: sites and providers are cluster-scoped objects linked to it by names and labels. A single operator replica reconciles the global object set and writes namespaced delivery artifacts. This makes the control plane easy to reason about for consistency, but the chart explicitly keeps `replicaCount` at one until multi-replica operation is qualified.

The design separates control-plane convergence from data-plane traffic. SWIM/CRDT state and provider probes feed a routing overlay; the overlay is applied idempotently to ConfigMaps and can be delivered quickly by overlay-sync. Provider credentials are referenced rather than serialized into generated configuration. TLS material is either supplied through referenced Secrets or generated by the operator, while SWIM encryption can use a Kubernetes Secret-backed AES-256-GCM key.

The main architectural risks are the broad cluster-scoped read/list/watch surface, the explicit namespace references for Secrets and gateway ConfigMaps, and the fact that the operator’s Rust TLS stack selects `ring`, which the analyzer identifies as not FIPS validated. Analyzer coverage also reports authentication as partial and gRPC as not verified; these limits should be considered when using this summary.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Shared operator ServiceAccount with ClusterRoles | Kubernetes | Cluster-wide CR reads/lists and explicit Secret namespace references require careful RBAC and admission governance. |
| Data storage | ConfigMaps and Secrets in referenced namespaces; no database/PVC | Kubernetes/API plus operator logic | Generated overlays are shared per network/gateway; token bytes are intentionally excluded, but ConfigMap readers must be trusted. |
| Network traffic | Optional provider-only NetworkPolicy in mock-provider chart; no operator-wide tenant policy | Kubernetes | Production cross-tenant network isolation is not defined by Grid. |
| Compute & resources | Single Deployment; optional scheduling knobs, no quotas or per-tenant compute controls | Kubernetes/platform | One operator and shared gateway/control-plane resources can be noisy neighbors. |
| Configuration & secrets | Explicit SecretRefs and namespaced ConfigMaps | Kubernetes plus application reference resolution | Cluster-scoped CR authors can point to Secrets across namespaces if RBAC permits; policy should constrain references. |
| API scoping | `Api::all` lists all GridSite and InferenceProvider objects; CRDs are cluster-scoped | Kubernetes plus application filtering by `gridNetworkRef`/labels | No namespace boundary exists for core objects; application filtering is a key correctness boundary. |
