## Purpose

**Short**: A Kubernetes-aware RBAC authorization proxy that enforces authentication and authorization on HTTP requests before forwarding to upstream services.

**Detailed**: kube-rbac-proxy is a lightweight sidecar container or standalone service that protects upstream HTTP endpoints (metrics, APIs, dashboards) by enforcing Kubernetes RBAC authorization. On receipt of an incoming request, it authenticates the caller (via client TLS certificate or bearer token), then performs a Kubernetes SubjectAccessReview to authorize the request against configured RBAC rules. Only authorized requests are proxied to the upstream service. This prevents unauthorized access to sensitive endpoints like Prometheus metrics, which might leak cluster topology or workload metrics to attackers with network access to a Pod. The component supports multiple authentication methods (client certificates, bearer tokens, OIDC), configurable authorization policies (per-resource, per-verb), and TLS/mTLS encryption on both inbound and outbound connections.

## Architectural Analysis

kube-rbac-proxy operates as a transparent security enforcement layer at the HTTP request boundary. Its architecture reflects three principal design concerns: authentication diversity (supporting client TLS, bearer tokens, and OIDC), authorization flexibility (SubjectAccessReview-based or static policy), and operational transparency (minimal performance overhead, path-based bypass for health checks).

**Authentication Flow**: Incoming requests are first authenticated. Client TLS certificates are validated against a configured CA; bearer tokens are verified via TokenReview against the Kubernetes API. OIDC flows are supported for user authentication. Once authenticated, the request is enriched with the user's identity and groups.

**Authorization Flow**: Each request (unless on an ignore-path) undergoes a SubjectAccessReview against the Kubernetes API. The proxy translates the incoming request into Kubernetes resource attributes (namespace, resource kind, verb) and forwards to kube-apiserver for evaluation against cluster RBAC. Responses with 403 status are returned immediately; only authorized (200) requests proceed to the upstream.

**TLS Posture**: The component enforces TLS 1.2+ on both inbound and outbound connections. Cipher suites are configurable (defaulting to Go's secure defaults). Certificate reloading is supported for zero-downtime rotations. The Konflux build enforces FIPS compliance via `GOEXPERIMENT=strictfipsruntime` and `CGO_ENABLED=1`, dynamically linking against OpenSSL in the UBI base image.

**Operational Patterns**: Health checks and metrics endpoints can be exposed on a separate, less-restrictive endpoint (`--proxy-endpoints-port`), avoiding circular auth dependencies. Request patterns (path-based allow/deny lists, verb overrides via request query parameters) allow fine-grained control over which endpoints are protected and how resource attributes are mapped.

**Risk Surfaces**: Token-based authentication can expose high-privilege credentials if the upstream service mishandles tokens (though the README warns against this). The proxy cannot control what the upstream does with authenticated requests. Misconfigured RBAC rules can grant unintended access. NetworkPolicy is recommended alongside kube-rbac-proxy for defense-in-depth.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-namespace RBAC + kube-rbac-proxy SubjectAccessReview | Kubernetes RBAC + application-enforced proxy rules | Upstream service receives authenticated user identity; if upstream mishandles credentials, isolation is lost. No enforcement of tenancy downstream. |
| Data storage | N/A (stateless proxy; no persistent storage) | N/A | N/A |
| Network traffic | Sidecar model (localhost proxy); cross-namespace traffic requires explicit ClusterIP exposure | Kubernetes networking (sidecar colocation) | If exposed via ClusterIP, any Pod can reach the proxy; RBAC on SubjectAccessReview is the sole boundary. No NetworkPolicy enforcement in proxy itself. |
| Compute & resources | None (proxy inherits resource limits from containing Pod) | Kubernetes Pod resource limits | Proxy and upstream compete for container resources; no per-tenant resource isolation. |
| Configuration & secrets | TLS certs, OIDC secrets mounted as Kubernetes Secrets per namespace | Kubernetes Secrets + filesystem mounts | Secrets accessible only to the Pod's SA and namespace admins (standard Kubernetes isolation). |
| API scoping | SubjectAccessReview evaluated per-request against cluster RBAC | Kubernetes kube-apiserver | Isolation depends entirely on upstream RBAC policy. A broad policy (e.g., "all users can get metrics") negates tenant isolation. |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Kubernetes kube-apiserver (TokenReview, SubjectAccessReview API) | Cluster-wide | RBAC: kube-rbac-proxy SA has only create on tokenreviews/subjectaccessreviews; cannot list/watch other tenants' resources |
| Upstream service | Per-sidecar instance (no sharing by design) | None (sidecar pattern isolates upstream per deployment) |

**Multi-Tenancy Posture**: kube-rbac-proxy is single-tenant by deployment model (one sidecar per protected service). Tenant isolation is enforced via Kubernetes namespace + RBAC on the Kubernetes API itself (TokenReview, SubjectAccessReview are namespace-unaware but RBAC-controlled). The proxy does not implement additional multi-tenant data isolation; it is a per-service enforcement point. Cross-tenant security depends entirely on correct Kubernetes RBAC configuration.
