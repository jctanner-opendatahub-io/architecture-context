## Purpose

**Short**: kube-rbac-proxy is a single-upstream HTTPS proxy that authenticates requests and authorizes them with Kubernetes RBAC before forwarding them.

**Detailed**: The component is designed to run beside an application, commonly a metrics endpoint, and provide an authenticated HTTPS boundary in front of an otherwise local HTTP service. It accepts bearer tokens, client certificates, or configured OIDC JWTs, then maps the authenticated identity and request to Kubernetes authorization attributes.

Authorization is implemented through Kubernetes SubjectAccessReview calls, with optional static authorization rules and path-scoped endpoint rules. The proxy can forward authenticated identity headers to the upstream, reload its serving certificate and client CA from files, and optionally use mutual TLS when connecting to the upstream.

## Architectural Analysis

This is a deliberately small, single-process security sidecar rather than a Kubernetes operator. Its main boundary is the HTTP handler chain: path filtering is followed by authentication, authorization, optional identity-header injection, and reverse proxying to one configured upstream. The Kubernetes API is a control-plane dependency for TokenReview and SubjectAccessReview, while the protected application remains a local pod-network dependency.

The release Dockerfile separates a Go build stage from a minimal PQC runtime image, runs the binary as UID 65534, and enables strict FIPS runtime build settings. Runtime security still depends on deployment configuration: the secure listener, certificate/key files, upstream TLS settings, and any explicitly configured ignored paths. An ignored path bypasses both authentication and authorization by design and therefore requires careful operational scoping.
