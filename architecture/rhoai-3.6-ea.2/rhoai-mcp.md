## Purpose

**Short**: Provides a Model Context Protocol server that lets AI agents inspect and manage Red Hat OpenShift AI resources.

**Detailed**: `rhoai-mcp` exposes RHOAI capabilities through FastMCP tools, resources, and prompts. Domain plugins cover cluster exploration, projects, workbenches/notebooks, pipelines, training, model serving, model registry, storage, connections, and planning. The server uses the Kubernetes Python client and dynamic API access to interact with core Kubernetes and RHOAI-related APIs.

The service can run with stdio for local clients or with SSE/streamable HTTP for a deployed service. In HTTP mode it listens on port 8000, provides a health endpoint, and can apply OIDC JWT or Kubernetes TokenReview authentication. Kubernetes authorization is additionally evaluated for user-scoped operations when OIDC is enabled; otherwise the service account is the effective cluster identity.

## Architectural Analysis

The component is a single Python service with a plugin-oriented MCP façade over a Kubernetes client abstraction. Startup eagerly connects to Kubernetes and runs plugin health checks before creating the FastMCP instance, which makes `/health` meaningful before an MCP session is established. The service is stateless apart from in-process plugin state, response caches, port-forward sessions, and workflow-token signing state.

Deployment has three important modes. The base and OpenShift overlays deploy a normal `Deployment` and `Service`; the ODH overlay consumes the OpenShift overlay and changes the operator-managed namespace; and the OpenShift OIDC MCPServer overlay replaces the Deployment and Service with an `MCPServer` custom resource reconciled by an external MCP Lifecycle Operator. Image injection is centralized through `params.env` and Kustomize replacements, supporting disconnected/operator-managed image selection.

The principal architectural risk is authorization scope: the default service account has a ClusterRole that can create/delete namespaces, secrets, PVCs, notebooks, training resources, and model-serving resources. The OIDC overlay narrows the service account to authentication/impersonation-oriented permissions so Kubernetes evaluates the caller's identity, but the non-OIDC deployment remains a powerful cluster-wide actor. Model Registry TLS verification can also be disabled by configuration and should remain false in production.
