## Purpose

**Short**: An MCP (Model Context Protocol) server that enables AI agents to interact with Red Hat OpenShift AI environments programmatically.

**Detailed**: The RHOAI MCP Server provides a programmatic interface to OpenShift AI (RHOAI) cluster capabilities, replicating the functionality of the RHOAI Dashboard through structured tools and prompts accessible to AI agents. It enables agents to perform complex multi-step operations across the RHOAI platform including project management, workbench provisioning, model serving via KServe, data pipeline configuration, and ML training using Kubeflow operators. The component runs as a standalone Python service within RHOAI clusters or can operate against remote clusters via kubeconfig. It supports multiple transport protocols (stdio, HTTP with SSE, streamable-http) to accommodate different deployment and integration scenarios, including integration with AI agent frameworks like Claude Desktop and general HTTP clients.

## Architectural Analysis

The RHOAI MCP Server adopts a **pluggable domain-driven architecture** where operational capabilities are organized into domain modules (project management, workbench operations, model serving, etc.), each exposing tools and prompts through the MCP framework. The architecture demonstrates careful attention to **security and multi-environment support**:

1. **Transport flexibility**: Supports stdio (for local/CLI integration), HTTP with SSE (for web clients), and streamable-http (for cloud agents). Defaults to stdio for Claude Desktop compatibility while exposing port 8000 for HTTP variants.

2. **Authentication layering**: Implements OIDC JWT validation for bearer token authentication, kubeconfig-based service account authentication (in-cluster), and auto-detection of the execution environment. The OIDC validator (oidc.py) enforces issuer URL HTTPS requirements and includes JWKS caching with TTL-based refresh.

3. **TLS and certificate handling**: Takes a pragmatic approach to TLS verification — disables verification for in-cluster Kubernetes service URLs (.svc / .svc.cluster.local) where service-serving certificates differ from the service account CA bundle, while maintaining verification for external endpoints. This trades off strict verification for practicality without compromising security (traffic stays in-cluster, bearer token auth enforced).

4. **Kubernetes integration patterns**: Uses the Kubernetes Python client for all cluster interactions, extensively leveraging RBAC to scope operations to project namespaces and managed resources (Notebooks, InferenceServices, TrainingJobs, DataSciencePipelinesApplications, etc.). The service account is granted broad cluster-wide permissions reflecting the scope of operations the component orchestrates.

5. **Container and supply chain**: Built on AIPCC CPU base image (quay.io/aipcc/base-images/cpu:3.6.0-ea.1), inheriting RHEL 9.6 foundation, Python 3.12, and RHEL AI package index integration. Runs as UID 1001 with read-only root filesystem and no capabilities (least-privilege container posture).

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | OIDC JWT validation for users; RBAC scoping via namespace-level permissions | Kubernetes + Application | No per-user RBAC; agent can act on behalf of any validated user within cluster scope |
| Data storage | Per-namespace PVCs (created on demand by agent) | Kubernetes | Shared Kubernetes API; secrets stored in namespaces (accessible via RBAC) |
| Network traffic | Default cluster networking (no NetworkPolicy defined) | Kubernetes | No NetworkPolicy; traffic between pod and API server is in-cluster (protected by service account token) |
| Compute & resources | ResourceQuota and LimitRange on per-project namespace (defined by agent tools) | Kubernetes | Deployment spec defines requests/limits (128Mi/512Mi memory, 100m/500m CPU) for the server itself; per-project resources managed via namespace quotas |
| Configuration & secrets | Per-namespace ConfigMap (rhoai-mcp-config) and Secrets (managed by agent) | Kubernetes | Shared ConfigMap within deployment; per-project secrets stored in target namespaces |
| API scoping | Namespace-aware CRD operations (agent tools create resources in target namespaces) | Application | No per-user quota; agent can provision unlimited resources if authorized by namespace quotas |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Kubernetes API Server | cluster-wide (all namespaces) | RBAC on service account rhoai-mcp; scoped to cluster-wide resources (pods, nodes, etc.) and CRDs across namespaces |
| Kubeflow Notebooks (multi-tenant) | per-namespace | Kubernetes namespace isolation + RBAC |
| KServe InferenceServices (multi-tenant) | per-namespace | Kubernetes namespace isolation + RBAC |
| OIDC Provider | cluster-wide | JWT validation scoped to token audience; no per-tenant isolation at provider level |

_The component is designed as a single-instance multi-tenant orchestrator. Tenancy is enforced at the Kubernetes namespace level; the agent tools must respect namespace scoping to avoid cross-tenant operations._

_The agent initiates a connection with a Bearer token (JWT). The server validates the token against the OIDC provider's JWKS (cached). If valid, the agent's identity (username, groups) is extracted and used for subsequent operations._
