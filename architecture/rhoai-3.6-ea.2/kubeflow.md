## Purpose

**Short**: Kubeflow Notebook controllers reconcile namespaced Notebook custom resources into notebook workbench workloads and their supporting Kubernetes resources.

**Detailed**: The upstream-style `notebook-controller` watches Kubeflow Notebook resources and manages the associated StatefulSet, Service, Pods, Events, and Istio VirtualService. Its culling reconciler can stop inactive notebooks.

The RHOAI `odh-notebook-controller` extends this model for OpenShift and RHOAI. It manages per-notebook ServiceAccounts, Services, Secrets, ConfigMaps, NetworkPolicies, RoleBindings, Gateway API HTTPRoutes, ReferenceGrants, image-stream lookups, data-science-pipelines configuration, TLS material, and kube-rbac-proxy authentication. The two controllers are separate Go binaries and Konflux images in this monorepo.

## Architectural Analysis

This is a shared, event-driven Kubernetes control plane with two controller binaries. The upstream controller owns the basic Notebook-to-workload lifecycle, while the ODH controller adds OpenShift/RHOAI concerns and deliberately separates central ingress objects from user-namespace backends. The ReferenceGrant and label-based mapping are the key mechanisms that bridge those namespaces.

The authenticated route mode places kube-rbac-proxy in front of each notebook and scopes its authorization check to the named Notebook resource. Admission webhooks enforce pod security and protect MLflow configuration transitions. The main analyzer limitations are dynamic route inventory, unresolved dynamic watch predicates, partial Kustomize resolution, and incomplete webhook semantic coverage; these should be verified against the deployed release configuration.

Supply-chain posture is mixed: Konflux Dockerfiles use digest-pinned UBI images and strict FIPS Go build settings, and Go module checksums are present. OS/RPM and Hermeto/artifact lock files were not found in this branch, so full build hermeticity cannot be established.
