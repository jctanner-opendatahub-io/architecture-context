## Purpose

**Short**: Manages the lifecycle of Jupyter notebook workbenches on OpenShift, including workload creation, idle culling, ingress routing, and RBAC-based access control.

**Detailed**: This repository contains two complementary Kubernetes controllers that work together to manage notebook workloads in RHOAI environments. The upstream Kubeflow Notebook controller handles core lifecycle management — creating StatefulSets and Services for each Notebook custom resource, monitoring idle status, and scaling idle notebooks to zero. The ODH Notebook controller, developed as an extension, adds OpenShift-specific capabilities including Gateway API routing (HTTPRoute creation), RBAC-based authorization injection via kube-rbac-proxy, Data Science Pipelines Application (DSPA) secret management, and dynamic Feast feature store configuration. Together, these controllers provide a complete notebook workbench platform where users can define notebook specifications declaratively via Kubernetes CRDs, and the controllers handle all provisioning, networking, and access control automatically.

## Architectural Analysis

The architecture follows a **dual-controller pattern** where responsibilities are cleanly separated along upstream/downstream lines. The upstream Kubeflow controller (forked from kubeflow/kubeflow) implements the core Notebook CRD and StatefulSet lifecycle, while the ODH controller (housed in the same repository) enhances this with ODH-specific features via webhooks, additional controller reconciliation loops, and resource synthesis.

**Key design patterns observed:**

1. **Layered reconciliation**: Both controllers watch the same `Notebook` CRD and reconcile independently. The ODH mutating webhook modifies the pod spec before persistence, allowing both controllers to react to the same resource without conflicts.

2. **FIPS-compliant builds**: Both Konflux Dockerfiles use `CGO_ENABLED=1 GOEXPERIMENT=strictfipsruntime` and the `-tags strictfipsruntime` Go build flag, ensuring dynamically-linked Go binaries that use OpenSSL for cryptographic operations. This passes the Konflux check-payload FIPS validation gate.

3. **Gateway API-first routing**: Instead of OpenShift Routes, the ODH controller creates `gateway.networking.k8s.io` HTTPRoute objects, enabling future transport layer flexibility while remaining compatible with the embedded Envoy proxy.

4. **Namespace-scoped multi-tenancy**: The Notebook CRD is namespaced. Tenancy boundaries are enforced through Kubernetes RBAC (role bindings, service accounts), namespace-scoped Secrets and ConfigMaps, per-namespace NetworkPolicies, and kube-rbac-proxy sidecar injection that performs `SubjectAccessReview` checks. No shared storage or database tier is evident from the codebase.

5. **Webhook-driven pod mutation**: The ODH mutating webhook intercepts Notebook CREATE/UPDATE operations, checks for the `notebooks.opendatahub.io/inject-auth: "true"` annotation, and injects the kube-rbac-proxy sidecar container and ConfigMap configuration. This decouples authentication logic from the notebook controller itself.

**Integration surface:**

- Watches and reconciles `Notebook` CRDs (kubeflow.org/v1, v1alpha1, v1beta1)
- Creates and owns `StatefulSet`, `Service`, `HTTPRoute`, `NetworkPolicy`, `RoleBinding`, `Secret`, `ServiceAccount` resources
- Watches `ConfigMap`, `Event`, `Pod`, `Gateway`, and `ReferenceGrant` resources
- Integrates with OpenShift: reads `ImageStream`, `Route`, `APIServer`, and `OAuthClient` resources
- Integrates with Data Science Pipelines Application (`DataSciencePipelinesApplication` CRD)
- Uses Kubernetes admission webhooks (mutating and validating) to enforce policy on Notebook mutations

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | per-namespace RBAC (Role/RoleBinding per notebook) + kube-rbac-proxy sidecar + SubjectAccessReview | Kubernetes RBAC + application webhook | Enforcement depends on kube-rbac-proxy being enabled via annotation; no default enforcement |
| Data storage | per-namespace Secrets, ConfigMaps, PVC (implicit via notebook pod spec) | Kubernetes namespace isolation | Notebook pods are free to mount PVCs from any namespace unless NetworkPolicy or PSP prevents it |
| Network traffic | NetworkPolicy (created per Notebook by odh-notebook-controller) | odh-notebook-controller reconciliation + Kubernetes NetworkPolicy enforcer | NetworkPolicy coverage depends on CNI support; egress to API server may not be blocked |
| Compute & resources | ResourceQuota (tenant responsibility) | Kubernetes (if configured by platform) | No per-notebook LimitRange or ResourceQuota defined; relies on platform-level quotas |
| Configuration & secrets | per-namespace Secrets and ConfigMaps | Kubernetes RBAC + namespace isolation | Secrets are namespace-scoped; controller has cluster-wide read access to manage credentials |
| API scoping | namespace-scoped Notebook CRD watches via cache configuration | controller-runtime cache (ByObject transform for ConfigMap) | Controller lists all resources cluster-wide for efficiency; filters applied in-memory |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Kubernetes API Server | Namespace + RBAC | RBAC checks enforced via ServiceAccount token |
| OpenShift OAuth (if enabled) | Per-OAuthClient | OAuthClient provisioned per Notebook; separate OAuth callback URLs |
| (No shared database tier) | N/A | N/A |

**Tenancy notes**: The Kubeflow Notebook system is designed for **namespace-scoped multi-tenancy**. Each namespace represents a logical tenant. Resources (Notebook CRDs, StatefulSets, Services, HTTPRoutes, Secrets, ConfigMaps) are all namespaced. RBAC enforcement happens at two levels: (1) Kubernetes role bindings limit which users can create/modify Notebooks in their namespace, and (2) kube-rbac-proxy sidecar (when enabled) performs per-request SubjectAccessReview checks, preventing unauthorized access to the notebook HTTP endpoint. Cross-tenant access is prevented by namespace boundaries and RBAC, but no explicit tenant identifier column or row-level filtering is present in the code — isolation relies on Kubernetes primitives.
