## Purpose

**Short**: llm-d is a high-performance distributed inference serving orchestration layer that optimizes LLM deployment on Kubernetes across multiple accelerator platforms.

**Detailed**: llm-d provides production-grade orchestration and optimization patterns above model servers (vLLM, SGLang) to maximize inference performance and reliability at scale. The component consists primarily of Kubernetes manifests, kustomize overlays, and guide documentation for deploying large language models with state-of-the-art techniques including intelligent routing with prefix-cache awareness, tiered KV-cache management, prefill/decode disaggregation, and flow control for multi-tenant serving. The repository acts as a reference architecture and toolkit enabling operators to achieve optimal throughput and latency across diverse hardware accelerators (NVIDIA GPUs, AMD MI series, Intel XPU, Google TPU, IBM Power) and cloud platforms (AWS, GCP, Azure, CoreWeave, on-premises).

## Architectural Analysis

llm-d functions as an orchestration and deployment reference layer that sits above model server implementations. Its architecture centers on:

1. **Pattern Documentation**: The repository packages well-tested recipes and architectural patterns as Kubernetes manifests and kustomize configurations, organized into "well-lit paths" covering intelligent routing, KV-cache management, disaggregated serving, and operational excellence.

2. **Container Image Focus**: The component provides build configurations for accelerator-specific vLLM/SGLang container images via multi-variant Dockerfiles (CPU, CUDA, ROCm, Intel XPU). These images are the actual runtime artifacts; the repository itself is documentation and build orchestration.

3. **Multi-accelerator Strategy**: Each accelerator variant (NVIDIA CUDA, AMD ROCm, Intel XPU, Google TPU) has dedicated Dockerfile with variant-specific dependencies (RDMA libraries, UCX, UCCL, accelerator SDKs). The CPU variant uses standard Python/PyTorch; GPU variants layer transport and communication libraries.

4. **No CRDs or Controllers**: The component does not define Custom Resource Definitions or operate controllers. Deployment is entirely through kustomize manifests representing standard Kubernetes resources (Deployments, Services, ServiceAccounts, ConfigMaps).

5. **Inference Service Model**: Core workloads are model server Deployments (decode, prefill stages) that run containerized vLLM or SGLang instances with OpenAI-compatible HTTP endpoints on port 8000.

6. **Configuration-Driven Deployment**: Kustomize overlays parameterize image selection, resource requests, monitoring configuration, and accelerator-specific settings. The "guides" directory provides end-to-end deployment examples for specific scenarios (single-host, disaggregated, multi-tenant).

Gaps in analyzer coverage: The analyzer discovered minimal HTTP endpoints and services (marked as "not-verified"), suggesting workload and ingress configuration lives in generated/templated guides rather than static manifests. Integration points with other platform components (kserve, routing sidecars, prometheus monitoring) are present but not fully extracted by the analyzer.
