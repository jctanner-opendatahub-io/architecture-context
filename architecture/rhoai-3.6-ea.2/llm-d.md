## Purpose

**Short**: llm-d provides Kubernetes-oriented orchestration, routing, caching, and deployment recipes for high-performance LLM inference using model servers such as vLLM, SGLang, and TensorRT-LLM.

**Detailed**: The repository is primarily an architecture and deployment reference rather than a single long-running controller. It defines accelerator-specific container builds, Kustomize examples, Gateway API routes, model-server and Endpoint Picker (EPP) integration patterns, and operational guidance for production inference. The actual model execution is delegated to model servers; llm-d adds intelligent routing, prefix/KV-cache management, prefill/decode disaggregation, flow control, autoscaling, observability, and batch-processing patterns.

The deployment model is compositional. A Gateway routes requests to an `InferencePool`; the pool selects model-server Pods and connects the Gateway to an EPP extension service. Optional helpers provide Mooncake KV-cache storage/client infrastructure and an interactive benchmark Pod. Recipes support multiple cloud providers and CPU, NVIDIA CUDA, AMD ROCm, Intel XPU, TPU, and other accelerator variants.

## Architectural Analysis

llm-d is a declarative integration layer around Kubernetes Gateway API and independently deployed model servers. `InferencePool` is the key boundary between the Gateway data plane, EPP scheduling logic, and selected model-server Pods. This separates request admission and endpoint selection from model execution, allowing model-server pools and routing components to scale independently. EPP policies can use protocol parsers, request metadata, queue state, prefix-cache state, fairness, and SLO-aware flow control.

The checkout contains several independent container build variants rather than one product binary. CPU, CUDA, ROCm, and XPU images launch the vLLM OpenAI-compatible API server; auxiliary images support RDMA diagnostics, modelexpress, interactive benchmarking, and Mooncake storage. Many deployment examples are intentionally provider- or workload-specific, so the analyzer’s zero-count baseline for services, endpoints, and workloads does not establish repository-wide absence. The summary below distinguishes documented interfaces and example manifests from resources generated by a controller.

The principal risks are supply-chain and deployment-context risks: builds download upstream source and Python packages at build time, use unpinned or externally supplied base images in several variants, and lack repository-wide OS/artifact lock files. The CPU image uses Ubuntu 22.04 while other variants inherit CUDA, vLLM, or Python images, and no explicit FIPS build or application crypto posture was found. The interactive helper’s broad namespace Role and wildcard LeaderWorkerSet access should be treated as a privileged diagnostic/benchmark aid, not a default production workload.
