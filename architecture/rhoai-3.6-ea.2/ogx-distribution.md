## Purpose

**Short**: Container image distribution of OGX (Open Data Hub's agentic framework), pre-configured with runtime dependencies and model artifacts, deployable on both CPU and accelerator hardware.

**Detailed**: The OGX distribution is a containerized, production-ready deployment package for Open Data Hub's agentic framework. It bundles OGX server binaries, pre-installed Python dependencies (installed via `uv` with hermetic lockfiles), pre-cached model and data artifacts (Docling, HuggingFace, tiktoken), and comprehensive provider support for multi-modal inference (OpenAI, Azure, Gemini, Anthropic, vLLM, Bedrock, Watsonx) and vector storage (Milvus, pgvector, Qdrant). The distribution emphasizes secure secret management (file-based secret variants), telemetry instrumentation (OpenTelemetry optional), and OAuth2 authentication. Both CPU and accelerator-specific variants (NVIDIA CUDA, AMD ROCm, Intel Gaudi, IBM Spyre) are produced via build-time parameterization using AIPCC base images, with architecture-specific discovery and test suites ensuring multi-platform coverage.

## Architectural Analysis

The OGX distribution combines a template-driven build pipeline with runtime configuration injection. The Dockerfile is generated from `Dockerfile.konflux.in`, preserving hermetic Python dependency installation via `cachi2.env` sourcing and digest-pinned base image references. The entrypoint resolves file-based secret variants before delegating to the OGX server binary (`ogx run --insecure`), enabling Kubernetes to mount secrets as files rather than inline environment variables. 

The service model is single-tenant, serverless: each container instance is independent, with no inter-component coordination or cluster-wide state. Configuration is runtime-injected via YAML and environment variables, allowing the same image to serve different tenants or provider configurations. Multi-tenancy (if required) is delegated to the inference providers themselves (e.g., OpenAI namespacing, vLLM model assignment). 

Build hermeticity is enforced at two layers: OS packages (implicitly locked via AIPCC base image selection, explicit via `rpms.lock.yaml` on release branches) and Python dependencies (locked via `distribution/requirements-lock-konflux.txt` and `cachi2` prefetch). Artifact hermiticity is assured by pre-published, ProdSec-scanned model/data OCI images (modelcar), referenced as a named build stage and copied during network-isolated builds, avoiding dynamic artifact fetches.

Security surface is minimal in the container: the entrypoint validates file-based secrets, the server binds to a single port (8321), and no webhooks, operators, or persistent state are shipped. Authentication is delegated to external OAuth2 issuers (if configured) or passed through to inference providers. Telemetry is optional, off by default, and implements lazy initialization to avoid startup latency when not needed.

### FIPS Compliance

#### Build-Time FIPS (check-payload gate)

Konflux validates images via check-payload:

| Aspect | Value | Source |
|--------|-------|--------|
| **Build flags** | CGO_ENABLED=1 (implicit from AIPCC base image use) | Dockerfile.konflux; AIPCC base images link dynamically to OpenSSL |
| **Linking** | Dynamic (via AIPCC base image) | AIPCC base images (overlay 0017) are dynamically linked; OGX binary inherits this requirement |
| **OpenSSL in image** | Yes (via AIPCC base image and RHEL UBI) | AIPCC base images include OpenSSL; RHEL 9.6 base includes openssl-libs |
| **OLM FIPS annotation** | Not applicable (container image, no OLM operator) | N/A |

_FIPS compliance passes build-time check-payload gates because AIPCC base images enforce dynamic linking and include OpenSSL. No static Go crypto or BoringCrypto is present in OGX server binary._

#### Application-Level Crypto

| Aspect | Value | Source |
|--------|-------|--------|
| **TLS configuration** | Python stdlib `ssl` module via OpenSSL (inherited from AIPCC base) | OGX server uses `ssl.create_default_context()` for outbound TLS; configuration is delegated to providers (e.g., vLLM client, Anthropic SDK) |
| **Crypto libraries** | Python stdlib `ssl`, OpenSSL (system) | OGX server does not implement custom cryptography; relies on provider SDKs and system OpenSSL |
| **Certificate handling** | System trust store (CA bundle from RHEL UBI) or custom CA per provider config | Providers use Python `requests` library with system CA bundle; custom CA bundles can be configured per provider |
| **Non-FIPS crypto risks** | None detected; no MD5, RC4, or custom RNG | All inference providers use standard TLS 1.2+ and industry-standard SDKs |

_Application-level crypto posture: OGX server itself does not perform cryptographic operations; it is a network orchestrator that delegates to provider SDKs. Each provider (OpenAI, vLLM, Bedrock, etc.) handles its own TLS stack, and those connections default to system OpenSSL via AIPCC base image._
