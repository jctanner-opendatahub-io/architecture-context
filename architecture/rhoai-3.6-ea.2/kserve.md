## Purpose

**Short**: KServe provides the Kubernetes control plane and runtime contracts for deploying, routing, scaling, and serving predictive and large-language models.

**Detailed**: KServe defines namespaced and cluster-scoped APIs for InferenceService, LLMInferenceService, InferenceGraph, ServingRuntime, TrainedModel, and local model caching. Its controllers reconcile those resources into Deployments, Services, Jobs, autoscalers, Gateway API or OpenShift routing resources, and model-serving pods. Admission webhooks validate and default API objects and mutate inference pods with the required runtime configuration.

The repository also contains the RHOAI Kserve module controller, model-serving utilities, a Python serving SDK, storage initialization code, a graph router, and queue-proxy extensions. Model artifacts may be staged from object stores, registries, HTTP, or local caches before the selected serving runtime handles inference traffic.

## Architectural Analysis

KServe is a multi-binary operator repository rather than one deployable service. The core manager reconciles predictive serving resources; the LLM controller handles LLM scheduling and Gateway API inference-extension resources; local-model controllers coordinate node-local model caches; and the Kserve module controller manages platform-level installation and configuration. The analyzer found 15 CRD facts, 25 serving-runtime definitions, 79 controller watches, 18 HTTP endpoints, 8 gRPC services, 4 Services, 12 RBAC-role facts, and no statically confirmed ingress routes.

The deployment has a layered security boundary. Controllers use in-cluster Kubernetes credentials and scoped RBAC, admission webhooks are exposed over TLS, and the metrics endpoint is fronted by kube-rbac-proxy. InferenceGraph routing can perform Kubernetes TokenReview and SubjectAccessReview checks. Runtime inference traffic is distinct from controller health and metrics traffic; the former is produced by workloads created during reconciliation and may be exposed through platform ingress selected by configuration.

## Data Flows

### Flow 1: CRD to inference workload

1. A user creates an inference CR in a tenant namespace.
2. Admission webhooks validate/default it and may mutate related pods.
3. The appropriate controller watches the CR and reconciles Deployments, Services, autoscalers, routes, and secrets.
4. A storage initializer or local-model path stages model artifacts.
5. Client inference traffic reaches the generated runtime through the configured service/ingress and the runtime returns predictions.

### Flow 2: LLM request routing

An LLMInferenceService is reconciled into the selected workload topology and Gateway API/inference-extension resources. The router or endpoint picker uses the generated service graph and optional authorization/TLS configuration to send requests to the model-serving pods.
