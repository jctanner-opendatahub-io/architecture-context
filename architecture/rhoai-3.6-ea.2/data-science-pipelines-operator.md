## Purpose

**Short**: The Data Science Pipelines Operator (DSPO) manages the lifecycle of Data Science Pipeline stacks on Red Hat OpenShift AI, provisioning and configuring per-namespace instances of the Kubeflow Pipelines v2 system.

**Detailed**: DSPO is a Kubernetes Operator that simplifies deployment of machine learning pipeline infrastructure in OpenShift environments. It abstracts the complexity of Kubeflow Pipelines v2 (based on Argo Workflows) by providing a declarative CustomResourceDefinition (DataSciencePipelinesApplication) that users can apply to create self-contained pipeline stacks in their namespaces. The operator reconciles DSPA resources, orchestrating the deployment of multiple sub-components (API server, persistence agent, scheduled workflow controller, optional database and object storage) and managing the supporting infrastructure (RBAC, networking, configuration). DSPO enables multi-tenant pipeline deployments via namespace-scoped CRs, making it the control plane for Data Science Pipelines in RHOAI installations.

## Architectural Analysis

The operator follows a standard Kubernetes controller-runtime pattern with a single reconciliation loop focused on the `DataSciencePipelinesApplication` (DSPA) CRD. The architecture is driven by the principle of declarative infrastructure: users define a DSPA CR in their namespace, and the operator ensures the cluster state matches that specification by creating and managing downstream Kubernetes objects.

**Key architectural patterns observed:**

1. **Declarative DSPA Resource**: The operator expects users to create a DSPA custom resource specifying database backend (MariaDB or external), object storage (MinIO or external S3-like), and optional components (ML Metadata, Kubeflow UI). The operator reconciles this single resource into a fully functional pipeline deployment.

2. **Namespace Isolation by Design**: DSPA resources are namespaced; each namespace can host its own independent pipeline stack. This supports multi-tenancy at the namespace boundary, with RBAC ensuring users can only manage their own DSPA instances. The operator watches DSPA, Deployment, ConfigMap, Secret, Service, and Route resources within the controller's namespace scope.

3. **Static Image Configuration via ConfigMaps**: Sub-component images (API server, persistence agent, workflow controller, etc.) are parameterized via environment variables in the manager Deployment and resolved at reconciliation time. This decouples the operator image from the versioning of sub-components, allowing updates without rebuilding DSPO itself.

4. **Heavy Use of Argo Workflows**: The operator creates Argo Workflow controllers, CRDs, and RBAC roles to support Workflow and CronWorkflow execution. The integration is deep: the operator manages Argo RBAC aggregation ClusterRoles (`argo-aggregate-to-admin/edit/view`) and the `argo` ServiceAccount, indicating strong coupling to Argo as the execution engine.

5. **Health Checks Before Component Deployment**: The operator includes optional health check probes (`disableHealthCheck` in DSPA) for database and object storage connectivity before deploying the pipeline API server. This prevents deployment failures when storage backends are unavailable.

6. **Admission Webhooks for Validation**: The operator creates mutating and validating webhook configurations, enabling server-side validation of DSPA resources during creation and updates.

**Build and Runtime Security:**
- FIPS140 compliance is enforced at build time via `GOFIPS140=v1.0.0` flag and static linking (`CGO_ENABLED=0`, `-tags no_openssl`). The operator is compiled with BoringCrypto (FIPS-certified crypto) and runs on the UBI9 PQC (Post-Quantum Cryptography) minimal base image.
- The operator runs as non-root (UID 65532) with dropped capabilities (`drop: ALL`) and read-only root filesystem constraints in the container security context.

**Integration Surface:**
The operator has broad RBAC permissions reflecting its role as an orchestrator:
- **Core Kubernetes**: creates/manages Deployments, Services, ConfigMaps, Secrets, PersistentVolumeClaims, and NetworkPolicies
- **Argo Workflows**: creates ClusterRoles/RoleBindings and watches all Workflow-related CRDs (Workflow, CronWorkflow, WorkflowTemplate, etc.)
- **Kubeflow**: manages Kubeflow Notebooks and Viewers; watches ScheduledWorkflow CRDs
- **OpenShift-specific**: reads ImageStreamTags, creates Routes, and manages webhook configurations
- **Observability**: creates ServiceMonitors for Prometheus and watches MLflow instances
- **Model Serving**: watches KServe InferenceServices and Seldon Deployments

The operator's broad permissions are architecturally justified because it needs to provision complete, self-contained environments per DSPA. The risk model assumes DSPO is deployed in a controlled namespace (`datasciencepipelinesapplications-controller` by default) and trusts its ServiceAccount only within organizations' OpenShift control planes.

## Multi-Tenancy

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| **Tenant boundary** | per-namespace | DSPA CRD scope: Namespaced; each namespace can host independent DSPA instances |
| **Deployment model** | multi-tenant (namespace-scoped instances) | config/manager/manager.yaml; operator watches namespace-scoped resources |
| **Tenant identifier** | namespace name (Kubernetes namespace) | Inferred from CRD scope and DSPAReconciler watch patterns |

Each DSPA instance is namespace-scoped, making the namespace the isolation boundary. Multiple DSPA instances can coexist in a single OpenShift cluster as long as they are in different namespaces.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | per-namespace RBAC (aggregate ClusterRoles for Argo, namespace-scoped Roles for DSPA) | Kubernetes RBAC | No built-in service-account-level isolation between DSPAs in the same namespace; both use the same `argo` ServiceAccount within a namespace |
| Data storage | per-namespace PVC or external S3 bucket (via spec.objectStorage) | Kubernetes (StorageClass) or external S3 bucket naming | Users must ensure external bucket naming avoids collisions; PVCs are namespace-isolated |
| Network traffic | No explicit NetworkPolicy created by the operator | Application-level | No default NetworkPolicy; operator does not restrict cross-namespace traffic; users must define NetworkPolicy |
| Compute & resources | ResourceQuota and LimitRange per namespace (user-managed) | Kubernetes | Operator does not create ResourceQuota; users must enforce via namespace quotas |
| Configuration & secrets | per-namespace Secrets (database creds, storage creds) | Kubernetes RBAC | Secrets are namespace-isolated; DSPA spec references secrets by name within its namespace |
| API scoping | namespace-scoped CRD watches (DSPA, Deployment, ConfigMap, Secret, Service, Route) | controller-runtime watch predicates | Operator reconciles DSPA resources only; per-tenant access to Argo Workflows is controlled via aggregate ClusterRoles |

**Risk Summary**: The operator's isolation model is namespace-based, which is appropriate for a multi-tenant Kubernetes cluster. However, multiple DSPAs in the same namespace share the same `argo` ServiceAccount and Argo Workflow namespace. This means users with permission to create DSPAs in a shared namespace can potentially access each other's Workflows. For strong tenant isolation, each tenant should have a dedicated namespace.

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Argo Workflow Controller | per-namespace (one Argo controller per DSPA) | Separate Argo ServiceAccount per DSPA, namespace-scoped Roles |
| APIServer (KFP) | per-DSPA (separate Deployment per DataSciencePipelinesApplication) | Kubernetes Namespace; each DSPA gets its own APIServer Deployment |
| Database (MariaDB) | per-DSPA if built-in; per-tenant/shared if external | Per-DSPA PVC for built-in; external database isolation via credentials + optional schema per tenant |
| Object Storage (MinIO) | per-DSPA if built-in; per-tenant/shared if external | Per-DSPA PVC for built-in; external S3 isolation via bucket naming or IAM policies |

Each DSPA instance is designed to be fully independent. If using built-in MariaDB or MinIO, storage is PVC-per-DSPA. If using external databases or object stores, isolation relies on credential scope and bucket/schema naming.

| 4 | Operator | External Database (health check) | 3306 or custom | TCP | TLS 1.2+ (optional) | Username/password or TLS client cert |

**Key insight**: The operator's primary data flow is declarative: it watches DSPA resource changes and reconciles cluster state. Health checks for external backends occur during reconciliation; if either database or object storage is unavailable, the operator can delay or fail the reconciliation unless `disableHealthCheck` is set to true.
