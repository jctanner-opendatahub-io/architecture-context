## Purpose

**Short**: Deploys and manages namespace-scoped Data Science Pipelines (DSP) stacks from `DataSciencePipelinesApplication` resources.

**Detailed**: The operator reconciles a namespaced `DataSciencePipelinesApplication` (DSPA) and renders the API server, persistence agent, scheduled workflow, Argo workflow controller, ML Metadata, storage, monitoring, RBAC, services, routes, network policies, and optional database/object-store resources for that DSP instance. It supports DSP v2 and can use either an external SQL/object store or development-oriented MariaDB/MinIO deployments.

Each instance is isolated primarily by namespace and by per-instance names and labels. The DSP API server exposes HTTP and gRPC interfaces, with an OpenShift Route and kube-rbac-proxy in the generated deployment. Pipeline execution is delegated to Argo Workflows and pipeline metadata is persisted in SQL/MLMD and artifacts in object storage. A conditional admission stack handles namespaced Kubeflow `PipelineVersion` resources when the Kubernetes pipeline store is used.

## Architectural Analysis

This is a controller-runtime operator whose central reconciliation boundary is the DSPA CR. `DSPAReconciler` watches the DSPA and the generated resources it owns, including Deployments, Services, Secrets, ConfigMaps, PVCs, NetworkPolicies, Roles, RoleBindings, and OpenShift Routes (`controllers/dspipeline_controller.go:887-903`). The cache applies label or name scoping for most generated resources, while ConfigMaps and Secrets are read directly because external CA/configuration resources are also consumed (`main.go:270-326`).

The deployment is deliberately compositional: a single DSPA can create several independent Deployments and data-plane services. The standard RHOAI path uses external storage, but templates retain MariaDB and MinIO for development/testing. The operator also integrates with MLflow, KServe, notebooks, Prometheus monitoring, OpenShift image streams, and Argo/Kubeflow APIs through Kubernetes API operations and typed Go clients.

Security is layered: the operator runs non-root with dropped capabilities, generated API-server traffic is fronted by kube-rbac-proxy, webhook/metrics TLS follows the cluster TLS profile, and generated routes use re-encryption. The principal risks are the broad cluster role required to manage arbitrary DSP child resources and the explicitly supported database `skip-verify`/`preferred` TLS modes (`controllers/database.go:136-150`), which must be constrained by deployment configuration.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|---|---|---|---|
| Auth & AuthZ | Kubernetes RBAC and kube-rbac-proxy | Kubernetes / generated proxy | Operator cluster role is broad; user access depends on platform RBAC |
| Data storage | Per-instance PVCs or configured external stores | Kubernetes/operator config | Shared external stores require correct tenant prefixes/credentials outside this repo |
| Network traffic | Per-instance NetworkPolicies with explicit component selectors | Kubernetes | API proxy ingress is intentionally broad on 8443; policy coverage varies by optional component |
| Compute & resources | Per-instance Deployments and optional resource fields | Kubernetes/operator | No tenant-wide quota is created by this component |
| Configuration & secrets | Namespaced ConfigMaps/Secrets and per-instance names | Kubernetes/operator | External credentials and referenced CA ConfigMaps rely on caller permissions |
| API scoping | Namespaced DSPA/child resources; filtered controller cache | Kubernetes/controller-runtime | Cluster-scoped Argo templates and operator RBAC remain cluster-level |
