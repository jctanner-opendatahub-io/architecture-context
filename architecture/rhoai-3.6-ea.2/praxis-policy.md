## Purpose

**Short**: Authorization and policy engine for AI agent traffic, deciding who may call which tools, what data returns, and where data flows next.

**Detailed**: 

Praxis Policy Engine (PPE) is a typed, phased plugin runtime and policy language evaluator embedded into proxy services. It serves as the authorization and data control layer for Praxis proxy, providing:

- **Identity resolution** for users, agents, and workloads
- **Authorization** using a pluggable policy language (APL) with relationship-based decision points
- **Credential delegation** via RFC 8693 OAuth 2.0 token exchange
- **Data redaction** at field level with session taint propagation
- **Header assertions** rendering derived identity onto upstream requests
- **Human-in-the-loop approval** (CIBA, OIDC-based)
- **Audit** for every authorization decision

The engine is distributed as a single-dependency Rust crate (praxis-policy), with optional builtin plugins for JWT identity, OAuth delegation, Cedar/CEL/OPA policy evaluation, CIBA human approval, and Valkey session storage. Hosts can implement custom plugins against the core runtime interfaces.

## Architectural Analysis

PPE is fundamentally a **library-based plugin system** rather than a standalone service. The 16-crate workspace is organized into three layers:

1. **Core Runtime** (crates/ppe-core): PolicyEngine, executor, hooks, identity/delegation/elicitation framework, assertions system, HTTP client infrastructure
2. **Policy Language** (crates/ppe-apl-*): APL compiler and evaluator, Canonical Message Format transforms, runtime phase dispatching
3. **Builtin Extensions** (builtins/): Pluggable factories for JWT identity resolution, OAuth delegation, CIBA elicitation, Cedar/CEL/OPA policy decisions, Valkey session storage
4. **Optional Facade** (crates/ppe with http-hyper feature): A hyper-backed HTTP transport for hosts that don't inject one

The engine is **feature-gated**: a dependency can include just the core runtime (praxis-policy = "0.2"), core + all builtins (features = ["builtins"]), or a subset (features = ["jwt", "cedar"]). This modularity allows embedding in different proxy architectures (Pingora, hyper, custom HTTP stacks) without pulling unnecessary crypto or session store dependencies.

**Key architectural decisions:**

1. **No external service calls**: PPE is in-process. All policy decisions, identity resolution, and delegation happen within the calling process. No separate policy service.

2. **Phased execution**: Policy is broken into phases (identity → authorization → redaction → delegation → response filtering). Each phase is pluggable, allowing partial evaluation or skipping of unsupported phases.

3. **Extension hooks**: Fine-grained hooks allow plugins to observe and modify execution at identity resolution, delegation, elicitation, and redaction stages. This enables audit logging, PII scanning, and custom claim mapping.

4. **Typed plugin system**: Plugins implement traits (IdentityFactory, DelegatorFactory, etc.) with compile-time registration. Missing plugin factories cause policy load to fail at startup (no runtime surprises).

5. **Pure-Rust crypto (with FIPS override)**: rustls + ring for TLS (non-FIPS embeddability), but aws-lc-rs for JWT signatures (FIPS-compatible, timing-attack resistant). This is a deliberate trade-off: embeddability over blanket FIPS compliance.

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-identity APL policies (relationship-based) | Application (policy rules) | Depends on policy correctness |
| Data storage | Request-scoped context + session labels in Valkey | Application / Valkey | Session taint relies on policy logic |
| Network traffic | Host proxy manages NetworkPolicy | Kubernetes | PPE doesn't enforce network segmentation |
| Compute & resources | Host proxy manages ResourceQuota | Kubernetes | No per-tenant resource limits |
| Configuration & secrets | Host-scoped (not per-tenant) | Application config | Delegation-sharing risk if credential collision |
| API scoping | APL policy rules | Application (policy) | Enforced by policy rules, not platform |
