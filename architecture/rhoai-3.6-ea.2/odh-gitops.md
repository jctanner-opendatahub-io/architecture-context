## Purpose

**Short**: A GitOps-based configuration repository providing standardized, repeatable deployment of OpenDataHub and RHOAI dependencies using Kustomize and Helm.

**Detailed**: odh-gitops is a centralized configuration repository that serves as the single source of truth for deploying the complete OpenDataHub and Red Hat OpenShift AI stack. Rather than implementing application logic, this repository provides layered Kustomize manifests and Helm chart configurations that administrators can apply via GitOps tools (ArgoCD, Flux) or directly via kubectl. It standardizes deployment procedures for platform operators (Cert-Manager, Kueue, Job Set, Leader Worker Set, etc.), operator configurations, and infrastructure dependencies. The repository addresses the needs of OpenDataHub administrators by providing a template for consistently deploying administrator-owned resources across environments, enabling reproducible cluster setups aligned with specific RHOAI versions.

## Architectural Analysis

odh-gitops operates as a pure **configuration repository** without application runtime logic. It is fundamentally different from other components in the platform—it does not ship container images, expose APIs, or contain service code. Instead, it serves as a **declarative deployment blueprint** organized in layers:

1. **Dependency Layer** (`dependencies/operators/`): Contains Kustomize components for upstream operator installations (Cert-Manager, Kueue, Cluster Observability, OpenTelemetry, Tempo, Node Feature Discovery, NVIDIA GPU Operator, etc.). These reference OLM subscription manifests for operator catalog installation.

2. **Configuration Layer** (`configurations/`): Provides operator-specific configuration after OLM installation. Examples include Kueue settings, Leader Worker Set resource pools, RHCL (Kuadrant/Authorino) network configuration, and TLS enablement scripts.

3. **Deployment Models**:
   - **Layered application**: Callers apply in sequence (`kubectl apply -k dependencies/` then `kubectl apply -k configurations/`) allowing selective operator inclusion.
   - **Composed application**: Top-level `kustomization.yaml` references both layers for unified application.
   - **ArgoCD sync**: Supports `SkipDryRunOnMissingResource=true` for CRDs installed by OLM in parallel.

4. **Chart Integration**: Helm charts for RHOAI deployment on XKS and OpenShift platforms encapsulate bundle versions, dependency chains, and platform-specific adjustments.

5. **Administrative Workflow**: The repository expects end users to fork/clone, select version-specific branches (`rhoai-3.x`, `odh-3.x`), and customize for their environments before applying via GitOps.

The architecture reflects a **separation of concerns**: operators (business logic, webhooks, CRD management) are installed via OLM from upstream registries; odh-gitops focuses exclusively on **consistent parameterization and ordering** of those operator deployments.

## Multi-Tenancy

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| **Tenant boundary** | Per-namespace | Kustomize namespaces and operator OLM configuration |
| **Deployment model** | Multi-tenant (multiple independent operator deployments) | Each operator installs in its own namespace; multiple clusters can use the same repository |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | OLM ServiceAccount + RBAC (operator-specific) | Kubernetes / OLM | Configuration repository trusts operator RBAC; no application-level policy |
| Data storage | Per-namespace Secrets and ConfigMaps | Kubernetes | No shared databases defined at this layer; operator-specific data isolation |
| Network traffic | (See Ingress/Egress) | Kubernetes / Optional Istio via configurations | No NetworkPolicy defined; RHCL provides Authorino-based API authorization |
| Compute & resources | OLM-managed resource requests per operator | Kubernetes | No ResourceQuota or LimitRange defined; delegated to administrator customization |
| Configuration & secrets | Per-operator ConfigMaps and Secrets | Kubernetes | Each operator manages its own configuration; no shared config |
| API scoping | Operator CRDs and Kubebuilder watches (per operator) | Kubernetes / Operators | Multi-tenant isolation is operator-responsibility; repository only orchestrates |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Cert-Manager | Cluster-wide | Single cert-manager instance per cluster; shared issuer/signer across namespaces (typical pattern) |
| Authorino (RHCL) | Cluster-wide (single instance) | Kuadrant custom resources per namespace; per-CR policy enforcement |

_odh-gitops does not enforce multi-tenancy at the configuration layer—it delegates tenancy models to each operator. Cert-Manager is intentionally cluster-wide for TLS provisioning. Authorino provides per-route authentication policies._
