## Purpose

**Short**: WVA selects replica counts and serving variants for LLM inference workloads using Prometheus metrics, accelerator capacity, and performance constraints.

**Detailed**: Workload Variant Autoscaler (WVA) is a controller-runtime based Kubernetes controller for inference model servers. It watches annotated HorizontalPodAutoscaler and optional KEDA ScaledObject resources, Gateway API InferencePool resources, configuration ConfigMaps, and ServiceMonitors. It gathers per-workload metrics from Prometheus and Kubernetes objects, runs throughput, saturation, queueing, and cost-aware analyses, and publishes desired-replica metrics.

The resulting `wva_desired_replicas` metrics are consumed by HPA or KEDA, while WVA can directly update scale subresources for scale-from-zero and actuator paths. It supports Deployment, StatefulSet, and LeaderWorkerSet scale targets, and tracks configuration globally or by namespace.

## Architectural Analysis

WVA is a cluster-scoped control-plane component with one controller-manager Deployment and a leader-election protected manager. Its primary control loop is deliberately decoupled from replica actuation: Prometheus supplies observations, WVA computes desired capacity, and HPA/KEDA applies the result. This permits multiple autoscaling strategies and keeps model-serving workloads independent of the controller process.

The component has a dynamic integration surface. InferencePool support is installed for both `inference.networking.k8s.io` and `inference.networking.x-k8s.io` API groups; KEDA and LeaderWorkerSet support are optional and discovered at startup, with a watcher able to request restart when optional CRDs appear later. Configuration is loaded from `/etc/wva/config.yaml` and watched ConfigMaps, with namespace-local overrides and a readiness gate until initial ConfigMap bootstrap completes.

The most significant operational boundary is the manager ClusterRole: the controller can observe cluster-wide workload, node, quota, service, monitoring, and autoscaling resources and can update scale subresources. Metrics are protected by controller-runtime TokenReview/SubjectAccessReview filtering, while Prometheus and EPP scraping use dedicated RBAC identities. The source also supports explicitly insecure Prometheus TLS verification or plain HTTP only through configuration, so release configuration must keep those development options disabled.
