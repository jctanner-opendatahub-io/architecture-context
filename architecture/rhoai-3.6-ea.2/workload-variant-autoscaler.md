## Purpose

**Short**: A Kubernetes controller that performs intelligent autoscaling for inference model servers based on saturation metrics and capacity modeling.

**Detailed**: WVA is a global autoscaler for LLM inference deployments that works alongside standard Kubernetes HPA and KEDA to drive replica counts. The controller operates on the concept of "variants"—multiple model server instances serving the same base model but differing in hardware configuration, serving configuration, or both. It continuously monitors request rates and server performance via Prometheus metrics, calculates optimal replica counts using capacity modeling (KV cache utilization and queue depth), and emits optimization metrics that external autoscalers (HPA/KEDA) consume to actually scale deployments. WVA supports multiple hardware variants (GPU types), disaggregated prefill/decode pipelines, and batch vs. interactive workload splitting through its variant abstraction.

## Architectural Analysis

WVA is a controller-runtime based Kubernetes operator with a sophisticated multi-engine architecture. The core design separates concerns into four main subsystems:

1. **Configuration System**: A unified configuration loader (Viper-based) that merges CLI flags, environment variables, and ConfigMap-backed settings. ConfigMaps (manager-config and saturation-scaling-configmap) drive runtime behavior without restart, enabling live tuning of saturation thresholds, analyzer selection (V1 vs V2), and limiter modes (inventory vs quota).

2. **Optimization Engines**: Two parallel optimization loops run under leader election:
   - **Saturation Engine**: Monitors InferencePool, HPA, and ScaledObject resources; queries Prometheus for request rates, KV cache, and queue depth; runs saturation analyzer algorithms (V1 percentage-based or V2 token/capacity-based); and emits `wva_desired_replicas` metrics.
   - **ScaleFromZero Engine**: Handles scale-to-zero behavior for deployments with minimum replicas set to zero.

3. **Controller Reconcilers**: Four independent reconcilers manage different resource types:
   - **ConfigMapReconciler**: Watches saturation-scaling ConfigMaps to sync analyzer configuration and validate policy changes.
   - **HPAReconciler**: Tracks HPA annotations (`llm-d.ai/managed: "true"`) to opt deployments into WVA management.
   - **ScaledObjectReconciler**: Watches KEDA ScaledObjects (annotation-based discovery when KEDA CRD is present).
   - **InferencePoolReconciler**: Watches inference.networking.k8s.io and inference.networking.x-k8s.io InferencePool resources (gateway-api-inference-extension).

4. **Prometheus Integration**: The controller maintains a direct Prometheus client with TLS support (CA certificates, mTLS, bearer tokens) and queries for per-variant metrics to feed saturation analysis. The client is initialized early in main() and validated before any reconciliation starts.

**Multi-tenancy & Namespace Scoping**: The controller can operate in single-namespace mode (via --watch-namespace) or multi-namespace mode with label-selector filtering on ConfigMaps to reduce memory overhead. HPAs and ScaledObjects are namespace-scoped; tenancy is per-namespace, not per-cluster.

**FIPS Signals**: The Dockerfile uses `GOEXPERIMENT=strictfipsruntime`, `CGO_ENABLED=1`, and deploys with the ubi-minimal-pqc base image (PQC-hardened for FIPS). TLS uses crypto/tls with enforced minimum TLS 1.2 and supports configurable cipher suites. Certificate validation is controlled via environment variables and config file settings.

**Extensibility**: The architecture supports pluggable analyzers (Throughput Analyzer can be registered conditionally) and limiters (quota-based or inventory-discovery). The coordinator (experimental) runs cluster-wide to dispatch HPAs/ScaledObjects to registered plugins for cross-model optimizations.

## Data Flows

### Flow 1: Saturation-Based Scaling Decision

| Step | Source | Destination | Port | Protocol | Encryption | Auth |
|------|--------|-------------|------|----------|------------|------|
| 1 | saturation-engine (controller pod) | Kubernetes API Server | 443/TCP | HTTPS | TLS 1.2+ | Bearer Token (SA token) |
| 2 | saturation-engine | Kubernetes API Server | 443/TCP | HTTPS | TLS 1.2+ | Bearer Token (SA token) |
| 3 | saturation-engine | Prometheus API | 443/TCP (configurable) | HTTPS | TLS 1.2+ (or HTTP if allowed) | Bearer Token / mTLS |
| 4 | saturation-engine | Kubernetes API Server | 443/TCP | HTTPS | TLS 1.2+ | Bearer Token (SA token) |
| 5 | HPA / KEDA autoscaler | Prometheus API | 443/TCP | HTTPS | TLS 1.2+ | Bearer Token / mTLS |
| 6 | HPA / KEDA autoscaler | Kubernetes API Server | 443/TCP | HTTPS | TLS 1.2+ | Bearer Token (SA token) |

**Detailed Flow**:
1. saturation-engine watches InferencePool resources (via cache) to discover variant pools
2. For each tracked HPA/ScaledObject, reconciler notifies engine of current state
3. saturation-engine queries Prometheus for `wva_*` metrics (request rate, queue depth, KV cache utilization) grouped by variant
4. Engine calculates desired replicas and patches HPA/ScaledObject with `wva_desired_replicas` metric
5. HPA / KEDA controller (external) reads the `wva_desired_replicas` metric from Prometheus
6. HPA / KEDA patches the Deployment's replicas based on metric value

### Flow 2: ConfigMap-Driven Policy Update

| Step | Source | Destination | Port | Protocol | Encryption | Auth |
|------|--------|-------------|------|----------|------------|------|
| 1 | User / Platform | Kubernetes API Server | 443/TCP | HTTPS | TLS 1.2+ | Bearer Token (admin) |
| 2 | ConfigMapReconciler | ConfigMap (saturation-scaling-configmap) | In-cluster | In-memory | N/A | In-cluster watch |
| 3 | saturation-engine | saturation-scaling ConfigMap | In-cluster | In-memory | N/A | Datastore (cache) |
| 4 | saturation-engine | Prometheus API | 443/TCP | HTTPS | TLS 1.2+ | Bearer Token / mTLS |

**Detailed Flow**:
1. User updates saturation-scaling ConfigMap (thresholds, analyzer selection, limiter mode)
2. ConfigMapReconciler detects change and validates policy
3. Engine rebuilds analyzer/limiter from updated config (live, no restart)
4. Next optimization cycle uses new configuration parameters
