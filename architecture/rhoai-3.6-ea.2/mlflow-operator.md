## Purpose

**Short**: MLflow Operator reconciles `MLflow` custom resources into running MLflow deployments on Kubernetes/OpenShift with integrated workspace and authentication management.

**Detailed**: The MLflow Operator is a Kubebuilder-based operator that transforms `MLflow` custom resource definitions (CRDs) into complete MLflow server deployments on Kubernetes or OpenShift clusters. Unlike operators that reimplement application behavior, the MLflow Operator focuses exclusively on the operational concerns: provisioning infrastructure resources (Deployments, Services, PVCs, RBAC), wiring TLS configuration, managing network exposure (HTTPRoute, ConsoleLink on OpenShift), and orchestrating database migrations.

The operator works in concert with the MLflow runtime, which provides Kubernetes-aware workspace resolution (`kubernetes://` workspace provider) and request-level authorization through the `kubernetes-auth` application plugin. This separation of concerns allows the operator to remain agnostic to MLflow's business logic while ensuring tight integration with the Kubernetes control plane.

In OpenShift/RHOAI, the operator is the supported path for deploying a shared, multi-tenant MLflow service. It enables platform administrators to define a singleton `MLflow` CR that specifies storage backends, database URIs, compute resources, and service exposure — the operator then ensures that configuration is consistently applied to running infrastructure. The operator also manages namespace-scoped RBAC bindings that tie MLflow access to platform identity groups from the ODH Auth CR.

## Architectural Analysis

The MLflow Operator implements a **multi-role reconciliation pattern**. The primary entry point is the `MLflow` CRD, a cluster-scoped singleton resource that specifies the desired deployment state (image, replicas, storage, TLS, environment variables). The reconciler watches `MLflow` CRs and triggers cascading reconciliation: each change to the CR causes the operator to re-render an internal Helm chart, apply those templates to the target namespace, and update in-pod TLS configuration from mounted secrets.

**Watch and Reconciliation Strategy**: The operator employs three distinct controller loops, each with different watch strategies and lifecycle guarantees:

1. **MLflow Reconciler** (primary): Watches cluster-scoped `MLflow` CRs and renders the Helm chart into Kubernetes resources (Deployment, Service, PVC, RBAC, NetworkPolicy, ServiceMonitor). Uses `ownerReference` to enable garbage collection — when an `MLflow` CR is deleted, all owned resources cascade-delete automatically.

2. **Namespace RBAC Reconciler** (secondary, gated): Watches Namespace objects carrying the `opendatahub.io/global-mlflow-workspace` label. For each labeled namespace, it reads the ODH `Auth` CR (external, unowned), extracts user groups, and creates or updates namespace-scoped `RoleBindings` that bind those groups to pre-existing aggregate `ClusterRoles` (`mlflow-operator-mlflow-view`, `mlflow-operator-mlflow-edit`). This reconciler runs as a separate loop gated behind `ENABLE_NAMESPACE_RBAC` to support platform integration without hard-wiring ODH dependencies.

3. **MLflowOperator Reconciler** (module-scoped, gated): Watches cluster-scoped `MLflowOperator` module CRs (in the `components.platform.opendatahub.io/v1alpha1` API group) as part of the ODH modular platform handoff. Currently gated behind `ENABLE_MLFLOW_OPERATOR_MODULE_CONTROLLER` to allow downstream operators to carry the implementation before platform-level module orchestration activates it.

**Storage and Artifact Handling**: The operator accepts multiple storage backends (SQLite for local testing, PostgreSQL/MySQL for production databases, cloud object storage like S3 for artifact roots). The `MLflow` CR's `backendStoreUri`, `artifactsDestination`, and related fields determine where MLflow stores its metadata and artifact files. When file-based storage (`file://` or `sqlite://`) is used, the operator provisions a PVC and mounts it at `/mlflow/storage` in the pod. The running MLflow instance then uses that storage to back its database or artifact root. This model allows the operator to remain storage-agnostic: it wires infrastructure, while MLflow's runtime configuration determines which storage backend to use.

**TLS and Network Exposure**: The operator renders TLS termination inside the MLflow pod. The Helm chart extracts a secret named `mlflow-tls` (created by cert-manager on OpenShift via service-ca annotations, or provisioned manually) and passes uvicorn SSL options and certificate paths to the MLflow entrypoint. The service exposed is HTTPS-only (port 8443 by default, configurable). For external exposure, the operator conditionally renders an `HTTPRoute` (if the Gateway API CRD is available) pointing at the MLflow service, with path rewriting rules (`/mlflow/api` → `/api`, `/mlflow/v1` → `/v1`) so that MLflow's internal routing is preserved while fitting under a stable product-facing prefix. A `ConsoleLink` (on OpenShift) is also rendered to add an application menu entry.

**Supported MLflow Version Enforcement**: The operator encodes a `SupportedMLflowVersion` constant at build time (via `-X` linker flags) and validates that deployed `MLflow` CRs do not request MLflow versions outside that supported range. This ensures downstream operators cannot accidentally deploy unsupported runtime versions.

**Initialization and Database Migration**: The operator supports operator-managed database migrations via an optional `migration` field in the `MLflow` CR spec. When migrations are enabled (default), the operator creates Kubernetes `Job` objects to run `mlflow db upgrade` against the configured backend store URI before starting the main server Deployment. This one-shot initialization step ensures schema compatibility between operator and runtime versions. A force-migrate annotation on the CR allows manual retry of migrations.

**Observability and Monitoring**: The Helm chart optionally renders a `ServiceMonitor` (Prometheus operator integration) when available, exposing operator-managed metrics at `/metrics` on port 8443 (authenticated via kube-rbac-proxy in the metrics service). The operator also exposes its own metrics on port 8443 (metrics bind address), separate from the deployed MLflow service metrics.

### Tenant Model

| Aspect | Value | Source |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-workspace RBAC via kubernetes-auth plugin; namespace-scoped RoleBindings bind Auth groups to view/edit ClusterRoles | MLflow runtime (kubernetes-auth plugin) + Kubernetes RBAC (namespace-scoped bindings) | MLflow workspace isolation depends on workspace provider implementation (kubernetes:// provider validates requester has access to target workspace namespace); no hard isolation at storage layer |
| Data storage | Workspace-scoped artifacts (per-workspace artifact root or shared backend with workspace filtering); metadata in shared backend (PostgreSQL/MySQL/SQLite) | MLflow workspace provider (per-workspace artifact root) + database schema (workspace namespacing) | Shared metadata database lacks row-level filtering; if workspace isolation fails, workspace data can leak across tenants |
| Network traffic | Service-to-Service TLS (in-pod termination); no NetworkPolicy by default (optional, configurable per MLflow CR spec.networkPolicy fields) | TLS 1.2+ termination in-pod | Default: no network isolation; NetworkPolicy must be explicitly configured; cluster network visibility allows pod-to-pod traffic without restrictions |
| Compute & resources | ResourceQuota (optional, per namespace); ResourceRequirements on MLflow Deployment (optional, configurable in spec.resources) | Kubernetes ResourceQuota + Deployment spec | No hard isolation; noisy neighbor problem possible if resource limits not set |
| Configuration & secrets | Per-workspace MLflowConfig (namespaced CR); shared TLS secret (mlflow-tls); optional per-workspace artifact credentials (mlflow-artifact-connection secret) | Kubernetes namespace scoping | TLS secret is cluster-wide (not namespace-scoped); compromise of TLS secret affects all workspace instances |
| API scoping | Workspace provider filters API requests by requester workspace membership (via kubernetes-auth plugin requesting Kubernetes API RBAC check) | MLflow runtime + Kubernetes API SAR (SubjectAccessReview) | Requires correct implementation of workspace-to-namespace mapping; misconfiguration allows unauthorized workspace access |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Database (PostgreSQL/MySQL) | Schema per MLflow instance (not per workspace; shared metadata database for single MLflow CR) | Application-level schema isolation (configurable via backendStoreUri) |
| Artifact storage (S3/Azure/GCS) | Workspace artifact roots (per-workspace directory prefix or bucket path) | Storage backend bucket/path ACLs (if configured) + MLflow workspace provider filtering |
| TLS certificate (mlflow-tls) | Cluster-wide (not tenant-scoped) | Kubernetes secret ACLs (view requires get on secrets with resourceNames=mlflow-tls); compromise affects all workspaces |
| Kubernetes API (workspace provider) | Per-workspace namespace mapping | Workspace provider logic (validates requester has access to workspace namespace via Kubernetes RBAC) |

**Tenancy Notes**: The MLflow Operator enables multi-tenancy at the **platform level** (multiple namespaces can have MLflow workspaces via the `opendatahub.io/global-mlflow-workspace` label and namespace-scoped RoleBindings). However, the **operator manages a single MLflow service** (cluster-scoped singleton CR). Multi-workspace support is then delegated to the MLflow runtime's workspace provider (`kubernetes://`), which maps workspace names to namespaces and performs per-request authorization. Isolation is **primarily logical** (workspace-to-namespace mapping + Kubernetes RBAC), not physical (single pod, single database); failures in workspace isolation directly compromise multi-tenant security.
