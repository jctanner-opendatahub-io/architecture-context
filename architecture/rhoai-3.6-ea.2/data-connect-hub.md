## Purpose

**Short**: Data Connect Hub centralizes tenant-scoped data-connection metadata and exposes heterogeneous data sources through REST and Apache Arrow Flight APIs.

**Detailed**: The component combines a Go controller with REST and Arrow Flight Rust services. The controller reconciles `DataConnectService`, `InitDataConnection`, and `InitDataConnectionType` resources and creates or manages the service workloads, routing, RBAC, secrets, and network policy associated with a deployment.

The REST service manages connection and connection-type metadata in PostgreSQL, exports credentials to Kubernetes Secrets, and delegates connection audits and binary reads to the Flight service. The Flight service loads connector implementations for PostgreSQL, SQLite, S3, Milvus, Elasticsearch, Neo4j, and generic URI sources; it resolves credentials from Kubernetes Secrets and serves read/query operations through Arrow Flight.

## Architectural Analysis

Data Connect Hub is a three-plane design: a Go controller plane, a REST metadata/control plane, and a Rust data plane. REST and Flight share PostgreSQL metadata and use a configured tenant identifier to scope metadata operations. The controller additionally maps the request tenant header to namespace-scoped Kubernetes authorization for sensitive REST operations.

The RHOAI deployment uses a Gateway API `HTTPRoute` to send REST and Flight traffic to separate ClusterIP services. REST is fronted by a kube-rbac-proxy sidecar terminating service TLS and enforcing Kubernetes authorization. Flight terminates optional server TLS itself and applies a Kubernetes TokenReview/SubjectAccessReview middleware when enabled. Both workloads run non-root with read-only root filesystems and dropped Linux capabilities.

Important configuration is intentionally split between ConfigMaps and mounted Secrets. The default release overlay enables Flight TLS, authentication, metrics, and the OpenShift service-ca certificates. The source also supports plaintext or unauthenticated modes, so the effective security posture depends on the deployed configuration. The component's NetworkPolicies are currently allow-all placeholders for service traffic and should be tightened when the gateway/client topology is finalized.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | kube-rbac-proxy endpoint mappings; Flight TokenReview/SubjectAccessReview | Kubernetes and platform proxy | REST application middleware validates the tenant header but the proxy is the principal endpoint authorization boundary. |
| Data storage | PostgreSQL metadata queries accept tenant ID; connection credentials are Kubernetes Secrets | Application plus Kubernetes namespace RBAC | Shared PostgreSQL isolation is application-enforced; database-level tenant isolation was not extracted. |
| Network traffic | NetworkPolicies exist for REST and Flight | Kubernetes | Both selected service policies explicitly allow all ingress and egress pending topology definition. |
| Compute & resources | One replica each; explicit CPU/memory requests and limits; non-root runtime | Kubernetes | No per-tenant quotas or scheduling isolation in component manifests. |
| Configuration & secrets | Secrets mounted per workload; exported connection Secrets target tenant namespace | Kubernetes RBAC/proxy | Secret provisioning/rotation is external or controller-managed and not fully established. |
| API scoping | Namespaced CRDs; proxy rewrites `X-Tenant-Id` to namespace in authorization requests; store APIs pass tenant ID | Kubernetes and application | Correctness depends on trusted header propagation and consistent tenant filtering. |
