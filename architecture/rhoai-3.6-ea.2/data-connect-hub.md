## Purpose

**Short**: Data Connect Hub (DCH) is a middleware service that provides a unified integration point for accessing data from heterogeneous data sources through standardized REST and gRPC APIs.

**Detailed**: Data Connect Hub centralizes connection metadata management and data access across multiple backend systems—S3, relational databases (PostgreSQL, SQLite), vector databases (Milvus), graph databases (Neo4j), and search engines (Elasticsearch). Rather than consuming applications maintaining separate client library stacks for each data source type, DCH exposes two purpose-built APIs: a REST HTTP service and an Arrow Flight gRPC service. The component consists of a Kubernetes operator (dc-controller) that manages the deployment lifecycle via custom resources (DataConnectService, InitDataConnection, InitDataConnectionType), paired with two deployable Rust services (rest-service, flight-service) that handle client requests and connector interactions. A PostgreSQL backend provides persistent metadata storage for connection definitions and configurations.

## Architectural Analysis

Data Connect Hub follows a classical three-tier architecture pattern where the Kubernetes operator (Go-based dc-controller) orchestrates the deployment and lifecycle of REST and Flight services, which are implemented as stateless Rust microservices. The operator uses custom resource definitions to allow declarative configuration of data sources and connection types, enabling multi-tenant scenarios where different namespaces can define their own isolated connection profiles. The component uses Cargo.lock and rpms.lock.yaml for hermetic builds, with Hermeto (cachi2) prefetch support enabling offline dependency resolution in Konflux. 

The dc-controller uses GOOS/GOARCH cross-compilation with strict FIPS runtime enforcement (GOEXPERIMENT=strictfipsruntime) and dynamic linking (CGO_ENABLED=1) to pass Konflux's check-payload validation. Both Rust services build on a UBI 9 minimal base image (ubi9-ubi-minimal or ubi9-ubi-minimal-pqc), use rustls for TLS with aws_lc_rs cryptographic provider, and expose their binaries as unprivileged containers (UID 1001:1001). The architecture supports optional TLS encryption for the Flight gRPC service via certificate-based identity configuration. NetworkPolicies and RBAC roles are defined for both services to enforce least-privilege access. A kube-rbac-proxy sidecar mediates HTTP requests to the REST service, enforcing authentication at the API proxy layer.

Connector libraries (postgres-connector, s3-connector, sqlite-connector, milvus-connector, neo4j-connector, elasticsearch-connector, uri-connector) are compiled as parts of the two services rather than separate containers, reducing the deployment footprint and simplifying version management. The PostgreSQL metadata store (pg-meta-store) is a shared Rust library used by both services for persisting connection definitions and audit data. All Rust crates deny unsafe code and enforce this via workspace-level lints, minimizing the attack surface for memory safety vulnerabilities.

### FIPS Compliance

FIPS compliance has two layers: **build-time enforcement** (check-payload validation in Konflux) and **application-level crypto correctness** (what the code actually does with cryptography). Both must be documented.

#### Build-Time FIPS (check-payload gate)

Konflux validates images via [check-payload](https://github.com/openshift/check-payload), which enforces:
- Go binaries must be **dynamically linked** (CGO_ENABLED=1, no static linking)
- **OpenSSL must be installed** in the container image
- No statically linked Go crypto (pure-Go crypto / BoringCrypto static gets rejected)

| Aspect | Value | Source |
|--------|-------|--------|
| **Build flags** | GOEXPERIMENT=strictfipsruntime / CGO_ENABLED=1 / -tags strictfipsruntime / N/A | dc-controller/Containerfile.konflux:14-15 for Go controller; Rust services N/A |
| **Linking** | Dynamic (CGO) for Go; Static for Rust | dc-controller/Containerfile.konflux uses CGO_ENABLED=1; Rust services compile static binaries |
| **OpenSSL in image** | Yes (via UBI base for Go controller); ubi-minimal-pqc for Rust services | Go: ubi9/go-toolset base; Rust: ubi9/ubi-minimal-pqc (post-quantum cryptography variant) |
| **OLM FIPS annotation** | Not present (operator not distributed via OLM) | N/A |

#### Application-Level Crypto

check-payload is the bare minimum -- it validates build artifacts but not runtime behavior. Document what the application actually does with cryptography:

| Aspect | Value | Source |
|--------|-------|--------|
| **TLS configuration** | Go controller uses crypto/tls with default config; Rust services use rustls with aws_lc_rs provider; Flight service TLS configurable (cert_file, key_file) | dc-controller/cmd/main.go:20; services/flight/src/main.rs has rustls::crypto::aws_lc_rs setup |
| **Crypto libraries** | Go: stdlib crypto/tls (FIPS via OpenSSL); Rust: rustls 0.23+ with aws_lc_rs (FIPS-compatible) | Cargo.lock, dc-controller/go.mod |
| **Certificate handling** | TLS certs for Flight service mounted from Kubernetes Secrets; kube-rbac-proxy handles REST service TLS termination | services/flight/src/main.rs:configure_tls(), kube-rbac-proxy sidecar |
| **Non-FIPS crypto risks** | None detected. No MD5 for crypto (only for checksums), no RC4, no custom RNG. Rustls uses modern ciphers by default. | Code audit of services/rest/src, services/flight/src |

_Document both layers. A component can pass check-payload (dynamically linked Go, OpenSSL present) while still using non-FIPS cipher suites in its TLS config or importing a non-FIPS crypto library. Conversely, a Rust component may "pass" FIPS simply by inheriting OpenSSL from the UBI base image without any explicit FIPS opt-in._

_If no FIPS signals are found at either layer, document that absence -- it is architecturally significant._

| Compute & resources | ResourceQuota / LimitRange can be applied at namespace level; services define resource requests/limits in Deployment | Kubernetes | Gaps depend on cluster administrator applying ResourceQuota/LimitRange policies; no application-level enforcement. |

| API scoping | CRD watches are namespace-scoped; operator reconciles only DataConnectServices in watched namespace | Kubernetes API + operator code | Depends on operator being deployed with appropriate leader election and namespace scoping. |

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| PostgreSQL (metadata store) | Shared database, no row-level filtering | Application query filter (requires verification) + Kubernetes RBAC on database credentials |
| Flight service (internal API) | Shared deployment, no query filtering | Network isolation (ClusterIP, internal-only) + Kubernetes authentication |

_If no shared services exist, keep the heading and table header but omit data rows._

**Multi-Tenancy Assessment**: **Partial / Risk**. The architecture supports per-namespace isolation at the CRD/deployment level, but the shared PostgreSQL backend with apparent lack of row-level security creates a significant data isolation risk. The architecture delegates tenant isolation to application-level query filtering, which requires careful code review. The REST service kube-rbac-proxy sidecar provides user identity enforcement, but the application must verify that user identity is correctly used to filter tenant-specific data (e.g., connection objects belong to the user's allowed namespace).
