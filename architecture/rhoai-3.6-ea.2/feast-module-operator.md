## Purpose

**Short**: The module operator reconciles the platform FeastOperator resource and deploys the Feast feature-store operator and its operands.

**Detailed**: This Go controller is managed by the OpenDataHub/RHOAI operator through the modular handler framework. It watches the cluster-scoped `components.platform.opendatahub.io/v1alpha1` `FeastOperator` resource, restricted by schema validation to the `default-feastoperator` instance.

During reconciliation it selects the ODH or RHOAI overlay, applies related-image and OIDC parameters, performs platform-version and deployment-selector upgrade handling, renders the bundled kustomize manifests, applies them in order, reports deployment and release status, and garbage-collects labeled cluster-scoped RBAC resources. The resulting Feast operator is installed in the configured applications namespace and uses related images for the Feast controller, feature server, and cron jobs.

## Architectural Analysis

This is a thin platform integration controller rather than the Feast data-plane implementation. Its principal boundary is the `FeastOperator` control-plane CR: the controller translates platform configuration into a bundled Feast operator deployment and records readiness and release state back on the CR. The controller-runtime cache is deliberately namespace-scoped for application workloads while retaining access to the cluster-scoped component CR, CRDs, and configuration objects.

The operator has a broad cluster-level RBAC footprint because it installs and cleans up Feast resources, workloads, monitoring objects, routes, and RBAC across the application namespace and cluster. The CRD itself permits only one named instance, reducing multiplicity but making the component inherently cluster-wide. Upgrade handling is intentionally extensible: current version-specific migration hooks are no-ops, while selector migration protects upgrades across an immutable Deployment selector change.
