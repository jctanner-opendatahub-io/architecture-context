## Purpose

**Short**: A Kubernetes Operator that manages Feast feature store deployments on OpenShift, deployed as a module by the ODH Operator framework.

**Detailed**: The feast-module-operator is a purpose-built operator that watches `FeastOperator` Custom Resources and reconciles the deployment of the upstream feast-operator workload using bundled kustomize manifests. It is deployed and managed by the ODH Operator via the modular handler framework. The operator integrates platform features like OIDC authentication, handles version transitions, and manages the lifecycle of the feast-operator controller-manager and feature-server sidecar components. It follows the operator pattern for shift-left validation using operator-chaos, ensuring backward compatibility across upgrades.

## Architectural Analysis

The feast-module-operator is structured as a Kubernetes operator that reconciles a cluster-scoped `FeastOperator` CRD (singular instance named `default-feastoperator`). Rather than managing feast deployments directly, it orchestrates the downstream feast-operator by rendering kustomize manifests with platform configuration.

Key architectural decisions:

1. **Module operator pattern**: Designed to integrate with the ODH Operator's modular handler framework, not as a standalone operator. The ODH Operator deploys this via Helm chart and creates the singleton `FeastOperator` CR with platform configuration.

2. **Configuration injection**: Uses environment variables (`OIDC_ISSUER_URL`) written to `params.env` before kustomize rendering, allowing the platform to customize feast-operator without forking or patching manifests.

3. **Upgrade safety**: Implements operator-chaos validation for shift-left testing. Breaking changes in the CRD schema or knowledge model are detected in CI before merge.

4. **Build-time FIPS**: Uses `GOEXPERIMENT=strictfipsruntime` and dynamic linking (`CGO_ENABLED=1`) with UBI9 base image, satisfying Konflux check-payload requirements.

5. **Manifest bundling**: Includes upstream feast-operator kustomize manifests in the operator container (`/manifests/`), rendered on demand. This avoids dynamic manifest fetching and keeps the operator self-contained.

The operator is cluster-scoped (not namespace-scoped), reflecting its role as a platform configuration agent. OIDC issuer URL is the primary integration point with the platform's identity system.

### Shared Services

_The feast-module-operator itself is not multi-tenant. It is a singleton operator managing a singleton CRD. Tenancy at the feature store level is delegated to feast-operator, which may implement multi-tenant feature store logic internally._

_If the platform supports namespace-level feature stores (e.g., separate feast-operator instances per namespace), this would require deploying multiple module operators or modifying the operator to be namespace-scoped — neither of which is currently supported._
