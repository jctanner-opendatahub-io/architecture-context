## Purpose

**Short**: Envoy ExtProc server that executes Praxis filter pipelines as an external processor for header and body inspection, mutation, and rejection over gRPC.

**Detailed**: Praxis ExtProc is an external processor service that integrates with Envoy proxies via the ExtProc filter protocol. It enables dynamic request/response processing through Praxis filter pipelines without requiring Envoy modifications. The service runs filter chains defined in YAML configuration, processing HTTP payloads (headers and bodies) and either allowing, modifying, or rejecting traffic based on filter outcomes. In RHOAI deployments, it serves as a payload processing layer in the model-as-a-service (MaaS) gateway stack, executing pre-processing and post-processing filters before/after inference requests reach backend models. It integrates directly with Istio EnvoyFilter resources for transparent filter injection into gateway mesh traffic.

## Architectural Analysis

Praxis ExtProc is a specialized network middleware component designed for payload transformation in inference pipelines. The architecture exhibits several key patterns:

**gRPC Protocol Specialization**: The service implements the Envoy ExtProc gRPC protocol (not REST), communicating via HTTP/2 on port 9004. It maintains two independent logical chains: pre-processing (failure_mode_allow=true, best-effort) and post-processing (failure_mode_allow=false, fail-closed) filters.

**Stateless Processing Model**: Each filter chain invocation is independent; no session state is maintained between requests. Configuration is loaded at startup from a YAML file mounted via ConfigMap, enabling dynamic reconfiguration through Kubernetes manifest changes without code redeployment.

**TLS and mTLS Support**: The codebase explicitly supports multiple TLS modes (self-signed, provided certificates, plaintext) via OpenSSL bindings, with mTLS client certificate verification available. This is documented in the architecture comments and enables secure inter-pod communication within the mesh.

**Security-First Rust Implementation**: The codebase enforces strict Rust clippy lints (deny on 150+ categories), prevents panic/unwrap/unsafe code, and disallows compile-time placeholders (todo!/unimplemented!), indicating production-grade quality requirements.

**Deployment Topology**: Runs as a single-replica Deployment with non-root security context (UID 1001), read-only root filesystem, dropped capabilities, and seccomp profiles. Resource limits (256Mi memory, 500m CPU) suggest it's designed for constrained gateway environments.

**Istio Integration Complexity**: The EnvoyFilter manifest reveals careful versioning support across multiple Istio releases (<=1.25 with typo "extenstions", 1.26-1.29 with typo fix, >=1.30 with TrafficExtension). Filter insertion priority (10) ensures execution after Kuadrant authentication, and per-route disables skip non-inference endpoints (MaaS API routes 0-3).

**FIPS Posture Summary**: The component uses OpenSSL for TLS (dynamically linked to system UBI9 OpenSSL) which can be FIPS-validated at the OS level via FIPS mode. However, the Rust ecosystem introduces transitive crypto dependencies (aws-lc-rs, ring) whose FIPS compliance is not explicitly enforced or documented. The codebase itself delegates TLS to OpenSSL and does not perform crypto operations directly, reducing risk. **Recommendation**: For strict FIPS compliance, ensure the runtime OpenSSL is FIPS-validated and audit transitive dependencies' crypto usage.
