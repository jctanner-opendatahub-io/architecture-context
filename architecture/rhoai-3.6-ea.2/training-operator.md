## Purpose

**Short**: Reconciles Kubeflow distributed-training job resources into framework-specific Kubernetes Pods, Services, RBAC, and scheduler resources.

**Detailed**: Training Operator provides the `kubeflow.org/v1` APIs for JAX, MPI, PaddlePaddle, PyTorch, TensorFlow, and XGBoost training jobs. Each job is namespaced and describes replica roles, pod templates, restart policy, and framework-specific options.

The controller manager watches these jobs and their owned workload resources, creates or updates training Pods and Services, records status and events, and optionally integrates with Volcano or scheduler-plugins for gang scheduling. It also runs validating admission webhooks and a TLS-protected webhook server, while exposing metrics and health probes for platform operations.

## Architectural Analysis

This is a single-replica, controller-runtime-based control plane with one reconciler per supported framework. Reconciliation is owner-oriented: job-created Pods, Services, and optional scheduler PodGroups are associated with their owning training job, while framework-specific reconcilers create the resources needed for distributed execution. MPI additionally creates a launcher ServiceAccount, Role, RoleBinding, and ConfigMap in the job namespace.

The RHOAI overlay installs the controller into `opendatahub`, prefixes resources with `kubeflow-`, replaces the image from a generated configuration value, exposes a metrics PodMonitor, and removes the metrics Service port in favor of a named container port. Webhook serving uses a generated certificate Secret and the internal ClusterIP Service. The operator can monitor all namespaces by default, or restrict its cache to one namespace with `--namespace`/`KUBEFLOW_NAMESPACE`; the ClusterRole remains cluster-scoped, so the default deployment model requires broad Kubernetes permissions.

The Konflux Dockerfile builds a CGO-enabled Go binary with `GOEXPERIMENT=strictfipsruntime` and `strictfipsruntime` tags, then runs it as UID 65532 on a digest-pinned UBI minimal image. The legacy Dockerfile still builds a statically linked, CGO-disabled binary on a distroless static image, so image selection is material to the FIPS and supply-chain posture.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Shared operator ServiceAccount with cluster-wide ClusterRole | Kubernetes RBAC | Broad permissions cross namespace boundaries; tenant users rely on API-server RBAC. |
| Data storage | No operator-owned database; job Pods, Services, ConfigMaps, Roles, and ServiceAccounts are created in the job namespace | Kubernetes namespaces and owner references | Training data/storage referenced by user pod specs is outside this component’s isolation policy. |
| Network traffic | PyTorch reconciler can create NetworkPolicies; no universal default-deny policy in base manifests | Kubernetes/controller logic | Network isolation is workload/framework dependent. |
| Compute & resources | Separate namespaced training Pods; optional scheduler gang scheduling and user-supplied resource requests | Kubernetes scheduler/controller | No operator-created ResourceQuota or LimitRange; noisy-neighbor control is delegated to the platform. |
| Configuration & secrets | Webhook certificate is operator-scoped; training job pod templates can reference namespace-local Secrets and ConfigMaps | Kubernetes namespace and RBAC | ClusterRole grants the operator broad read/write access to resources needed for reconciliation. |
| API scoping | Namespaced CRDs; controllers use job namespace in Get/List/Create operations; cache can be limited with `--namespace` | Kubernetes/controller-runtime | Empty namespace flag is cluster-wide by design. |

### Shared Services

No shared database, cache, or message queue is used. The controller manager is shared across namespaces when deployed cluster-wide, and its ServiceAccount is the cross-tenant control-plane identity.
