## Purpose

**Short**: vLLM Hardware Plugin for Intel® Gaudi® provides optimized large language model inference on Intel Gaudi AI accelerators through a modular vLLM plugin architecture.

**Detailed**: vLLM Gaudi is a downstream fork that integrates Intel Gaudi accelerators with vLLM's inference engine, enabling high-performance LLM serving on Intel Gaudi AI hardware. It implements the vLLM plugin system (RFC #11162 and #19161) to provide a modular, pluggable hardware backend while maintaining compatibility with vLLM's OpenAI-compatible API server interface. The component packages a Python plugin (`vllm_gaudi`) that registers with vLLM at runtime and provides hardware-specific execution kernels, quantization support (INC, AWQ, GPTQMODEL), dynamic KV cache optimization, bucketing strategies for variable sequence lengths, and multi-node training/inference capabilities tuned for Habana Labs Synapse AI software stack and Intel Gaudi hardware versions 1 and 3.

## Architectural Analysis

vLLM Gaudi operates as a three-stage containerized application with distinct roles:

1. **Base Stage (gaudi-base)**: Establishes RHEL 9.6 + Habana Synapse runtime (1.23.0-695) + Gaudi drivers, media loader, and system dependencies (NUMA, libfdt, image processing). Removes FIPS provider and adds CentOS AppStream/CRB repos for development libraries.

2. **PyTorch Stage (gaudi-pytorch)**: Installs Habana-specific PyTorch 2.9.0 modules from Habana's Artifactory repository with hardware-specific optimizations. Uses environment-driven installer that respects Synapse version and revision detection.

3. **vLLM Runtime Stage (vllm-openai)**: Clones upstream vLLM project + vLLM Gaudi fork, installs dependencies, applies Gaudi plugin on top of base vLLM. Configures OpenAI API server entrypoint with unprivileged user (UID 2000) for OpenShift compatibility. Supports optional benchmarking and inference scripts in .cd/ hierarchy.

The architecture emphasizes **strict external dependency management**: PyTorch, Gaudi drivers, and base OS packages are obtained from Habana's secure artifact repositories with revision pinning; vLLM commits are explicitly tracked via `VLLM_STABLE_COMMIT` metadata. Runtime inference flows through `vllm.entrypoints.openai.api_server` — a vLLM standard entry point that delegates hardware-specific operations to the registered Gaudi plugin via vLLM's plugin loader. No Kubernetes CRDs, no Istio integration, no multi-tenant isolation — this is a pure inference container designed for direct deployment or KServe runtime integration.
