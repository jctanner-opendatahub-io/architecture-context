## Purpose

**Short**: OpenAI-compatible batch API gateway for llm-d, providing large-scale batch inference processing with intelligent job scheduling, adaptive flow control, and cost-optimized inference in Kubernetes environments.

**Detailed**: 

Batch Gateway is a high-performance, distributed system designed to process large-scale batch inference jobs (up to 50,000 requests per job) alongside interactive inference workloads without causing unacceptable interference. It exposes an OpenAI-compatible API (`/v1/batches`, `/v1/files`) allowing users to submit, track, and manage batch jobs with real-time progress updates.

The system separates concerns into three independently scalable components: an API Server (request handling, metadata management), a Batch Processor (job execution with adaptive concurrency control), and a Garbage Collector (cleanup of expired jobs). Data is persisted in PostgreSQL (metadata), Redis/Valkey (queues and events), and S3-compatible storage (batch files). The processor includes built-in AIMD-based flow control to dynamically adjust request dispatch based on downstream inference system health, minimizing batch traffic impact on interactive workloads.

This architecture enables cost-optimized inference by supporting differential billing for batch vs. interactive workloads while maintaining strict SLO compliance for both.

## Architectural Analysis

Batch Gateway follows a distributed, stateless service architecture optimized for high throughput and isolation between batch and interactive inference:

**Component Separation**: The three primary components (apiserver, processor, gc) are deployed as independent Kubernetes workloads, allowing each to scale independently. The API server is stateless and horizontally scalable; the processor pools jobs and scales with demand; the garbage collector runs as a singleton. This separation prevents one component's resource contention from affecting the others.

**Data Layer Abstraction**: Pluggable storage backends (PostgreSQL for metadata, Redis/Valkey for queues, S3/filesystem for files) are decoupled from application logic. Configuration drives backend selection at runtime. This enables multi-tenant deployments to share infrastructure or use isolated backends per tenant.

**Batch-Interactive Isolation**: The system is explicitly designed for dual-workload environments. Model-aware scheduling groups inference requests by model and system-prompt hash, enabling KV-cache prefix sharing within batch jobs. Adaptive AIMD flow control monitors downstream inference metrics and throttles batch dispatch to protect interactive traffic. Security boundaries separate batch and interactive routes via distinct Kubernetes HTTPRoute manifests.

**Security-First Design**: All containers run non-root (UID 65532:65532), with read-only root filesystems, all Linux capabilities dropped, and seccomp enabled. TLS is configurable (default TLS 1.2+) with cipher suite control. Processor-to-inference connections support custom CAs and mutual TLS. Secrets are mounted read-only; credential access via `os.OpenInRoot()` prevents path traversal.

**Observability by Default**: Prometheus metrics, OpenTelemetry distributed tracing (gRPC OTLP), liveness/readiness probes, and pprof endpoints (gated by configuration flag) are integrated throughout. ServiceMonitor and PodMonitor resources enable integration with Prometheus Operator.

**Supply Chain Hermeticity**: Dockerfiles use multi-stage builds with explicit base image digests. Static linking (CGO_ENABLED=0) yields hermetic Go binaries; distroless base images minimize attack surface. No dynamic base image resolution. This design is compatible with Konflux check-payload validation (though FIPS runtime compliance is not explicitly enabled).

### FIPS Compliance

#### Build-Time FIPS (check-payload gate)

Konflux validates images with check-payload. Batch Gateway's approach:

| Aspect | Value | Source |
|--------|-------|--------|
| **Build flags** | CGO_ENABLED=0 (no CGO, no FIPS enforcement) | docker/Dockerfile.{apiserver,processor,gc} |
| **Linking** | Static (pure Go, no C dependencies) | Dockerfile.apiserver:23, Dockerfile.processor:23, Dockerfile.gc:14 |
| **OpenSSL in image** | Not present (distroless/static:nonroot base) | docker/Dockerfile.* (stage 2: FROM gcr.io/distroless/static:nonroot) |
| **OLM FIPS annotation** | Not present (no Operator Lifecycle Manager CSV) | N/A |

**FIPS Status**: Batch Gateway binaries **fail check-payload validation** for FIPS compliance because:
1. CGO_ENABLED=0 means no OpenSSL linkage (pure Go crypto)
2. Distroless base image has no OpenSSL runtime library
3. No FIPS-specific build flags or runtime enforcement

This is intentional: batch-gateway prioritizes minimal attack surface (distroless) over FIPS compliance. If FIPS is required, the deployment would need to use a UBI base image with OpenSSL and set CGO_ENABLED=1 and GOEXPERIMENT=strictfipsruntime.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Delegated to gateway (Kuadrant/Authorino); batch-gateway validates tenant context in HTTP headers or JWT claims | External API Gateway | **Risk**: If gateway fails to inject tenant context, batch-gateway assumes unauthenticated requests and may return 400/401. No fallback isolation. |
| Data storage | All queries to PostgreSQL include WHERE clause filtering by tenant ID; jobs and files returned only if tenant ID matches | Application (batch-gateway database queries) | **Risk**: Tenant ID filtering relies on correct HTTP header from gateway; if header is forged or missing, isolation fails. |
| Network traffic | No explicit NetworkPolicy; optional Kubernetes NetworkPolicy can restrict processor egress to specific inference gateway | Kubernetes NetworkPolicy (optional, not enforced by default) | **Gap**: No built-in network segmentation; relies on external policies. |
| Compute & resources | ResourceQuota and LimitRange per namespace (Kubernetes-level); batch jobs share compute within namespace | Kubernetes | **Gap**: No per-tenant resource reservation within shared deployment; batch jobs can starve interactive workloads if AIMD flow control is disabled. |
| Configuration & secrets | Secrets mounted per-component (apiserver, processor, gc share global `batch-gateway-secrets`); no per-tenant secret isolation | Kubernetes Secrets | **Risk**: All components access the same database and storage credentials. Tenant data is logically isolated, not cryptographically sealed. |
| API scoping | All batch API queries include tenant filter; cross-tenant requests return 404 | Application (internal/apiserver/batch/) | **Good**: Enforced consistently across all endpoints. |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| PostgreSQL database | Row-level filtering (WHERE tenant_id = ?) | Application query filter (batch-gateway enforces on all reads/writes) |
| Redis / Valkey queue | Tenant ID prepended to queue key names (e.g., `tenant-123:batch-queue`) | Application (consistent key naming) |
| S3 / filesystem storage | Path prefix per tenant (e.g., `s3://bucket/tenant-123/batch-jobs/`) | Application (consistent path construction) |
| llm-d inference router | No per-tenant isolation; router processes all batches equally | None (inference gateway treats batches as peer requests) |

**Multi-Tenancy Summary**: Batch Gateway supports a single-deployment multi-tenancy model where tenant isolation is enforced entirely via application-level query filters and header injection from a gateway layer (Kuadrant/Authorino). There is no cryptographic sealing or storage-layer isolation. This model is suitable for internal OpenStack/Red Hat deployments with trusted gateway operators but may not be suitable for untrusted multi-tenant SaaS deployments.

**Data Flow Summary**:
1. User submits batch job with input file to API server (via gateway).
2. API server stores job metadata in PostgreSQL, input file in S3/filesystem, enqueues job in Redis/Valkey.
3. Processor polls queue, retrieves input file, parses requests grouped by model/prompt.
4. Processor sends per-model requests to llm-d router with adaptive concurrency control (AIMD).
5. Processor writes results to output file, updates job status in PostgreSQL.
6. GC daemon periodically scans PostgreSQL for expired jobs and deletes them (and associated files).
