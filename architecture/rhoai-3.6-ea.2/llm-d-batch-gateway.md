## Purpose

**Short**: Provides an OpenAI-compatible batch API, durable batch/file state, asynchronous processing, and cleanup for LLM inference workloads.

**Detailed**: The API server accepts batch and file operations under `/v1`, records metadata in PostgreSQL, Redis, or Valkey, and stores uploaded and generated files on a filesystem/PVC or S3-compatible object store. Requests carry a tenant identity through the configurable `X-MaaS-Username` header by default.

The processor polls the shared queue, reads batch inputs, resolves either a global or model-specific inference gateway (including optional async llm-d pools), sends inference requests with selected headers, and writes results and progress. The garbage collector removes expired database/file objects and can reconcile orphaned in-flight jobs by watching processor pods and StatefulSets. The Helm chart runs these roles as an API Deployment, processor StatefulSet, and single-replica GC Deployment.

## Architectural Analysis

This is a horizontally separable control/data-path design: the API server handles client-facing REST traffic, the processor provides bounded worker concurrency and adaptive AIMD backpressure, and GC handles retention and crash recovery. PostgreSQL is the default durable backend in the chart; Redis/Valkey is used for queue/exchange and transient progress where configured. A shared filesystem is mounted when filesystem storage is selected, while S3 provides an alternative object store.

The API and storage model is explicitly multi-tenant. Batch and file records retain tenant IDs, queries are filtered by tenant, and filesystem/S3 paths are derived from a SHA-256 tenant-folder mapping. This provides application-level isolation, but the chart does not define NetworkPolicies or per-tenant Kubernetes resources; deployment security boundaries therefore remain dependent on the platform namespace, ingress, and database/object-store configuration.

Ingress and TLS are optional rather than enabled by the default values. When enabled, the chart creates a Gateway API HTTPRoute for batch/file paths and can mount a Secret or cert-manager-issued certificate. Observability is deliberately served as plain HTTP on separate ports and has optional pprof endpoints, so those ports should remain internal.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Tenant header plus tenant-filtered operations | Application; upstream ingress auth is external | No in-repo token validation; trust in the ingress/header source is required. |
| Data storage | Tenant column/filtering for records; hashed tenant folder/S3 prefix for files | Application | Shared backend credentials and backend policy are not tenant-specific. |
| Network traffic | No NetworkPolicy in chart | External platform/Kubernetes | Default network isolation is not supplied by this component. |
| Compute & resources | Shared Deployment/StatefulSet; configurable replicas/resources and worker ceilings | Kubernetes scheduling plus application limits | No per-tenant quota or priority enforcement. |
| Configuration & secrets | One projected Secret shared by all three components in a namespace | Kubernetes Secret volume | Shared credentials cross component boundaries; rotation is external. |
| API scoping | Batch/file lookups and lists use tenant identity; model routing can use `<tenantID>/<modelID>` keys | Application | Header spoofing or incorrect middleware integration could cross tenant boundaries. |
