## Purpose

**Short**: Kubernetes Operator for Apache Spark that manages SparkApplication and SparkConnect resource submissions, scheduling, monitoring, and lifecycle on RHOAI clusters.

**Detailed**: spark-operator provides declarative, Kubernetes-native specification and management of Apache Spark applications via custom resources (SparkApplication, ScheduledSparkApplication, SparkConnect). It automatically handles spark-submit submission, driver/executor pod orchestration, metrics collection, and webhook-based pod customization (mounting volumes, setting affinity, injecting sidecars). The operator consists of two primary deployments: a controller that reconciles Spark resources and watches over their execution, and a webhook service that validates and mutates Spark application specifications and pod templates. On RHOAI, it is deployed as a managed platform component via the SparkOperator ODH component CR, with the spark-operator-module controller managing the operator's lifecycle, configuration, and integration with the broader platform.

## Architectural Analysis

spark-operator is a multi-faceted operator with several key architectural characteristics:

**Dual Deployment Model**: The repository produces two container images and deployments. The primary image (`Dockerfile.konflux`) bundles the Spark operator controller with Java 17, PySpark 4.0.4, and supporting tools (podman, catatonit) to enable on-cluster Spark job execution. The module controller image (`Dockerfile.konflux.module-controller`) is a separate ODH component manager that handles the operator's lifecycle as defined by the `SparkOperator` CR.

**FIPS-Enabled Build**: Both Dockerfiles explicitly enable FIPS compliance via `GOEXPERIMENT=strictfipsruntime` and `CGO_ENABLED=1`, ensuring dynamically linked Go binaries with OpenSSL backing. The operator controller uses Go's stdlib crypto/tls configured by controller-runtime. The Konflux-based builds validate FIPS compliance via check-payload gates.

**Webhook Admission Architecture**: The operator provides 7 admission webhooks (4 mutating, 3 validating, 1 conversion) for Pod, SparkApplication, ScheduledSparkApplication, and SparkConnect resources. The webhook service runs on port 9443 and is backed by TLS certificates managed through Kubernetes secrets (`spark-operator-webhook-certs`). Webhook configuration is reconciled by dedicated controllers monitoring MutatingWebhookConfiguration and ValidatingWebhookConfiguration resources.

**Multi-CRD Scope**: The operator manages four CRDs: SparkApplication and ScheduledSparkApplication (upstream sparkoperator.k8s.io), SparkConnect (v1alpha1, namespaced), and SparkOperator (components.platform.opendatahub.io, cluster-scoped for component management). Each CRD has viewer and editor RBAC roles exposing them to users.

**Hermeticity**: Downstream (RHOAI) branch includes `rpms.lock.yaml` (759 KB) and `go.sum` for supply chain pinning. Hermeto (cachi2) prefetch is used in both Dockerfiles for reproducible builds. No Python lock file is present (downstream release branches may add poetry.lock or uv.lock).

**Platform Integration**: The operator integrates with cert-manager for webhook certificate provisioning and prometheus-operator for metrics collection. It depends on odh-platform-utilities for platform detection and manifest rendering, enabling the spark-operator-module to dynamically manage operator deployments across ODH and RHOAI distributions.

### Tenant Model

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-namespace RBAC (viewer/editor roles); shared controller-runtime RBAC checks | Kubernetes RBAC | Controller watches all namespaces by default; no per-tenant RBAC restrictions in operator code |
| Data storage | Kubernetes namespaces isolate ConfigMaps, Secrets, PVCs | Kubernetes namespace isolation | Shared ConfigMap watches may expose cross-namespace references |
| Network traffic | Pod network policies can restrict traffic (cluster admin responsibility) | Kubernetes NetworkPolicy | Operator does not auto-generate NetworkPolicies |
| Compute & resources | ResourceQuota and LimitRange per namespace | Kubernetes ResourceQuota, LimitRange | No namespace-aware resource throttling in operator |
| Configuration & secrets | Per-namespace Secrets; webhook TLS secret is shared cluster-wide | Kubernetes namespace isolation | Webhook TLS secret is cluster-scoped; compromise affects all applications |
| API scoping | Namespaced CRD watches | controller-runtime | Watch predicates use dynamic values; exact filtering behavior unclear |
