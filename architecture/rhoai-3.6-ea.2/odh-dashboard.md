## Purpose

**Short**: odh-dashboard is the central user interface for Open Data Hub and RHOAI platforms, providing unified navigation and management of platform components through an operator-managed Controller, multiple federated backend services, and a React-based SPA frontend.

**Detailed**: odh-dashboard consists of three primary layers: (1) a **dashboard-operator** Kubernetes controller that manages Dashboard custom resources and coordinates component availability state via status subresources; (2) multiple **federated backend-for-frontend (BFF) services** built in Go (core-bff, agent-ops, automl, autorag, data-registry, eval-hub, gen-ai, maas, mlflow, model-registry) that each provide domain-specific APIs for platform components while delegating Kubernetes API calls and authentication through shared patterns; (3) a **React/TypeScript SPA frontend** (with module federation micro-frontend architecture) served by a Node.js backend (Fastify framework) that proxies API requests and serves static assets. Subsidiary controllers for Workspace and WorkspaceKind management (in packages/notebooks/upstream/workspaces/) handle the lifecycle of Jupyter notebook environments. The dashboard reconciles the desired Dashboard CR, projects component availability state to the API layer, and presents a unified control plane for platform administrators and end users.

## Architectural Analysis

The odh-dashboard architecture exhibits a **modular multi-package design** leveraging TypeScript workspaces and Go modules to isolate domain logic across BFF services. Each BFF sidecar (agent-ops, automl, etc.) is independently deployable as a container variant while sharing a common authentication pattern (Bearer token validation from forwarded headers or in-cluster ServiceAccount tokens) and Kubernetes client library (client-go).

**Authentication & Authorization Model**: 
- HTTP endpoints in all BFFs are protected by middleware that validates Bearer tokens from the `Authorization` header (user flow) or in-cluster ServiceAccount tokens (internal operators) via the `-auth-method` flag (`internal` or `user_token`).
- The dashboard-operator controller uses its ServiceAccount token to interact with the Kubernetes API server (client-go dynamic client, in-cluster kubeconfig).
- Webhook admission controller (ValidatingWebhookConfiguration) validates Dashboard CRs before creation.
- RBAC cluster role grants the operator permission to manage Dashboard CRs, core resources (ConfigMaps, Secrets, Services), and OpenShift Routes for URL extraction.

**Multi-Tenancy Posture**: 
Dashboard resources are cluster-scoped (not namespaced). The operator does not enforce per-namespace isolation; tenancy is delegated to the Workspace CR (namespaced), which allows per-namespace notebook environments. Component availability is projected at the cluster level via the Dashboard CR's `.status.conditions` and `.spec.components` fields, enabling global visibility but not per-tenant billing or resource isolation.

**TLS & Cryptography**: 
- Build-time FIPS enforcement is active: Dockerfile.konflux.dashboard-operator uses `CGO_ENABLED=1` and `-tags strictfipsruntime` to build the operator binary dynamically linked against system OpenSSL.
- Application-level TLS is configured in BFF services: server-side TLS uses certificate and key files specified via command-line flags; client-side Kubernetes API calls use client-go's standard TLS verification (can disable via `InsecureSkipVerify` flag for dev/test).
- CA bundles are loaded from multiple sources: system trust stores (`/etc/pki/ca-trust/`), in-cluster ServiceAccount CA (`/var/run/secrets/kubernetes.io/serviceaccount/ca.crt`), and custom ODH CA bundles (`/etc/pki/tls/certs/odh-ca-bundle.crt`).
- No hardcoded certificates or non-FIPS crypto libraries detected; crypto/tls stdlib is used exclusively in Go services.

**API Proxy & Module Federation**: 
- Frontend requests to `/api/*` and `/_mf/*` paths are proxied by the Node.js backend to the appropriate BFF sidecar or service, allowing federated module loading and dynamic component plugin architecture.
- WebSocket support via gorilla/websocket for real-time updates (Kubernetes watch streams, health probes).

**Notebook Workspaces**: 
Separate Workspace and WorkspaceKind controllers (packages/notebooks/upstream/workspaces/) manage notebook pod lifecycle and template management. Workspaces are namespaced; WorkspaceKind is cluster-scoped. Controllers watch Pods, StatefulSets, Services, and ConfigMaps to reconcile notebook state.

## Multi-Tenancy

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| **Tenant boundary** | Cluster-level (Dashboard) and per-namespace (Workspace) | Dashboard CRD is cluster-scoped; Workspace CRD is namespaced |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Dashboard-level RBAC (cluster admin), Workspace-level RBAC (namespace admin); BFF auth-method allows user_token (forwarded) or internal (ServiceAccount) | Kubernetes RBAC + BFF middleware | No per-user quotas; no cross-workspace auth isolation (users with namespace access can access all Workspaces in that namespace) |
| Data storage | Workspace PVCs are namespaced; Workspace Secrets are namespaced; Dashboard ConfigMaps are cluster-wide | Kubernetes namespacing | BFF queries are user-scoped (forwarded token), but bulk Kubernetes queries (e.g., list all namespaces) are not filtered by tenant |
| Network traffic | No NetworkPolicy by default; optional Istio AuthorizationPolicy can restrict service-to-service traffic | Optional (Istio not required) | Default: no network isolation; all services can communicate within cluster |
| Compute & resources | ResourceQuota per namespace (optional, admin-configured) | Kubernetes ResourceQuota | Not enforced by dashboard; relies on cluster admin to set quotas |
| Configuration & secrets | Workspace Secrets are namespaced; dashboard-operator ConfigMaps are cluster-wide; BFF app-config is shared across all users | Kubernetes namespacing | Shared app-config and k8s-core libraries mean all frontend instances share configuration; no per-tenant customization |
| API scoping | BFF queries use forwarded user token (scoped to user's RBAC); Kubernetes watch streams are namespaced for Workspace resources | Kubernetes API + BFF forwarding | Operator-level Dashboard queries are cluster-wide; component discovery is global, not per-tenant |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Kubernetes API Server | Cluster (shared across all tenants) | RBAC policies scoped to namespace (for Workspaces) or cluster (for Dashboard); forwarded user token enforces RBAC |
| Dashboard operator | Cluster (single instance) | No multi-tenant isolation; operator manages global component state |
| core-bff | Cluster (single instance or replicated set) | Forwarded user token provides isolation; BFF does not enforce per-user quotas or rate limits |
| Frontend (SPA) | Cluster (single instance or CDN) | User token from client (forwarded) scopes subsequent API requests |

**Multi-Tenancy Posture**: odh-dashboard is designed for **cluster-level management** (single Dashboard CR per cluster) with **namespace-level workspaces** (multiple Workspace CRs per namespace). There is no built-in per-user or per-team billing, quotas, or data isolation beyond Kubernetes namespacing. The operator assumes cluster-admin role; end users interact with Workspaces and component UIs. Suitable for shared clusters with namespace-level RBAC; not suitable for strict SaaS multi-tenancy without additional platform-level isolation layers (e.g., Istio policies, network policies, custom quota enforcement).
