## Purpose

**Short**: Kubeflow SDK is a unified Python SDK that provides Pythonic APIs for interacting with Kubeflow components (Trainer, Katib, Model Registry, Spark Operator) and submitting ML workloads to Kubernetes clusters without requiring direct Kubernetes knowledge.

**Detailed**: Kubeflow SDK serves as the primary user-facing interface for the Kubeflow ecosystem within RHOAI. It abstracts away Kubernetes complexity through consistent, familiar Python APIs that enable users to define, configure, and execute AI/ML workloads at scale. The SDK supports multiple Kubeflow projects including Trainer (distributed training), Katib (hyperparameter optimization), Model Registry (artifact management), and Spark Operator (data processing). It includes RHAI-specific extensions for advanced LLM training scenarios, such as speculative decoding and custom model optimization. The SDK also supports local development backends (Docker, Podman, local process) for rapid prototyping before deployment to production Kubernetes clusters.

## Architectural Analysis

Kubeflow SDK is a pure Python library with no container operators or Kubernetes controllers of its own. Its architecture centers on client-side abstractions for submitting workloads to external services (Kubernetes API, Kubeflow Trainer, Katib, Model Registry, Spark Operator). The codebase is organized into backend implementations (Kubernetes, Docker, Podman, LocalProcess) that provide pluggable execution environments, allowing the same training code to run locally or on a cluster with minimal changes.

The RHAI-specific components (under `kubeflow/trainer/rhai/`) introduce advanced training patterns: speculative decoding for LLM optimization, vLLM integration for hidden state extraction, and instrumentation for monitoring and profiling. These RHAI modules integrate with the Kubeflow Trainer API and depend on external services (vLLM sidecars, managed inference endpoints) for their operation.

Dependencies are managed through `pyproject.toml` with pinned versions on RHOAI release branches (via `rhoai-3.6-ea.2` branch) to ensure reproducible builds and test environments. The SDK uses standard Python packaging (pip/uv) and does not currently use AIPCC base images for container builds—containers are built from upstream `python:3.11-slim` base images.

**Intent**: Core component for distributed model training across multiple frameworks and backends. Abstracts Kubernetes Training Job submission into Pythonic APIs; supports local Docker/Podman development and remote Kubernetes execution.

**Language**: Python

**Key Classes and APIs**:
- `TrainerClient`: Main entry point for job submission, monitoring, and logging
- `CustomTrainer`: Execute user-defined training functions with framework-agnostic argument passing

## Multi-Tenancy

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| **Tenant boundary** | Per-namespace (delegated to Kubernetes) | kubeflow.trainer.options.kubernetes: user-supplied namespace parameter; upstream Trainer controller enforces namespace scoping |
| **Deployment model** | Multi-tenant at platform level; SDK itself is stateless | Each user/application instantiates TrainerClient independently; no shared state |
| **Tenant identifier** | Kubernetes namespace (for CRD scoping); user identity (inherited from kubeconfig) | Namespace in TrainJob metadata; user in kubeconfig credentials |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-tenant RBAC (Kubernetes namespace RBAC) | Kubernetes API server; upstream Trainer/Katib operators | SDK does not enforce multi-tenant isolation; relies entirely on Kubernetes and upstream operators |
| Data storage | Separate Kubeflow TrainJob CRDs per namespace; Spark executor pods isolated by namespace | Kubernetes / Upstream Trainer/Spark operators | No application-level tenant validation; SDK trusts kubeconfig credentials |
| Network traffic | NetworkPolicy per namespace (if configured) or Istio AuthorizationPolicy | Kubernetes / Istio (if deployed) | SDK makes no network-level isolation guarantees |
| Compute & resources | ResourceQuota per namespace (if configured) | Kubernetes | SDK does not enforce or validate resource quotas |
| Configuration & secrets | kubeconfig per user/service account; per-namespace Secrets for credentials | Kubernetes | HF_TOKEN read from environment; no per-tenant isolation of environment variables |
| API scoping | Trainer/Katib controllers enforce namespace-scoped CRD watches | Upstream operators | SDK does not validate tenant membership; accepts any namespace parameter |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Kubernetes API | Per-namespace Secrets, RBAC, ResourceQuota | Kubernetes native isolation |
| Trainer controller | Per-namespace Job scoping | Trainer operator enforces namespace filtering |
| Katib controller | Per-namespace Experiment scoping | Katib operator enforces namespace filtering |
| Model Registry (if shared) | API-level access control (not tenant-aware by default) | Model Registry role/permission system (tenant isolation not verified) |
| Spark cluster (if shared) | Per-namespace SparkConnect pods | Kubernetes namespace isolation + Spark Connect auth |

**Summary**: Kubeflow SDK is **tenant-aware but not tenant-enforcing**. Tenant isolation is delegated entirely to Kubernetes namespace RBAC and upstream component operators. The SDK is a stateless library and does not maintain tenant context. Proper multi-tenant isolation requires:
1. Kubernetes namespace-based isolation via RBAC and NetworkPolicy
2. Upstream operators (Trainer, Katib, etc.) enforcing namespace scoping
3. Shared services (Model Registry, Spark) configured with tenant-aware access control
