## Purpose

**Short**: REST API service for responsible AI workflows including drift detection, fairness monitoring, and model explainability that consumes inference data from KServe, persists it to configurable backends (HDF5 or MariaDB), and computes metrics on a schedule.

**Detailed**: TrustyAI Service is a cloud-native microservice that consumes inference data from KServe, persists it to configurable backends (HDF5 on Persistent Volumes or MariaDB), and computes AI quality metrics on a schedule. It publishes metrics to Prometheus for monitoring. The service implements multiple drift detection algorithms (Kolmogorov–Smirnov, Jensen–Shannon, Maximum Mean Discrepancy), fairness metrics (Statistical Parity Difference, Disparate Impact Ratio), and supports explainability endpoints for model prediction analysis. Built on FastAPI + Hypercorn with dual-protocol support (HTTP for internal requests with kube-rbac-proxy, optional HTTPS for direct access), it is designed to run on Kubernetes with configurable storage backends and comprehensive health probes.

## Architectural Analysis

TrustyAI Service adopts a composable, feature-flag-gated metrics architecture where drift detection algorithms and fairness computations are decoupled from the HTTP transport layer. The service distinguishes between two runtime modes: a main HTTP API (port 8081 for kube-rbac-proxy, optional 4443 for direct HTTPS) and a dedicated health probes server (port 8080) for Kubernetes liveness and readiness checks. This separation allows authentication middleware (kube-rbac-proxy) to validate API requests while health probes bypass it.

The core computation engine relies heavily on scientific Python libraries (scikit-learn, scipy, numpy, pandas, polars) to implement streaming and batch statistical tests. A background task runs a Prometheus scheduler at configurable intervals (default 30 seconds) to compute requested metrics and publish results as Prometheus gauges. Storage is pluggable: either HDF5 files on Persistent Volumes (PVC default) or MariaDB with optional SSL support. Configuration is environment-variable driven, enabling safe operation in restricted deployments.

**Key architectural decisions:**
- **Dual-server design**: Separates metrics/data APIs (guarded by kube-rbac-proxy) from health probes (always accessible to kubelet). This prevents authentication blocking health checks.
- **Policy-aware TLS**: Custom `PolicyAwareConfig` respects the system crypto policy set by `update-crypto-policies`, allowing automatic compliance with cluster FIPS profiles without hardcoded cipher lists.
- **Lazy imports for optional storage**: MariaDB support is imported only when `SERVICE_STORAGE_FORMAT=MARIA`, reducing image size and dependency surface when PVC storage is used.
- **Background metrics scheduler**: Decouples metric computation from HTTP request latency, preventing long-running statistical tests from blocking inference requests.
- **Feature-flag gating**: Explainer endpoints, fairness metrics, and drift algorithms are individually toggled via environment variables, allowing graceful degradation.

**Security considerations:**
- HTTP API has no built-in authentication; authentication is delegated to kube-rbac-proxy (recommended on Kubernetes).
- All HTTP endpoints return configurable encryption (HTTP by default, HTTPS if certificates are present).
- Database passwords and MariaDB credentials are read from environment variables; TLS CA certs for database connections are checked at `/etc/tls/db/ca.crt` by default.
- Protobuf >= 7 is required to resolve CVE-2026-0994 (buffer overflow).
