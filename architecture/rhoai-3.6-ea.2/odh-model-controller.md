## Purpose

**Short**: A companion controller to KServe that extends model serving capabilities in Red Hat OpenShift AI with OpenShift-specific integrations, certificate management, monitoring, and NVIDIA NIM support.

**Detailed**: ODH Model Controller augments KServe's core model serving functionality (InferenceService, ServingRuntime, InferenceGraph, LLMInferenceService) with platform-specific features for Red Hat OpenShift and ODH. It manages OpenShift Route creation for model endpoints, aggregates cluster CA bundles for secure TLS communication, orchestrates Prometheus monitoring integration with ServiceMonitors and dashboards, handles NVIDIA NIM Account lifecycle, manages multi-node Ray cluster TLS configuration, synchronizes model metadata with Model Registry, provisions KEDA autoscaling authentication context, enforces Model-as-a-Service (MaaS) gateway authentication via Kuadrant AuthPolicies, and bootstraps Gateway API infrastructure. Two binaries are produced: the primary Kubernetes controller-runtime manager (cmd/main.go) and a standalone Model Serving API REST server (server/main.go) for querying gateway and endpoint discovery.

## Architectural Analysis

The component follows a three-layer pattern of model-serving abstraction:

1. **KServe layer** (upstream): Core serving primitives (InferenceService, ServingRuntime) managed by the upstream KServe controller in a separate pod
2. **ODH controller layer** (this component): Watches KServe resources and adds OpenShift-specific lifecycle management, platform integrations, and observability
3. **Model Serving API layer** (embedded binary): Provides a separate REST API for discovering and querying gateway/endpoint configuration, independent of the controller

The controller uses a sub-reconciler pattern where the main InferenceService and LLMInferenceService reconcilers delegate to specialized reconcilers for each cross-cutting concern: routes, metrics, RBAC, image pull secrets, KEDA provisioning, and MaaS auth. This design isolates concerns and allows gradual enablement—e.g., KEDA reconciliation only runs if an InferenceService specifies Prometheus-based autoscaling.

Webhook enforcement adds validation for InferenceService naming constraints and Ray TLS injection for multi-node clusters. The Gateway controller watches Gateway API resources and orchestrates EnvoyFilter + AuthPolicy changes on shared gateways, decoupling gateway infrastructure setup from individual model deployments.

Security and observability are built into the controller: FIPS-compliant build (strictfipsruntime, dynamic linking, OpenSSL), controller-runtime metrics with optional authn/authz filtering, OpenTelemetry instrumentation on the model-serving-api server, and granular RBAC for metrics scraping and pod authentication.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | InferenceService namespace scope; per-namespace RBAC via ServiceAccounts and Roles; ClusterRoleBindings for metrics access | Kubernetes RBAC + controller-runtime watches | Metrics RBAC (kserve-prometheus-k8s) is cluster-wide; any Service can be scraped if Prometheus has access |
| Data storage | Per-namespace PVCs (delegated to KServe Predictor deployment); per-namespace Secrets for pull credentials and TLS | Kubernetes namespace isolation | InferenceService watches Secrets cluster-wide; tenant could theoretically reference secrets in other namespaces via cross-namespace references (risk depends on webhook validation) |
| Network traffic | NetworkPolicy per namespace (delegated to KServe); Istio EnvoyFilter for gateway mTLS (shared Gateway, per-route policies) | Kubernetes NetworkPolicy + Istio | Shared gateway (Gateway API) creates cross-namespace exposure risk if AuthPolicy is misconfigured |
| Compute & resources | ResourceQuota and LimitRange per namespace (delegated to cluster admin) | Kubernetes | Controller itself is a cluster-wide singleton (leader-elected); no per-tenant compute isolation for controller |
| Configuration & secrets | Per-namespace ConfigMaps and Secrets; per-namespace Roles and RoleBindings | Kubernetes | Webhook validation checks namespace protections; Model Registry sync and NIM Account state are cluster-wide if MODELREGISTRY_STATE=managed |
| API scoping | InferenceService watches per-namespace; Gateway watch is cluster-wide | Kubernetes API + controller-runtime | Gateway watcher is not namespace-scoped; reconfigures shared gateways across tenants |

**Tenancy Assessment**: The component assumes single-tenant (per-cluster) or per-namespace multi-tenancy at the InferenceService level. Sharing of Prometheus, Authorino, Gateway, and optional Model Registry / NIM services introduces cross-tenant exposure risks. Webhook validation (system namespace protection) and RBAC (per-namespace Roles) provide baseline isolation, but shared infrastructure (Gateway, Authorino) requires careful policy configuration to prevent token leakage or auth bypass.
