## Purpose

**Short**: High-performance KV-Cache indexer library for vLLM-based distributed LLM inference with KV-cache-aware routing.

**Detailed**: llm-d-kv-cache is a pluggable service and library designed to enable KV-cache-aware routing in distributed vLLM inference platforms. It maintains a near-real-time, global view of KV-cache block locality across a fleet of vLLM pods, using KVEvents streamed from vLLM instances to track which blocks reside on which nodes and storage tiers (GPU, CPU). This metadata powers intelligent routing decisions, optimizing Time To First Token (TTFT) and throughput by reusing cached KV blocks rather than recomputing them.

The project provides core libraries (`kvcache`, `kvblock`, `kvevents`) that were recently moved upstream to llm-d-router, along with example implementations (KVCache Indexer, KVCache Aware Scorer, KV-Events processors) and utility connectors (PVC Evictor for disk space management, llmd-fs-backend for vLLM offloading).

## Architectural Analysis

llm-d-kv-cache exhibits a layered architecture separating concerns across event ingestion, indexing, and scoring interfaces. The **read path** (scoring) involves a scheduler requesting pod scores for a prompt, the KVCache Indexer querying the KV-Block Index, and returning KV-cache-hit scores. The **write path** (event ingestion) processes KVEvents emitted by vLLM pods, updating the Block Index in near-real-time via a concurrent event subscriber pool.

Key architectural decisions:

1. **Multi-tier Storage Modeling**: The design explicitly models KV-cache blocks across GPU and CPU tiers, enabling placement decisions that account for data movement costs.

2. **Event-Driven Index Updates**: Rather than polling vLLM instances, the system consumes structured KVEvents (creation/eviction metadata) via ZeroMQ publishers, reducing latency and decoupling index updates from workload operations.

3. **gRPC-First Service Interface**: The IndexerService wraps the core `pkg/kvcache.Indexer` behind a minimal gRPC API (GetPodScores), enabling in-process library use and remote service deployment.

4. **Redis/Valkey Backend**: Integration with Redis or compatible backends (Valkey) for runtime queue and key-value data storage, with pluggable client configuration.

5. **OpenTelemetry Tracing**: All components have built-in OTLP/gRPC trace export with configurable endpoints, supporting production observability without vendor lock-in.

6. **Kubernetes-Native Runtime**: One example (pod_reconciler) uses controller-runtime to watch Kubernetes Pod resources, enabling integration with Kubernetes cluster operations.

**Gaps and Observations**: 

- The core scheduling libraries have been extracted to llm-d-router; this repository now primarily houses examples and connectors. This separation reflects maturation and planned deprecation paths.
- The PVC Evictor and llmd-fs-backend are important runtime utilities but operate independently from the indexer core, requiring explicit orchestration.
- OpenTelemetry export is configured with `WithInsecure()` in examples, indicating development-time defaults that must be explicitly hardened for production (TLS credentials required).
- gRPC service options in the IndexerService reference unresolved interceptors and credentials, suggesting flexibility for platform-specific auth but requiring runtime configuration.
