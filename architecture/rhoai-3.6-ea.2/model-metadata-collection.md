## Purpose

**Short**: Extracts, enriches, and catalogs metadata from Red Hat AI container images and HuggingFace collections.

**Detailed**: model-metadata-collection is a Go CLI application that processes Red Hat AI ModelCar container images and generates structured model catalogs for downstream consumption by RHOAI and ODH platforms. The tool fetches OCI image manifests, scans container layers for embedded modelcard metadata, enriches model information from HuggingFace APIs, and produces YAML catalogs of models, MCP (Model Context Protocol) servers, and agents. It supports parallel processing, static catalog merging, and multiple index sources (validated models, other models, MCP servers across Red Hat/Partner/Community categories). The containerized deployment (using UBI 9 minimal-pqc base) serves pre-generated catalogs as read-only volumes for platform integration.

## Architectural Analysis

The component is fundamentally a **catalog generation and serving system** rather than a runtime operator. Its architecture centers on three processing phases:

1. **Discovery & Collection Phase**: Fetches HuggingFace validated model collections via API, generates version-specific index files, merges with static catalogs from `input/supplemental-catalog.yaml`.

2. **Enrichment & Extraction Phase**: Processes each model reference in parallel (bounded concurrency, default 5 goroutines) by fetching OCI manifests using `github.com/containers/image/v5`, scanning layers for modelcard annotations, extracting structured metadata, and enriching from HuggingFace README files and vLLM configuration files.

3. **Catalog Generation Phase**: Merges enriched metadata with static catalogs, deduplicates entries, validates model types, and writes aggregated `models-catalog.yaml`, `validated-models-catalog.yaml`, and other variant catalogs (redhat/partner/community MCP servers, agents).

The **Dockerfile.konflux** (runtime) differs significantly from the CLI entrypoints: it is a minimal data-serving container that copies pre-generated catalogs into `/app/data` and runs `sleep infinity` for mounting by other applications. This is a deliberate design choice—the CLI tools (`model-extractor`, `metadata-report`) run as part of the CI/CD pipeline to generate catalogs; the container image distributes read-only catalog artifacts.

**Key architectural patterns**:
- **Bounded goroutine pools** using `sync.WaitGroup` and semaphore channels to limit concurrency and resource usage.
- **Data prioritization hierarchy**: HuggingFace YAML frontmatter > extracted modelcard.md > HuggingFace API > registry metadata.
- **Normalization & similarity scoring**: Container image model names are normalized and matched to HuggingFace entries using fuzzy text similarity to handle variations.
- **Decoupled I/O**: Separate packages for HuggingFace API client, container registry operations, and metadata extraction reduce coupling and enable testing.

**Supply chain considerations**: The `go.mod` lock file is present (Go 1.24/1.25); Dockerfiles use specific image digests (UBI 9 minimal-pqc sha256 hash). No explicit hermetic OS package locks detected; relies on UBI base image pinning and Konflux attestation. The analyzer found 2 active platform alias references (serving.kserve.io) in `other-models-catalog.yaml` and `validated-models-catalog.yaml`, indicating this component is a data provider for KServe serving runtimes.

### Model Metadata Schema

Each model entry in the catalog contains:

```yaml
name: string                           # Model name (normalized from HuggingFace or container image)
provider: string                       # Organization/creator (e.g., IBM Research, Swiss AI)
description: string                    # Human-readable description
readme: string                         # Markdown documentation (from modelcard or HuggingFace)
language: []string                     # ISO language codes (e.g., ["en"])
license: string                        # SPDX identifier (e.g., apache-2.0)
licenseLink: string                    # URL to license text
tags: []string                         # Tags merged from labels, modelcard, HuggingFace
tasks: []string                        # Task categories (e.g., ["text-generation", "tool-calling"])
artifacts: []Artifact                  # OCI references and metadata
  - uri: string                        # OCI reference (oci://registry/path:tag)
    createTimeSinceEpoch: number       # Milliseconds since epoch
    lastUpdateTimeSinceEpoch: number   # Milliseconds since epoch
    customProperties: map              # Registry annotations
customProperties: map                  # Tool-calling config, model_type, validated_tasks, etc.
  model_type:
    metadataType: MetadataStringValue
    string_value: string               # "generative" | "predictive" | "unknown"
  servingConfig.toolCalling:           # When tool-calling is configured
    toolCallParser: string
    chatTemplate: string               # Path converted to /opt/app-root/template/
    enableAutoToolChoice: boolean
    requiredArgs: []string
  validatedTasks: []string             # Validated tasks (e.g., ["tool-calling"])
```
