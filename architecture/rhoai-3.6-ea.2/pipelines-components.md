## Purpose

**Short**: A centralized Python library of reusable Kubeflow Pipelines components for data processing, model training, deployment, and evaluation within RHOAI workflows.

**Detailed**: The Kubeflow Pipelines Components repository is a community-maintained collection of standardized, reusable components and end-to-end pipeline templates for the Kubeflow Pipelines SDK (v2.16.1+). The repository organizes components into four primary domains: **Data Processing** (data loading, transformation, chunking, document parsing); **Training** (AutoML hyperparameter tuning, AutoRAG optimization, fine-tuning with LoRA/SFT/OSFT); **Evaluation** (model benchmarking via Eval Hub, LM-Eval); and **Deployment** (KServe InferenceService creation, embedding model serving). Each component is packaged as a Python function decorated with `@dsl.component`, executed via Kubeflow Pipelines' Container Execution Environment (Python runtime within containers). The container image (UBI 9 Python 3.12 base) is built during the Konflux CI process and contains the entire component library plus runtime dependencies. End users consume this library by importing components into their pipeline definitions, or by running managed pipelines that have been generated and installed into the RHOAI platform.

## Architectural Analysis

The pipelines-components repository exemplifies a **component library distribution pattern** rather than a deployed service. Its primary artifact is the `kfp-components` Python package (v1.11.0), which ships as:

1. **Managed Container Image** (`Dockerfile.konflux.pipelines-components`): A UBI 9 Python 3.12 image that bundles the entire kfp-components library, all production dependencies (boto3, kubernetes, cryptography, etc.), and a startup script that initializes managed pipelines. This image is built and pushed by Konflux CI.

2. **Reusable Component Modules**: Each component (e.g., `tabular_data_loader`, `model_deployment`, `evalhub_evaluator_kserve`) is a Python function in the `kfp_components.components.*` namespace, annotated with Kubeflow Pipelines decorators. Components are stateless functions that execute in isolated container pods; they communicate via Kubernetes artifacts (ConfigMaps, Secrets, PVCs) and environment variables.

3. **Pipeline Templates**: Pre-built, end-to-end pipelines (e.g., `autogluon_tabular_training_pipeline`, `finetuning_evalhub_sft_minimal`) combine components and wire outputs to inputs. These templates are written in Python, compiled to KFP protobuf YAML, and stored as managed pipelines accessible via the RHOAI UI.

**Key architectural properties**:
- **No persistent runtime state**: Components are ephemeral Kubernetes pods. State flows through artifact storage (S3, PVCs) and environment configuration (ConfigMaps, Secrets, HardwareProfiles).
- **Multi-tenant via Kubernetes namespaces**: Pipelines run in user namespaces; RBAC, resource quotas, and NetworkPolicies enforce isolation.
- **Declarative orchestration**: All component orchestration is declarative KFP YAML; no custom operators or webhooks.
- **External integration at component level**: Components make outbound calls to AWS S3, HuggingFace Hub, Kubernetes API, and KServe InferenceServices. These integrations are localized to individual component implementations, not platform-wide.
- **RHOAI ecosystem integration**: Several components directly reference RHOAI-specific APIs (`infrastructure.opendatahub.io` for HardwareProfiles, `serving.kserve.io` for InferenceServices) and use RHOAI-curated base images and tooling.

## Multi-Tenancy

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| **Tenant boundary** | per-namespace | Kubernetes namespace isolation; pipelines run in user-provisioned namespaces |
| **Deployment model** | multi-tenant (shared KFP backend instance serving multiple namespaces) | KFP controller runs in system namespace; user pipelines run in user namespaces |
| **Tenant identifier** | Kubernetes namespace name | Inferred from `.metadata.namespace` in KFP-generated pod specs |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Kubernetes RBAC per namespace; component pods use namespace-scoped service accounts | Kubernetes API server | Component code does not explicitly check authorization; relies on inherited SA token |
| Data storage | PVC per namespace or per-user volume mount; S3 buckets and access via credentials (env vars) | Kubernetes volume mounts + AWS IAM | Multi-user access to shared S3 buckets must be controlled via IAM policy; no per-tenant row-level filtering in components |
| Network traffic | NetworkPolicy per namespace (if configured by platform); in-cluster communication to KServe via service DNS | Kubernetes NetworkPolicy / Istio | Default: no NetworkPolicy; traffic between components is unrestricted unless platform layer enforces it |
| Compute & resources | ResourceQuota per namespace; LimitRange for pod resource constraints | Kubernetes admission controller | Components respect resource requests/limits at pod level but do not enforce quotas internally |
| Configuration & secrets | Secrets per namespace; environment variables from Secrets | Kubernetes Secret mount + RBAC | Secrets are namespace-scoped; components do not validate secret sources |
| API scoping | Components query Kubernetes API within their own namespace or cluster-wide (HardwareProfile lookup); no explicit tenant filtering | Kubernetes API + component code | HardwareProfile lookup is cluster-wide (infrastructure.opendatahub.io); components may inadvertently use wrong cluster-wide resource if naming collides |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Kubernetes API server | Cluster-wide (shared across namespaces) | RBAC on API resources (HardwareProfiles, InferenceServices are cluster-scoped or namespace-scoped depending on CRD definition) |
| KServe backend | Cluster-wide (shared controller) | InferenceServices are namespaced; model serving traffic is isolated by Istio mTLS if configured |
| S3 / S3-compatible storage | Shared bucket (single credentials per tenant) | Bucket-level and object-level IAM policies; no row-level isolation at KFP level |
| HuggingFace model hub | Shared external service (all tenants access same models) | API token-based rate limiting; no tenant-specific access control |

**Summary**: Tenant isolation is enforced at the Kubernetes namespace level. Components do not perform explicit cross-tenant data access control; isolation relies entirely on Kubernetes RBAC, network policies, and infrastructure-level configuration (e.g., IAM policies for S3). A compromised component pod or leaked service account token could access other namespaces' resources unless NetworkPolicy and RBAC are strictly configured.
