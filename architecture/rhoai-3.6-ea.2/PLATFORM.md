## Platform Overview

Red Hat OpenShift AI (RHOAI) 3.6-ea.2 is an enterprise-grade, Kubernetes-native machine learning operations platform built on OpenShift Container Platform. The platform provides a comprehensive set of tools and services for data scientists, ML engineers, and platform operators to develop, deploy, monitor, and govern AI/ML workloads at scale. The distribution is organized around the RHODS Operator, which orchestrates a managed set of 80 interconnected components spanning model serving, inference optimization, guardrails and safety, experiment tracking, distributed training, batch processing, and observability.

The platform is deployed using an operator pattern leveraging the Operator Lifecycle Manager (OLM), with operators for core services including KServe (model serving), KubeRay (distributed compute), Argo Workflows (pipeline orchestration), Data Science Pipelines, MLflow, training operators, and multiple inference gateway components. Security is enforced through kube-rbac-proxy at service boundaries, mTLS between mesh services, and a layered gateway authentication architecture. Ingress is exposed through OpenShift Routes, Gateway API (HTTPRoute), and distributed gateway infrastructure including data-science-gateway, models-gateway, and praxis-gateway components for routing and payload processing.

The platform emphasizes operational excellence through 213 validated webhooks providing cross-component coordination, 171 Custom Resource Definitions (CRDs) enabling declarative workload management, and extensive observability via Prometheus endpoints and health probes. Key architectural patterns include CRD-based orchestration (operator reconciliation), gRPC service boundaries for performance-critical paths, and plugin-based extensibility for model serving and guardrails. The platform supports disconnected (air-gapped) deployments through OLM relatedImages, RELATED_IMAGE environment variables, and manifest-driven kustomize overlays for distribution-specific variants.

### Ingress Analysis

RHOAI 3.6-ea.2 employs a **multi-tier ingress architecture** that separates concerns across Gateway API (Envoy-backed) and OpenShift Router (HAProxy-backed) surfaces:

1. **Gateway API Tier (Istio-based)**: The three managed Gateways (`data-science-gateway`, `models-gateway`, `praxis-gateway`) are created and reconciled by the ai-gateway-operator in response to AIGateway CRs. Each Gateway is backed by Envoy (deployed as part of ai-gateway-payload-processing's external processor integration). HTTPRoute resources route traffic to backend services and are created by client components (e.g., KServe creates routes for InferenceService predictors, Models-as-a-Service creates routes for model endpoints). Authentication is enforced via EnvoyFilter rules that trigger `ext_authz` calls to kube-auth-proxy sidecar instances, which perform token validation and RBAC checks before forwarding to the application.

2. **OpenShift Router Tier (HAProxy-based)**: Primary ingress for RHODS Operator-managed services (odh-dashboard, odh-model-controller) and user workloads. Routes are created declaratively by operators or dynamically by applications. Authentication is typically delegated to OpenShift's built-in OAuth provider or optional sidecar injection.

3. **Request Path Composition**: A typical user request to odh-dashboard flows: Client (browser) → OpenShift Router (OAuth intercept) → odh-dashboard service. A model inference request flows: Client (SDK/REST) → Gateway API HTTPRoute → Envoy (data-science-gateway or models-gateway) → EnvoyFilter (ext_authz rule) → kube-auth-proxy (token validation + RBAC) → KServe InferenceService (predictor) → model server (MLServer/vLLM/etc.). Praxis-routed requests add an additional policy enforcement layer via PPE.

4. **Gateway Ownership and Naming**: Each AIGateway CR specifies a namespace, gateway name, and routing class. The ai-gateway-controller renders and applies manifests (praxis-extproc overlays for Praxis gateways) using kustomize with placeholder substitution. HTTPRoute naming follows owner conventions (e.g., KServe creates routes named `<inferenceservice-name>-route`); unresolved or generic route names indicate dynamic routing or overlay-based creation that requires source inspection.

5. **Cross-Component Surfaces**: External model ingestion (Praxis ExternalModel CRs) and gateway-level guardrails (Praxis Policy Engine policies) are routed through praxis-gateway, enabling fine-grained control over model endpoint authentication and policy enforcement without modifying individual model services.

## Deployment Architecture

### Deployment Topology

RHOAI 3.6-ea.2 organizes deployments across **four primary namespace tiers**:

1. **Operator Namespace (`redhat-ods-operators`)**: Hosts all platform operators and control plane services. RHODS Operator and dependent operators (Data Science Pipelines, KServe, KubeRay, Trainer, MLflow, Model Registry, TrustyAI, MCP Lifecycle, Kubeflow components) are deployed here as single-instance (or HA replica) Deployments with ClusterRole permissions for cluster-scoped resource reconciliation. Webhook servers (mutation/validation) listen on `:8443` and are registered via ValidatingWebhookConfiguration / MutatingWebhookConfiguration. RBAC: ClusterRole + ClusterRoleBinding grant operators full CRUD on their managed CRD groups.

2. **Applications Namespace (`redhat-ods-applications`)**: Hosts user-facing services and dashboards. Key deployments:
   - `odh-dashboard`: Central web console (Deployment, Service, Route/Ingress)
   - Kubeflow Hub (Model Registry & Catalog): Deployment + Service
   - Models-as-a-Service (MaaS): Controller + Service
   - Gateway infrastructure: `data-science-gateway`, `models-gateway`, `praxis-gateway` (Gateway API + Envoy Deployment)
   - ai-gateway-controller: Reconciles gateway manifests
   - ai-gateway-payload-processing: External processor for Envoy (Deployment, gRPC Service)
   - kube-auth-proxy: Auth sidecar proxy instances (DaemonSet or injected)
   - TrustyAI Service: Explainability backend (Deployment + Service)
   - Notebooks: Notebook controller (Deployment)
   - Workbenches Operator: Notebook provisioning (Deployment)

3. **Platform Infrastructure Namespace (`redhat-ods`)**: Hosts cluster-wide services and observability. Deployments:
   - `odh-observability`: Prometheus, Grafana (if enabled), monitoring stack
   - `OGX K8s Operator`: Optional OGX distribution support
   - `Model Metadata Collection`: Telemetry agent (DaemonSet or Job)
   - `RHAII Cluster Validation`: Health check service (CronJob or Deployment)

4. **User Namespaces**: Created on-demand by RHODS Operator or user request for data science workspaces. Each user namespace (e.g., `user-john`, `team-ml`) contains:
   - Notebook instances (StatefulSet or Deployment)
   - Training job pods (managed by Trainer Operator)
   - Data Science Pipeline runs (managed by Argo Workflows, spawned by DSP)
   - KServe InferenceService predictions (model server Deployment)
   - Secret resources (model artifacts, external API keys)
   - PersistentVolumeClaims (for notebook state, shared data)
   - ServiceAccount for workload identity
   - RBAC: RoleBinding grants user ServiceAccount permissions scoped to user namespace

All intra-cluster communication uses Kubernetes DNS (`<service>.<namespace>.svc.cluster.local`). External egress is routed via OpenShift Egress IP or cluster NAT. Istio mTLS is enforced for service-to-service communication within the mesh (data-science-gateway, models-gateway, praxis-gateway, ai-gateway-payload-processing).

#### Manifest Consumption Pipeline

Component manifests are authored in individual component repositories (e.g., `kserve-repo/config/`, `data-science-pipelines-repo/manifests/`). The RHOAI platform aggregates these manifests via:

1. **Upstream Component Repos**: Each component (KServe, MLflow, Data Science Pipelines, etc.) maintains its own manifests.
2. **get_all_manifests.sh**: Central script (in RHOAI Operator repo) fetches all component manifests and applies distribution-specific overlays.
3. **Kustomize Overlays**: `overlays/rhoai/` applies patches, namespace substitutions, and resource policies across all components.
4. **RHODS Operator Reconciliation**: RHODS Operator downloads and applies manifests to the cluster. For managed components, it installs via OLM (OperatorHub integration); for unmanaged components, it uses SSA (Server-Side Apply).
5. **Platform Delivery**: Final manifests are packaged as a single RHOAI distribution image or delivered via RHODS Operator's embedded bundle.

### Disconnected Support

RHOAI 3.6-ea.2 supports **air-gapped (disconnected) deployment** via:

1. **OLM relatedImages**: Each operator's ClusterServiceVersion (CSV) declares `relatedImages` for all transitive dependencies (base images, init containers, sidecars). OLM uses this to verify image availability in the air-gapped registry before operator installation.

2. **RELATED_IMAGE Environment Variables**: Operators and controllers reference images via environment variable (set by OLM from relatedImages). When deployed offline, these variables are rewritten to point to mirrored registries (e.g., `quay.io/redhat/` → `internal-mirror.example.com/redhat/`).

3. **oc-mirror Tooling**: Customers use `oc-mirror` to sync RHOAI operator bundles and component images to an air-gapped registry. Manifests are automatically rewritten to use mirrored image references.

4. **Manifest Kustomize Overlays**: `overlays/disconnected/` provides additional patches (e.g., disabling webhooks that require external image pulls, setting `imagePullSecrets` for private registry access).

5. **Digest Pinning**: Component manifests pin images to specific digest hashes (`image: quay.io/redhat/kserve@sha256:abc123...`) for reproducibility and signature verification in high-security environments.

**Known Limitations**: External model providers (OpenAI, Bedrock, etc.) still require outbound egress for API calls (handled via Egress IP or proxy). NeMo Guardrails and llm-d services may require downloading guardrails models at startup; these should be pre-cached in disconnected environments.

## Platform Architectural Analysis

RHOAI 3.6-ea.2 represents a **maturing, operator-driven ML platform** exhibiting three distinct architectural tiers:

1. **Control Plane Tier** (RHODS Operator + dependent operators) — Declarative orchestration of ML infrastructure via CRDs. Operators reconcile desired state to actual state, handle lifecycle management (install, upgrade, scale), and coordinate cross-component dependencies. Heavy reliance on webhooks (213 total) ensures constraint enforcement and state consistency across component boundaries.

2. **Gateway & Authentication Tier** (ai-gateway-operator, Envoy, kube-auth-proxy, Praxis components) — Sophisticated multi-layer request routing and auth composition. Request paths are decomposed: OAuth2 token validation (external or OpenShift), RBAC enforcement (kube-auth-proxy), optional policy evaluation (Praxis PPE), optional request/response transformation (ai-gateway-payload-processing plugins). This architecture enables pluggable auth and observability without requiring modifications to individual model servers.

3. **Workload Tier** (Model servers, training operators, notebook controllers, inference gateways) — Diverse runtime environments for data science workloads. Model serving spans MLServer (scikit-learn, XGBoost, ONNX, Hugging Face), vLLM (LLM inference), KServe-managed runtimes (PyTorch, TensorFlow), and external model providers (OpenAI, Bedrock). Training workloads span Kubeflow Training Operator (distributed TensorFlow/PyTorch), KubeRay (distributed Ray), and Spark (via spark-operator). This diversity enables customers to choose best-fit runtimes without vendor lock-in.

### Key Architectural Tensions & Trade-offs

1. **Distributed Gateway Complexity vs. Security**: The multi-gateway architecture (data-science-gateway, models-gateway, praxis-gateway) provides fine-grained routing and policy enforcement but increases operational complexity. Each gateway requires its own Envoy deployment, authentication policy, and route management. The platform mitigates this via ai-gateway-operator (automated gateway provisioning) and ai-gateway-controller (manifest rendering).

2. **Plugin Extensibility vs. Version Stability**: MLServer's plugin architecture (runtimes for sklearn, XGBoost, ONNX, etc.) and Praxis's IPP plugin framework enable extensibility without forking, but version mismatches between plugins and core can cause runtime failures. The platform addresses this via strict version pinning in manifests and automated webhook validation.

3. **External Model Provider Integration vs. Data Governance**: Praxis ExternalModel CRs and ExternalProvider resources enable seamless integration with external LLMs (OpenAI, Bedrock) but introduce data exfiltration risk (model inputs/outputs sent to external provider). The platform provides policy controls (Praxis Policy Engine), request/response transformation (ai-gateway-payload-processing), and audit logging (TrustyAI) but requires customer configuration.

4. **Operator Proliferation vs. Operational Overhead**: The platform includes 20+ operators (RHODS, KServe, MLflow, Data Science Pipelines, KubeRay, Trainer, TrustyAI, Model Registry, MCP Lifecycle, etc.), each with its own RBAC, webhooks, and CRDs. While each operator is independently useful, their interdependencies create a "critical mass" effect—removing one operator may break others. The platform mitigates this via clear dependency documentation (internal_deps, dependency graph) and test coverage for multi-operator scenarios.

### Serving Path Evolution

The platform supports **five distinct model serving paths**, each suited to different use cases:

| Path | Evidence Components | Entry/Routing Surface | Runtime or Provider Role | Source |
|------|---------------------|-----------------------|--------------------------|--------|
| **KServe Unified Inference** | KServe Operator, InferenceService CRs, KServe predictor/explainer/transformer, models-gateway | HTTPRoute (models-gateway) → Envoy | KServe-managed runtimes (PyTorch, Tensorflow, Scikit-learn) or custom predictor | KServe component analysis; observed via CRD watches and gateway routing |
| **MLServer Model Serving** | MLServer (FastAPI), MLServer runtimes (sklearn, XGBoost, ONNX, MLflow, Hugging Face), model servers deployed as KServe predictors | HTTPRoute (models-gateway) → Envoy → KServe predictor service → MLServer | MLServer as KServe runtime adapter; supports 11+ model formats via pluggable runtimes | MLServer component analysis; integrated with KServe via v2 inference protocol |
| **vLLM LLM Inference** | vLLM CPU, vLLM Gaudi (HLS accelerator variant), vLLM deployed as KServe transformer or standalone model server | HTTPRoute (models-gateway or custom Route) → Envoy → vLLM service | vLLM standalone server or KServe transformer; supports LLM model families (Llama, Mistral, etc.) | vLLM component analyses; observed in models-gateway ingress |
| **External Model Provider Integration** | Praxis AI, ExternalModel CRs, ai-gateway-payload-processing, Istio ServiceEntry/DestinationRule, external providers (OpenAI, Bedrock, Azure OpenAI) | HTTPRoute (praxis-gateway) → Envoy → Istio ServiceEntry (external provider endpoint) | External API (OpenAI GPT, Bedrock Claude, Azure OpenAI, etc.) with Praxis routing/policy layer | Praxis AI component analysis; observed via ExternalModel CRs and DestinationRule objects |
| **Custom Model Server** | User-deployed model server pod (any image), optional kube-rbac-proxy sidecar, custom Service + Route | OpenShift Route or HTTPRoute (custom) → model server pod | User-provided container image with model loading and inference logic | Inferred from Notebooks and distributed workloads patterns; not explicitly modeled in component inventory |

All paths are **coexistent**—a cluster can run KServe-managed models, vLLM servers, external provider calls, and custom servers simultaneously. Routing decisions are made at the gateway layer (HTTPRoute matching hostname, path, headers); backend enforcement uses kube-auth-proxy for RBAC and optional Praxis PPE for policy. The platform does not mandate a single serving path, enabling gradual adoption and migration across runtimes.

### Critical Cross-Cutting Observations

1. **Ingress Architecture Dependency**: Nearly all user-facing services (odh-dashboard, model endpoints, training APIs) depend on the multi-gateway architecture. A failure in Envoy or kube-auth-proxy sidecars affects multiple workflows simultaneously. The platform provides no explicit circuit breakers or fallback ingress paths; downtime in the gateway tier cascades to all downstream consumers.

2. **Webhook Validation Criticality**: 213 webhooks validate and mutate CRs across the platform. A single validating webhook with a bug (e.g., rejecting valid CRs) can block all deployments of that resource type. Webhook timeout (10 seconds default) or unavailability triggers admission failures; no "warning only" mode for webhooks. Platform stability depends on webhook server availability and correctness.

3. **Secret Reference Complexity**: Model servers, external providers, artifact stores, and auth proxies all reference Secrets (API keys, TLS certs, database passwords). Secret rotation and version updates require coordinated restarts across multiple components. No explicit secret versioning or rotation framework is observed in this generation.

4. **Operator Update Orchestration**: Updating multiple interdependent operators (e.g., RHODS → KServe → KubeRay) requires careful coordination to avoid transient compatibility issues. The platform relies on OLM's installplan approval workflow; no explicit orchestration for multi-operator updates is observed.

5. **Resource Quota Management**: User namespaces lack explicit resource quotas by default. A single user workload (large training job) can exhaust cluster resources, affecting all other users. The platform relies on HPA limits and optional RBAC network policies; no cluster-wide quota enforcement is observed.
