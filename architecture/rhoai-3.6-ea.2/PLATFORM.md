## Platform Overview

RHOAI 3.6-ea.2 is an operator-led OpenShift AI platform assembled from 91 analyzed components. `rhods-operator` is the platform control root: it reconciles the platform CRs, component modules, shared gateway resources, admission webhooks, RBAC, and supporting services. The platform also includes KServe-based predictive and LLM serving, MaaS APIs, notebook and pipeline workflows, distributed training, observability, and optional AI gateway/ext-proc data planes.

Ingress is in transition. The platform operator creates Gateway API/HTTPRoute resources and an authenticated gateway stack while retaining OpenShift Routes for legacy redirects and gateway-mode traffic (`rhods-operator` Architectural Analysis; `internal/controller/services/gateway/resources/envoyfilter-authn.tmpl.yaml:1-127`). MaaS uses `maas-default-gateway` with a Gateway AuthPolicy for API-key, Kubernetes TokenReview, and optional OIDC JWT authentication (`models-as-a-service` `maas-controller/pkg/controller/maas/maasauthpolicy_controller.go:989`). Gateway-level authentication is distinct from backend `kube-rbac-proxy` and application authorization.

The security posture is layered: Kubernetes service-account/RBAC control planes, TLS admission endpoints, gateway policy and Envoy filters, service-account token or mTLS checks, and component/application policies. Source evidence also shows FIPS-oriented operator builds and non-root/read-only/drop-capability patterns for selected data-plane images. Supply-chain, disconnected-deployment, HA, and several runtime joins remain unresolved where the analyzer emitted only coverage placeholders.

### Ingress Analysis

RHOAI contains parallel ingress generations. The current platform gateway path is controller-created Gateway API plus HTTPRoutes and an Envoy authentication filter. The older OpenShift Route path remains for redirects and selected component overlays. The RHOAI source gate confirms the authentication wiring: `rhods-operator/internal/controller/services/gateway/resources/envoyfilter-authn.tmpl.yaml:15-45` inserts `envoy.filters.http.ext_authz` for gateway workloads and calls `https://<kube-auth-proxy>.<gateway-namespace>.svc:<https-port>/oauth2/auth`; the same template permits cookie and Authorization input and forwards identity/access-token headers. `kube-auth-proxy` source/tests confirm bearer-token TokenReview fallback and OAuth/OIDC cookie flows. This is an observed gateway-level chain, not evidence that every backend uses the same auth mechanism.

MaaS is a separate, more specific composition. Its controller creates `maas-api-route` and AuthPolicy resources; the structured evidence identifies API-key, TokenReview, and optional OIDC JWT authentication. Praxis and AI Gateway overlays target `maas-default-gateway` with Envoy ext-proc filters, per-route disable rules for non-inference MaaS API paths, and TLS clusters to port 9004. These are source-backed integration relationships, while exact runtime activation depends on the selected overlay and gateway labels.

KServe, notebooks, model registry, workbenches, llm-d, and optional services contribute additional routes. Several records intentionally say “Gateway-selected,” “deployment-defined,” or “runtime-dependent”; those are retained as candidate/unresolved joins rather than negative findings.

## Platform Architectural Analysis

The platform’s central architectural tension is the coexistence of a shared, authenticated Gateway API ingress model with legacy OpenShift Routes and capability-specific provider gateways. This enables migration and independent component deployment, but it leaves route ownership, gateway selection, and authentication composition deployment-sensitive. Missing dependency edges must not be read as absence: generated manifests, selectors, runtime labels, and overlays often carry the join.

Authentication is intentionally layered rather than uniform. The RHOAI data-science gateway has a source-resolved Envoy `ext_authz` → `kube-auth-proxy` `/oauth2/auth` chain, while MaaS uses Kuadrant/Authorino AuthPolicy and backend identity checks. KServe/notebooks may add pod-side `kube-rbac-proxy`, and model registry uses Istio source-principal/JWT policies. These layers have different owners, credentials, failure behavior, and feature-assessment implications.

The ext-proc design is powerful but tightly coupled to gateway labels, filter ordering, route names, Istio versions, and certificate trust. Praxis documents pre-auth fail-open and post-auth fail-closed stages. MaaS TLS overlays explicitly use `insecureSkipVerify` for gateway-to-service transport, and IPP/Praxis defaults include development-oriented plaintext or self-signed modes. These are deployment controls requiring release-profile verification, not evidence of a universal platform weakness.

Evidence limitations are material. `dockerfiles` is empty; special-topic coverage for disconnected deployment, high availability, supply chain, and many ingress rows is unresolved; webhook enrichment lacks overlay membership, enable conditions, handler data reads, and cross-cutting classification. Consequently, platform maturity claims must remain bounded to observed source and structured inventory.
