## Purpose

**Short**: The vllm-orchestrator-gateway is an HTTP gateway service that provides OpenAI-compatible chat completion endpoints with configurable detector-based content filtering and safety policies.

**Detailed**: vllm-orchestrator-gateway acts as a routing and filtering layer between clients and the FMS Guardrails Orchestrator. It accepts OpenAI-compatible chat completion requests on dynamically configured endpoints (one per configured safety policy), transforms those requests to include detector specifications, and forwards them to the orchestrator. The gateway enforces content safety by running input and output detectors and optionally returning fallback messages when detections occur. This enables drop-in replacement of unguardrailed chat completion endpoints with safety-guarded equivalents without requiring changes to client code. The component supports both streaming and non-streaming request modes, mTLS for secure communication with the orchestrator, and custom CA certificate validation.

## Architectural Analysis

vllm-orchestrator-gateway is a lightweight Rust-based proxy that transforms chat completion requests with safety constraints. Its core responsibilities are request routing (based on configured pipelines), detector injection (adding safety parameters to the forwarded request), and response filtering (optionally replacing content if detections occur). 

The architecture is request-flow-centric: requests arrive at dynamically registered endpoints (e.g., `/pii/v1/chat/completions`, `/passthrough/v1/chat/completions`), each tied to a route configuration that specifies which detectors apply. The gateway reads a YAML configuration file at startup that defines the orchestrator location, available detectors, and route definitions. For each configured route, it registers an Axum HTTP route handler. Request payloads are intercepted, enriched with detector specifications, and forwarded to the orchestrator. Responses flow back through the same handler, which applies fallback message substitution if safety detections occurred.

The component demonstrates several architectural patterns: 
- **Configuration-driven routing**: routes are not hard-coded but generated from a YAML config, enabling multi-tenancy via route-based isolation.
- **Protocol bridging**: it bridges OpenAI-compatible clients to the internal FMS Guardrails Orchestrator API (`/api/v2/chat/completions-detection`).
- **Streaming transparency**: handles both streaming (SSE) and non-streaming response modes transparently, parsing and filtering SSE chunks when needed.
- **Credential pass-through**: forwards authorization headers from clients to the orchestrator, enabling credential delegation.
- **mTLS support**: can load and use client certificates for mutual TLS with the orchestrator if `/etc/tls/private/tls.{crt,key}` exist.

Notable design choices: the gateway does not validate detector outputs deeply; it only checks for the presence of detections and substitutes a fallback message if configured. The actual detection logic and detector chain composition is delegated entirely to the orchestrator.
