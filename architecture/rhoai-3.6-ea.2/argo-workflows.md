## Purpose

**Short**: Argo Workflows is a container-native workflow engine that schedules and manages parallel, DAG, and step-based jobs on Kubernetes.

**Detailed**: The repository defines the Argo Workflow CRDs and supplies the workflow-controller, argo-server, and argoexec executables. The controller watches workflow resources and creates/manages Kubernetes workload resources, while argo-server exposes HTTP and gRPC APIs for workflow submission, observation, artifact access, events, templates, and authentication.

The RHOAI checkout contains downstream `rhoai/` image definitions plus Konflux Dockerfiles for the executor and controller. The declarative installation is Kustomize-based and supports cluster-wide and namespace-scoped RBAC variants. Workflow artifacts can use Kubernetes resources and external object stores through the Go dependency set; the analyzer directly establishes Kubernetes API connectivity but not every optional artifact backend at runtime.

## Architectural Analysis

This is a two-workload control plane: `workflow-controller` reconciles workflow state and launches executor pods, while `argo-server` provides the user/API surface. The API model is Kubernetes-native: seven namespaced workflow-related CRDs and one cluster-scoped `ClusterWorkflowTemplate` are installed from the minimal CRD set. The server combines generated gRPC services with an HTTP gateway, static UI, artifact handlers, metrics, OAuth callbacks, and pprof endpoints.

The repository provides both cluster-install and namespace-install modes. Cluster mode grants the controller and server broad cross-namespace permissions; namespace mode constrains their Roles to one namespace. This makes the deployment choice a primary tenancy and blast-radius decision. No NetworkPolicy or ingress object is present in the analyzed manifests, so external exposure and network isolation are expected to be supplied by the consuming platform.

The downstream Konflux images are digest-pinned UBI 9 PQC runtime images, but compile Go statically with `CGO_ENABLED=0` and `-tags no_openssl`. This is materially different from the runtime server's TLS configuration: TLS is implemented in Go and can use generated or Secret-backed certificates, but build-time check-payload/FIPS compatibility is not established by these Dockerfiles.
