## Purpose

**Short**: Container-native workflow engine for orchestrating parallel jobs on Kubernetes via Custom Resource Definitions.

**Detailed**: Argo Workflows is a Kubernetes-native workflow orchestration system implemented as a CRD, enabling users to define multi-step computational pipelines as DAGs or sequential task sequences. The component consists of the workflow-controller (reconciles Workflow CRs, manages pod execution, handles artifact storage/retrieval) and argo-server (provides REST/gRPC APIs, web UI, authentication integration). It supports complex workflow patterns including loops, conditionals, retries, timeouts, resource quotas, and artifact management across multiple storage backends (S3, Azure Blob, GCS, etc.). The platform is widely adopted for machine learning, data processing, CI/CD, and infrastructure automation workloads.

## Architectural Analysis

Argo Workflows follows a classic Kubernetes operator pattern with clear separation of concerns: the workflow-controller watches Workflow CRs and orchestrates execution via pod creation and lifecycle management, while argo-server provides user-facing APIs and visualization. The implementation demonstrates FIPS-aware cryptography with explicit `GOFIPS140=v1.0.0` build flags and dynamic linking strategy, though InsecureSkipVerify is set in certain TLS configurations (tls.go:127), which represents a notable security consideration for environments requiring strict certificate validation.

The architecture supports multi-backend artifact storage through a pluggable abstraction layer, enabling workflow portability across cloud providers. RBAC is fine-grained, with workflow-controller requiring pod lifecycle permissions and namespace-scoped secret access, while argo-server exposes broader API permissions for workflow CRUD operations. The system uses HTTP/1.1 for artifact endpoints and HTTP/2 (gRPC) for service-to-service communication with unspecified encryption/auth (likely inherited from Istio or cluster networking).

Key architectural patterns: leader election via Kubernetes leases, health endpoints for container orchestration, metrics exposure on port 9090 for Prometheus integration, and event-driven execution through Argo Events integration. The component is designed as a shared service within a cluster, delegating multi-tenancy boundaries to Kubernetes namespace isolation and RBAC.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | RBAC per namespace (workflow-controller role scoped to argo namespace; argo-server role in argo namespace) | Kubernetes RBAC | Workflow-controller has cluster-wide pod permissions; namespace isolation relies on Kubernetes network policy to prevent cross-namespace communication |
| Data storage | Workflows stored in etcd per namespace; artifacts in shared storage backend (S3, etc.) with no tenant isolation | Kubernetes etcd, artifact storage backend | **Artifact backend has no native tenant isolation** — all tenants share the same S3 bucket, GCS bucket, or Azure blob storage; filtering must be application-level or bucket policy enforced externally |
| Network traffic | Service-to-service communication (controller to API server, pods to controller) unencrypted within cluster | Kubernetes NetworkPolicy (if configured), Istio mTLS (if enabled) | Default: no encryption between internal components; relies on platform network policy |
| Compute & resources | Pod resource requests/limits per step; no cross-namespace resource isolation | Kubernetes ResourceQuota per namespace | Resource quotas per namespace; controller itself not subject to per-tenant limits |
| Configuration & secrets | Secrets sourced from workflow namespace for artifact credentials, OAuth2 configs | Kubernetes Secrets | Secret access is namespace-scoped; argo-server needs get/create permissions on secrets to facilitate OAuth2 |
| API scoping | Workflow-controller watches all namespaces; argo-server APIs return workflows scoped to user's namespace context | RBAC / API filtering | Cluster-wide watch; API filtering depends on argo-server authorization layer |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Artifact storage (S3/GCS/Azure) | None (shared backend) | Artifact naming convention (e.g., workflow UID in path); no native row-level or bucket-level isolation |
| Kubernetes etcd | Per-namespace | Kubernetes API server RBAC |
| Workflow database (if archived workflows enabled) | Shared database | Database query filters on namespace |
| Leader election (Kubernetes Lease) | Shared (workflow-controller namespace) | Lease object namespaced to argo; no cross-tenant impact |

_Multi-tenancy assessment: Argo Workflows in its current deployment (single shared instance per cluster) relies entirely on Kubernetes namespace isolation for tenant separation. Artifact storage backends (S3, etc.) are shared across all namespaces, creating a cross-tenant risk if artifacts are not properly namespaced. Recommended practice: enforce artifact path prefixes per namespace (e.g., s3://bucket/<namespace>/<workflow-uid>/) and apply storage backend policies to prevent cross-namespace access._
| Artifact Backend (S3, GCS, etc.) | Configurable per deployment | Backend-level access control (IAM, bucket policies) |
| Argo Server API | Cluster (single instance serves all namespaces) | Bearer token or OIDC; no namespace scoping in gRPC/REST APIs |

**Multi-Tenancy Gap**: The argo-server gRPC/REST APIs expose all namespaces' workflows if a user has a valid token. Enforcement of namespace-scoped API access (e.g., via RBAC proxy or API gateway) is required for strict tenant isolation. The workflow-controller itself respects RBAC but does not implement per-tenant rate limiting or resource quotas.
