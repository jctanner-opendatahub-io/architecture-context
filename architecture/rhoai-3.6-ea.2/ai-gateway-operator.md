## Purpose

**Short**: A Kubernetes operator that manages AI Gateway sub-components for multi-tenant LLM inference and serving.

**Detailed**: 

The AI Gateway Operator is a module operator running under the OpenDataHub Operator framework. It reconciles the `AIGateway` custom resource to manage and coordinate the deployment of sub-components including the Batch Gateway Operator and Models as a Service (MaaS) controller. The operator handles multi-tenant LLM inference services with support for external model providers, batch processing, and tenant-scoped configuration. It vendors and deploys manifests from downstream sub-components (batch-gateway-operator, llm-d-async, llm-d-batch-gateway, models-as-a-service) and manages CRDs, RBAC, and cluster-wide validation webhooks for its managed components.

The operator delegates infrastructure concerns (gateway routing, network isolation) to the managed components while maintaining the principal integration surface: the `AIGateway` CR and its lifecycle management. It operates in a cluster-scoped context and coordinates namespace creation for application deployment.

## Architectural Analysis

The AI Gateway Operator follows a **three-tier composition pattern**:

1. **Platform Integration Layer**: Receives `AIGateway` CR and `DSCInitialization` lifecycle events from the parent opendatahub-operator
2. **Kustomize Rendering Layer**: Uses controller-runtime's kustomize action to render manifests from vendored sub-component directories (`config/manifests/batchgateway/`, `config/manifests/maascontroller/`)
3. **Component Management Layer**: Deploys rendered manifests and manages the lifecycle (creation, patching, deletion) of batch-gateway and MaaS sub-components

**Key architectural decisions**:

- **Vendored manifests**: Sub-component manifests are checked into the repo under `config/manifests/` and updated via `make get-manifests` (pinned by commit SHA in `hack/scripts/get-manifests.sh`). This eliminates dynamic manifest fetching and ensures reproducible builds.
- **Namespace scoping**: Applications are deployed to a namespace specified by `cfg.ApplicationsNamespace`, determined from the operator's config. The operator creates namespaces as needed.
- **CRD management**: The operator creates and manages CRDs for its managed components (LLMBatchGateway, MaaS-related CRDs, Tenant, Config, etc.), then patches them during reconciliation to track ownership.
- **RBAC escalation**: The operator must escalate RBAC to create/update ClusterRoles and ClusterRoleBindings for managed components. This is a high-privilege operation documented extensively in the controller's kubebuilder RBAC markers.
- **Component contracts**: The `AIGateway` CR defines `spec.batchGateway.managementState` and `spec.modelsAsAService.managementState` fields — these are component contracts defining which managed sub-components should be deployed (Managed) or removed (Removed).
- **Leader election**: Supports leader election for HA deployments (`LeaderElect: true`, `LeaderElectionID` from config).

**Operational concerns**:

- The operator uses managed fields stripping (via `libcache.StripUnusedFields()`) to reduce memory overhead in large clusters.
- It watches AIGateway CRs and DSCInitialization CRs at the cluster scope.
- Metrics service exposes HTTPS on port 8443 for Prometheus scraping; health probes use HTTP on port 8081.
- The operator must survive restarts while sub-components are reconciling — it uses finalizers to ensure cleanup.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | per-tenant RBAC (MaaS controller creates per-tenant roles); kube-rbac-proxy on MaaS endpoints | Kubernetes RBAC + Kubernetes API Server | MaaS validates tenant identity via MaaSAuthPolicy CRs; ai-gateway-operator doesn't directly enforce tenant isolation (delegates to MaaS) |
| Data storage | per-namespace secrets (MaaS stores tenant creds in namespace secrets); shared database with tenant column (MaaS backend) | MaaS controller + Kubernetes | Operator creates namespaces but doesn't enforce per-tenant storage quotas |
| Network traffic | NetworkPolicy optional (config/network-policy/ present but not deployed by default) | Kubernetes NetworkPolicy | Default-allow posture; no mandatory network isolation between tenants at operator level |
| Compute & resources | LimitRange per namespace (managed by MaaS); ResourceQuota (not visible in operator manifests) | Kubernetes | Operator doesn't explicitly create quotas; delegated to MaaS controller |
| Configuration & secrets | per-namespace Secrets (MaaS stores auth tokens, model credentials per Tenant) | Kubernetes namespace isolation | Secrets are per-namespace; validation webhook ensures consistent MaaSAuthPolicy configuration |
| API scoping | namespace-scoped watches for Tenant, AITenant, MaaSAuthPolicy, MaaSSubscription | MaaS controller (not operator) | Operator watches cluster-scoped AIGateway CRs; tenancy enforcement happens in MaaS sub-component |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| MaaS backend database | per-tenant row filtering (tenant_id column) | Application query filter in MaaS controller |
| External model providers | per-provider credentials (ExternalProvider CRs per namespace) | RBAC + Kubernetes namespace isolation |
| Batch processing (LLM-D) | per-LLMBatchGateway instance (cluster-scoped) | Namespace scoping in batch job submissions (delegated to batch-gateway-operator) |

**Tenancy summary**: The operator itself is single-tenant (one AIGateway CR per cluster); multi-tenancy is delegated to the MaaS controller via managed Tenant and AITenant CRs. The operator creates deployment namespaces but does not explicitly enforce tenant isolation — Kubernetes RBAC and MaaS's application-level filtering provide the boundaries.
