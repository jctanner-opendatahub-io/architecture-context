## Purpose

**Short**: RHODS Operator is the primary platform operator for Red Hat OpenShift AI (RHOAI), responsible for orchestrating all component lifecycles, platform configuration, and ingress infrastructure.

**Detailed**: RHODS Operator manages the deployment, configuration, and lifecycle of all RHOAI components including KServe (model serving), Ray (distributed computing), Kueue (job queueing), Dashboard, Workbenches, AI Pipelines, Model Registry, and TrustyAI. The operator defines the platform's tenancy model through the `DataScienceCluster` and `DSCInitialization` CRs, manages platform-wide services including OIDC authentication, gateway infrastructure (Gateway API with Envoy), and networking. It also includes a Cloud Manager controller (`cloudmanager`) that provisions cloud-based Kubernetes clusters on Azure, CoreWeave, and AWS, managing their dependencies.

## Architectural Analysis

RHODS Operator is a complex, multi-faceted platform controller that spans three major responsibilities:

1. **Component Orchestration**: Reconciles 15+ platform components via a modular handler architecture, where each component (dashboard, kserve, ray, etc.) has dedicated controller logic. The component lifecycle is managed through kustomize manifests stored in `opt/manifests/`.

2. **Platform Infrastructure**: Deploys and maintains the platform's ingress infrastructure (Gateway API + Envoy), OIDC authentication via kube-auth-proxy, certificate management, and namespace-scoped tenancy boundaries. The gateway infrastructure is dynamically generated via templates (`.tmpl.yaml`) and reconciles against GatewayConfig CR settings.

3. **Cloud Infrastructure Management**: The CloudManager sub-controller (separate binary `cloudmanager`) implements infrastructure-as-code for cloud clusters on Azure and CoreWeave, managing dependencies like cert-manager, Gateway API, and Sail Operator.

**Key Design Patterns**:

- **Modular component handlers**: Each component (datasciencepipelines, kueue, ray, trustyai) is isolated in its own controller package with dedicated watches, RBAC, and resource templates.
- **Dynamic resource generation from templates**: Ingress resources, proxy deployments, and component-specific manifests are generated at reconciliation time from `.tmpl.yaml` files, allowing parameterization by GatewayConfig and DSC CR settings.
- **Named watch predicates**: Controllers watch specific namespaces (e.g., `models-as-a-service`, `kuadrant-system`) by name rather than broad label selectors, reducing watch cardinality.
- **Webhook validation and defaulting**: 13 webhooks (10 observed in source, 3 in manifests) enforce API correctness and default values for DataScienceCluster, DSCInitialization, and component CRs.
- **FIPS-hardened build**: The operator binary is built with `CGO_ENABLED=1 GOEXPERIMENT=strictfipsruntime` and dynamically linked against OpenSSL, passing Konflux `check-payload` validation.

**Multi-Tenancy Model**: 
- Tenant boundary is per-namespace or per-CR, delegated to component CRDs which are cluster-scoped.
- Platform applications (dashboard, workbenches) are deployed to an applications namespace (default: `opendatahub` in ODH, `rhods-notebooks` in RHOAI).
- RBAC isolation is enforced by Kubernetes (namespace-scoped ClusterRoles + RoleBindings per namespace), not by application code.
- Auth is delegated to platform auth service (kube-rbac-proxy + OIDC) in front of component services.

**Risks**:
- **Dynamic resource generation**: Large numbers of `.tmpl.yaml` files with templated values ({template-value}) introduce runtime dependency risk if template substitution fails.
- **Conditional controller behavior**: Some controllers watch CRDs dynamically (unresolved watch predicates in analyzer), making the set of watched resources data-dependent rather than static.
- **Shared ClusterRole inheritance**: Component-level RBAC rules are scattered across many manifests (dashboards-editor-role, kserve-viewer-role, etc.), each requiring manual audit.

## Multi-Tenancy

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| Tenant boundary | Per-namespace (primary); per-CR (component-specific CRDs are cluster-scoped) | api/datasciencecluster/v1/datasciencecluster_types.go (DataScienceCluster is cluster-scoped); api/dscinitialization/v1/dscinitialization_types.go (DSCInitialization is cluster-scoped); api/infrastructure/v1/hardwareprofile_types.go (HardwareProfile is namespaced for resource scoping) |
| Deployment model | Multi-tenant cluster with namespace-scoped applications; platform operator is single-tenant (one cluster-wide DataScienceCluster) | One DataScienceCluster CR per cluster (enforced by operator); applications deployed to single applications namespace (opendatahub / rhods-notebooks); workbenches deployable to custom workbench namespace |
| Tenant identifier | Kubernetes namespace (for workbenches and user namespaces); DataScienceCluster CR name (single per cluster) | inferred from DSCInitialization spec.applicationsNamespace and workbenches workbenchNamespace (immutable) |

**Multi-Tenancy Summary**: The platform is primarily **single-tenant at the cluster level** (one DataScienceCluster per cluster) but **multi-tenant at the namespace level** (workbenches and user applications in separate namespaces). Tenancy is delegated to component operators and Kubernetes namespace isolation, not enforced by the platform operator itself.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | per-tenant RBAC (component-scoped roles like dashboard-editor-role) + kube-rbac-proxy (platform auth sidecar) | Kubernetes RBAC + kube-auth-proxy sidecar (auth delegated to OIDC provider) | No per-namespace service accounts for user workloads; auth relies on OIDC token validation in proxy. Gap: if OIDC provider is shared across multiple Kubernetes clusters, tokens could be reused across clusters. |
| Data storage | Per-namespace PVC (workbenches, notebooks); per-application database (component-specific) | Kubernetes PersistentVolumeClaim namespace scoping | Minimal risk: component data isolation is delegated to each component operator. Some components may share backend (e.g., shared Model Registry DB) — review component-specific isolation. |
| Network traffic | None explicitly configured by operator (delegated to NetworkPolicy or Istio/Envoy) | Operator deploys platform gateway + HTTPRoutes, but does not create NetworkPolicy by default. GatewayConfig can optionally enable NetworkPolicy for kube-auth-proxy. | Gap: No default NetworkPolicy between tenant namespaces. Operators recommend: manual NetworkPolicy creation per namespace for workload isolation. |
| Compute & resources | No ResourceQuota or LimitRange deployed by operator; delegated to cluster administrator or component operators | Kubernetes ResourceQuota + LimitRange (if configured by admin) | Gap: Operator does not enforce per-namespace resource quotas. Cluster admin must configure; vulnerable to resource starvation if quotas not set. |
| Configuration & secrets | Per-namespace Secrets (GatewayConfig, component auth secrets) + shared ConfigMap (component manifests in opt/manifests/) | Kubernetes Secret namespace scoping | Minimal risk: ConfigMaps are operator-internal; user Secrets are namespace-scoped. Component-level Secrets (image pull secrets, auth credentials) are responsibility of component operators. |
| API scoping | Cluster-scoped watches (DataScienceCluster, GatewayConfig, Platform CRs are not namespaced); component-scoped watches via named watch predicates on specific namespaces (models-as-a-service, kuadrant-system) | Kubernetes API scope enforcement + controller-runtime watch predicates | Gap: Cluster-scoped CRDs allow any admin to view platform configuration. Named watch predicates on specific namespaces reduce blast radius but introduce fragility (hardcoded namespace names). |

**Shared Services**: 
- **Model Registry**: Potentially shared across tenants (cluster-scoped ModelRegistry CR); if backend database is shared, requires row-level filtering by component.
- **Prometheus**: Single cluster-wide monitoring stack (if configured); metrics from all components visible to monitoring namespace RBAC holders.
- **Kueue**: Cluster-wide job queueing; queue isolation is delegated to Kueue controller and workqueue configuration.

### Tenancy Risks & Observations

1. **No per-namespace resource quotas**: Operator does not deploy ResourceQuota; cluster admin must configure. Risk: noisy neighbor (one workload consumes all cluster resources).
2. **Shared component backends**: Model Registry, Kueue, Ray, and other components may use shared database or cache. Risk: data leakage if component isolation is weak.
3. **Hardcoded namespace watches**: Controllers watch specific namespaces by name (models-as-a-service, kuadrant-system), not by label. Risk: if namespace names change or new namespaces are added, watches must be updated in code.
4. **Cluster-scoped Platform CRs**: DataScienceCluster and GatewayConfig are cluster-scoped, allowing any cluster admin to view/modify platform configuration. This is by design (one platform per cluster), but limits multi-tenancy at the cluster admin layer.
5. **OIDC token reuse across clusters**: Auth is delegated to OIDC provider (e.g., Keycloak) via kube-auth-proxy. Risk: if tokens are not cluster-specific, they could be reused across clusters.
