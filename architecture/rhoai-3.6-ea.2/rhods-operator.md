## Purpose

**Short**: Reconciles the RHOAI platform configuration and component lifecycle, including cluster APIs, authentication, gateway ingress, monitoring, and optional component operators.

**Detailed**: `rhods-operator` is the cluster-scoped control plane for RHOAI. It watches `DataScienceCluster`, `DSCInitialization`, `Platform`, `GatewayConfig`, `Auth`, component-management CRs, and supporting Kubernetes objects, then creates or updates the resources needed by enabled platform capabilities. The repository contains both the main controller manager and a cloud-manager command for infrastructure-related APIs.

The operator also owns the RHOAI 3.x ingress transition. Gateway API and HTTPRoute resources are paired with a kube-auth-proxy/Envoy-oriented gateway stack, while OpenShift Routes remain for gateway-mode and legacy redirect traffic. The operator exposes health/readiness endpoints, a TLS webhook server, and secure metrics, with Kubernetes RBAC and admission webhooks providing the primary authorization and validation boundaries.

## Architectural Analysis

This is a platform operator rather than a single workload operator: one manager coordinates many independent component handlers and shared services. Cluster-scoped platform CRs select enabled capabilities, while namespaced `HardwareProfile` resources provide the principal namespaced API surface. The controller deliberately watches secrets, namespaces, services, deployments, RBAC objects, and gateway resources so that changes to generated infrastructure converge back to the desired platform state.

The gateway implementation is a migration boundary. Main component traffic uses Gateway API HTTPRoutes and an authenticated proxy service, but the repository also creates OpenShift Routes for gateway mode and legacy URL redirects. Template values are resolved at reconciliation time, so concrete hostnames, ports, names, and some TLS settings are not statically knowable from the analyzer inventory.

The release build path is designed for FIPS: Konflux uses a digest-pinned UBI builder, `CGO_ENABLED=1`, `GOEXPERIMENT=strictfipsruntime`, and a `strictfipsruntime` build tag; the RHOAI Dockerfile uses strict FIPS tags and a UBI runtime. Runtime TLS is centrally configured with TLS 1.2 minimum and the OpenShift intermediate cipher profile when a cluster TLS profile is available. The remaining supply-chain limitation is that RPM locking is present but Hermeto/artifact-lock evidence was not established by the analyzer.
