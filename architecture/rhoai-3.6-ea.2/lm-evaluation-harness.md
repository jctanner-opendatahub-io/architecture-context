## Purpose

**Short**: Provides a unified command-line and Python framework for evaluating language models against standardized and custom benchmarks.

**Detailed**: `lm_eval` loads local or hosted language models and runs them against a broad catalog of academic and product evaluation tasks, producing metrics and optional samples/results. It supports Hugging Face Transformers, vLLM-compatible endpoints, commercial model APIs, adapters, and custom task definitions (`README.md:37-51`, `pyproject.toml:21-47`).

In RHOAI this checkout is packaged as the LMEval batch runtime. The image prepares writable Hugging Face, output, custom-task, and Unitxt catalog directories, then starts Python as an unprivileged UID; the evaluation command and its arguments are supplied by the workload invoking the image (`Dockerfile.konflux.lmes-job:18-42`). It is a workload runtime rather than a long-running control-plane service: analyzer discovery found no CRDs, workloads, Services, ingress routes, HTTP server registrations, or gRPC registrations.

## Architectural Analysis

The component is a library-plus-runner architecture. `lm_eval.__main__:cli_evaluate` is exposed through both `lm-eval` and `lm_eval` console scripts, while the container CMD starts the Python interpreter so a batch workload can invoke the module or a script (`pyproject.toml:56-58`, `Dockerfile.konflux.lmes-job:41-42`). Evaluation behavior is extended through model adapters, task YAML/Python modules, metrics, and optional dependency groups rather than through Kubernetes APIs.

The Konflux path is accelerator-aware and multi-architecture: CPU and CUDA base images are selected through build arguments, and the image installs the package with API, ifeval, math, and IBM watsonx extras (`.konflux/base-images.conf:1-2`, `Dockerfile.konflux.lmes-job:1-21`). A legacy Dockerfile remains as a separate build path with architecture-specific Arrow, PyTorch, and OpenBLAS compilation (`Dockerfile.lmes-job:5-24`, `Dockerfile.lmes-job:33-166`). This creates a clear product-build path alongside a more self-contained legacy build, with dependency reproducibility stronger in the legacy path because it installs `requirements.txt` explicitly.
