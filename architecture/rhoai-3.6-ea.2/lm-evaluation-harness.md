## Purpose

**Short**: A framework for evaluating language models against standardized academic benchmarks, integrated into RHOAI's evaluation pipeline for batch-oriented model assessment.

**Detailed**: The Language Model Evaluation Harness (`lm-eval`) is a unified framework that enables comprehensive evaluation of large language models against over 60 standard academic benchmarks with hundreds of subtasks and variants. Sourced from the upstream EleutherAI project and maintained downstream by Red Hat Data Services, it provides support for models loaded via HuggingFace transformers, vLLM, commercial APIs (OpenAI, IBM WatsonX), and local evaluation backends. The component integrates with RHOAI's evaluation hub (`eval-hub-sdk`) to expose standardized evaluation workloads, enabling one-shot batch execution of model tests with configurable task selection, few-shot settings, output post-processing, and custom metrics. The Konflux-built container image (`rhoai/odh-ta-lmes-job-rhel9`) serves as a secure, isolated runtime for ephemeral evaluation jobs, including built-in support for Unitxt task card framework and offline dataset evaluation.

## Architectural Analysis

The lm-evaluation-harness represents a **batch-oriented evaluation workload** rather than a long-running service. Its architecture is **stateless and composable**:

1. **Entry Points**: Multiple entry points are defined (CLI `lm-eval`/`lm_eval` console scripts, Dockerfile CMD for container execution, and `main.py` for EvalHub integration). The primary production path is through `main.py`, which accepts a job specification JSON file defining the benchmark(s), model, and parameters. This design decouples evaluation configuration from the container image, enabling dynamic task selection at job submission time.

2. **Dependency Composition**: The component depends on 100+ PyPI packages organized into optional feature groups (`api`, `ifeval`, `math`, `ibm_watsonx_ai`), plus large ecosystem libraries (transformers, torch, accelerate, datasets, peft). The `poetry.lock` file ensures reproducible builds. The Dockerfile installs optional feature groups (`api`, `ifeval`, `math`, `ibm_watsonx_ai`) for maximum task and model coverage, including support for mathematical reasoning (sympy, antlr4), IBM WatsonX inference, and remote code evaluation (langdetect).

3. **Non-Kubernetes Nature**: Unlike typical RHOAI controllers or operators, lm-evaluation-harness does not define or watch Kubernetes CRDs, ClusterRoles, Services, or Ingress resources. It is a **library component packaged as a batch container**, not a controller. Kubernetes integration (Job dispatch, ConfigMap/Secret handling, result persistence) is handled by external orchestration (the EvalHub adapter in `main.py` or upstream Kubernetes job templates).

4. **Build & Artifact Strategy**: The component uses multi-architecture Dockerfiles with build-arg templating (CUDA_BASE_IMAGE, CPU_BASE_IMAGE). The Konflux variant (`Dockerfile.konflux.lmes-job`) adds RHEL integration, UBI base images, and artifact retrieval. It does **not** use AIPCC base images; instead, it uses UBI base images with system-provided Python 3.12. This represents a gap in AIPCC ecosystem adoption for Python workloads.

5. **Credential & External Integration**: The container expects environment variables for external integrations (HF_TOKEN for HuggingFace Hub, ANTHROPIC_API_KEY for Anthropic models, WATSONX_API_KEY for IBM services, OPENAI_API_KEY for OpenAI, AWS_SECRET_ACCESS_KEY for S3). No embedded credentials or secrets; all are runtime-provisioned. Outbound HTTPS communication is established to datasets-server.huggingface.co and AWS S3-compatible storage.

6. **Offline & Air-Gap Support**: The `main.py` adapter includes explicit support for disconnected environments. Before importing lm_eval, it checks for offline HuggingFace datasets and tokenizers under `/test_data`, enabling evaluation jobs to run without internet access. This is critical for disconnected OpenShift clusters.

## Architecture Synthesis Notes

**Key Observations**:

1. **Batch-Oriented Design**: Unlike controllers or operators, lm-evaluation-harness is a stateless, ephemeral workload. Each execution is independent; there is no persistent state management or long-running daemon. Jobs are invoked via container entrypoint with configuration passed through JSON specs and environment variables.

2. **No Kubernetes APIs**: The component defines zero CRDs, Services, Ingress resources, or workload controllers. It is a **pure Python library packed as a container**, not a Kubernetes-native operator. Kubernetes integration (Pod/Job creation, Secret handling, result persistence) is delegated to EvalHub orchestration.

3. **AIPCC Adoption Gap**: The component installs 100+ Python packages but does **NOT use AIPCC base images**. This is a supply chain risk because:
   - No RHEL AI Python Package Index integration (no pre-configured pip.conf or vendor repos)
   - No `/usr/libexec/rhaipcc/dnf` or `/etc/rhaipcc/env` support for additional RPM installs
   - No Hermeto/cachi2 lockfile support for offline-capable, reproducible builds
   - **Recommendation**: Migrate to AIPCC base images (coordinate with overlay 0017) and add rpms.lock.yaml + Hermeto integration for downstream release branches.

4. **Offline-First Design**: The `main.py` adapter explicitly supports air-gapped clusters by pre-loading HuggingFace datasets and tokenizers from `/test_data` mounted volumes, with path-traversal protection (CWE-22). This is a strong architectural choice for restricted/disconnected environments.

5. **Credential Injection**: All external credentials (HF_TOKEN, OPENAI_API_KEY, ANTHROPIC_API_KEY, WATSONX_API_KEY, AWS_SECRET_ACCESS_KEY, REGISTRY_PASSWORD) are injected via environment variables at runtime. No secrets are embedded in the image. This follows security best practices but requires careful Secret management and rotation in Kubernetes.

6. **Multi-Model Support**: The framework supports local inference (Transformers, vLLM, DeepSpeed with quantization), remote APIs (OpenAI, Anthropic, IBM WatsonX), and custom adapters through a pluggable model adapter pattern. This modularity enables dynamic model and task selection at job submission time without image rebuilds.

7. **Result Reporting**: Evaluation results are reported via HTTP(S) callback to an external EvalHub service (URL provided in job spec), enabling asynchronous, distributed job processing and result aggregation across RHOAI.

8. **Hermeticity**: The component achieves **partial hermeticity** via `poetry.lock` (100% of Python dependencies pinned). However, OS packages are not pinned (no rpms.lock.yaml), and Hermeto artifact prefetching is not used. Downstream release branches must add these layers for full offline-capable builds.

9. **Multi-Architecture Support**: Dockerfiles use `TARGETARCH` templating (amd64, arm64, ppc64le, s390x) with conditional base image selection (CUDA_BASE_IMAGE for GPU, CPU_BASE_IMAGE for CPU-only), enabling deployment across diverse Red Hat hardware platforms.
