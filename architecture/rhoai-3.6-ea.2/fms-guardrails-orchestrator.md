## Purpose

**Short**: REST API orchestrator that coordinates AI text generation with safety guardrails by mediating between clients and language models through content safety detection, filtering, and secure text generation.

**Detailed**: The FMS Guardrails Orchestrator (fms-guardrails-orchestr8) is a middleware service that acts as a REST API gateway for managing AI guardrails in text generation workflows. It orchestrates multiple downstream services—detector services (for content safety analysis), chunker services (for text segmentation), and text generation services (for LLM backends)—through unified APIs. The orchestrator handles classification of input/output text, detection of harmful content, and streaming of generation results, while optionally enforcing TLS encryption and supporting header-based authentication passthrough. It is configured via YAML to manage the topology of downstream services and their connection parameters.

## Architectural Analysis

The guardrails orchestrator implements a hub-and-spoke pattern where it receives API requests from clients and routes them through a configurable pipeline of downstream services. The architecture emphasizes pluggability through configuration: detector services, chunker services, and generation backends are specified in a YAML configuration file, allowing operators to wire up different safety detection systems without code changes.

**Key Design Patterns**:
- **Service Mesh Adapter**: Acts as a mediator between frontends (clients) and backend safety/generation services, managing service discovery, timeouts, and health probes.
- **Configuration-Driven Topology**: Downstream services are defined declaratively in `config/config.yaml`, enabling runtime changes without recompilation.
- **Streaming Support**: Implements both unary (POST) and server-streaming (POST with streaming response) API patterns for real-time guardrail application.
- **Header Passthrough**: Supports forwarding client headers (e.g., request metadata, access tokens) to downstream services, enabling cross-service authentication and correlation.

**Cryptographic Approach**: The service uses Rust-native TLS via `hyper-rustls` (which defaults to the `ring` cryptographic provider) for optional server TLS and optional mTLS client authentication. It does **not** use FIPS-validated crypto providers—it relies on the pure-Rust `ring` library rather than OpenSSL, which means TLS is not validated under Konflux's check-payload gate for FIPS compliance. The presence of `openssl` in `Cargo.lock` (version 0.10.81) reflects transitive dependencies only; application-level TLS uses rustls/ring.

**Concurrency Model**: Built on Tokio (async runtime) with axum (web framework) and tonic (gRPC client library). Supports concurrent requests to downstream detectors and chunkers (configurable via `detector_concurrent_requests` and `chunker_concurrent_requests`, default 5 each).

**Deployment Footprint**: Containerized in UBI 9 minimal (post-quantum variant), requires Rust, OpenSSL dev libraries, and protoc for build-time code generation from protobuf definitions. Multi-architecture support: amd64, ppc64le, s390x (with dedicated Dockerfiles for each).

**Summary**: The application **does not use FIPS-validated cryptography**. It uses pure-Rust `rustls` with the `ring` cryptographic provider. While the container image includes OpenSSL (installed for build-time compatibility), the application does not link against it for TLS. This is a deliberate architectural choice: rustls provides memory safety guarantees that statically linked OpenSSL would not, but it sacrifices FIPS compliance. The `ring` library is not on the FIPS-validated algorithms list.
