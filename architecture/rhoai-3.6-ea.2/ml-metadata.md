## Purpose

**Short**: ML Metadata (MLMD) is a library and service for recording and retrieving metadata associated with ML developer and data scientist workflows.

**Detailed**: ML Metadata provides a central metadata store for ML pipeline artifacts, executions, and contexts. It tracks provenance relationships, enabling reproducibility and lineage analysis across ML workflows. The component includes both a Python library for programmatic access and a gRPC server for remote access to metadata storage backends (SQLite3 or MySQL). MLMD is a Google upstream project maintained in RHOAI for integration with OpenDataHub ML pipeline orchestration and KFP (Kubeflow Pipelines) integration.

## Architectural Analysis

ML Metadata functions as a dual-mode component:

1. **Python Library**: Provides programmatic access to metadata operations via `MetadataStore` class and protobuf-based APIs. The library wraps C++ extensions built with Bazel, enabling efficient binary serialization and database interactions.

2. **gRPC Server**: A standalone C++ binary (`metadata_store_server`) exposes the MetadataStoreService via gRPC on configurable ports, enabling remote metadata access over the network. The server is containerized across multiple variants (Fedora, RHEL UBI, Konflux).

3. **Type System**: Defines Artifact Types, Execution Types, and Context Types with schema evolution support. Types support custom properties with type validation and backward compatibility checks.

4. **Lineage Graph**: Tracks directed acyclic graphs of artifacts produced/consumed by executions within contexts. Supports both legacy GetLineageGraph (deprecated) and modern GetLineageSubgraph APIs with field masking for selective data retrieval.

5. **Transaction Semantics**: Implements optimistic concurrency control (OCC) and atomic multi-entity operations (PutExecution, PutLineageSubgraph) to ensure consistency across lineage updates.

6. **Multi-Tenancy Pattern**: Achieves logical tenant isolation via namespacing in application logic. No cluster-level RBAC or Kubernetes secrets; tenancy is application-enforced through context names and artifact filtering.

**Key Risks and Observations**:
- **C++ Core**: Performance-critical path written in C++ with Bazel build system. Requires careful version management during compilation.
- **gRPC Security**: Server does not implement built-in authentication; expects deployment-level auth (Istio, reverse proxy, mTLS sidecar).
- **Database Configuration**: No built-in encryption at rest; database security depends on backend (SQLite file permissions, MySQL connection TLS).
- **Python Binary Wheels**: Multi-platform wheels built via manylinux2010 Docker builds; platform detection in setup.py.

**gRPC Service Definition**: `ml_metadata/proto/metadata_store_service.proto` (1500+ lines)

**40+ RPC Methods** covering:
- Type management (Put/Get ArtifactType, ExecutionType, ContextType)
- Artifact operations (Put, Get, Filter by type, by URI, by external ID)
- Execution operations (Put, Get, Filter by type, by name)
- Context operations (Put, Get, Filter, parent/child relationships)
- Event/Edge management (lineage edges between artifacts and executions)
- Lineage traversal (GetLineageSubgraph with field masking)
- Batch operations (e.g., GetParentContextsByContexts, GetChildrenContextsByContexts)

### Protobuf Message Types

Core data model defined in `ml_metadata/proto/metadata_store.proto`:

| Message Type | Purpose |
|-----------|---------|
| Artifact | Entity representing ML pipeline outputs (models, datasets, metrics) with ID, type, properties, URI |
| Execution | Entity representing pipeline step runs with state, properties, timestamps |
| Context | Entity representing experiment/run grouping with hierarchical parent-child relationships |
| Event | Directed edge connecting Artifact to Execution (INPUT/OUTPUT) with timestamp |
| ArtifactType | Schema defining Artifact properties and constraints |
| ExecutionType | Schema defining Execution properties and constraints |
| ContextType | Schema defining Context properties and constraints |
| LineageGraph | DAG response combining artifacts, executions, contexts, events for provenance queries |

## Multi-Tenancy

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| Tenant boundary | Per-context or per-artifact (application-enforced) | ml_metadata/metadata_store/metadata_store.py and gRPC service definition |
| Deployment model | Single instance shared across logical tenants | Stateless gRPC server; database is shared |
| Tenant identifier | Context name or namespace prefix in artifact/context names | Application responsibility; no enforcement |

**Note**: ML Metadata provides **no built-in multi-tenancy enforcement**. Tenancy is entirely application-driven through naming conventions and query filtering.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Application-level (context/artifact name filtering) | Application code | Tenant isolation depends on query accuracy; no SQL-level row filtering |
| Data storage | Shared database with name-based filtering | Application / Database schema | No row-level security or database views per tenant |
| Network traffic | Kubernetes NetworkPolicy or Istio AuthorizationPolicy | Kubernetes / Istio | Deployment-dependent; no built-in isolation |
| Compute & resources | Kubernetes ResourceQuota on Deployment | Kubernetes | Deployment-dependent |
| Configuration & secrets | Shared config via environment variables or config file | Deployment | Single instance; config is not per-tenant |
| API scoping | Cluster-wide list operations; filtering in code | Application | GetArtifacts, GetExecutions return all results; filtering happens in client code |

**Multi-Tenancy Risk**: Without explicit row-level security or per-tenant views, logical isolation can fail if application code omits tenant filters in queries. Example: `GetArtifacts()` returns all artifacts across all tenants; application must filter by context name.

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Metadata database (SQLite/MySQL) | Schema/namespace per tenant (name-based) | Application query filtering |
