## Purpose

**Short**: ML Metadata (MLMD) records and retrieves metadata about machine-learning artifacts, executions, contexts, types, events, and lineage.

**Detailed**: The repository provides the `ml-metadata` Python package, backed by native C++ extensions and protobuf contracts. Clients use the package APIs or generated gRPC stubs to persist and query metadata associated with ML workflows.

It also builds `metadata_store_server`, a standalone C++ gRPC service. The server initializes or migrates a configured metadata store and exposes the `MetadataStoreService` API over port 8080 by default. Storage can be an in-memory/fake or SQLite store, or an external MySQL or PostgreSQL database selected through flags or a text-format protobuf configuration file.

## Architectural Analysis

MLMD separates the client-facing data model and generated protobuf APIs from storage-specific access objects. The C++ service implementation translates the gRPC service into metadata-store operations, while the Python package exposes native bindings and generated protobuf modules. The same service contract supports writes, typed metadata queries, pagination, associations, contexts, and lineage traversal.

The Konflux image uses a multi-stage UBI 9 build and a UBI 9 minimal PQC runtime, copies only the server binary and database connector sources into the runtime image, reinstalls `tzdata`, and runs as UID/GID 65534. The image is a standalone service artifact; this repository contains CI/build definitions but no Kubernetes workload or Service manifests.

The principal deployment risk is transport posture: the server explicitly starts with insecure gRPC credentials and enables TLS only when the configuration contains `ssl_config`. Database TLS is likewise configuration-driven. Consequently, secure deployment depends on supplying and protecting the configuration and certificate material through the consuming platform.
