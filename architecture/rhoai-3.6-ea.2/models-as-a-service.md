## Purpose

**Short**: Provides policy-controlled, tenant-aware model discovery, subscription, and API-key management for models served by KServe or external providers.

**Detailed**: Models as a Service (MaaS) combines a controller-runtime operator with the `maas-api` HTTP service. The controller reconciles tenant, model reference, subscription, authentication policy, external-model, and lifecycle resources; it deploys the API into the configured infrastructure namespace and creates the Gateway API and policy resources needed to expose model APIs.

The API serves OpenAI-compatible model discovery and subscription operations, API-key lifecycle operations, tenant discovery, health, and metrics. PostgreSQL stores API-key data, while Kubernetes resources and KServe `InferenceService` objects provide model and tenant metadata. Gateway API routes connect callers to the service; Authorino/Kuadrant or RHCL performs gateway authentication and injects validated MaaS identity and subscription metadata.

## Architectural Analysis

MaaS is a two-process control/data-plane design. The controller is cluster-aware and reconciles namespace-scoped tenant resources, shared Gateway API routing, certificates, policies, and the API deployment. The API is deliberately narrow in Kubernetes permissions: it reads only the named database Secret, uses TokenReview and SubjectAccessReview for caller validation, and watches the MaaS resources required for discovery and subscription selection.

The RHOAI 3.x deployment uses HTTPRoute rather than an OpenShift Route. The route sends model, subscription, API-key, and selected public API paths to the API backend, while the controller's tenant reconciliation can rename and retarget the route for per-tenant infrastructure namespaces. TLS is configurable and follows the OpenShift cluster TLS security profile. The TLS overlay encrypts gateway-to-API traffic but currently sets Istio `insecureSkipVerify: true` because the managed gateway path cannot yet receive the service-ca trust bundle; this is an explicit verification gap.

The release supports both operator-driven and Kustomize deployment paths and separates controller, API, monitoring, networking, policy, and CRD resources. The base manifests default to HTTP API and metrics for development, while the OpenShift TLS overlay enables HTTPS and service-ca certificates. The controller image also carries deployment templates for the API, payload processing, and auxiliary resources, making the controller a deployment orchestrator as well as a CR reconciler.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Gateway policy, TokenReview/SAR, namespace-scoped CRs, aggregated viewer/admin roles | Authorino plus Kubernetes and API code | API and gateway policy must remain aligned for identity/subscription headers |
| Data storage | Shared PostgreSQL configured by `maas-db-config`; MaaS API applies tenant/user context | Application/database | Shared database isolation is application-enforced; schema-level separation was not established |
| Network traffic | NetworkPolicies allow Gateway, Authorino, monitoring, and deployment namespace paths | Kubernetes NetworkPolicy | Deployment-namespace allowance is namespace-wide; Authorino namespace list must match installation |
| Compute & resources | Separate tenant/infrastructure namespace support; no tenant ResourceQuota/LimitRange found in core manifests | Controller/Kubernetes | Per-tenant quota and node isolation are not established by this component |
| Configuration & secrets | Per-namespace resources plus named database Secret RBAC | Kubernetes and controller | Shared database credential spans tenants where a shared API instance is used |
| API scoping | Namespace-scoped CRs, cached model/subscription references, explicit tenant discovery | Kubernetes cache and API auth code | Cluster-wide namespace/service reads are intentional and require careful SAR policy |
