## Purpose

**Short**: Models-as-a-Service provides a multi-tenant API gateway and policy management layer for model serving, enabling policy-driven access control, API key management, subscription handling, and authorization integration with Kuadrant/Authorino.

**Detailed**: MaaS is a comprehensive platform for managing model serving in RHOAI via a dual-component system:

1. **maas-controller**: A Kubernetes operator that reconciles AITenant, Tenant, MaaSAuthPolicy, MaaSSubscription, MaaSModelRef, ExternalModel, and Config CRDs. It provisions tenant-scoped Gateway API HTTPRoutes and drives per-tenant deployment of the maas-api service. The controller leverages Gateway API and Kuadrant's Authorino for per-tenant policy enforcement and credential validation while preventing credential exfiltration to model backends.

2. **maas-api**: A REST API service (Gin-based) that manages API keys, subscriptions, model metadata, and request routing. It exposes OpenAI-compatible endpoints (`/v1/models`, `/v1/subscriptions`, `/v1/api-keys`) and acts as the gateway for tenant traffic, enforcing credential stripping and optional external model delegation.

The architecture enforces strict multi-tenancy: each tenant operates in its own namespace with dedicated Gateway references, auth policies, and subscription management. Traffic flows through Gateway API listeners defined by network admins, with Authorino validating credentials and stripping authorization headers before forwarding to model backends (KServe InferenceServices or external providers).

## Architectural Analysis

Models-as-a-Service implements a **policy-driven, credential-aware multi-tenant platform** with clear separation of concerns:

**Core Design Decisions:**

1. **Gateway API as the Ingress Abstraction**: The system relies entirely on Gateway API (standard Kubernetes networking) rather than OpenShift Routes or ingress controllers. This allows operators to define Gateways (traffic entry points) separately from MaaS, delegating network provisioning to infrastructure admins.

2. **Credential Stripping as a Security Boundary**: A defining architectural principle is that user credentials (OpenShift tokens or API keys) must be validated by Authorino but never forwarded to model backends. This is enforced through Kuadrant 1.4.2+'s header manipulation capabilities. Without credential stripping, a compromised or malicious model service could exfiltrate and replay user credentials.

3. **Multi-Tenancy at the Kubernetes Namespace Level**: Each tenant (AITenant CR) bootstraps its own namespace with dedicated:
   - Service accounts and RBAC roles
   - MaaS API deployment (maas-api-{tenant-name})
   - Authorization policies (MaaSAuthPolicy)
   - Subscription management (MaaSSubscription)
   - Model references (MaaSModelRef)

   This creates a per-namespace blast radius and allows tenants to upgrade independently.

4. **Operator-Driven Tenant Provisioning**: The maas-controller watches AITenant CRs and automatically:
   - Creates the tenant namespace and RBAC
   - Provisions a per-tenant maas-api Deployment
   - Registers HTTPRoute rules with the shared Gateway
   - Syncs Authorization policies from Authorino configuration

   This automation eliminates manual deployment steps and ensures consistency.

5. **Dual HTTP Port Model**: The maas-api listens on multiple ports:
   - **Port 8443 (public, HTTPS)**: External traffic routed via Gateway API, validation delegated to Authorino
   - **Port 8080 (internal, HTTP)**: Kubernetes-internal health and metrics endpoints
   - **Port 9090 (metrics)**: Prometheus scraping

   This design isolates public endpoints (validated at the gateway) from internal management endpoints.

**Architectural Risks and Observations:**

- **Gateway Availability**: If the shared Gateway becomes unavailable, all tenant traffic is blocked. The system does not implement per-tenant fallback gateways or multi-gateway failover.
- **Authorino Dependency**: Credential validation is entirely delegated to Authorino. A misconfigured Authorino policy or version mismatch can silently allow or deny traffic. Testing and policy audits are critical.
- **PostgreSQL Hard Requirement**: In production, the system requires a PostgreSQL database for API key management. A database outage directly impacts key rotation and creation, disabling tenant onboarding.
- **HTTPRoute Rule Order Sensitivity**: The HTTPRoute rules are indexed and referenced by EnvoyFilter configurations. Adding, removing, or reordering rules requires careful coordination with the EnvoyFilter deployment to avoid traffic misrouting.
- **Per-Tenant Deployment Overhead**: Each new tenant adds a full Deployment, Service, RBAC, and config objects. At scale (100+ tenants), this can strain Kubernetes API and etcd.

**Key Integration Points:**

- **KServe InferenceService**: MaaSModelRef watches InferenceService status to discover available models and their endpoints. This creates a tight coupling to KServe's serving infrastructure.
- **Gateway API (data-science-gateway)**: All external traffic is routed through a cluster-wide Gateway named `data-science-gateway` (provisioned by network admins, not MaaS).
- **Kuadrant / Authorino**: Tenant authorization policies are authored as MaaSAuthPolicy CRs and translated into Authorino AuthPolicy resources for policy enforcement.
- **OpenShift API Server**: The maas-api queries `config.openshift.io/apiservers` to determine platform identity and OAuth settings.

**Authorization Model**: The system enforces three layers of authorization:

3. **Per-tenant Policies (MaaSAuthPolicy)**: Each tenant defines its own authorization rules (OIDC issuers, JWT validation, role mappings) translated into Authorino AuthPolicy resources.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-tenant RBAC (tenant-admin Roles created per namespace) + Authorino AuthPolicy per MaaSAuthPolicy | Kubernetes RBAC + Authorino (via Kuadrant) | Authorization policies are defined in MaaSAuthPolicy CRs; misconfiguration can leak tenants. Requires careful policy audit. |
| Data storage | Per-tenant PostgreSQL schema or row-level isolation via API key tenant-id scoping | PostgreSQL + application query filters | API keys and subscriptions are scoped by tenant ID; no schema-level isolation. If a SQL injection exists in key generation, cross-tenant data leakage is possible. |
| Network traffic | NetworkPolicy enforced per namespace (optional, tenant-controlled) | Kubernetes NetworkPolicy | Not enforced by default; tenants must author their own NetworkPolicies. A misconfigured or missing policy allows cross-namespace traffic. |
| Compute & resources | ResourceQuota per namespace (optional) | Kubernetes ResourceQuota | Not enforced by default; each tenant's Deployment may consume unbounded CPU/memory, impacting cluster stability. |
| Configuration & secrets | Per-tenant Secrets (including database credentials if per-tenant connections needed) | Kubernetes Secrets + application scoping | Secrets are namespace-scoped; a tenant admin cannot directly access another tenant's Secrets. However, maas-controller has cluster-wide access to all Secrets. |
| API scoping | Tenant-scoped CRD watches (AITenant, Tenant, MaaSAuthPolicy, MaaSSubscription all namespaced) | Kubernetes namespace scoping + controller filtering | Controllers watch namespaced resources; cluster-wide Config CR requires careful handling to avoid unintended cross-tenant effects. |

**Multi-Tenancy Strengths:**
- Namespace isolation is a strong boundary in Kubernetes; RBAC policies are enforced per namespace.
- Per-tenant maas-api Deployments allow independent upgrades and resource allocation.
- Authorino policies are tenant-scoped via MaaSAuthPolicy, preventing policy leakage.

**Multi-Tenancy Risks:**
- **Cluster-wide Config CR**: The single Config CR (cluster-scoped) affects all tenants. Misconfiguration can globally disable MaaS or change default providers for all tenants.
- **maas-controller Privileges**: The controller has cluster-wide permissions and can be a single point of compromise affecting all tenants.
- **Shared Gateway**: All tenants route through a single data-science-gateway. If the Gateway becomes unavailable, all tenants lose external access.
- **Database Isolation**: If a single PostgreSQL database is shared by all tenants (common for simplicity), SQL injection or application bugs can leak data across tenants. Row-level isolation via application logic (tenant ID filtering) is not as strong as schema-level isolation.

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| PostgreSQL database | row-level (tenant ID column) | Application query filtering (all queries include tenant ID in WHERE clause) |
| data-science-gateway (Gateway API) | shared (single gateway for all tenants) | HTTPRoute per tenant (each tenant's routes are isolated via Gateway rules) |
| Authorino | shared (single Authorino instance) | AuthPolicy per tenant (each MaaSAuthPolicy translates to per-tenant AuthPolicy) |

## Data Flows

### Flow 1: User Authenticates and Lists Models

| Step | Source | Destination | Port | Protocol | Encryption | Auth |
|------|--------|-------------|------|----------|------------|------|
| 1 | User client | data-science-gateway | 443 | HTTPS | TLS 1.3 | None (incoming) |
| 2 | Gateway listener | Authorino | 50051 | gRPC | mTLS (cert-manager) | Service account token |
| 3 | Authorino | PostgreSQL (optional, for policy metadata) | 5432 | TCP | TLS (optional) | Service account credentials |
| 4 | Authorino | data-science-gateway (validated token) | 8443 | HTTPS | TLS 1.2+ | Bearer token (with header stripped) |
| 5 | Gateway | maas-api pod | 8443 | HTTPS | TLS 1.2+ | Bearer token |
| 6 | maas-api | PostgreSQL | 5432 | TCP | TLS (optional) | Username/password (from secret) |
| 7 | PostgreSQL | maas-api | 5432 | TCP | TLS (optional) | (response) |
| 8 | maas-api | maas-api Service | 8443 | HTTPS | TLS 1.2+ | (internal response) |
| 9 | Gateway | User client | 443 | HTTPS | TLS 1.3 | Bearer token (response) |

**Flow Notes**: The user's credential is validated by Authorino at the gateway before reaching maas-api. The original Authorization header is stripped (per Kuadrant 1.4.2+ feature), preventing credential exfiltration to model backends. The maas-api receives a clean request and can safely forward to KServe or external providers without leaking the user's credential.

### Flow 2: User Runs Inference via External Model

| Step | Source | Destination | Port | Protocol | Encryption | Auth |
|------|--------|-------------|------|----------|------------|------|
| 1 | User client | Gateway | 443 | HTTPS | TLS 1.3 | Bearer token |
| 2 | Gateway | Authorino | 50051 | gRPC | mTLS | Service account token |
| 3 | Authorino | Gateway | 8443 | HTTPS | TLS 1.2+ | Validated token (header stripped) |
| 4 | Gateway | maas-api (routing to external model) | 8443 | HTTPS | TLS 1.2+ | None (user auth stripped) |
| 5 | maas-api | ExternalModel provider (OpenAI, etc.) | 443 | HTTPS | TLS 1.2+ | API key (from ExternalModel.spec.credentialRef Secret) |
| 6 | ExternalModel provider | maas-api | 443 | HTTPS | TLS 1.2+ | (response) |
| 7 | maas-api | Gateway | 8443 | HTTPS | TLS 1.2+ | (response to user) |
| 8 | Gateway | User client | 443 | HTTPS | TLS 1.3 | (response) |

**Flow Notes**: The user's authentication credential is completely hidden from the external model provider. Only the maas-api's API key (stored in a Secret and injected into the request) is sent to the external provider. This prevents credential exfiltration and allows separate rate-limiting and audit trails per tenant.
