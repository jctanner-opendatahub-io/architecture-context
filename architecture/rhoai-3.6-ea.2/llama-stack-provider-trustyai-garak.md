## Purpose

**Short**: Red-teaming evaluation adapter for RHOAI that integrates NVIDIA's Garak vulnerability scanner with eval-hub to detect LLM safety issues (jailbreaks, prompt injection, toxicity, bias).

**Detailed**: This component provides a `FrameworkAdapter` that enables eval-hub (RHOAI's evaluation platform) to orchestrate automated red-teaming scans against Large Language Models using Garak. It supports two execution modes: **Simple** (garak runs directly in the eval-hub Kubernetes Job pod) and **KFP** (Kubeflow Pipelines mode for advanced intents-based testing with synthetic data generation). The adapter handles job specification parsing, benchmark profile resolution, Garak command construction, result parsing, and artifact reporting back to eval-hub. It integrates with RHOAI's evaluation workflow, enabling security and compliance assessments against OWASP LLM Top 10, AVID taxonomy, and custom intents-based risk models.

## Architectural Analysis

The architecture reflects a **pipeline orchestration pattern** for LLM evaluation. The component acts as a translation layer between eval-hub's job abstraction and Garak's red-teaming framework, enabling the RHOAI platform to treat LLM vulnerability scanning as a first-class evaluation capability alongside accuracy, latency, and other metrics.

**Key architectural decisions:**

1. **Dual execution modes** (`simple` vs `kfp`) decouple evaluation granularity from job complexity. Simple mode is stateless and ideal for quick scans; KFP mode enables six-step pipelines (validate→taxonomy→SDG→prompts→scan→parse) supporting intents-based adversarial testing with synthetic data generation.

2. **Profile-based config resolution** uses deep-merge semantics. Predefined benchmark profiles (OWASP, AVID, intents) are loaded from `config.py` and overlaid with user overrides, allowing platform-level defaults while preserving operator customization. The intents benchmark adds an extra overlay for model endpoint configuration, with `__FROM_ENV__` placeholders for Kubernetes Secret injection.

3. **S3 artifact flow** (KFP mode only) via Data Connection secrets. Intermediate results (taxonomy, SDG-generated prompts, scan logs) flow through S3, enabling horizontal scaling of pipeline components across namespaces and persistent artifact storage independent of the Job pod's lifecycle.

4. **XDG environment variables** override Garak's default cache paths to `/tmp`, ensuring read-write access inside non-privileged containers (uid 1001) without requiring persistent storage mounts for cache.

5. **Subprocess runner pattern** for Garak. Rather than embedding Garak as a library, the adapter spawns it as a subprocess, isolating dependency conflicts and allowing in-place Garak updates without redeploying eval-hub.

**Security considerations:**

- **Environment variable injection** for API keys (`OPENAICOMPATIBLE_API_KEY`, `KFP_AUTH_TOKEN`, `AWS_SECRET_ACCESS_KEY`). The adapter reads these from the pod's environment (populated by Kubernetes Secrets) rather than config files, preventing accidental secret persistence in artifacts.
- **Non-root execution** (uid 1001 from UBI9 base). The container runs unprivileged at build and runtime, reducing blast radius if the Python process is compromised.
- **No FIPS signals detected** in the codebase. The component uses stdlib `cryptography` (49.0.0, dynamically linked) but does not set GOEXPERIMENT or explicit FIPS flags. Crypto operations (TLS for API calls, boto3 for S3) rely on the UBI9 base's OpenSSL.

**Design gaps and risks:**

- **Intents model configuration complexity**. The overlay logic for `intents_models` uses `x.get("key") or default` pattern, which silently overwrites empty values but respects pre-filled ones. This creates implicit ordering: operators must clear the field (set to `null` in the Job spec) to force a default, not merely omit it.
- **No declared output schema** between pipeline steps. The six-step KFP pipeline (in `core/pipeline_steps.py`) relies on filename conventions and JSONL format, with loose coupling on what SDG generates vs. what the scan step expects.
- **Garak version pinning to a fork**. The adapter depends on `garak==0.15.0+rhaiv.5`, a Red Hat maintained fork. Updates to the fork are decoupled from upstream NVIDIA releases, creating a supply chain dependency on the midstream repo's release cadence.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Pod's service account for callbacks; model API key from Secret | Kubernetes / eval-hub | Service account is shared across Job pods in a namespace; no per-Job RBAC |
| Data storage | S3 bucket (Data Connection) scoped to namespace; artifacts stored under namespace-prefixed path | eval-hub + Data Connection RBAC | Shared S3 bucket requires namespace prefix in artifact paths; enforce via S3 bucket policy |
| Network traffic | No explicit NetworkPolicy in this component; inherited from namespace isolation | Kubernetes | Outbound egress to model endpoints and KFP not restricted; could benefit from NetworkPolicy |
| Compute & resources | ResourceQuota applied by eval-hub to Job pods | Kubernetes | Component does not declare resource limits; requests are eval-hub's responsibility |
| Configuration & secrets | Secrets mounted per Job; ConfigMap per JobSpec (unique per evaluation) | Kubernetes | Secrets are shared at namespace level; a compromised pod could leak other pods' secrets |
| API scoping | Eval-hub SDK handles JobSpec isolation; Garak does not isolate scans by tenant | Application | Garak subprocess runs in single process; no per-tenant isolation within Garak probe execution |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Model Endpoint | Cross-namespace (shared LLM service) | API key-based access control at model endpoint |
| KFP Server | Cross-namespace | KFP service account RBAC (namespace-scoped) |
| S3 Bucket | Shared (Data Connection) | IAM policy + namespace-prefixed artifact paths |

_Multi-tenancy is enforced at the namespace level by Kubernetes and eval-hub. Within a namespace, there is no per-Job isolation of secrets or service accounts. Operators must rely on Kubernetes NetworkPolicy, RBAC, and S3 bucket policies to prevent lateral movement between Jobs._
