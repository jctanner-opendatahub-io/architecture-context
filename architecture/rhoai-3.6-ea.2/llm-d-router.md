## Purpose

**Short**: Extensible inference request router implementing pluggable scheduling via Kubernetes-native Gateway API Inference Extension, with support for disaggregated encode/prefill/decode inference execution across heterogeneous model-serving pods.

**Detailed**: llm-d Router is an open-source component providing intelligent scheduling for inference workloads in multi-model, multi-tenant Kubernetes clusters. Built on the Kubernetes SIGs Gateway API Inference Extension specification, it consists of three primary services: the Endpoint Picker (EPP) gRPC server that routes requests using pluggable filters, scorers, and a configurable data layer; the pd-sidecar for coordinating disaggregated inference phases (encode/prefill/decode); and the coordinator for managing cluster-level scheduling state. The architecture supports complex inference patterns including KV-cache locality awareness, session affinity, load balancing, and optional disaggregated execution. Scheduling logic is extensible via YAML-driven plugins without requiring core code changes, following a clean separation of screening (mandatory constraints), filtering (per-profile constraints), and scoring (optimization).

## Architectural Analysis

llm-d Router is a **plugin-based scheduling system** with clear architectural patterns:

**Endpoint Picker (EPP) design**: Implements the Envoy External Processor (ExtProc) protocol, receiving inference requests and returning routed endpoints. Uses sequential filter chains (screeners + per-profile filters) followed by weighted scoring. Request control runs once per request; scheduling profiles run per phase (e.g., separate prefill/decode profiles).

**Upstream alignment**: Code is adapted from Kubernetes SIGs Gateway API Inference Extension project (Apache 2.0 licensed). Downstream RHOAI tracks upstream changes via merge commits from upstream/main.

**FIPS compliance architecture**: Konflux Dockerfiles (`Dockerfile.konflux.epp`, `Dockerfile.konflux.sidecar`) set `GOEXPERIMENT=strictfipsruntime` and `CGO_ENABLED=1`, enforcing dynamically linked OpenSSL and FIPS-compliant TLS. Non-Konflux variants use `CGO_ENABLED=0` (static Go crypto, fails Konflux validation).

**Configuration-driven extensibility**: Behavior defined via YAML plugins configuration specifying filters, scorers, screeners, and data producers. No core changes required to extend scheduling logic.

**Multi-component deployment**: Three separate binaries (EPP, sidecar, coordinator) with independent FIPS postures. Coordinator and non-Konflux images use static crypto, only Konflux variants meet FIPS gate requirements.

**Kubernetes-native**: Uses controller watches on Pods, InferenceObjective, InferenceModelRewrite, and InferencePool CRDs. Interacts with Kubernetes API via kubeconfig credentials.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Platform RBAC on CRD creation/update (e.g., EndpointPickerConfig per namespace) | Kubernetes API | Component does not validate tenant identity in requests; assumes upstream gateway enforces isolation |
| Data storage | Per-namespace CRDs; shared cluster-wide Redis cache (optional) | Kubernetes + optional Redis | Redis cache has no per-tenant scoping; shared state could leak across namespaces if Redis is used |
| Network traffic | Expected platform NetworkPolicy; no built-in gateway auth | Kubernetes | No request-level auth; EPP is cluster-internal, assumes network isolation |
| Compute & resources | Pod-level resource requests/limits; pod disruption budgets | Kubernetes | Standard pod-level isolation |
| Configuration & secrets | Per-namespace ConfigMaps and Secrets for tls-cert, tls-key, config files | Kubernetes | Configuration is per-namespace; shared global config file could affect all tenants if misconfigured |
| API scoping | CRD watches are cluster-wide; request filtering occurs at gateway level | Application + Kubernetes | EPP receives requests from any gateway; assumes gateway enforces source validation |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Redis (optional) | None (cluster-wide cache) | Application-level filtering required (not implemented); shared state risk |
| Kubernetes API | Namespace-scoped CRDs | RBAC on CRD operations |
| OpenTelemetry Collector (optional) | None (cluster-wide traces) | Trace filtering by platform |

**Summary**: Multi-tenancy is delegated to the Kubernetes platform. The router is a cluster-scoped service that assumes upstream gateways enforce request source/identity validation. Per-namespace CRD configuration provides logical isolation, but shared caches (Redis) and shared metrics (/metrics endpoint) are not tenant-aware. This is a reasonable division of responsibility for a Kubernetes-native component, but operators must enforce network policies and RBAC to prevent cross-tenant data leakage.
