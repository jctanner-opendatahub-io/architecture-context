## Purpose

**Short**: TrustyAI provides a REST API for explainable AI (XAI) metrics calculation and model explainability integrated with KServe/ModelMesh inference servers.

**Detailed**: TrustyAI is an Explainable AI toolkit that calculates fairness metrics (Statistical Parity Difference, Disparate Impact Ratio) and provides local/global explainability algorithms (LIME, SHAP, Counterfactuals, TSSaliency, PDP) for monitored AI models. The TrustyAI Explainability Service is deployed as a Quarkus REST microservice that integrates with KServe-deployed models via gRPC and exposes metrics via Prometheus. It consumes model inference payloads (inputs/outputs) either through REST consumer endpoints or CloudEvents, persists them to storage (PVC or memory), and calculates fairness metrics on demand or on a schedule. Primarily designed for RHOAI deployments where it is managed by the TrustyAI operator.

## Architectural Analysis

TrustyAI Explainability is a pure service component (no operator) deployed as a stateless Quarkus application with a single responsibility: calculating and exposing AI fairness and explainability metrics. The service follows a clean separation of concerns: the core XAI algorithms live in the Java library (`explainability-core`), the service exposes REST endpoints for metrics and explainability requests, and connectors (`explainability-connectors`) handle integration with external model servers via gRPC.

**Key Architectural Patterns**:

1. **Framework Choice**: Quarkus 3.8.5 (RESTEasy Reactive) is selected for fast startup and low memory footprint, critical for containerized deployments.
2. **Protocol Bridging**: The service bridges multiple protocols—REST for external consumers, gRPC for KServe connections, and internal Arrow serialization for Python integration. Netty 4.1.125 provides the HTTP/2 and gRPC transport layer.
3. **Storage Abstraction**: A pluggable `Storage` interface supports multiple backends (PVC, in-memory, database). This allows flexibility in deployment scenarios without code changes.
4. **Metrics Pipeline**: Quarkus scheduler drives periodic metric calculations, which are then published to Prometheus at `/q/metrics` for scraping. This enables time-series monitoring of fairness drifts.
5. **Namespace-aware Configuration**: An init container writes a ConfigMap containing the TrustyAI service's in-cluster endpoint (`http://trustyai-service.$NAMESPACE/consumer/kserve/v2`), allowing ModelMesh to dynamically target the correct consumer endpoint.
6. **Data Scoping**: Metrics and explanations are scoped by model ID and optional batch size, supporting multi-model scenarios within a single deployment.

**Design Risks and Observations**:

- **No explicit tenancy enforcement**: The service accepts `modelId` as a request parameter and trusts the caller to provide valid values. There is no built-in namespace isolation; tenancy is delegated to the platform (RBAC and namespace scoping).
- **In-memory metrics calculation**: Fairness metrics are calculated in-process using TrustyAI core algorithms. Large datasets or concurrent requests may cause memory pressure; batch size configuration mitigates this.
- **Platform dependency**: The service assumes Prometheus is available for metrics scraping and relies on Kubernetes to provide ConfigMaps and PVCs. Deployment outside of K8s requires significant adaptation.
- **gRPC transport unencrypted by default**: The service communicates with KServe models over gRPC with no TLS configuration visible in the deployment manifests; security relies on in-cluster networking (NetworkPolicy or Istio).

## Multi-Tenancy

TrustyAI service does **not** implement explicit multi-tenancy enforcement. Instead, it assumes namespace-level isolation enforced by the platform:

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| **Tenant boundary** | per-namespace | Deployment manifests (Deployment, Service, RBAC in target namespace) |
| **Deployment model** | single-tenant per namespace | Each RHOAI user namespace receives one TrustyAI service instance |
| **Tenant identifier** | namespace name (implicit) | Kubernetes namespace where Deployment is created |

_The service identifies models by `modelId` (a string parameter), not by user or tenant. It is the responsibility of the operator (TrustyAI service operator) to ensure separate instances for separate tenants._

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Kubernetes RBAC (namespace-scoped ServiceAccount) | Kubernetes | Service accepts any modelId; no per-model authorization check |
| Data storage | Shared PVC (no tenant scoping in filename) | Kubernetes (PVC per namespace) | If multiple tenants share a namespace, data is not isolated |
| Network traffic | Service in same namespace as models | Kubernetes | NetworkPolicy (optional) can restrict inter-namespace traffic |
| Compute & resources | Pod resource limits (if set) | Kubernetes | No per-model resource allocation |
| Configuration & secrets | Per-namespace Secrets / ConfigMap | Kubernetes | Operator must provision separate ConfigMaps per tenant |
| API scoping | No API-level scoping | Application | Service does not enforce tenant boundaries in request validation |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| None (single-tenant per namespace) | N/A | N/A |

_Each namespace has its own TrustyAI service instance and storage. There are no shared backends across tenants unless explicitly configured by the operator (e.g., shared database)._
