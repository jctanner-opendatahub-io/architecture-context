## Purpose

**Short**: TrustyAI Explainability is a Quarkus service that collects model-inference data and provides fairness, drift, and model-explanation APIs.

**Detailed**: The service exposes REST endpoints for inference payload ingestion, data upload/download, fairness and drift metric calculation, and local/global explainers. It stores inference and metric data in memory, a CSV file on a PVC, or Hibernate-backed MariaDB/MySQL; MinIO is also supported by the service dependency set.

In RHOAI, the service is deployed as one replica behind a ClusterIP Service and an OpenShift Route. The deployment creates a namespace-aware `model-serving-config` ConfigMap whose KServe v2 payload processor URL points back to the service, and Prometheus scrapes the service's Quarkus metrics endpoint.

## Architectural Analysis

This is a single-container, stateful-by-configuration application rather than a Kubernetes controller. Quarkus REST resources are selected through profile-specific feature flags: the RHOAI profile enables fairness and drift while disabling the local and global explainer endpoints; the default and ODH profiles enable the explainer families as well. The same service therefore presents different API surfaces depending on the runtime profile.

The deployment couples the application to a namespace-local PVC and to Kubernetes API access through an init container. That init container reads the pod namespace from the service-account mount and uses `oc apply` to create or update a ConfigMap containing the service's KServe v2 callback URL. The corresponding ClusterRole is cluster-scoped and grants broad ConfigMap mutation verbs, which is a notable privilege and tenancy risk for a service otherwise deployed as a namespaced instance.

The release Dockerfile uses digest-pinned UBI 9/OpenJDK 17 images and cachi2-prefetched Maven artifacts. The application has no explicit Java TLS or certificate-validation configuration in the inspected source; production HTTPS is configured through Quarkus certificate file properties, while the checked-in OpenShift Route has no TLS stanza and the ServiceMonitor uses HTTP.
