## Purpose

**Short**: MLflow provides experiment tracking, model and artifact management, model registry, tracing, evaluation, and an AI gateway for the machine-learning lifecycle.

**Detailed**: The primary deployable is a Python MLflow tracking server backed by a configurable database or file store and an artifact store. It exposes the MLflow tracking and registry APIs, artifact proxy endpoints, a browser UI, health/version endpoints, and optional gateway and assistant APIs. The RHOAI image starts the server on port 5000 with Kubernetes workspace support, artifact serving, and job execution disabled.

The repository also publishes the `mlflow-skinny` minimal Python distribution and `mlflow-tracing` SDK. The Konflux build produces the full MLflow wheel plus these packages, builds the web UI, and assembles them into a UBI-based runtime image. The Helm chart supplies a general Kubernetes deployment with optional TLS, ingress, persistence, metrics, garbage collection, and NetworkPolicy resources.

## Architectural Analysis

MLflow is a multi-function Python service rather than a Kubernetes controller. Its logical architecture separates the HTTP server/UI, backend store for tracking and registry metadata, and artifact repository. Artifact traffic can be direct from clients to a remote URI or proxied through the server with `--serve-artifacts`. Optional gateway and GenAI features add outbound calls to model providers and cloud storage integrations.

The RHOAI-specific Konflux command enables the Kubernetes-auth application and workspace store (`kubernetes://`) while disabling the assistant and AI gateway in the image defaults. The chart is independently configurable and defaults to one replica, a ClusterIP service, HTTP on port 5000, and disabled ingress/TLS/network policy. The chart's readiness and liveness checks both use `/health`; scaling and rolling-update safety depend on the selected backend and storage access mode.

Analyzer evidence identifies 54 registered HTTP endpoints, but does not determine application ownership for every dynamic route, a concrete service target port, or an authentication mechanism. Those limitations are retained below rather than inferred away.
