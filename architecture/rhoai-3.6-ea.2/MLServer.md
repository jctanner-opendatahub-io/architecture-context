## Purpose

**Short**: Open-source inference server for machine learning models with support for KFServing V2 dataplane protocol via REST and gRPC interfaces.

**Detailed**: MLServer is a Python-based inference serving platform designed to simplify deploying and scaling machine learning models in production environments. It provides a unified interface supporting multiple inference frameworks including scikit-learn, XGBoost, ONNX, LightGBM, CatBoost, MLflow, HuggingFace, and others. The service implements the standard KFServing V2 Inference Protocol for both REST and gRPC transports, enabling seamless integration with Kubernetes-native frameworks like Seldon Core and KServe. MLServer supports multi-model serving with adaptive batching, parallel inference across worker pools, and dynamic model loading/unloading from repositories. The component is critical infrastructure for model serving in RHOAI deployments.

## Architectural Analysis

MLServer follows a modular runtime architecture where framework-specific inference logic is packaged as pluggable runtimes (e.g., `mlserver-sklearn`, `mlserver-onnx`). The main service runs as a FastAPI-based HTTP server with a corresponding gRPC interface powered by protobuf definitions. The server implements a two-tier security model: **PRODUCTION mode** enforces a trusted runtime allowlist (stored in `/etc/mlserver/trusted-runtimes.json`) that prevents arbitrary code execution, while **DEVELOPMENT mode** permits dynamic loading of custom runtimes directly from model folders. This security distinction is exposed via the `RuntimeSecurity` gRPC endpoint. The component uses AIPCC base images for hermetic builds and ships with pre-configured access to the RHEL AI Python Package Index. Both CPU and GPU (NVIDIA CUDA) variants are supported via separate Dockerfiles.

**Multi-Tenancy Assessment**: MLServer is fundamentally a single-tenant inference server. It does not implement built-in multi-tenant isolation. When used in a shared Kubernetes cluster, tenant isolation is delegated to the orchestration layer (namespace isolation, NetworkPolicy, Istio AuthorizationPolicy, RBAC on KServe InferenceService resources).

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Inherited from KServe/Seldon RBAC | Kubernetes (KServe operator) | MLServer itself has no built-in auth; relies on ingress and service mesh |
| Data storage | Per-deployment model repository (no data sharing) | Kubernetes (PVC mount) | No row-level or model-level isolation within a deployment |
| Network traffic | NetworkPolicy, Istio VirtualService | Kubernetes / Istio | Unencrypted gRPC by default; requires mTLS configuration |
| Compute & resources | ResourceQuota, LimitRange | Kubernetes | No resource limits enforced within MLServer |
| Configuration & secrets | Per-deployment configmap/secrets | Kubernetes | Secrets in environment variables, not encrypted at rest |
| API scoping | No API-level scoping (all models accessible to all requests) | N/A | All models in a deployment are equally accessible |
