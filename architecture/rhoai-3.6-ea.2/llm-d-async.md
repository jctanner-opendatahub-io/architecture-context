## Purpose

**Short**: Consumes asynchronous inference requests from a configurable broker, applies dispatch and concurrency policies, and sends requests to an inference gateway while delivering results back through the broker.

**Detailed**: llm-d-async is the Async Processor for LLM inference workloads. It consumes requests through Redis/Valkey pub/sub, Redis sorted sets, or Google Cloud Pub/Sub; schedules work through named worker pools and optional budget/admission gates; and invokes configured inference-gateway endpoints over HTTP. Results, retries, cancellation, and durable result delivery are handled by the selected transport implementation.

The process is a single Go executable with controller-runtime logging, OpenTelemetry tracing, Prometheus metrics, graceful signal handling, and Kubernetes health probes. It does not define CRDs or reconcile Kubernetes resources. The Helm chart deploys one namespace-scoped Deployment and ServiceAccount; broker credentials and optional client TLS material are supplied through Secrets.

## Architectural Analysis

The design separates transport from processing. A common pipeline abstraction supports ephemeral Redis channels, durable Redis sorted-set queues, and GCP Pub/Sub. Queue/topic configuration can map requests to inference-gateway URLs and request paths, while worker pools, merge policies, and dispatch gates provide capacity control. Redis sorted sets additionally support polling, retries, backlog metrics, and queue configuration hot reload.

The runtime exposes only health and metrics surfaces; inference traffic is outbound from the worker to the gateway. Metrics authentication is configurable and enabled by default in the Go options, while the Helm chart defaults `ap.metrics.secure` to false unless overridden. Health endpoints are intentionally unauthenticated pod-local Kubernetes probes. The chart fails fast on missing transport, broker connection, project ID, or inference-gateway configuration, reducing silent misconfiguration but requiring deployment values beyond the chart defaults.

The Konflux Dockerfile uses `CGO_ENABLED=1` and `GOEXPERIMENT=strictfipsruntime` for the RHOAI build, whereas the legacy Dockerfile builds a static `CGO_ENABLED=0` binary into a distroless image. Application TLS defaults to system Go behavior when enabled, enforces TLS 1.2 minimum, supports a custom CA and client certificate/key, and exposes an explicitly insecure certificate-verification bypass for development. No application-level tenant identifier or cross-tenant data filter was found; isolation is delegated to the deployment namespace, Kubernetes credentials, and broker configuration.
