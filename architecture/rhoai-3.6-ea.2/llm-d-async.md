## Purpose

**Short**: Async Processor is a composable asynchronous worker queue system for LLM inference workloads that decouples job submission from execution, optimizing accelerator utilization for latency-insensitive batch jobs.

**Detailed**: The Async Processor enables efficient processing of bulk or time-insensitive inference requests by maintaining a message queue-based architecture. It pulls jobs from configurable message brokers (Redis or Google Cloud Pub/Sub), applies admission control and dispatch gates based on Prometheus metrics and capacity policies, merges requests across worker pools, and dispatches them to inference gateways (such as llm-d-router). This design allows organizations to fill slack capacity in high-performance accelerators without blocking real-time serving traffic, supporting use cases like batch summarization, classification, and sentiment analysis at near-realtime scale. The component integrates tightly with gateway-api-inference-extension for flow control and observability, exposes health check endpoints for Kubernetes orchestration, and supports mTLS for secure inference gateway communication.

## Architectural Analysis

The Async Processor is implemented as a single containerized Go application deployed as a Kubernetes Deployment. Its architecture centers on four core subsystems:

1. **Message Transport Layer** — pluggable interface supporting Redis (Pub/Sub and Sorted Set) and Google Cloud Pub/Sub. Configuration is unified at the Helm chart level; the processor receives a single `--transport` flag and structured config (JSON). This design decouples queue semantics from the core processor, enabling operator teams to swap backends without code changes.

2. **Flow Control Gates** — binary capacity gates that regulate admission based on Prometheus metrics. Gates implement sliding-window SLO budgeting, preventing inference gateway overload by rejecting or delaying requests when utilization thresholds are exceeded. The gate factory integrates with gateway-api-inference-extension for runtime decision-making.

3. **Worker Pools and Merge Policies** — configurable worker concurrency and request merging strategies (per-queue or per-topic). The processor supports static pool definitions via Helm values or dynamic configuration files, enabling runtime tuning without redeployment.

4. **HTTP Inference Client** — multiplexed HTTP client with TLS/mTLS support, configured via command-line flags for certificate paths, CA bundles, and optional certificate verification skipping (for non-production use).

Health checks (`/healthz`, `/readyz`) are registered via a separate internal health server package and are accessed by Kubernetes kubelet probes without authentication, following the standard platform-delegated health probe pattern. The processor gracefully shuts down all servers and services on signal (SIGTERM/SIGINT) and manages resource cleanup through structured context cancellation.

The repository structure is modular: `cmd/main.go` is the entry point; `pkg/server/` contains server initialization and TLS configuration; `pkg/async/` houses core processing logic including flow control and worker pools; `pkg/asyncworker/` implements the request dispatch and HTTP client; `internal/health/` manages health probes; and `internal/otel/` handles observability setup. The Helm chart (`charts/llm-d-async/`) parameterizes transport configuration, worker pools, Prometheus integration, and deployment manifests, enabling flexible multi-tenant deployments.

## Sub-Component Details

### async-processor

**Dockerfile**: `Dockerfile.konflux`  
**Intent**: Primary container entry point for all deployments. Runs the Async Processor service (request queue polling, admission gating, worker dispatch, result handling).  
**Image**: Built from source; deployed as `$(image-registry)/llm-d-async` (configurable via Helm values and kustomize image transforms)  
**Language**: Go 1.26  
**Port**: Configurable; health server defaults to 8888 (HTTP, pod-local only)  

**Health Probes**:
- Liveness: HTTP GET `/healthz` (default: `localhost:8888`)
- Readiness: HTTP GET `/readyz` (default: `localhost:8888`)

**Configuration**:
- `--transport` (redis-pubsub, redis-sortedset, gcp-pubsub) — Message queue backend
- `--transport-config` (JSON) — Transport-specific configuration (URLs, credentials, topics/queues)
- `--prometheus-url` — Prometheus instance for metrics queries (optional; used for gate SLO budgeting)
- `--prometheus-cache-ttl` — Prometheus response cache TTL (optional)
- `--pool-config-file` — Path to worker pool configuration (JSON)
- `--transform-config-file` — Path to request transformation plugin configuration (JSON)
- `--tls-ca-cert` — Path to CA certificate for inference gateway verification
- `--tls-cert` — Path to client certificate for mTLS
- `--tls-key` — Path to client private key for mTLS
- `--tls-insecure-skip-verify` — Skip TLS verification (dev/test only)
- Kubernetes signal handling via controller-runtime (SIGTERM/SIGINT)

**Upstream Dependencies** (Outbound):
- **Inference Gateway (IGW)**: HTTP/HTTPS to llm-d-router or compatible inference server. Port and path configurable via `ap.igwBaseURL` in Helm values. Requests include inference tasks (LLM prompts, model parameters).
- **Message Broker (Redis/Pub/Sub)**: TCP connection to Redis instance or Google Cloud Pub/Sub API (HTTPS). Endpoints and credentials configured via `--transport-config`.
- **Prometheus (optional)**: HTTPS to Prometheus instance (read-only queries for SLO metric collection). Optional; if omitted, gates use static configuration.
- **Kubernetes API**: REST (via k8s.io/client-go) for resource operations (leader election, logging, health status). Connects to `kubernetes.default.svc.cluster.local:6443` with ServiceAccount credentials.
- **OpenTelemetry Collector (optional)**: gRPC to OTLP endpoint if tracing is enabled.

## Multi-Tenancy

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| **Tenant boundary** | Per-queue (or per-topic for Pub/Sub) — each queue/topic is independently configured and processed | pkg/async/worker_pool.go, pkg/redis/, pkg/pubsub/ |
| **Deployment model** | Single-instance per namespace; multi-tenancy achieved via queue/topic namespacing in the message broker | charts/llm-d-async/templates/ap-deployments.yaml (replicas: 1) |
| **Tenant identifier** | Queue name (Redis) or topic name (Pub/Sub); inferred from message metadata or transport configuration | ap.workerPools / ap.transportConfig in Helm values |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | ServiceAccount-scoped access to Kubernetes API; per-queue auth to message broker (Redis password or Pub/Sub service account) | Kubernetes RBAC + Message Broker | No per-queue RBAC within processor; all queues accessible if transport credentials are compromised |
| Data storage | Message isolation by queue/topic name; per-queue result handling via Redis Sorted Sets | Message Broker (Redis/Pub/Sub) | Shared Redis instance (if used) with weak credentials is a single point of failure; no row-level filtering within the processor |
| Network traffic | No inter-pod communication required; pods communicate only with external message broker and inference gateway | Pod-only deployment | NetworkPolicy can restrict egress to message broker and IGW; ingress policy not required |
| Compute & resources | ResourceQuota and LimitRange applied at namespace level (not enforced by component) | Kubernetes | No per-tenant resource limits within processor; single processor instance can be starved by high-volume queues |
| Configuration & secrets | Per-queue configuration in ap.workerPools; per-queue secrets (e.g., Redis password, IGW API key) managed externally | Helm values + Secret mounts | Shared credentials across queues if Helm chart is not carefully parameterized |
| API scoping | N/A (no inbound API exposed) | N/A | Pod-local health endpoints only; no API scoping required |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Message Broker (Redis or Pub/Sub) | Queue/topic name | Separate queues per tenant; credentials scoped to broker-level auth (password or service account) |
| Inference Gateway | Single upstream per deployment | HTTP request includes tenant context (inferred from queue name or request payload); IGW routing logic handles tenant isolation |
| Prometheus (optional) | Namespace-scoped metrics | Prometheus scrape paths include Kubernetes namespace; metric labels identify per-queue metrics |

**Isolation Summary**: The Async Processor supports single-instance, queue-based multi-tenancy. Tenants are isolated by message queue/topic name and external authentication (message broker credentials, inference gateway API keys). No in-app tenant filtering or access control is implemented; tenants must trust the message broker's access controls and the inference gateway's request routing.

**Summary**: The LLM-D Async Processor is a **FIPS-compliant, composable, multi-queue async inference dispatcher** designed for latency-insensitive workloads. It decouples request submission from execution via message queues, applies sophisticated dispatch gating (budget-based, quota-based, or tier-priority), and distributes load across worker pools to inference gateways. Build-time FIPS compliance is guaranteed by Konflux check-payload; runtime crypto uses stdlib crypto/tls with dynamic OpenSSL linking. Hermeticity gaps are expected to be resolved in downstream GA releases.
