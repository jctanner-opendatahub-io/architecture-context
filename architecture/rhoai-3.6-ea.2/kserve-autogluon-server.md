## Purpose

**Short**: AutoGluon model server implementation for KServe that provides tabular and time-series prediction capabilities.

**Detailed**: This component is part of the KServe model serving ecosystem and provides the AutoGluon model server runtime. It enables users to deploy and serve AutoGluon-trained tabular models and time-series predictors within the KServe framework on Kubernetes. The repository is a downstream fork of the upstream KServe project (maintained at https://github.com/kserve/kserve), synced from the midstream OpenDataHub fork, and contains Go-based controller infrastructure along with Python model server implementations for multiple ML frameworks including AutoGluon, scikit-learn, XGBoost, LightGBM, and others.

The autogluonserver Python package provides the core model server implementation that handles model loading, prediction, and the KServe v1/v2 protocol endpoints. It supports both tabular models via AutoGluon's TabularPredictor and time-series models via TimeSeriesPredictor.

## Architectural Analysis

This is a complex, multi-component repository that serves dual purposes:

1. **Control Plane**: Go-based controllers (InferenceService, LLMInferenceService, LocalModelNode, TrainedModel, etc.) that reconcile Kubernetes custom resources and orchestrate model serving lifecycle.

2. **Data Plane**: Python model server implementations (autogluonserver, sklearnserver, xgbserver, lgbserver, etc.) packaged as container images that run within Kubernetes and handle prediction requests.

The component's architecture reflects the KServe three-tier sync model: upstream contributions flow through the midstream OpenDataHub fork before landing in this downstream RHOAI-specific variant. The downstream branch (`rhoai-staging`) includes Red Hat customizations for security, RHEL base images, and integration with RHOAI infrastructure.

Key architectural patterns observed:

- **ClusterServingRuntime CRDs**: Define available model server types (autogluon, sklearn, xgboost, etc.). The autogluonserver runtime is a ClusterServingRuntime that accepts `autogluon:1` model format and exposes metrics on port 8080.
- **Model Server Binaries**: Dockerfiles package Python model servers as standalone services. The `Dockerfile.konflux.autogluon` uses the AIPCC RHEL AI base image and installs AutoGluon dependencies via the secure RHAI PyPI index.
- **Build Hermiticity**: The Dockerfile uses Hermeto-prefetched dependencies and locks all package versions, enabling reproducible builds.
- **Security Posture**: Containers run as non-root user (UID 1001), with dropped capabilities and no privilege escalation. TLS termination is handled by kube-rbac-proxy sidecar.
- **Multi-Framework Support**: Beyond autogluonserver, the repository includes model servers for TensorFlow, scikit-learn, XGBoost, PMML, Paddle, and others, each with its own Python package and Dockerfile variant.

The repository also contains extensive controller infrastructure for managing InferenceGraph (pipeline routing), LocalModelCache (distributed model caching), and LLMInferenceService (specialized LLM serving), representing an evolved architecture for production AI workloads on Kubernetes.

### FIPS Compliance

#### Build-Time FIPS (check-payload gate)

Konflux validates images via [check-payload](https://github.com/openshift/check-payload), which enforces:
- Go binaries must be **dynamically linked** (CGO_ENABLED=1)
- **OpenSSL must be installed** in the container image
- No statically linked Go crypto

| Aspect | Value | Source |
|--------|-------|--------|

## Multi-Tenancy

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| **Tenant boundary** | per-namespace | InferenceService is Namespaced; isolation enforced by Kubernetes RBAC and NetworkPolicy |
| **Deployment model** | multi-tenant (single KServe controller manages InferenceServices across all namespaces) | config/manager/manager.yaml (controller watches all namespaces) |
| **Tenant identifier** | namespace name (inferred from CR namespace) | kserve-controller-manager watches all namespaces; isolation enforced by Kubernetes scheduler |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Kubernetes RBAC (per-namespace role/rolebinding), kube-rbac-proxy sidecar on webhooks | Kubernetes API server | User-created InferenceServices can be accessed by any pod in the same namespace; no built-in network-level segregation unless NetworkPolicy is deployed |
| Data storage | per-namespace PVC (models mounted as volumes), per-namespace Secrets for cloud credentials | Kubernetes scheduler | If multiple tenants share the same namespace, isolation is weak. Cross-namespace access to models is prevented by Kubernetes RBAC. |
| Network traffic | Default allow (Kubernetes default CNI); optional NetworkPolicy per namespace | Kubernetes CNI / Calico / OVN | If Istio is deployed, mTLS can be enforced via PeerAuthentication; otherwise network traffic is unencrypted between InferenceServices. Egress to external storage (S3, etc.) uses TLS. |
| Compute & resources | ResourceQuota (per namespace), LimitRange (per pod), request-based autoscaling | Kubernetes scheduler, Knative Autoscaler, or KEDA | No explicit resource isolation (cpu/memory share may be noisy neighbor); autoscaling is linear (proportional to request rate) and can be gamed by high-request workloads. |
| Configuration & secrets | per-namespace Secrets for cloud credentials (mounted into model server pods) | Kubernetes RBAC | Namespace isolation enforced; risk: if a user compromises one InferenceService, they can read all Secrets in that namespace. |
| API scoping | namespace-scoped watches (InferenceService, InferenceGraph, TrainedModel are Namespaced) | KServe controller | Controllers list all InferenceServices in all namespaces; ClusterServingruntimes are cluster-scoped (shared across tenants). |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| ClusterServingRuntime | Cluster (shared across all namespaces) | None; all tenants can reference the same runtime (e.g., autogluonserver). Isolation is at the pod level (each InferenceService creates isolated Knative Service + Deployment). |
| Model artifact storage (S3/GCS/Azure) | Tenant-managed (user supplies bucket/credentials) | IAM policies (cloud provider) or bucket-level access control; KServe does not enforce multi-tenancy at the storage layer. |
| Knative Service (internal) | per-namespace | Kubernetes RBAC; traffic is routed by Knative's istio/alb ingress. |

**Multi-Tenancy Assessment**: KServe provides namespace-level isolation via Kubernetes RBAC and per-namespace resource definitions. However, the multi-tenancy model is **implicit and not opinionated**. Users must deploy Kubernetes NetworkPolicy, ResourceQuota, and Istio AuthorizationPolicy to enforce strong isolation. The component is suitable for shared clusters with cooperative tenants (e.g., different teams within an organization) but not for adversarial multi-tenancy (e.g., SaaS).
