## Purpose

**Short**: Detects predefined and caller-supplied regular-expression patterns in text submitted over HTTP.

**Detailed**: The service is a lightweight Rust/Axum detector used by the FMS Guardrails Orchestrator. A request contains one or more text strings and detector parameters; the service applies built-in email, Social Security number, and credit-card patterns, or compiles and applies custom regular expressions.

The response reports each match's offsets, matched text, detection type, detector name, and a fixed score of `1.0`. The service is stateless and has no persistence, Kubernetes API interaction, or application-managed tenant database. Tracing middleware provides request and response logging.

## Architectural Analysis

This is a single-process, synchronous-in-purpose HTTP detection component built around Tokio and Axum. The binary binds one TCP listener and serves both health and application traffic from the same port; `HTTP_PORT` and `HOST` provide the only runtime network configuration.

The detector combines three named built-ins with arbitrary request-provided patterns. Invalid custom patterns are logged and skipped, while an empty pattern list returns `400 Bad Request`. The handler logs the complete deserialized request at info level, so callers should consider submitted text potentially sensitive when configuring log collection.

The image uses a multi-stage Rust build and includes test, lint, and format stages, then copies only the compiled binary into a UBI Minimal runtime. The build is reproducible at the Cargo dependency-resolution level through `Cargo.lock`, but the Dockerfile uses an unpinned `latest` UBI tag and has no visible RPM or Hermeto lock metadata.
