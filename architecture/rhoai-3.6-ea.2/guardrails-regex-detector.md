## Purpose

**Short**: A lightweight HTTP service for detecting sensitive information patterns (PII, credentials) in text using predefined and custom regular expressions, integrated with the FMS Guardrails Orchestrator.

**Detailed**: guardrails-regex-detector is a Rust-based HTTP service that provides pattern matching capabilities for text analysis. It exposes a POST API endpoint (`/api/v1/text/contents`) that accepts text content and regex patterns, then returns detected matches with location and confidence information. The service supports built-in pattern detectors for social security numbers, credit card numbers, and email addresses, and allows clients to provide custom regular expressions. The service listens on a configurable HTTP port (default 8080) and exposes a health check endpoint for Kubernetes readiness/liveness probes. It is designed to operate as a dedicated microservice within the RHOAI guardrails framework, handling detection requests from upstream orchestration services.

## Architectural Analysis

guardrails-regex-detector is a stateless, HTTP-based microservice with a minimal attack surface. The architecture follows a simple request-response pattern: incoming text detection requests are parsed, validated, and routed through the Axum web framework to the handler function, which applies the configured regex patterns and returns structured detection results. The service uses asynchronous I/O via Tokio for handling concurrent requests efficiently.

The component has two logical API endpoints—a health check (`/health`) for orchestration probes and a functional endpoint (`/api/v1/text/contents`) for pattern detection. Authentication is delegated to the calling service; the application accepts and forwards custom headers without local validation, allowing the upstream orchestrator (typically Guardrails Orchestrator or similar) to enforce its own authentication and authorization policies.

Build hermeticity is partially addressed: the Dockerfile uses Cargo lock files (`Cargo.lock`) to pin Rust dependencies, and the multi-stage build pattern (builder → tests → lint → release) ensures reproducibility and minimal final image size. The runtime environment inherits OpenSSL from the UBI 9 base image (`compat-openssl11` explicitly installed), providing TLS capability for potential future outbound connections.

Key observations:
- **No Kubernetes manifests** — the repository contains no kustomize, Helm, or declarative deployment configuration. Deployment is managed by the RHOAI platform through its own orchestration.
- **No state persistence** — the service is stateless; all detection logic is ephemeral per-request.
- **Header passthrough** — authentication and tenant context (if any) flow via HTTP headers, requiring the upstream caller to enforce boundaries.
- **Configurable ports** — HTTP_PORT and HOST environment variables allow flexible network binding, supporting various deployment topologies.
