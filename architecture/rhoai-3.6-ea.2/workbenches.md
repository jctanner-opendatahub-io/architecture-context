## Purpose

**Short**: Kubeflow Notebooks v2 workbenches provides the APIs, UI, and Kubernetes controllers for creating and operating interactive AI/ML development workspaces.

**Detailed**: The component models a user workspace with the namespaced `kubeflow.org/v1beta1` `Workspace` CRD and models reusable workspace templates, images, ports, options, and activity rules with the cluster-scoped `WorkspaceKind` CRD. The Workspace controller reconciles these objects into a per-workspace StatefulSet, Service, ServiceAccount, RoleBinding, and optional Istio/Gateway routing resources.

The Go backend exposes a REST API for namespaces, workspaces, workspace kinds, secrets, PVCs, storage classes, pod details, logs, and the current user. It uses Kubernetes clients and SubjectAccessReview-backed authorization. The React/TypeScript frontend is packaged as a separate nginx image and reaches the backend through the shared Kubeflow Istio gateway. The controller also hosts validating admission webhooks and a conversion webhook surface, with certificates provisioned by cert-manager or the OpenShift CA injection variant.

## Architectural Analysis

Workbenches is a three-part deployment with a clear control-plane/data-plane split. The controller owns the declarative lifecycle of workspaces and their execution pods; the backend is the user-facing API and performs Kubernetes reads and mutations under a dedicated, cluster-scoped service account; and the frontend is a static SPA. Workspace workloads are isolated by namespace and receive generated service accounts and bindings derived from the selected WorkspaceKind.

The key platform integration is the controller's dynamic routing layer. Workspace ports can be published through per-workspace Istio `VirtualService` resources or Gateway API `HTTPRoute` resources, while kube-rbac-proxy can be injected as a workspace sidecar for authenticated access. The repository's RHOAI Konflux controller build is hardened for strict FIPS runtime behavior and uses a digest-pinned PQC UBI runtime. The backend and frontend Dockerfiles are not equivalent release artifacts: the backend's generic image is statically linked into distroless, and the frontend uses nginx:alpine, so release image selection and downstream overlays matter.
