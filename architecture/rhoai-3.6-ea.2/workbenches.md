## Purpose

**Short**: Kubeflow Notebooks v2 is a platform component that runs interactive development environments (JupyterLab, RStudio, VS Code) for AI/ML workloads on Kubernetes, managed via a controller and backend API.

**Detailed**: This component provides a complete multi-tenant notebook management system for Red Hat OpenShift AI. It consists of three primary services: a Kubernetes operator (controller) that reconciles `Workspace` and `WorkspaceKind` custom resources, a backend REST API that manages workspace instances and resources, and a React-based frontend UI. The system enables users to create, configure, and manage interactive notebook containers with persistent storage, resource constraints, and integrated access control. The v2 architecture separates concerns between cluster-wide configuration (WorkspaceKind, RBAC, networking) and user-scoped execution (Workspace pods running JupyterLab/RStudio/code-server). Multi-tenancy is achieved through namespace-scoped Workspace resources, namespace-specific RBAC, and controller-managed isolation of workspace networking via Istio VirtualServices.

## Architectural Analysis

The Kubeflow Notebooks v2 implementation demonstrates a modern Kubernetes-native architecture with strong separation of concerns. The controller operates at cluster scope, managing cluster-wide policy (WorkspaceKind definitions, clusterwide RBAC roles, webhooks), while individual Workspaces are namespaced resources that users create within their own namespaces. This design pattern enables multi-tenancy: admins define standard notebook image templates globally via WorkspaceKind CRDs, while users provision notebook instances (Workspace CRs) in their own namespaces.

The backend service exposes a RESTful API for interactive workspace management—listing running pods, querying storage classes, executing commands in running workspace containers, and retrieving pod logs. It directly watches the Kubernetes cluster for Pod and PersistentVolumeClaim objects, enabling near-real-time UI updates. The backend uses Go's standard `crypto/tls` library with optional certificate-based encryption (enabled when cert files are provided), supporting secure communication in multi-tenant deployments.

The controller implements sophisticated reconciliation logic: it watches Workspace and WorkspaceKind resources, automatically generates StatefulSet deployments from Workspace specs, manages ServiceAccount and RoleBinding creation for workspace-scoped RBAC, and orchestrates Istio networking resources (VirtualServices) for traffic routing. The operator also handles critical lifecycle operations: pausing workspaces (scaling down pods), graceful shutdown with 30-second termination grace periods, and cleanup of dependent resources via finalizers.

Multi-tenancy is further reinforced by networking: the controller creates namespace-scoped VirtualServices that route traffic only to pods running in the workspace's own namespace, preventing cross-namespace communication. Istio isolation is complemented by Kubernetes NetworkPolicy resources (defined in manifests/kustomize/components/istio/network-policy.yaml) that restrict egress and ingress traffic to workspace pods.

A notable design decision is the separation of container image build variants: the controller (Dockerfile.konflux) uses UBI 9 minimal (post-quantum variant) with FIPS runtime enforcement (CGO_ENABLED=1, GOEXPERIMENT=strictfipsruntime), while the backend service uses a generic golang:1.26 builder and distroless:nonroot runtime image. This distinction reflects different deployment contexts: the operator requires FIPS compliance for compliance-sensitive environments, while the backend prioritizes minimal attack surface via distroless.

## Multi-Tenancy

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| **Tenant boundary** | per-namespace | Workspace CRD is Namespaced; users create Workspaces in their own namespaces |
| **Deployment model** | per-namespace instance (each user namespace gets its own Workspace pods) | workspaces/controller/internal/controller/workspace_controller.go |
| **Tenant identifier** | namespace name + Workspace resource name | Kubernetes namespace + metadata.name |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | per-tenant RBAC; controller validates ownership via namespace | Kubernetes + Application | Backend API relies on token validation; no service-to-service authz |
| Data storage | per-namespace PVC (bound to Workspace StatefulSet) | Kubernetes | PVCs are namespace-scoped; backend can query all PVCs in namespace (no quota isolation) |
| Network traffic | Istio VirtualService per namespace; NetworkPolicy restricts to workspace pods | Istio + Kubernetes | NetworkPolicy enforcement depends on CNI support; default-deny rules may not be enforced cluster-wide |
| Compute & resources | ResourceQuota per namespace (admins create; not enforced by component) | Kubernetes | Component does not enforce; depends on admin configuration |
| Configuration & secrets | per-namespace Secrets mounted by workspace pods | Kubernetes | Controller does not isolate Secrets; all workspace pods in namespace can access namespace Secrets |
| API scoping | Workspace CRs watched per namespace by controller | Application | Backend API validates bearer token; no explicit tenant header |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Kubernetes API Server | none (cluster-wide) | RBAC: controller has ClusterRole; workspace pods use ServiceAccount per namespace |
| Istio Ingress Gateway | namespace | VirtualService per namespace routes traffic to correct workspace pods |
| Storage Classes | cluster-wide | Admins configure which StorageClasses are available to users; no per-tenant quotas |

_Multi-tenancy isolation is strong at the namespace level but depends on cluster RBAC configuration. Controller does not prevent privileged Workspace specs or cross-namespace resource sharing; relies on admission webhooks and ClusterRole restrictions._
