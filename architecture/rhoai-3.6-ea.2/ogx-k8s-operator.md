## Purpose

**Short**: Kubernetes operator that creates and manages OGX (Open GenAI Stack) server instances with declarative configuration and multi-provider support.

**Detailed**: The OGX K8s Operator provides a Kubernetes-native control plane for deploying and managing OGX servers across RHOAI and standalone Kubernetes clusters. The operator reconciles two primary Custom Resources: `OGXServer` (ogx.io/v1beta1) for standalone server deployments and `OGX` (components.platform.opendatahub.io/v1alpha1) for ODH platform integration. The operator supports declarative runtime configuration generation from CR fields, multiple inference providers (vLLM, OpenAI, Azure, Bedrock, VertexAI, Watsonx), vector storage backends, and comprehensive networking, security, and monitoring capabilities. It manages Deployments, Services, NetworkPolicies, ConfigMaps, Secrets, ServiceMonitors, and PrometheusRules for complete lifecycle management of OGX server instances.

## Architectural Analysis

The OGX operator exhibits a two-tier architecture serving distinct deployment models: (1) **Standalone path** at repository root reconciles OGXServer resources (ogx.io/v1beta1) with declarative config generation, provider routing, and workload management. (2) **ODH module path** (ogx-module/) introduces a separate control plane reconciling OGX resources (components.platform.opendatahub.io/v1alpha1) for platform integration, managing root operator manifest deployment.

The operator implements sophisticated declarative config generation: resolving base configs from OCI labels or provided ConfigMaps, computing content-addressed ConfigMaps with immutable deployment triggers, supporting both inline and remote provider configurations. A validating webhook enforces mutual exclusivity constraints.

Security addresses RBAC policies for namespace operations, ServiceAccount-based authentication, secret reference resolution with watch-label filtering enabling instant reconciliation on credential updates, and NetworkPolicy generation with safe defaults plus user customization. TLS includes server termination via user certificates and outbound mTLS with configurable trust anchors and client identity.

Multi-tenancy follows per-namespace isolation: each OGXServer creates isolated ConfigMaps (immutable, hashed), Secrets (watched), and Deployments within declared namespace. State storage (KV/SQL) is per-server.

Provider configuration uses plugin architecture where each API type (inference, vector_io, tool_runtime, files, batches, responses, file_processors) supports remote/inline instances with secret resolution, settings, and timeouts, enabling flexible integration without code changes.

State consistency leverages content-addressed config hashing triggering pod restarts on changes and supporting graceful lifecycle transitions (Pending→Initializing→Ready→Failed→Terminating). All control state resides in Kubernetes API objects and in-memory reconciliation loops.

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | RBAC per-namespace; operator has cluster-wide ClusterRole; workload uses user-provided SA | Kubernetes RBAC | Users can specify custom SA; no audit trail |
| Data storage | Per-namespace PVC; per-CR immutable ConfigMaps (hashed); per-CR Secrets | Kubernetes isolation | Shared SQL/KV backends opt-in; no per-tenant schema isolation |
| Network traffic | NetworkPolicy per-CR (default: same-namespace + operator-namespace; user-configurable) | Kubernetes NetworkPolicy | Optional (enabled by default); egress unrestricted by default |
| Compute & resources | ResourceQuota per-namespace; per-CR resource requests/limits | Kubernetes ResourceQuota | No per-CR isolation beyond requests |
| Configuration & secrets | Per-namespace ConfigMaps/Secrets (watch-labeled); per-CR immutable ConfigMap | Kubernetes isolation + watch-labels | Users can reference any Secrets in namespace |
| API scoping | OGXServer watches in reconciliation loop | Kubernetes watch/list | No cross-CR aggregation |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Inference Providers | Per-CR (spec.providers) | Application routing; no namespace isolation |
| Vector Databases | Per-CR or shared | Application filtering; no row-level security |
| File Storage (S3) | Per-CR or shared | Application bucket selection; no per-tenant prefix |
| KV/SQL State | Per-CR or shared | Application connection isolation; no per-tenant schema |

Multi-tenancy enforces namespace-level isolation via RBAC and per-CR resource isolation. Shared backends are per-user-specification without per-tenant isolation enforced. Appropriate for self-service; requires documentation for multi-tenant backend sharing.
