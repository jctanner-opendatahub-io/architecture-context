## Purpose

**Short**: Deploys and manages Open GenAI Stack (OGX) server workloads from Kubernetes custom resources.

**Detailed**: The operator reconciles namespaced `OGXServer` resources into server Deployments, Services, service accounts, PVCs, ConfigMaps, HPAs, PodDisruptionBudgets, monitoring resources, Ingresses, and NetworkPolicies. It resolves a named or direct-image distribution, generates runtime configuration from CR fields or referenced ConfigMaps, and propagates Secret references into the managed workload.

The companion OGX module controller reconciles the cluster-scoped ODH `OGX` module resource and manages installation/lifecycle of the operator. Both controllers use controller-runtime and Kubernetes client APIs, leader election, health/readiness probes, and Kubernetes-native ownership and status conditions. The operator also retains legacy-resource adoption behavior for migration of prior OGX server resources.

## Architectural Analysis

This checkout combines a component operator with a platform-module controller. The namespaced `OGXServer` API is the principal user-facing contract, while the cluster-scoped `OGX` API provides ODH module lifecycle integration. Reconciliation is manifest-driven and uses Kustomize transformations to apply names, namespaces, field substitutions, service ports, secret hashes, and NetworkPolicy rules consistently to each server instance.

Runtime configuration is deliberately content-addressed: generated configuration is stored in immutable, hash-named ConfigMaps, and changes to referenced configuration or Secrets trigger reconciliation and workload rollout. This reduces stale configuration risk, but the operator requires broad Kubernetes permissions because it creates and updates workload, monitoring, networking, RBAC, and OpenShift security resources.

The component has no Gateway API or OpenShift Route ingress inventory in the analyzed source. It can create/own Kubernetes `Ingress` resources for an OGXServer when external access is configured, but external authentication and TLS termination are platform-dependent and not established by this checkout. The module controller watches configured operator/application namespaces, so its effective tenancy boundary depends on deployment configuration.
